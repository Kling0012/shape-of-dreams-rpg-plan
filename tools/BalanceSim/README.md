# バランスシミュレーター

Dreamforge RPG の遠征を、ゲーム本体を起動せずに繰り返す .NET 8 のコンソールアプリです。新しいプロフィールから何回遊ぶと育つかを調べるために使います。コアの数値は変更せず、開始、撃破、部屋突破、確保、帰還、装備、強化、分解、依頼の進捗を `SodRpg.Core.Game.Rules` の公開APIに通します。

## 使い方

リポジトリのルートで実行します。

```powershell
dotnet run --project tools/BalanceSim -c Release -- --runs 20 --players 300 --seed 1 --out tools/BalanceSim/result-baseline.md
```

Markdownを標準出力に表示し、`--out` を指定した場合は同じ内容をUTF-8（BOMなし）のファイルにも保存します。出力先の親ディレクトリは自動で作ります。引数を間違えた場合の終了コードは2、ファイル出力に失敗した場合は1です。

SDKがPATHにない環境では、次のように場所を選んで実行できます。ネットワークへの依存を増やさないよう、このプロジェクトには追加のNuGetパッケージはありません。

```powershell
$dotnet = if ($env:DOTNET_ROOT) {
    Join-Path $env:DOTNET_ROOT 'dotnet.exe'
} else {
    Join-Path $env:LOCALAPPDATA 'dotnet-sdk\dotnet.exe'
}
& $dotnet build SodRpg.sln
& $dotnet test tests/SodRpg.Core.Tests
& $dotnet run --project tools/BalanceSim -c Release -- --runs 20 --players 300 --seed 1 --out tools/BalanceSim/result-baseline.md
```

| 引数 | 既定値 | 意味 |
| --- | --- | --- |
| `--runs` | `20` | 1人あたりの遠征数（1以上） |
| `--players` | `300` | 独立した新規プロフィールの数（1以上） |
| `--seed` | `1` | 非負の64ビット整数の乱数シード |
| `--zones` | `4` | 遠征のゾーン数（1以上） |
| `--rooms` | `5` | 1ゾーンの戦闘部屋数（1以上） |
| `--lesser` | `10` | 部屋あたりの Lesser 撃破数（0以上） |
| `--normal` | `8` | 部屋あたりの Normal 撃破数（0以上） |
| `--miniboss` | `0.25` | 部屋ごとに MiniBoss を1体倒す確率（0〜1） |
| `--bosses` | `1` | 各ゾーン最後の Boss 撃破数（0以上） |
| `--policy` | `secure` | `secure` / `delve1` / `greedy` |
| `--wipe` | `0.15` | 遠征ごとの全滅確率（0〜1） |
| `--bounty` | `0.6` | 本体の行動が必要な依頼の達成を予定する確率（0〜1） |
| `--item-level` | `1` | 最初のゾーンのアイテムレベル（1以上） |
| `--item-level-per-zone` | `1` | 次のゾーンで増えるアイテムレベル（0以上） |
| `--out` | なし | Markdownの保存先。相対パスは実行時の作業ディレクトリ基準 |
| `--help` / `-h` | なし | 引数の説明を表示 |

小数点には `.` を使います。シードからコア用と模擬行動用の乱数列をプレイヤーごとに分け、コアの `Rng`（SplitMix64）を使います。同じコア、引数、シードなら、実行時間の行を除いて同じ結果になります。

## 模擬する遊び方と仮定

敵数と部屋構成は本体の実測ではなく、仕様書の仮定です。既定では部屋ごとに Lesser 10体、Normal 8体、MiniBoss は25%で1体、そのゾーンの最後に Boss 1体を倒します。アイテムレベルはゾーン番号と同じ1〜4で、次の遠征でも1から始まります。引数で開始値とゾーンごとの増分を変えられますが、コアの上限60を超えないようにします。この対応は仕様書に指定がなかったための仮定です。

2ゾーン目以降の入口では `ReachSecurePoint` を呼びます。`secure` は毎回確保し、`delve1` は深度1に達した次の入口で確保し、`greedy` は深度3に達した次の入口で確保します。条件に届くまでは契約なしで潜行します。4ゾーンの `greedy` では入口が3回しかないので、途中では確保せず、踏破時の `EndRun(victory: true)` で深度3の報酬を確保します。

全滅の有無は遠征ごとに先に決めます。全滅する場合はゾーンとその中の戦闘部屋を一様に選び、その部屋の撃破・突破処理の後、ボスを倒す前に遠征を終えます。装備や深度に応じた戦闘勝率は計算しません。全滅した後の敵は倒しません。未確保品の損失、欠片の残響、次の遠征での遺失物回収はコアの規則のままです。

撃破数、ボス数、レア発見数、部屋数、確保数、潜行深度に関する依頼はコアが実際の条件で進めます。本体行動を要する6種（Chaosの祭壇、商人、Memory/Essenceの強化・合成・分解、ハンターの領域）は、依頼ごとに `--bounty` の確率で達成を予定します。遠征の戦闘部屋を一様に選び、そこを突破した時に必要回数の `OnGameAction` を呼びます。その部屋に届かず全滅すれば達成しません。このため `--bounty 0.6` は全依頼の達成率60%を意味しません。悪夢化・契約の依頼は未達です。依頼の `Done` や素材を直接書き換えることはありません。

遠征と遠征の間に、レア度を最優先し、同じレア度なら ItemLevel が高い遺物を自動で装備します。同値なら装着中の品を残し、空き枠の候補同士も先に見つかった品を選びます。強化済みだからといって新しい品へ強化値を移すことはありません。装着中・鍵付き以外の弱い遺物から分解し、次回の鞄1つ分の空きを作るため保管庫を50個以下に整理します。分解順はレア度、ItemLevel、強化値の低い順です。その後は低い強化値の装備から、欠片が足りる限りコアの上限まで強化します。主装備、防具、装飾品の順で同値を決めます。セット部位を特別に保護する遊び方ではありません。

今日の夢、契約、悪夢化、Limbo、確保地点の出来事は使いません。工房購入、初期装備配布、製作、合成、再調律、星図へのポイント配分も行いません。あくまで `Profile.CreateNew` の空のプロフィールから始め、固定の遠征構成で報酬と装備の成長を観察します。

伝説のセット部位にはコアの収集補助が自動で適用されます。保管庫（装着品を含む）か未確保の鞄に1部位以上あるセットの、まだ所持していない部位は抽選の重みが `Loot.SetCompletionWeight`（既定25）倍になります。セット品そのものも `Loot.SetPieceWeight`（既定3）倍で選ばれます。狙い系統の重みとは掛け合わせ、未着手のセット・所持済み部位・通常の固有品は変えません。遺失物と図鑑は所持に含めません。シミュレーターの追加引数は不要で、倍率はコアの定数で調整します。

## 表の読み方

遠征ごとの平均表には新しく発見した遺物のレア度別の数、実際に保管庫へ移った確保数、欠片・調律石の純増減、夢のレベル、装備の平均レア度・平均強化値を載せます。素材の純増減は遠征の前から整理・強化の後までの差なので、強化への支出と分解の収入も含みます。回収した遺物は新規発見に含めませんが、確保した場合は確保数に含みます。装備レア度はコモン0、アンコモン1、レア2、エピック3、伝説4です。空き枠は装備平均の分母に含めず、装着品がなければ平均0として装着枠数も表示します。

節目は初めてのレア以上・エピック以上・伝説の発見、セット3部位の同時所持、夢のレベル5/10/20、全装備+3以上です。レア・エピックの節目は上位の品でも達成し、ドロップ時に自動分解された場合でも「発見」には含みます。セット完成には同じセットの異なる3部位が必要で、同じ部位の重複は数えません。装備は保管庫の品への参照なので二重に数えず、未確保品と遺失物も含めません。確保直後の所持を確認してから帰還後に整理するため、その時に完成していたセットを後で分解しても節目は残ります。全+3は3枠すべてが埋まり、各枠が+3以上になった遠征です。

節目の中央値と10/90パーセンタイルは、指定した遠征数の中で到達した人だけの値です。未到達割合を必ず併読してください。誰も到達していなければ値は `—` です。百分位は昇順標本の位置 `(n−1)×p` を線形補間するので、小数の遠征回数が出ることがあります。最後の分布表では、遠征ごとの各指標について全プレイヤーの平均・中央値・P10・P90を表示します。

上限の表は、上限未満から満杯になった操作の回数と、上限を超えてコアが自動分解した遺物数を別々に出します。満杯のまま追加する操作を満杯到達として再計上せず、遠征間に意図的に分解した数も自動分解には含めません。

## コアAPIの不足と限界

本体の敵配置や部屋構成、アイテムレベルのゾーン対応、戦闘勝敗は、このコアの公開APIだけでは再現できません。上記の仮定として指定しています。本体行動の発生頻度も仮定ですが、公開 `OnGameAction` があるので依頼の報酬処理そのものはコアへ任せられます。

鞄・保管庫の上限到達回数と上限超過で分解された数を直接取り出す構造化APIはありません。鞄については公開イベントの `Kind` / `Rarity` と追加前の個数、保管庫については確保直前の保管庫・鞄の個数から計数します。通知の日本語文字列の解析には依存しません。シミュレーター独自の抽選規則は追加せず、`tests/` は変更しません。

レポートの実行時間はシミュレーション部分のみの実測で、ビルド、レポートの整形、ファイル書込を含みません。ゲーム本体での手応えや実際の勝率を保証する表ではありません。
