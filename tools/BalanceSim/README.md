# バランスシミュレーター

Dreamforge RPG の遠征を、ゲーム本体を起動せずに繰り返す .NET 8 のコンソールアプリです。新しいプロフィールから何回遊ぶと育つかを調べるために使います。コアの数値は変更せず、開始、撃破、部屋突破、確保、帰還、装備、強化、分解、依頼の進捗を `SodRpg.Core.Game.Rules` の公開APIに通します。

鞄の上限超過は低レア度、同レア度なら低スコアから欠片へ換えます。Coreと同じ集約分をシミュレーションのtickでローカルプロフィールへ確定し、ダスト換金・ホスト取引や欠片フォールバックは使いません。実機MODの通信・描画・ログI/Oの測定ではありません。 / Satchel overflow converts the lowest-rarity, then lowest-score relic into shards. Each simulated tick settles the same Core batch into the local profile without Dust trades, host authority, or shard fallbacks. Native networking, rendering, and log I/O are not measured.

## 使い方

リポジトリのルートで実行します。

```powershell
dotnet run --project tools/BalanceSim -c Release -- --runs 20 --players 300 --seed 1 --out tools/BalanceSim/result-baseline.md
```

Markdownを標準出力に表示し、`--out` を指定した場合は同じ内容をUTF-8（BOMなし）のファイルにも保存します。出力先の親ディレクトリは自動で作ります。引数を間違えた場合の終了コードは2、ファイル出力に失敗した場合は1です。

## Infinity報酬モード

```sh
DOTNET_ROLL_FORWARD=Major dotnet run --project tools/BalanceSim -c Release -- --mode infinity --players 2000 --seed 95 --out tools/BalanceSim/result-infinity.md
```

通常20戦闘部屋＋4ボス／35戦闘分の比較基準と、Infinityの周期10/15/20・30/60/120分を、同じ `Rules` / `Loot` / `BossSets` / `InfinityRewards` の実経路で測ります。通常速度・4倍速、深度5の悪夢昇格、宝庫×3、保証付き道標の4時間認可待ちを分けて計測します。抽選Epic+とLegendaryの解析予算・実際の機会認可／抑止・保証別枠・資源・合法確保帰還後のclone/codec記録を出力します。通常の4ボスのうち登録済みボスセット対象は1体、Infinityは固定対象です。解析予算は本体対象ボス出現頻度の未実測を理由にセット分を比較基準から除外します。

Infinityの抽選予算は、深度を変更した遠征へcreditを持ち越しても安全な深度0の下限（Epic以上0.586805／時・Legendary0.052875／時）で補充します。保証の実行機会と最終出力予約は各0.25／時の別枠。初期0で、貯めたcreditのburstを許す累積戦闘時間のrate上限であり、任意の短時間窓の厳密上限ではありません。135分の戦闘creditを実APIで蓄積した認可済み実ボスの観測も分離し、#48の通常10%抽選が上限の内側で動く経路を計測します。

この環境は.NET 10のみのため、net8.0のツールをMajor roll-forwardで実行しています。対象frameworkは変更しません。

`--players`、`--seed`、`--item-level`、`--out`を使用し、期間・周期・撃破構成は比較表の固定条件です（`--runs`、`--zones`、`--rooms`等はこのモードでは使いません）。結果は全セッションを実戦闘時間とする経済モデルであり、本体の実時間測定ではありません。有限サンプルの高レア実数が通常を上回ることはあり、抽選の時間あたり期待値認可上限と同義ではありません。

## 星振りモード（v1.31）

`--mode stars` で遠征ではなく星図の振り方を調べます。500ポイント（`StarProgression.MaxPoints`）までの購入を `Rules.AddTalentRank` / `Rules.SetKeystone` で実際に行い、節目 0/50/100/150/200/250/300/350/400/450/500 で `Build.Compute` の結果を記録します。実行前に `StarClusters.RegisterAllGenerated` で生成済み星図を登録し、`HeroSigils.TreeFor` が返す現行ツリーを使います。

3つの振り方を全旅人で試します。能力値優先はプロキシ増分がポイント単価あたり最大の購入を毎回選び、記憶特化は星数最大の星群（なければ記憶ルート）を完成させてから能力値優先に切り替え、核先行は核の前提を最安で満たして `Rules.SetKeystone` を呼んでから能力値優先に戻ります。プロキシは本体が悪夢化抽選の強さに使う式（攻撃力%か魔力%の大きい方＋最大HP%の半分）で、戦闘出力ではありません。夢の圧は `DreamPressure.ForPlayer` の実式、深度の効果は `DreamDepth` / `Nightmares` の実式で、`--dream-level`（1〜30、既定30）が夢レベルの仮定です。乱数を使わない決定的なシミュレーションなので `--seed` は使いません。

候補の仮ビルドで発信側・受信側の二重強化などの禁止組合せになった場合は、その候補だけを除外します。ゲーム側の割当検証でも拒否される組合せであり、合法な候補の評価・購入規則やゲームの数値は変更しません。その他の計算エラーは隠しません。

修正後の通常実行（`--mode stars --dream-level 30`）は全9旅人・3戦略・0〜500ポイントを完走しました。実測7581.667秒（約126分22秒、ビルド・レポート出力を除く）。ゲーム実機の性能測定ではありません。

全500ポイントの評価は重いため、`--star-max-points 50` で軽量実行できます（50〜500、50刻み、既定500）。全9旅人・3戦略を通常と同じ購入手順で指定節目まで実行し、それ以降は未測定として出力しません。星経験は通常と同じ500ポイント分を与えたままで、残ポイントもその基準です。50ポイント版は実測330.948秒（ビルド・レポート出力を除く、通常版との同時実行時）。

```sh
DOTNET_ROLL_FORWARD=LatestMajor /usr/bin/dotnet run --project tools/BalanceSim -c Release -- --mode stars --dream-level 30 --star-max-points 50 --out /tmp/stars-light.md
```



## セット6部位モード（v1.32）

`--mode sets` で遠征ではなく、48組のセット装備の2・3・6点の強さを測ります。基準は「同じ枠に入る最良の非セット代替品」で、各枠について伝説とエピックを64個ずつ固定シードで抽選し、その中で最も高いものを当てます（セット品と連携は候補から外す）。セット品も代替品もアイテムレベル10・強化なし・覚醒なしです。

強さは `Build.Compute` の結果に代理値（PowerScore）を割り当てて比べます。能力値と固有効果を、それぞれコア自身が定める上限（`Content.StatCap` / `Content.PowerCap`）で割って足した「予算の消化率」の合計です。Build が上限で抑えた後の値を使うので、3つ装着と重なる効果は上限の内側だけが数えます。戦闘の出力そのものではありません。

各組について、2点（登録順の最初の2部位＋代替4枠）・3点（3部位＋代替3枠）・6点（6部位）の代理値と基準との差、6つ装着の効果そのものの利得（6点の状態で `SixPiece` を空にした差分）、6点ビルドに占めるその割合を表にします。6点差分の計測中だけ `SetDef.SixPiece` を一時的に空にして必ず戻すため、Content は変更されません。乱数は使いません（コアの `Rng` を固定シードで呼ぶだけ）。

6点ボーナス利得の中央値の0.5〜1.5倍を許容帯とし、外れた組を「強すぎ」「弱すぎ」と表示します。設計文書は [docs/specs/v1.32-six-piece-balance.md](../../docs/specs/v1.32-six-piece-balance.md) にあります。

```powershell
dotnet run --project tools/BalanceSim -c Release -- --mode sets --out tools/BalanceSim/result-v1.32-sets.md
```

## v1.32 星図の追加効果モード

`--mode v132stars` で、v1.32 の「巡る富」（共有の外縁星団 outer.fortune：撃破ゴールド＋12%・エリート/ボス＋25%・夢のダスト＋22%（潜行中＋32%））と「遠征の鍛錬」（Vesper・Cetus・Mist・空殻の RunGrowth）を測ります。結果は `result-v1.32-stars.md` を参照。

- **経済**：遠征モードと同じループ（`Rules.BeginRun` に `dreamDepth` を渡し、1ゾーンの部屋数は `DreamDepth.ExtraZoneNodes` で増えます）に通貨の帳簿を重ね、星なし／全取得を同じシードで比べます（欠片が増えた分だけ遠征間の強化の回数が変わり、依頼の抽選を通じて遠征の詳細がわずかにずれるため、変化率には±2%弱のぶれが残ります）。撃破ゴールドは本体の `GameManager.GetKillGoldAmount` の式（ゾーン倍率 (1+0.4x)×(1+0.20x)・±10%のぶれ・確率丸め）、受け取りは `Pickup_BaseGoldOrb.GrantGold` と同じ形で `CurrencyStars.KillGoldMultiplierDelta` / `EliteKillGoldPercent` を通します。夢のダストは部屋・ボスごとの拾得を `CurrencyStars.DreamDustBonusForPickup`（潜行中は `CurrencyStars.IsDelving` の実式）、未確保品のダスト化は `TradeAuthority` + `Economy.SalvageDust`、欠片への換金は `Rules.ConvertDust` の実経路です。種別ごとの撃破ゴールドの基礎額とダストの拾得量は本体アセットが読めないための文書化した仮定です。
- **遠征の鍛錬**：`Rules.AddTalentRank` で入口の星・上限の星・2択を実際に買った `Build`（`Build.RunGrowths`）を作り、模型化した出来事（被ダメージ・障壁の吸収・パリィ・会心の基本攻撃でのとどめ）を本体のホストと同じ `RunGrowthLedger.Gain` に流して、ゾーンごとのスタックと上限到達ゾーンを測ります。深度は `DreamDepth.DamageMultiplier`、潜行は `Build.DamageTakenPerDelvePct` の実係数を使い、仮定の感度も3段階で報告します。
- 割り当て検証（効果が出る購入しか許さない）を通れない経路の星（記憶にスコープされた選択肢など）は、コアのテストと同じ直接割り当てで足します（報告書の「補足」に件数を記載）。効果の集計（`Build.Compute`）とスタック（`RunGrowthLedger`）は常に実経路です。

```powershell
dotnet run --project tools/BalanceSim -c Release -- --mode v132stars --runs 10 --players 100 --seed 3 --out tools/BalanceSim/result-v1.32-stars.md
```

## 模擬する遊び方と仮定

敵数と部屋構成は本体の実測ではなく、仕様書の仮定です。既定では部屋ごとに Lesser 10体、Normal 8体、MiniBoss は25%で1体、そのゾーンの最後に Boss 1体を倒します。アイテムレベルはゾーン番号と同じ1〜4で、次の遠征でも1から始まります。引数で開始値とゾーンごとの増分を変えられますが、コアの上限60を超えないようにします。この対応は仕様書に指定がなかったための仮定です。

2ゾーン目以降の入口では `ReachSecurePoint` を呼びます。`secure` は毎回確保し、`delve1` は深度1に達した次の入口で確保し、`greedy` は深度3に達した次の入口で確保します。条件に届くまでは契約なしで潜行します。4ゾーンの `greedy` では入口が3回しかないので、途中では確保せず、踏破時の `EndRun(victory: true)` で深度3の報酬を確保します。

全滅の有無は遠征ごとに先に決めます。全滅する場合はゾーンとその中の戦闘部屋を一様に選び、その部屋の撃破・突破処理の後、ボスを倒す前に遠征を終えます。装備や深度に応じた戦闘勝率は計算しません。全滅した後の敵は倒しません。未確保品の損失、欠片の残響、次の遠征での遺失物回収はコアの規則のままです。

撃破数、ボス数、レア発見数、部屋数、確保数、潜行深度に関する依頼はコアが実際の条件で進めます。本体行動を要する6種（Chaosの祭壇、商人、Memory/Essenceの強化・合成・分解、ハンターの領域）は、依頼ごとに `--bounty` の確率で達成を予定します。遠征の戦闘部屋を一様に選び、そこを突破した時に必要回数の `OnGameAction` を呼びます。その部屋に届かず全滅すれば達成しません。このため `--bounty 0.6` は全依頼の達成率60%を意味しません。悪夢化・契約の依頼は未達です。依頼の `Done` や素材を直接書き換えることはありません。

遠征と遠征の間に、レア度を最優先し、同じレア度なら ItemLevel が高い遺物を自動で装備します。同値なら装着中の品を残し、空き枠の候補同士も先に見つかった品を選びます。強化済みだからといって新しい品へ強化値を移すことはありません。装着中・鍵付き以外の弱い遺物から分解し、次回の鞄1つ分の空きを作るため保管庫を50個以下に整理します。分解順はレア度、ItemLevel、強化値の低い順です。その後は低い強化値の装備から、欠片が足りる限りコアの上限まで強化します。主装備、防具、装飾品の順で同値を決めます。セット部位を特別に保護する遊び方ではありません。

今日の夢、契約、悪夢化、Limbo、確保地点の出来事は使いません。工房購入、初期装備配布、製作、合成、再調律、星図へのポイント配分も行いません。あくまで `Profile.CreateNew` の空のプロフィールから始め、固定の遠征構成で報酬と装備の成長を観察します。

伝説のセット部位にはコアの収集補助が自動で適用されます。保管庫（装着品を含む）か未確保の鞄に1部位以上あるセットの、まだ所持していない部位は抽選の重みが `Loot.SetCompletionWeight`（60）倍になります。セット品そのものも `Loot.SetPieceWeight`（4）倍で選ばれます。狙い系統の重みとは掛け合わせ、未着手のセット・所持済み部位・通常の固有品は変えません。遺失物と図鑑は所持に含めません。シミュレーターの追加引数は不要で、倍率はコアの定数で調整します。今回の上位品調整では、この収集補助を維持したまま伝説の出現数を減らします。比較条件と結果は [高レア装備の比較仕様](../../docs/specs/rare-gear-difficulty.md) を参照。

## 表の読み方

遠征ごとの平均表には新しく発見した遺物のレア度別の数、実際に保管庫へ移った確保数、欠片・調律石の純増減、夢のレベル、装備の平均レア度・平均強化値を載せます。素材の純増減は遠征の前から整理・強化の後までの差なので、強化への支出と分解の収入も含みます。回収した遺物は新規発見に含めませんが、確保した場合は確保数に含みます。装備レア度はコモン0、アンコモン1、レア2、エピック3、伝説4です。空き枠は装備平均の分母に含めず、装着品がなければ平均0として装着枠数も表示します。

節目は初めてのレア以上・エピック以上・伝説の発見、セット3部位の同時所持、夢のレベル5/10/20、全装備+3以上です。レア・エピックの節目は上位の品でも達成し、ドロップ時に自動分解された場合でも「発見」には含みます。セット完成には同じセットの異なる3部位が必要で、同じ部位の重複は数えません。装備は保管庫の品への参照なので二重に数えず、未確保品と遺失物も含めません。確保直後の所持を確認してから帰還後に整理するため、その時に完成していたセットを後で分解しても節目は残ります。全+3は3枠すべてが埋まり、各枠が+3以上になった遠征です。

節目の中央値と10/90パーセンタイルは、指定した遠征数の中で到達した人だけの値です。未到達割合を必ず併読してください。誰も到達していなければ値は `—` です。百分位は昇順標本の位置 `(n−1)×p` を線形補間するので、小数の遠征回数が出ることがあります。最後の分布表では、遠征ごとの各指標について全プレイヤーの平均・中央値・P10・P90を表示します。

上限の表は、上限未満から満杯になった操作の回数と、上限を超えてコアが自動分解した遺物数を別々に出します。満杯のまま追加する操作を満杯到達として再計上せず、遠征間に意図的に分解した数も自動分解には含めません。

## コアAPIの不足と限界

本体の敵配置や部屋構成、アイテムレベルのゾーン対応、戦闘勝敗は、このコアの公開APIだけでは再現できません。上記の仮定として指定しています。本体行動の発生頻度も仮定ですが、公開 `OnGameAction` があるので依頼の報酬処理そのものはコアへ任せられます。

鞄・保管庫の上限到達回数と上限超過で分解された数を直接取り出す構造化APIはありません。鞄については公開イベントの `Kind` / `Rarity` と追加前の個数、保管庫については確保直前の保管庫・鞄の個数から計数します。通知の日本語文字列の解析には依存しません。シミュレーター独自の抽選規則は追加せず、`tests/` は変更しません。

レポートの実行時間はシミュレーション部分のみの実測で、ビルド、レポートの整形、ファイル書込を含みません。ゲーム本体での手応えや実際の勝率を保証する表ではありません。
