# Dreamforge の原則（constitution）

Dreamforge RPG の開発で、すべての変更が守る原則です。Issue の要件、PR の審査、リリースの判断はこの文書を基準にします。
「MUST」は守らなければマージしない原則、「SHOULD」は理由を PR 本文に書けば外してよい原則です。

## I. 一部が壊れても MOD 全体を止めない（MUST）

- データの食い違い、読み込みの失敗、想定外の値があっても、止めてよいのはその機能だけです。MOD 全体の起動や、ほかの機能を止めません。
- 失敗したときは、ログに原因を残し、その機能を既定の動きに戻します。

## II. 動かすのに必要な PC の性能を上げない（MUST）

- 毎フレーム呼ばれる処理では、新しくメモリを確保しません（LINQ、クロージャ、配列やリストの作り直しを使わない）。
- 見た目の効果には上限を設け、数が増えても処理が重くならないようにします。
- 処理を軽くする変更は、結果が変わらないことをテストで確かめます。

## III. 画面は 1920×1080 の既定の大きさに収める（MUST）

- メニューや表示は、1920×1080 で UI の拡大率が既定のときに、はみ出さず読めるようにします。

## IV. 実機での確認をマージの条件にしない（MUST）

- この開発環境ではゲームを起動できません。コードとテストで理論上正しいと言える変更は、そのまま PR にしてマージします。
- 実機でしか分からない点は、PR 本文の「未実行」に1行で書きます。実機で確かめたいだけの Issue は立てません。
- 再現できなかった不具合も、原因の筋道をコードで示せれば修正します。筋道を示せないときは、調査用の記録を入れて、そのことを Issue に書きます。

## V. セーブと協力プレイの互換を守る（MUST）

- 前の版のセーブデータは、そのまま読めるようにします。形式を変えるときは、古い形式を読んで変換します。
- 協力プレイの通信を変える変更は、全員が同じ版に更新する必要があることを、更新履歴とリリースノートに書きます。

## VI. 頼まれたことだけを変える（MUST）

- Issue の要件にない変更を、同じ PR に混ぜません。気づいた改善案は、PR 本文かレビューの提案に書きます。
- 要件があとのコメントで変わったときは、新しいコメントを優先します。どのコメントに従ったかを PR 本文に書きます。

## VII. 更新履歴は新機能と不具合の修正だけを書く（MUST）

- 更新履歴とリリースノートに書くのは、新機能と不具合の修正だけです。数値の調整は書きません。
- 例外として、難易度を緩める変更（動的難易度の見直しなど）は、プレイヤーに伝わるように明記します（2026-10-20 利用者の指示）。細かな数値までは書かなくてかまいません。
- 日本語と英語を並べて書きます。中国語は更新履歴・リリースノート・告知には書かず、MOD 本体の表示、`docs/README.zh.md`、ワークショップ説明文の案内だけにします（2026-10-20 利用者の指示）。
- PR では `CHANGELOG.md` を変えず、`changelog.d/` にファイルを足します（書き方は `changelog.d/README.md`）。

## VIII. 版番号は X.Y.Z で意味を分ける（MUST）

- X は動かす環境が変わるとき（協力プレイの作り直しなど）、Y は新機能を足すとき、Z は不具合の修正だけのときに上げます。

## IX. 変更の理由を残す（SHOULD）

- PR 本文には、何を直したか、なぜそう直したか、何を確かめて何を確かめていないかを書きます。
- 設計を決めた変更は、`docs/specs/` に決めたことと理由を残します。

## この文書の変え方

- 原則を足す・変えるときは、この文書を変える PR を出し、理由を本文に書きます。
- 審査では、MUST の原則に反する変更を最も重い指摘として扱います。
