# v1.28「星図をスキルツリー型に」

利用者の指示（2026-10-03）：
- 星図に「何のルートか」を書く必要はない。設計の意図として考えるだけで、自由に触れるようにしてよい。
- いまの形（核・折りたたみのルート一覧・夢の輪）は非常に見づらいので、スキルツリー型にする。参考は Path of Exile やディアブロのようなもの。
- 自由度を保ちながら、ツリーの中で「ルート」を探して伸ばしていける形にする。

## 振り方（つながりで開く）
- 旅人ごとに、星を**点と線のつながり（グラフ）**で並べる。中心に「始まりの星」（振らなくても取得済み）がある。
- 星は、**取得済みの星と線でつながっていれば**振れる。前提の星の決まり（ルートの順番、「手前の星に6振ると奥が開く」）は、つながりに置き換える。
- 外すときは、外したあとも残りの星がすべて始まりの星とつながっている場合だけ外せる（つながりが切れるなら、先に外側を外す）。全部の振り直しは今までどおり無料。
- 到達刻印（2つから1つ）と熟練度3の条件、連装・四の型の費用、エッセンス枠の星の費用（5）、星のポイント（旅人ごと・最大150）、夢の圧は今までどおり。

## 形（設計の意図。画面には書かない）
- 中心から外へ広がる放射状。
  - 中心のまわり：いまの「手前の星」と到達刻印、連装・四の型。
  - その外側：いまの「奥の星」。
  - さらに外へ、7本の枝：アイデンティティ記憶2つ・旅人記憶5つに合わせた星の列（いまのルートの星をそのまま使う）。枝の先に大きな星（頂点）と、エッセンス枠の星。
  - 枝と枝の間：夢の輪の小さな星を「橋」として置き、隣の枝へ渡れるようにする（ルートを跨いだ組み合わせを作れる）。枝の途中にも、隣の枝への渡りを2か所ほど作る。
- 星の大きさで重みを見せる：小さな星（能力値1段ずつ）、目立つ星（固有効果・連携・頂点）、要の星（到達刻印・エッセンス枠・連装/四の型）。
- 星の数・効果・ID は v1.27.1 のまま（保存の互換）。位置とつながりのデータを足す。

## 画面
- 星図タブを、パンとズームのできる図に置き換える（マウスのドラッグで移動、ホイールで拡大縮小、中心に戻すボタン）。
- 線：取得済みどうしは金色、取得済みから伸ばせる先は明るく、まだ届かない先は暗く。
- 星：取得済みは金、振れる星は白く光る縁、届かない星は灰色。段のある星は「2/3」のように段を表示。
- 星にマウスを乗せると説明（名前、効果、1段ごとの値、費用、条件）。左クリックで1段振る、右クリックで1段外す（つながりの決まりに従う）。
- 上部に「使えるポイント 残り n / 合計」「星のレベルと次まで」。どの記憶のためのルートかは書かない（連携の星の説明に「『記憶名』を装着していると」と出るのは効果の説明なのでよい）。
- IMGUI で描く。線は細い四角の回転か GL で描き、毎フレームの割り当てを増やさない（いまのキャッシュのやり方に合わせる）。1080p で読めること。

## 試験
- 各旅人のグラフ：すべての星が始まりの星からつながる、つながりは双方向、位置が重ならない（最小距離）、各枝の星がその枝の中で順につながる、枝と枝の間に橋がある。
- 振る：つながっていない星は振れない。外す：つながりが切れる外し方は拒否、切れない外し方は許可。費用・段・到達刻印の条件は今までどおり。
- 保存と読み込み：振った星はそのまま。読み込んだときにつながっていない星があれば（古い保存など）、無料で振り直しにして知らせる。

## 実装記録（v1.28.0）

- Core の `HeroTreeLayout` が旅人ごとの位置・双方向の辺を決定的に生成し、共有する。Core は純 C#・netstandard2.0、Mod は netstandard2.1 を維持。
- 全9旅人とも、既存の73星と無料の始まりの星の計74点・83辺。中心の周囲に7星、次の輪に6星、外側に7本・計52星の枝を配置した。既存のエッセンス枠の星は3本の枝の先端にあり、星の追加や効果変更はしていない。
- 夢の輪8星を隣接する枝の橋として配置し、さらに枝の途中に2本の横断辺を設けた。最小間隔の基準は80座標単位、全旅人の実測最小間隔は95。既存の星ID・段数・効果・費用を保持。
- 購入・発動は始まりから取得済みの星をたどった接続で判定する。最後の1段の返却、到達刻印の返却・付け替えは、残る星がすべて始まりにつながる場合だけ許可。旧来の前提IDと手前の星6段による解放判定は撤去した。
- 到達刻印は従来どおり2つから1つ、ツリー合計6段・熟練度3が必要。旅人ごとの星の成長、ポイント費用、夢の圧は維持。
- 読み込み時、接続の切れた配分は該当する旅人だけ無料で振り直し、通知する。星の経験・熟練度・素材や他の旅人の配分は保持する。
- 星図画面をドラッグ移動・マウス位置を中心とした拡大縮小・中心復帰に対応するキャンバスへ変更した。辺と星の取得状態、段数、ホバー説明、左クリック取得・右クリック返却を表示し、枝の用途や記憶名の見出しは表示しない。配置・文字列・説明寸法をキャッシュする。
- 接続、双方向性、間隔、枝の順序、隣接橋、横断後の返却、費用、保存の往復と旅人単位の振り直しを検証した。全旅人の取得・保存・返却・旧配分移行の一連の動作も確認した。実ゲームでの1080p描画と入力の目視確認は未実施。

- **Husk の到達刻印「瞬歩の刃」**（「処刑の影」から戻す）：Husk 専用の新しい固有効果。回避（移動の枠の記憶）・ダッシュ・テレポートのどれかの後3秒以内の次の通常攻撃に、攻撃力か魔力の高い方の X% を上乗せする（重ならず、ダッシュ・テレポートのたびに時間を延長）。一歩一殺の「ダッシュ・テレポート後の基本攻撃は必ず会心」、風の傷の突進斬りと噛み合う。
  - 判定：本体の `EntityControl.ClientEvent_OnTeleport` と `ClientEvent_OnDisplacementStarted`。**自分から動いたものだけ**（敵に吹き飛ばされた・引き寄せられたものは数えない）。見分け方は `Displacement` の型・持ち主を型の一覧と逆コンパイルで確かめる。

### Husk「瞬歩の刃」の実装記録

- `h.husk.key2` のIDと取得条件を保持し、名前を「瞬歩の刃 / Flash-Step Blade」、効果をHusk専用の `Power.ShadowStep` 60に変更した。列挙値は末尾に追加し、既存の保存・通信上の番号を維持。上限は150。一歩一殺の移動後の確定会心と、風の傷の突進斬りに合わせた日英の説明を付けた。
- Coreは純C#・netstandard2.0のまま。回避の残響とは別の3秒窓を持ち、移動の枠の記憶の使用、または下記の自発移動で開始・更新する。次の通常攻撃の命中で一度だけ消費し、攻撃力と魔力の高い方の60%を上乗せする。3秒に達した時点で失効し、繰り返しても量や回数は重ならない。Modは回避の残響と同じ `PureDamage(..., 0f).Dispatch(victim)` で与え、`LogPowerTrigger(Power.ShadowStep)` で記録する。
- `EntityControl.ClientEvent_OnTeleport`（始点・終点）と `ClientEvent_OnDisplacementStarted`（`Displacement`）を、各ヒーローの既存ハンドラーと同じ寿命で登録・解除する。型と引数は `.ref/dump/EntityControl.txt`・`.ref/dump/_events.txt` で確認した。
- **ホストへの通知**：ゲームの `Shape of Dreams_Data/Managed/Dew.Core.dll` を読み取り専用で逆コンパイルし、`EntityControl.StartDisplacement → StartDisplacementLocal`、`Teleport → TeleportLocal` がサーバー上でも同期的にイベントを呼ぶことを確認した。両RPCの `UserCode_...` は `!isServer` の場合だけローカル処理を行うため、ホストで二重発火しない。別のサーバーイベントへの置換は不要。
- **自発的なダッシュの判定**：`Dew.Core.dll` の `Displacement` にはsource/caster/ownerがない。`isFriendly` を本体の自発移動分類として使い、`isCanceledByCC` や `isDodging` は必須にしない。`Dash.ApplyByDirection` は `isFriendly=true`、`Ai_GenericDodge.OnCreate` もtrueだが `isCanceledByCC=false`。`Knockback.ApplyWithDirection` はfalseであり、`Dew.Contents.dll` の `Ai_Mon_Ink_BossWhiteNight_OneInchPunch_Pull.OnCreateSequenced` も敵の引き寄せをfalseで作る。`Ai_D_ScarOfTheWind_DashAtk.OnCreate` が自分のcasterに `Dash.ApplyByDirection` を使うことも確認した。したがって自分の回避・突進は受け付け、敵のノックバック・引き寄せは受け付けない。
- **自発的なテレポートの判定**：位置だけのイベントを無条件では受け付けない。`Dew.Core.dll` の `Actor.Teleport(Entity, Vector3)` は同期的に `entity.Control.Teleport` を呼ぶため、HarmonyのPrefix/Finalizerでその呼出元を一時的に保持し、`AbilityInstance.info.caster` が対象ヒーロー自身であること（通常のActorなら自身または `firstEntity` が自身）を確認する。`Actor.firstEntity` は `FindFirstOfType<Entity>()`。公開型は `.ref/dump/Actor.txt`・`AbilityInstance.txt`・`StatusEffect.txt`、実装は同DLLで確認した。入れ子と例外時にも直前の呼出元へ戻す。
- `Dew.Contents.dll` の `Ai_E_Blink.OnCreateSequenced` は上記の `Actor.Teleport` を使う。一方、`Ai_E_WinterDive.OnCreateSequenced` は自分のcasterの `EntityControl.Teleport` を直接使うため、そのイテレーターの `MoveNext` ごとに同じ呼出元情報を保持する。`<OnCreateSequenced>d__17` の `<>4__this : Ai_E_WinterDive` は同DLLのメタデータで確認した。yield中に情報を持ち越さない。`EntityControl.DoDisplacement` の経路補正によるテレポートは、進行中のdisplacementがfriendlyのときだけ受け付ける。敵の移動に伴う補正、出所を確認できない直接ワープ、他者が起こしたテレポートは除外する。
- 読み込み・部屋遷移中と、非アクティブ・戦闘不能のヒーローは自発移動のイベント対象外。遷移条件は `Dew.Contents.dll` の `Se_D_TheKillingFlow` と `St_D_ScarOfTheWind` が使う `ZoneManager.isInAnyTransition`・`TransitionManager.StateType.Loading` に合わせた。両効果がサーバーで同じ移動イベントを購読し、friendlyな移動で次の通常攻撃の会心を準備することも確認した。
- 星図の回避系4効果の禁止は維持し、新効果の例外はHuskの `h.husk.key2` のみ。装備の回避の残響などは、引き続き移動の枠の記憶だけで発動する。独立した窓・一度だけの消費・期限・延長・攻撃力/魔力の選択はCoreの連続した戦闘シナリオで確認した。Unity内の実プレイ確認は未実施。
- 同梱のHarmonyと実ゲームのアセンブリを使い、Unity外の.NET Framework環境で `Actor.Teleport` とWinter Diveの `MoveNext` の両パッチが実際に適用できることを確認した。ゲームのディレクトリは読み取り専用とし、成果物の配置先は別ディレクトリにした。
