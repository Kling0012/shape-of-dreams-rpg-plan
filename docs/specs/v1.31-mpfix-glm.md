## 1. mp-host.md #2 — 取引ハンドラが任意のドリームダストを払い出し、同一取引を再実行する（高）

**判定：確認（confirmed）**

確認：旧 `HostAuthority.OnTrade`（削除前の `Mod/HostAuthority.cs:1161-1186`）は `earnDust` を `0..Economy.MaxDustEarnPerTrade` の範囲だけ見て `caller.EarnDreamDust(msg.earnDust)` を呼んでいた。取引の種別・対価・トークンの管理は一切なく、`spendGold=0/spendDust=0/earnDust=2000` を送れば何度でも 2000 ダストが手に入った。トークンは応答への書き戻しにしか使われていなかった。

**根本原因**：取引の金額をクライアント申告のまま本体の通貨へ反映していた。ホスト側に「何の取引か」の概念がなく、同じ取引idを2回受けたことも分からなかった。

**修正**：

- `Core/TradeAuthority.cs` の `TradeAuthority.Evaluate` が金額を決める。入力は種別と計算に必要な引数（熱度・束数・希少度・強化値・分解対象の識別子）と、ホストが本体から読んだ権威ある値（`caller.gold`・`caller.dreamDust`・本体の価格補正 `GameManager.GetAdjustedGoldAmount_Cost(1f)`）だけ。**金額を申告する項目は新しい方式に存在しない**。
  - 商人：`Economy.MerchantGoldBase(heat)` × 本体の価格補正（ホスト側で評価）。
  - 換金：束数 × `Economy.DustPerBatch`。
  - 分解：`Economy.SalvageDust(rarity, enhance)`（`Content.SalvageShards` と強化値から。正規の引数の範囲で最大でも `MaxDustEarnPerTrade` を超えない）。
- 取引id（トークン）は**1プレイヤーにつき1回だけ実行**する。再送には記録済みの結果を `Replayed=true` で返し、通貨は動かさない（`Mod/HostAuthority.Trades.cs` は `Ok && !Replayed` のときだけ `SpendGold/SpendDreamDust/EarnDreamDust` を呼ぶ）。
- 台帳は上限付き：1プレイヤーの実行済みトークン 256 件（ランをまたいで保持。上限を超えた古い物から忘れる）、分解済みの識別子 1ラン 256 件、追跡するプレイヤー 32（超えたら全消去）。プレイヤーの鍵は本体の `netId`（接続単位。再接続したプレイヤーは別人として数え直す）。

**テスト**（`TradeSecurityTests.cs`）：

- `Authority_derives_amounts_from_Economy_rates_never_from_the_client`：レビューの「2000 ダスト」メッセージと同じ結果が起きないこと（金額の申告項目が存在しないこと、換金・商人・分解の金額がすべて Economy のレートから出ること）。
- `Authority_accepts_a_token_once_and_replays_return_the_recorded_result`：同一トークンの再送が `Replayed` になり、通貨の動きが最初の1回だけになること。
- `Authority_rejects_out_of_range_parameters`／`Authority_ledgers_stay_bounded`：範囲外の引数の拒否と、台帳の上限。

## 2. mp-ui-save.md #10 — OnTrade のダスト受け取りを検証できず、無制限に繰り返せる（低中）

**判定：確認（confirmed）。ただし「遺物の分解が本当にあったか」はホストからは原理的に検証できない（遺物はクライアントのプロフィール側のデータ）なので、修正は「1つの領収書（遺物）につき1回」に限定される**

確認：旧実装は `earnDust` の範囲確認のみで、`token` の重複も、同じ遺物の再分解も見ていなかった（上記 #2 と同じ場所）。

**根本原因**：#2 に加え、分解の対価（どの遺物を渡したか）が通信に乗っていなかったため、ホストは領収書の消費を記録できなかった。

**修正**：

- 分解の要求には遺物の識別子（`Uid` の64bit。本体の形式 `r`+16桁の16進ならその値、それ以外は FNV-1a 64bit）を含める。
- ホストの台帳は**同じ識別子の分解を1プレイヤー・1ランにつき1回だけ**受け付ける。2回目以降は `reason="dup"` で断る（クライアントは「この遺物の分解は今回の遠征で受け付け済み」を出す）。
- 繰り返しの残りのはけ口：同一トークンの再実行は #2 の台帳で、同一遺物の再分解は識別子の台帳で、それぞれ塞がれた。

**テスト**：`Authority_salvages_the_same_relic_once_per_run`（同じ遺物の2回目が `dup`、別の遺物と別のランは通る）、および後述の `Salvage_timeout_rollback_returns_the_relic_without_duplicating_dust`。

**残る限界（仕様上の判断を要するもの）**：悪意あるクライアントが**毎回別の識別子を作って**分解を申し込むと、1回あたり `Economy.SalvageDust` の上限（正規の引数の最大で 850）までの付与は防げない。これを完全に塞ぐには「1プレイヤー・1ランの受け取り総額の上限」が必要になるが、その値はゲームデザインの決定（遠征の長さ・鞄の流入量との釣り合い）であり、本作業では値を決めずに `questions` に挙げた。レビュー自身も「例：」と値を残している。

## 3. mp-ui-save.md #7 — 取引の応答待ちに期限がなく、応答が消えると確保・潜行が永久に押せない（中）

**判定：確認（confirmed）**

確認：`TradeLedger.ExpireSalvage`（`Economy.cs`）は分解のみ30秒で期限切れにし、「支払い待ちの取引は捨てない」と設計されていた（`TradeFixV1131Tests.Paid_trades_are_not_expired` がその動作を固定している）。`MerchantGold` と `DustToShards` の保留はホストの応答以外で解除されることがなく、`CanResolveSecureChoice = !HasPendingTrades`（`ClientSession.RunChoices.cs`）経由で確保・潜行のボタンとホットキーが接続が替わるまで無効のままだった。

**根本原因**：応答が失われる状況（ホストの受信登録の隙・読み直し中の破棄）を「応答が遅れているだけ」と同じ扱いにしていた。

**修正**：

- `Economy.TradeTimeoutSeconds = 10.0` を定数にし、`TradeLedger.Expire` が**全種別**の保留をこの期限で解く（`ClientSession.Tick` が毎フレーム呼ぶ。`ExpireSalvage` は旧テスト互換で残す）。
- **期限切れの rollback の正確な定義**（二重に物や通貨が増えないことを保証する）：
  1. 保留を台帳から外す。このとき**対価の確定は一切しない**（商人の遺物も欠片も付与しない）。
  2. 分解は予約を解いて遺物を使える状態に戻す（鞄に残っていれば何もせず、遠征の終わりで預かり `PendingSalvage` へ移っていれば `Rules.RestorePendingSalvage` で戻す）。
  3. 遅れて来た成功応答は `Complete` が null を返して捨てられるので、確定は起きない。
  4. 遺物を戻しても、ホストの識別子の台帳が同一ランの再分解を `dup` で断るので、**ダストを得たまま遺物も戻る二重取りは1ランの中では起きない**。
- UI：期限切れのとき「取引の応答がなかったため、待ちを解除しました。ゴールドとドリームダストの増減をご確認ください。」（"No trade response; the pending trade was released. Please check your gold and Dream Dust."）を警告として出す（既存の出来事の通知経路）。保留が消えるので「取引の応答を待っています。」の表示も消え、確保・潜行が再び押せる。
- 結果が不明のままの損得：ホストが実行済みで応答だけが消えた場合、支払ったゴールド/ダストに対する対価は付かない（逆に付与はされない）。表示はこれを正直に伝える。本体の通信（Mirror）は信頼順序付きなので、応答消失の主因はレビューが挙げたホスト側の受信登録の隙（＝未実行）であり、その場合は無損得。

**テスト**：`Ledger_expires_every_trade_kind_after_the_timeout`（全種別がちょうど10秒で切れ、保留が残らない＝`HasPendingTrades` が false になる）、`Timed_out_merchant_and_dust_trades_grant_nothing_and_drop_late_results`（遅い成功応答の破棄と、すぐ再依頼できること）、`Salvage_timeout_rollback_returns_the_relic_without_duplicating_dust`（上の rollback の全容）、`Salvage_reserved_across_run_end_is_restored_on_timeout`（預かりへ移った遺物の復帰）。

## プロトコルの決定

**`Protocol.Version` は 12 のまま、上げない。** `NetMessages.cs` の形も変えない（本作業の禁止対象）。代わりに、既存の `DreamforgeTradeMsg` の3つの int（`spendGold/spendDust/earnDust`）を新しい符号として使い直す（符号化は `Core/TradeAuthority.cs` の `TradeWire` に集約）：

- `spendGold` が**負**の物を v1.31 の「種別付き要求」とする（`spendGold = -(1000 + kind + rarity*4 + enhance*32)`）。`spendDust/earnDust` は種別ごとの引数（熱度／束数）か分解対象の識別子の下位/上位32bit。
- **旧ホスト × 新クライアント**：旧ホストは `spendGold < 0` を「invalid」で拒否して応答を返す（検証済みの旧実装の分岐）。取引は失敗表示で終わり、悪い副作用はない。
- **新ホスト × 旧クライアント**：金額申告（`spendGold ≥ 0`）は `TradeWire.TryDecode` が復号できず、`reason="protocol"`（版違いの文言）で断る。
- 本体の RPC は JSON（`DewPersistence.ToJson`、`Dew.Core/Actor.cs` の `CustomRpc_SendMessageToServer/Client`）なので、未知の項目・既定値の取り扱いは欄の追加・解釈変更に対して寛容。今回は項目すら追加していない。

## 互換性と残る限界

- 旧テスト `TradeFixV1131Tests`（v1.13.1）は `ExpireSalvage` の挙動を固定しているため、互換のために残した。新しい全種別の期限切れは別の `Expire` で、実運びするのは `ClientSession.Tick` のみ。
- 分解の識別子の台帳はラン単位。遠征をまたいで「敗北で遺失物→回収→再分解」をすると、別ランの別の取引として通る（過去ランで応答消失があった場合のみ二重になり得る。ごく狭い窓）。
- クライアントの再接続（本体の `netId` が変わる）でプレイヤーの台帳は新しく始まる。同一ラン内での偽の再実行を防ぐ効果は接続単位まで。
- 1ランの受け取り総額の上限は未実装（`questions` 参照）。
