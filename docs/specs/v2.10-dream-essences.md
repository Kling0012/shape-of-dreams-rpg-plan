# MOD独自の記憶・エッセンス：実現方式と候補一覧（2026-10-07）

利用者の依頼（2026-10-07）：「独自の記憶とエッセンスを作成，追加検討」。
位置づけ：**検討資料**。ここに書いた数値は案であり、承認済みの仕様ではない。実機での確認は一つもしていない。

## 0. 先に結論

1. **本体の記憶（SkillTrigger）・エッセンス（Gem）の型そのものを新しく足す方式は、いまは前提にしない。** 本体の記憶・エッセンスは Mirror のネットワーク型（プレハブつき Actor 派生）で、MOD の DLL に置いた型が登録・同期されるかは未検証。既存の調査（`docs/specs/v1.24-monster-research.md` 2b・2d）も、Actor 派生の新規型は「Mirror の Weaver が MOD の DLL に走らない・本体のリソース DB に入れないと保存・プールで不整合が出る恐れ」として避ける判断をしている。クラウドでは確かめられないので、確かめる手順（§3 の検証 S1）を用意した。
2. **当面の現実解は「本体の型を増やさず、MOD が持つ疑似の記憶・エッセンス」。** 部品はすでにある（記憶の仕掛け22効果、記憶に帰属するダメージ、記憶ごとの追加ソケット、連携）。
   - **夢のエッセンス**：記憶1つにつき「夢のソケット」を1つ与え、そこへ入れるとその記憶の性質が変わる。本体のエッセンスと同じ役割を、既存の仕掛け（`GimmickEffect`）で実現する。**12種は既存の部品だけで組める**（§4）。
   - **夢の記憶**：入力を持たない「自動で発動する記憶」。専用の枠に入れ、条件を満たすと自動で出る。**新しい実行部（自動発動の予約とクールダウン）が要る**（§5）。
3. README 第10章の「装備側ソケットは公開版（1.0）では導入しない（決定）」と「専用ルーン案 対 既存Essenceの限定互換案は試作後に比較」の、**前者の再検討にあたる**。1.0 は過ぎているので、いまは判断してよい時期。
4. 今回のPR（ドラフト）は**定義と上限の確認だけ**。ゲームには何も出ない。ソケット・保存・画面・通信は、方式を決めてから別の段階で入れる（§6）。

## 3. 推奨の形と守るルール

### 3.1 夢のソケット（エッセンス側）

- 装備中の記憶（Q・W・E・R・アイデンティティ・移動）1つにつき、夢のソケットを**1つ**。本体のエッセンス枠とは別で、競合の検出対象にしない。
- 入れられるのは夢のエッセンス1つ。**同じ系統の効果は重複装着しても強い方だけ有効**（README 第10章の「同系統は上書き」）。
- 効果は、そのソケットの記憶に対してだけ働く（本体のエッセンスと同じ向き）。移動の記憶は受け手のみ（既存の不変条件：移動は発動元にならない。例外は既存の `h.husk.key2`）。
- 効果が記憶に属する条件（命中・撃破・会心・使用）は、既存の「仕掛けの帰属（C02）」の規則に従う。MOD が出す追加ダメージでは再発動しない。
- 品質は I・II・III の3段。入手方法は §6 の判断事項。

### 3.2 夢の記憶（記憶側）

- 専用の枠は2つ。押して使う技ではなく、**条件を満たすと自動で出る**。
- ホストが条件を判定し、ホストが出す（クライアントの入力に依存しない）。クールダウンはホストの時計で数える。
- ダメージは無属性・攻撃効果の係数0・連鎖なし（既存の仕掛けの規約と同じ）。回復と障壁は親なしの `serverActor` から与える。

### 3.3 強さの原則

1. **能力値・時間・回復・障壁を通す効果を主役にする。** 倍率加算の山に入るダメージ増幅は、値を大きくしても薄まる（レビュー §1.2）。
2. **各効果の既存の上限を超えない。** 仕掛けは `Gimmicks.Cap`（例：Echo・Burst 1000、Wound・Primed 120、Weakspot 25、Sap 15、Siphon 10、Crescendo 8）、条件付きAD/AP は覚醒前120%の共通枠。
3. **夢の圧との釣り合い（案 P1）：** 装備中の夢のエッセンス1つにつき、夢の圧の計算上の使用星点へ品質I/II/IIIで 6/9/12 点（概算）を足す。星の点だけ課税される現行の仕組みでは、ソケットが「課税のない強さ」になるため。点の換算は、記憶の冴え（主力記憶で約1.4〜4.7%/点）に対する各効果のおおよその価値から置いた粗い値で、BalanceSim で確かめる前提。**P2：課税しない**（装備は楽しさのための報酬として軽く扱う）も選べる。推奨は P1 の軽い版。
4. **説明文は `docs/description-style.md` に従う。**（半角の `+` `-` `%`、常体、単位を省かない、内部IDを出さない、など）

### 3.4 検証 S1：本体型の新設が通るか（実機が要る）

案 A を捨てる前に、**1時間ほどの実機の確認**で可否だけ決められる。

1. MOD の DLL に `Gem` の派生型（最小：装着すると攻撃力 +1 を足すだけ）を置き、`DewResources` に登録できるか、ロード時に Weaver 由来の例外が出ないか。
2. ゲーム内の入手経路（ショップ・ドロップ）に出せるか、装着・保存・再読み込みで残るか。
3. ホストだけがMODを持つ協力で、MODなしのクライアントに壊れずに見えるか。

通れば、案 A は夢のエッセンスの「入れ物」として使い、中身（§4）はそのまま移せる。通らなければ案 B で進める。クラウドからはできないので、利用者のPCでの Remote Control が要る。

## 7. 未確認（この資料の限界）

- 本体型の新設の可否（S1）。
- 夢のソケットに入れた効果が、本体の記憶の再生成・記憶の差し替え・協力の再接続で正しく外れる・付き直るか（既存の記憶帰属の仕組みに乗る前提）。
- 点の換算（P1の 6/9/12 点）は粗い概算。BalanceSim の実測で置き換える。
- 自動発動の記憶（M1〜M8）の見た目と通知。MODを持たない参加者から見えるものは何か。
- 値の組み合わせの強さ。6つのソケットが全部埋まったとき、同じ系統の重複上書きと、各効果の既存上限だけで十分に抑えられるか。
