# #623 責任の宝石の被弾演出キャッシュに関する改善案

2026-10-24、PR #1131 のレビュー指摘 F1（C-II 部分未達）を確認し、対応を決めた記録である。

## 指摘の内容

この節は指摘時点（修正前）の状態の記録である。現在の状態は「対応したこと」と「残る制限と見直す条件」以降に書いてある。

`NativeGemResponsibilityHitPerf` は処理を軽くする変更だが、結果が変わらないことの保証が IL の指紋（本体の形の確認）と spec の論証だけで、Prefix への転写（`pitchCurve`・`volumeCurve`・`shakeAmpCurve` の割当先、`localScale` へ `volumeMultiplier` を使う式など）に誤りがあっても検出する手段がコードレビューしかなかった。また指紋は `GetComponentsInChildrenNonAlloc` の呼び出し回数しか数えておらず、走査する型・`includeInactive` の引数・`localScale` に渡す値の式を見ていなかった。テスト環境では受け口の境界スタブが空実装のため指紋検査は必ず不一致になり、追加した Prefix 本体は全テストで一度も実行されていなかった。

## 対応したこと

修正ラウンド（head 84895c68 の後）で、境界（`tests/Issue73.Native.Tests`）に記録可能な `DewAudioSource`・`FxCameraShake`・曲線・子の置き場を整え、`GemResponsibilityHitPerfTests` から Prefix を直接呼び出した。このテストで、`strength` から `pitchMultiplier`・`volumeMultiplier`・`amplitude`・`localScale` への書き込み値と `FxPlayNew(fx, e)` の呼び出し引数が曲線の評価結果から意図どおり導かれること、キャッシュの再作成が `fxHit` の参照が変わったときだけであることを検証した。あわせて指紋検査（`ValidateShape`）を強化し、走査のジェネリック型引数（`DewAudioSource`・`FxCameraShake`）、2引数の `GetComponentsInChildrenNonAlloc`（`includeInactive=false` の意味）、`set_localScale` の直前の `op_Multiply` が `volumeCurve` の評価結果を使っていること、曲線と書き込み先の対応まで確かめるようにした。拒否の見本（型の替え間違い・3引数化・別の曲線で `localScale` を作る・`fxHit` 以外を走査する・割当て替え・`FxPlayNew` の引数替え）を弾くことも同じテストで確認した。spec（`perf-loop/20261024-1529.md`）には、`fxHit` がプレハブアセットである根拠（ilspycmd の逆コンパイルで、受け口は `fxHit` へ値を書いて `FxPlayNew` に渡すだけでシーンへ置かない）を1行添えた。テストの作成はこのラウンドの依頼で明示的に許可されたもので、憲章の「専用のテストは作らない方針」と C-II（処理を軽くする変更は結果が変わらないことをテストで確かめる）の衝突は、境界テストを足す側で解決した。

## 残る制限と見直す条件

指紋は既知の命令（曲線の評価・子走査・書き込み・`localScale`・`FxPlayNew`）の並びと回数を見るため、本体がこれら以外の種類の文（新しいメソッド呼び出しや別フィールドへの書き込み）を追加しても検出できない。ゲーム更新のたびに spec の規定どおりこの指紋を見直すこと。検出強化の改善案として、対象メソッドの命令総数の比較や IL のハッシュ化など、数えていない文も検出できる指紋への拡張を今後検討する（実装時期は未定。現行の指紋で誤検知なしに運用できている間は必須としない）。なお修正ラウンド2から、`SOD_MANAGED` 環境変数で実 DLL（`Dew.Contents.dll`）を指せる環境では `GemResponsibilityHitPerfTests` の2件（実物の命令列全体の受理と、見本 IL の窓と実物の突き合わせ）が実 DLL との照合を行い、修正ラウンド4からは走査の意味の照合（2引数の `GetComponentsInChildrenNonAlloc` が `includeInactive=false` を意味することを `Dew.Core.dll` と `UnityEngine.CoreModule.dll` の両方から確かめる `NativeScanOverloadMeansIncludeInactiveFalse`）も加わったため、現在は計3件である。ゲーム更新後はこの3件がまず変化を拾う。実 DLL が無い環境（CI など）ではこの3件は確認なしに終わる。

## 交互参照時のキャッシュ再構築の割り当て（2026-10-24 追記）

PR #1131 のレビューで指摘された残る制限である。`_cachedFx` と受け口の `fxHit` の参照が変わるたび、Prefix は `GetComponentsInChildren<DewAudioSource>` と `<FxCameraShake>` で新しい配列を2本作ってキャッシュを作り直す。書き込みの値・順序・`FxPlayNew` の引数は本体と同一のままなので結果の等価性は保たれるが、複数の `Gem_C_Responsibility` インスタンスが異なる `fxHit` プレハブを参照して被弾が交互に届く状況では、RPC 受信ごとに再構築が起き、プールの NonAlloc（確保なし）で走査していた本体より1受信あたり2配列の割り当てが増える。本 PR の調査では受け口は `fxHit` を書き換えず、既定運用では全インスタンスが同一プレハブを参照してキャッシュが命中し続けるため、通常の運用では発生しない。改善案は2つ。キャッシュを参照ごとの小さなマップ（`ConditionalWeakTable` 等）に持つか、再構築が閾値以上続いたらこの機能だけ無効化して本体経路へ戻すかである。対応時期は未定（既定運用で発生しないため必須としない）。境界テストは同一参照での再走査なしと参照変更時の再構築を検証しているが、交互参照時の挙動（再構築が毎回起きること）は検証していない。

## FxPlayNew 例外の伝播の境界テスト（2026-10-24 追記）

PR #1131 のレビュー指摘 F2 の追記である。Prefix は書き込みまでの例外ではこの修正だけを無効化して本体経路へ戻すが、`FxPlayNew` の呼び出しは try の外にあるため、その中で例外が出たときは戻さず伝播させる。本体へ戻すと演出がもう1つ入る（または同じ例外がもう1回出る）ためである。修正ラウンド2ではこの経路を直接確かめるテストが無く（テストの作成が許可されていなかった）、レビューは「境界テストを1件足すか、この台帳に追加案を記録すること」を求めた。修正ラウンド3でテストの作成が許可されたため、追加案として残す代わりに `GemResponsibilityHitPerfTests` に `PrefixPropagatesFxPlayNewExceptionWithoutDoublePlay` を実装した。境界の `FxPlayNew` スタブに例外へ切り替えるスイッチ（`fxPlayNewException`）を付け、例外が Prefix から伝播すること・呼び出しが1回のままであること（本体が再実行されず演出が二重に入らない）・`_disabled` が立たないことを確かめる。呼び出しを try の中へ戻すとこのテストが失敗することも確かめてある。あわせて実 DLL との照合2件（修正ラウンド3時点の件数。修正ラウンド4で走査の意味の照合が加わり、現在は計3件）は、`SOD_MANAGED` に `Dew.Contents.dll` が無い環境では合格にならずスキップとして報告するようにした（DLL の有無で `FactAttribute.Skip` を与える）。

## 実行中の子構成変更と stale キャッシュ（2026-10-24 追記）

PR #1131 のレビュー指摘 F1 で確認した残る制限である。Prefix のキャッシュの無効化は `fxHit` 参照の変更と例外時だけのため、実行中に第三者 MOD が `fxHit` プレハブの子へ `DewAudioSource` や `FxCameraShake` を追加してもキャッシュは作り直されず、追加分へ曲線値が書かれない。本体は毎回走査するため、共存した場合に音・揺れが食い違い得る。本体にも本 MOD にも子の構成を変える処理は無い（spec に記録済み）のため、通常運用では発生しない。「交互参照時のキャッシュ再構築の割り当て」の改善案（参照ごとのキャッシュ、再構築が閾値以上続いたらこの機能だけ無効化して本体経路へ戻す）はこの stale ケース自体は除かないため、それらを検討する際には子の数の変化でキャッシュを作り直すような案も含めて併せて扱い、ゲーム更新時の指紋見直し（「残る制限と見直す条件」）とあわせて進める。
