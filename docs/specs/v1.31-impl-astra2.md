## C06 — ModShieldPools

Implemented `Game/Mechanisms/ModShieldPools.cs` as an independent pool runtime with an explicit native adapter contract. Identity is owner/recipient/pool kind; Ordinary is capped at 15% recipient maximum HP, Rampart at 10%, and Allied at 3%. Reapplication uses the larger of actual remaining and the new processed award, refreshes expiry, and applies the final pool cap. A lower award cap applies to the new amount only, so a 10% sacrifice award cannot reduce an existing 13% Ordinary shield. Amounts remain floating point at the native application boundary.

`HostAuthority.ModShieldPools.cs` constructs the same native status as `Actor.GiveShield`, from the root serverActor. A narrowly scoped Harmony postfix caps `Actor.ProcessShieldAmount` only for the exact new status being constructed, before its shield is registered or its support events are published. Reapplication invokes the existing status's processors once and writes the processed result directly to `ShieldEffect.amount`; it never calls `SetAmount` with an already processed value. Identity includes the actual `ShieldEffect` object, which is newly constructed per status lifetime, so native status pooling cannot make an old MOD handle own an unrelated shield.

Existing star-gimmick Shield and Rampart dispatches now use these pools. Rampart keeps the existing distinct-victim budget and target-limit producer, clamps each victim's value to 2%, and applies its separate final 10% pool cap. Ordinary/Rampart player descriptions state the finite count, maximum-remaining rule and final cap in Japanese and English. Other Power/native/equipment shields are untouched. Pending awards capture equipment epoch when queued. Exact native equip/unequip postfixes refresh the epoch immediately, including removing and re-equipping the same skill object before the next update; old pending grants cannot recreate a pool. Death, expiry, equipment-instance changes, zone reset and detachment clear or invalidate only these tracked handles. Maximum-HP decreases reclamp tracked pools. Expiry/removal calls status destruction, not an enemy damage or shieldbreak event.

## C07 — ScopedKeystoneModifiers

Implemented `Game/Mechanisms/ScopedKeystoneModifiers.cs` and `ScopedKeystoneModifiersTests.cs`. Immutable definitions carry required memories, prerequisites, cost, upside/downside transforms and explicit memory/effect/channel/receiver/recipient/argument/source scopes. Magnitudes use hundredths of a percent; native damage, star MemoryDamage contributions, generated damage and MOD effect payloads remain separate typed layers. Operations cover scale, explicit seconds, integer targets/EveryN, intentional disablement and Wound final total/lifetime redistribution. C09/C10/C11/C12 payload kinds can be bound by their handlers without registering concrete keystone stars.

Selection accepts exactly one registered existing/new key, validates its prerequisites and both sides together, and rejects changed selection/equipment without a new epoch. Missing required equipment disables both sides with no substitute. Intentional disablement rejects incompatible paid allocation witnesses so C15 can refund/retry explicitly. Ordinary Wound duration preserves rate; an explicit total/lifetime transform does not multiply duration into total a second time.

## C11 — SacrificeShield

Implemented `Game/Mechanisms/SacrificeShield.cs`, `HostAuthority.SacrificeShield.cs` and `SacrificeShieldTests.cs`. The Core runtime captures positive net HP loss across an admitted exact native payment, retains recovery within that dispatch, subtracts signed completed nested deltas so one payment is not counted twice, and awards zero for maximum-HP resizing. Tokens are new for each capture even if a native instance is reused. Abort/finalizer cleanup invalidates incomplete enclosing captures; owner death, equipment/selection epoch changes and zone resets remove pending work.

The host transpiler verifies each actual native iterator's PureDamage call, caster target, shield/armor/immunity flags and Dispatch count, then replaces only its self-sacrifice Dispatch with a wrapper. The original native payment still executes exactly once; the enemy damage call remains native. Runtime C11 validation failures explicitly log and stop that MOD binding while allowing the original payment and skill to proceed. The wrapper never substitutes a generic HealthCost hook or invents a zero-payment award.

The next host update grants 50% of measured paid HP for 4s through C06, with a new-award cap of 10% recipient maximum HP after processors and the existing Ordinary 15% pool. The explicit C07 binder requires a live verifier that the simultaneous native G/D downside is bound. No keystone data or active default binding was added. Zone cleanup preserves registered bindings while clearing transient captures; owner detach removes the binding.

## C12 — AlliedWard

Implemented `Game/Mechanisms/AlliedWard.cs` with immutable typed recipient, amount-basis, pool, profile, radius, duration, base/max targets and activation-budget fields. `ValueUnits` uses integer hundredths of one percent. Definitions validate explicit effective limits. The standard profile permits up to 100% offense basis, 15m, 8s, four travelers or five owned summons. The recipient-HP summon profile requires Allied/OwnedSummons/RecipientMaxHP and base one target, with maximum three targets and 9s. The Ordinary recipient-HP traveler variant stays an explicit typed choice.

Selection filters active living recipients, ownership, relation and radius before sorting by HP ratio, distance, then instance ID. The host also excludes knocked-out travelers before selection and again before dispatch. IncludeOwner is explicit; ally-only never substitutes the owner. Raw amount uses either caster max(AD, AP) or recipient maximum HP. The activation runtime consumes a supplied real activation serial only on a successful condition, with per-activation or per-activation/victim deduplication and explicit lifecycle clearing.

`HostAuthority.AlliedWard.cs` is the payload sink for an already admitted C02 activation. It enumerates actual party heroes or the caster's actual summons, rechecks relation/ownership/lifetime/distance before dispatch, applies the caster's MOD shield stat once, and calls C06 from serverActor. Native summon lifetime/AI and PackMend are unchanged. No authored channels or synthetic gameplay registrations are installed.

## C13 — PressureDividend

Implemented `Game/Mechanisms/PressureDividend.cs`, `PendingPressureDividends.cs` and `Rules.PressureDividend.cs`, with `HostAuthority.PressureDividend.cs`, `ClientSession.PressureDividend.cs`, `PressureDividendMessages.cs` and localized lifecycle/registration calls. Same-condition contributions add before one GB multiplier and Chance addition, with final 40% probability cap and exact hundredths-percent validation. Source memory must be known, equipped and non-movement. Generated/unknown attribution is excluded. The host roll ledger admits at most one roll per run/zone/spawn/owner, including failed rolls and repeated notifications.

Each tracked native Monster spawn receives a new monotonic spawn serial. Its own final-stat processor records the HP multiplier it actually applied and advances that spawn's snapshot version. Synchronous death freezes the applied snapshot before the native actor kill notification and before pressure cleanup changes the dead monster's stats. Eligibility checks native disableLoot/hunter rewards. Admission additionally requires an explicit verified NativeLootEnemy victim classification; Unknown and EnemySummon are rejected. No ancestor heuristic substitutes for that classification. Unapplied or below-1.25 snapshots do not qualify; later unrelated global pressure cannot rewrite death history.

The reward sink sends a separate optional host TargetRpc receipt, authenticated by native client-handler routing and local run/hero identity checks. Pending receipts deduplicate nonce and death/owner identity, then use Rules to add exactly one unsecured shard. Normal loot count is not a condition. Existing secure, victory and defeat/25% Echo behavior remains unchanged; no normal loot multiplier is introduced. This is an optional message type under protocol 12, not a Build grammar change.

## Questions and work not completed

1. C02/C03/C14 integration must supply verified activation/source/equipment facts and typed effective payloads to the new sinks. C07 and C11 specifically require the exact ordered native downside binding before real key activation. No legacy source approximation was substituted.
2. C13 needs native provenance for boss-created Monster adds that may be enemy summons. Native Summon entities and disabled loot/hunter guards are verified; they are not proof that all such Monster adds are eligible. Unknown classification rejects admission.
3. C13 defines same-condition chance addition and one roll per death/owner, but does not define composition if more than one non-equivalent condition simultaneously matches. The runtime rejects that case; a probability rule is needed before such data can be registered.
4. Live Unity combat/co-op tests remain open: processed shield visibility, exact net sacrifice capture, recipient lifecycle and authenticated reward delivery. Source inspection, offline IL inspection and Release compilation do not constitute those tests. C14/C15 publication and allocation UI integration remain the overall release gates.
