# v1.31 build aggregation and wire capacity

The build path is `Build.Compute` → `Build.Encode` → `DreamforgeBuildMsg` → `HostAuthority.OnBuild` → `Build.Decode` → the power, gimmick, pair-combo, and link runtimes. Core remains pure C# 9 / netstandard2.0; the Mod remains netstandard2.1. This document distinguishes allocation/transport limits from intentional gameplay rules. Increasing transport capacity must not replace a largest-only effect with an additive one, combine independent cooldowns, or alter a selected choice.

## Aggregation semantics

Additive links use a canonical key containing kind and the ordinally sorted, canonicalized requirement set. This retains the beneficiary memory and all equipment/traveler conditions. Their fixed-point values are added without imposing the single-source equipped cap on the aggregate. MemorySurge remains a separate source because its expiry and largest-only behavior are stateful.

Gimmick condition identity includes memory, trigger, effect, argument/receiver, cooldown, and supported duration/radius/target/chance modifiers. The star ID remains a state discriminator. Gimmick stars are retained independently: even equal zero-cooldown effects can produce separate target selections, random rolls, caps per application, native callbacks, or generated-damage requests. Sharing a condition key does not prove those applications commute. Runtime build refresh compares the complete identity/value and retains each star's existing cooldown state.

Pair combos remain registered bridge-ID/rank entries. Their authored trigger memory and payoff memory, activation identity, marks, and windows are restored from the registry. Choice nodes contribute only the explicitly selected option. Cluster boosts are collected by beneficiary memory and applied to the selected gimmick without converting its fractional value to a whole percentage.

Link and gimmick values use integer thousandths (`value × 1000`) through composition and transport (`src/SodRpg.Core/Game/BuildPrecision.cs:8`). The authoring `Value` accessor is exact decimal; `ValueMilli` is the stored integer; `ValuePercent` supplies the native floating-point application value. Conversion to floating-point occurs where game APIs consume damage, healing, shielding, probabilities, or cooldown ratios. Awakened link values and their single-source caps also retain fractions: the two- and three-requirement MemoryDamage caps are 115.2 and 158.4 rather than 115 and 158. Values that cannot be represented in exact thousandths fail explicitly instead of silently rounding. Existing Stat and Power catalogs retain their authored integer units and total gameplay caps.

The 300-point budget and six equipment slots give an allocation envelope independent of whether a registered tree has 80 or 720 visible nodes. Registered-tree analysis accounts for rank costs and selected choice alternatives; pair and enum registries bound their own record categories. Bounds cover raw records as well as normalized collections so duplicate/invalid records cannot evade rejection. Oversized input fails as a whole; it never produces a prefix build.

The implementation is in `src/SodRpg.Core/Game/BuildAggregation.cs:10` (link key), `:25` (addition and independent Surge sources), `:48` (gimmick condition key), `:59` (per-star state key), and `:62` (bridge/receiver key). `GimmickRuntime.SetBuild` validates before replacing active state (`src/SodRpg.Core/Game/Gimmicks.cs:350`); equal definitions retain their per-star state via the complete key and exact value (`:384`). Pair runtime capacity likewise rejects before mutation (`src/SodRpg.Core/Game/PairComboRuntime.cs:25`).

Primed now retains the parameter-scaled window up to 20 seconds, derived from its five-second base and +300% maximum duration. Convergence no longer clears live target cooldowns at the 200-record pruning threshold (`src/SodRpg.Core/Game/PowerRuntime.cs:173`). These changes preserve existing state across larger builds and target populations.

## Capacity derivation

`BuildLimits.Analyze` (`src/SodRpg.Core/Game/BuildLimits.cs:76`) groups talents by their real tree, applies a 300-point 0/1 knapsack using first-rank costs, and chooses only one option's output for a choice. Extra ranks change magnitude rather than entry count. The per-category theoretical maxima deliberately relax graph connectivity and pair prerequisites, so they are upper bounds on legal allocations, not claims that all categories can be maximized together. The generic tree is analyzed separately. Tests independently enumerate the registered maxima.

The current registry contains 678 talents and yields per-traveler maxima of 24 gimmick entries, 25 star links, 7 pair combos, 6 cluster modifier stars, and 56 total effect entries. Each individual registered star currently emits at most one gimmick and one link, with a maximum combined output arity of two. The transport envelope reserves those registered output arities for every one of the 300 legal points, so adding the full cluster tables does not require another arbitrary limit increase.

The bound prevents integer overflow or invented extreme sums without clamping a legitimate aggregate to one source's cap.

## Protocol 12 and message bound

`Protocol.Version` is bumped once, from 11 to **12** (`src/SodRpg.Mod/NetMessages.cs:155`). Link and gimmick value fields now mean integer thousandths. Both Build uploads and applied-summary acknowledgements use the bounded multipart transfer in this same protocol version. Old packets cannot be reinterpreted as current values: the host requires protocol 12, and the current gimmick decoder requires exactly eleven fields. There is no legacy-value inference.

The section grammar remains `s`, `p`, `h`, optional `u`, `d`, `a`, `l`, `g`, and `c`. A link is `kind:valueMilli:requirement+requirement`; a gimmick is `starId:memory:trigger:effect:valueMilli:arg:cooldown:durationPercent:radiusPercent:extraTargets:chancePercent`; a pair combo is `registeredId:ranks`.

The maximum complete Build payload is **195,820 ASCII characters = 195,820 UTF-8 bytes**, computed by `src/SodRpg.Core/Game/BuildLimits.cs:60`. It reserves maximum lengths for every independent record category, including separators, signed 32-bit decimal fields (11 characters), round-trip single-precision cooldown text (24 characters), 96-character star/memory/requirement tokens, three link requirements, and the longest registered pair ID (16 characters). This is a conservative envelope; a legal allocation cannot simultaneously maximize every category. The number bounds the complete Build string, including the acknowledgement's same encoded summary. It is not sent as one native RPC string.

Encode validates list counts and aggregate value bounds before producing a packet, then enforces the character/byte bound (`src/SodRpg.Core/Game/Build.cs:255`, `:340`, `:345`). Decode checks the global bound and ASCII grammar before allocating entry arrays, bounds raw record counts before normalizing, and rejects malformed entries, unknown sections/IDs, duplicate sections or identities, invalid enum values, invalid link conditions, non-finite cooldowns, and oversized aggregate values (`src/SodRpg.Core/Game/Build.cs:357`). Intentional scalar gameplay clamps remain separate from these structural rejections.

`BuildTransfer.Split` (`src/SodRpg.Core/Game/BuildTransfer.cs:32`) divides the complete string into records carrying data, a 32-character transfer ID, zero-based index, part count, and total length. The Mod adds protocol and, for acknowledgements, the target hero network ID (`src/SodRpg.Mod/NetMessages.cs:20`, `:43`). The largest JSON wrapper is bounded at **174 bytes**, including maximum-width metadata values (`src/SodRpg.Core/Game/BuildTransfer.cs:26`). Reserving six JSON bytes for every input character, including the worst possible escaping, yields **10,893 characters per part** and at most **18 parts** for a complete Build (`:29`). Therefore each serialized message is bounded by `174 + 6 × 10,893 = 65,532 bytes`, below Mirror's 65,534-byte string limit. The reliable transport's larger packet limits do not tighten this bound.

`BuildTransferReceiver` retains at most one bounded in-progress transfer per peer and exposes a string only after every correctly sized, consistently identified part arrives (`src/SodRpg.Core/Game/BuildTransfer.cs:88`). Invalid metadata, count/length mismatches, oversized parts, duplicate indexes, and replay of the just-completed transfer reject without applying a prefix. A new valid transfer ID supersedes the previous incomplete transfer; disconnect/session reset clears its state. The host reassembles before `Build.Decode` or any runtime update (`src/SodRpg.Mod/HostAuthority.cs:1100`). The client splits uploads (`src/SodRpg.Mod/ClientSession.cs:913`), the host splits acknowledgements (`src/SodRpg.Mod/HostAuthority.cs:1141`), and the client reassembles only protocol-matching acknowledgements for its local hero (`src/SodRpg.Mod/ClientSession.cs:786`).
