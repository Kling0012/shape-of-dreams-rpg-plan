# 遺物融合の追補確認（Issue #445）

## 能力値の仕様（R1 / R8）

既存の `Relic.EffectiveStats` は基礎・特性・禁忌の追加能力値を計算してから
`Fusion.ScaleStat` で一律に増幅する。既存の `RelicFusionTests` も禁忌の契約を含めて
符号を変えずに増幅することを確認しているため、この仕様を維持する。
1段につき6%、5段で30%の増幅で、禁忌の契約の最大HP -50% は -65% になる。
不利な能力値も強まる。装備全体の最大HP%の下限 -75% は従来どおり。
固有効果、連携、セット効果は融合の増幅対象外。
説明書 `src/SodRpg.Mod/README.md` の融合欄と `ScaleStat` に明記した。
既存の最終能力値テストは5段と -65% の具体例を確認するよう最小限修正した。

## イベントの確認（R2）

製品コードで `EventKind.LevelUp` の受信側を確認した。
`DreamforgeUi.Decorate` はレベルアップ色にし、`ClientSession.Emit` はビルド変更通知を行う。
このイベントによる音・レベルアップ集計の受信処理は見つからなかったが、今後の受信側との
干渉も避けるため `EventKind.Fused` を末尾に追加し、既存列挙値の番号は維持した。
融合だけを専用イベントにし、`Emit` で必要なビルド変更通知を引き続き行う。
通知・保存は共通経路を使い、融合で経験値やレベルを増やす処理は追加しない。
既存の融合成功テストの2ケースで専用種別を確認する。

## 表示名の参照確認（R3 / R9）

`src` の `DisplayName` 参照を検索し、遺物の参照は通知文・タイトル・取引表示用の
スナップショットで使われていることを確認した。星図の同名プロパティは遺物と無関係。

- 遺物の一致と装着・検索: `Uid`、`BaseId`、`UniqueId`、`NamedId`。
  融合候補の名前の一致は `Fusion.SameName`、検索入力は `PlainName` を使う。
- 並べ替え: `Rules.FusionCandidates` と `DreamforgeUi.SortedCached` は `Score`。
  融合でScoreが変わる際は既存の融合段階比較で一覧と行文字を更新する。
- 保存: `ProfileCodec.WriteRelic` は明示的な保存欄からJSONを作り、表示名を保存しない。
  段階0では融合欄自体を省略し、旧版の保存バイト列を維持する。
- チェックポイント: `ProfileCodec.CheckpointRelicKey` は `Json.Write(WriteRelic(relic))`。
  `RunCheckpoint` と `CoopTrade` もこのキーを使う。言語や「◆N」の文字列には依存しない。
  正の融合段階は保存欄として比較するので、実際の性能の差は検出できる。

照合キーの修正は不要と判断し、表示専用であることを `Relic.DisplayName` にコメントした。
既存の保存互換・融合候補・協力取引のチェックポイント復元・表示キャッシュテストを実行した。

## 受領書と通信欄（R5 / R6 / R7 / R11 / R12）

前ラウンドで追加済みの `Fused_receipt_for_legacy_peer_drops_only_fusion_keys_and_keeps_unknown_fields`
を維持する。今回の新しいテストメソッドはない。このケースの融合キーをJSONの
`fusionLevel` 表記にして、パース後にも融合キーが残らないことを確認するよう修正した。
未知の受領書欄・プロフィール欄・欄順・融合以外の遺物データと、変換不要なもう一方の
プロフィールの元文字列を保持する。

`CoopTradeCodec.WithoutFusionForLegacyReceipt` と `ProfileCodec.WithoutFusionForLegacyTrade`
の文字列検索を除去した。パース後の `JsonObject.TryGet("fusionLevel", ...)` に基づいて
再帰変換し、実際のキーを除去した場合だけ再エンコードする。値の文字列内に同じ文字が
あっても変換理由にならない。融合キーがなければ元の文字列参照をそのまま返す。

`HostBuildValidation.Encode` は禁忌がなく融合があるとき、禁忌欄 `fields[14]` を空で残し、
`fields[15]` に融合段階を置く。読み側との対応と、空欄を詰めてはいけない理由をコメントした。

## SyncFusion の実測と修正（R4 / R10）

依頼の自律度high方針に従い、ゲームは起動できない前提でコードと計測ツールを使った。
**以下はこのLinuxホストでの実測であり、Unity/Mono上の実機フレーム時間ではない。**
ゲーム内計測・音や演出の実視認・1920x1080での画面確認は未実行。
レイアウトや表示領域の変更はない。

日時: 2026-10-15 JST。ホスト: womakase、Linux x86_64、Intel Core i7-6700HQ 2.60GHz、
.NET SDK 10.0.111 / runtime 10.0.11、Release、`DOTNET_TieredCompilation=0`。
他の処理が走る共有ホストなので、時間には変動がある。

再実行:

```sh
python tools/measure_fusion.py --revision fc54ee1
python tools/measure_fusion.py
```

`tools/measure_fusion.py` は対象版の `DreamforgeUi.Fusion.cs` から描画直前までの
フィールド・状態構造体・`FusionState`・`SyncFusion` をそのまま抽出してコンパイルする。
Coreはこのブランチを参照し、タイトル整形も製品ソースを使う。
差し替えはUI/session/時計の境界だけ。成果物は無視対象の `tools/obj/fusion-perf/` に保存する。
新規のテストスイートではなく、再現可能なCPU/割り当て量の計測ツールである。

9人の旅人、4件の分解予約、100/1,000/10,000件の保管庫で測定。
目標と名前が一致する材料は置かず、初期構築後の無変更同期を切り出す。
1,200回のウォームアップ後、各600フレーム×Layout/Repaintの2呼び出しを7回実行。
表は各ラウンドの平均時間の中央値と、スレッド割り当て量の平均。
候補変更時のリスト構築・描画・保存・ネットワーク時間は含まない。

|---:|---:|---:|---:|---:|
| 100 | 67.828 | 0.372 | 10,400.000 | 2.848 |

時計を進めずキャッシュヒットだけを測った修正後は、それぞれ0.106 / 0.105 / 0.107 μs、
割り当ては全件数で0 B/呼出だった。1万件の60fps相当の最も遅いラウンド平均は
修正前6,410.076 μs、修正後30.228 μs。これらは1回の最大遅延ではない。

修正前は値型の状態生成の内部で `Profile.IsEquippedAnywhere` を全件呼び、
SortedDictionaryの列挙が件数に比例した割り当てを生んでいた。
修正後は全件の状態比較を最大0.3秒に1回へ抑え、装備UID・予約UIDを再利用する
HashSetへ一度まとめてから各遺物の状態を確認する。全件走査自体は残し、直接的な変更も
遅くとも次の比較で検出する。再比較時の旅人列挙の小さい割り当ては残るが、保管庫件数には比例しない。
`TradeLedger.ReservedSalvageUids(HashSet<string>)` は内容を消して詰め直し、解除された予約が
集合に残らない。引数なしの既存APIは維持した。

対象・選択材料・通貨・安全条件・件数の変化は待たずに処理する。
選択変更、メニューの開閉、別操作の実行でキャッシュを無効化する。
確定ボタンでは期限を待たず再比較し、変化があれば確認を取り直す。
消費直前は既存の `Rules.Fuse` が予約・装着・鍵・同一性・費用・安全条件を検証する。
例外時は融合機能だけを停止して警告する。
