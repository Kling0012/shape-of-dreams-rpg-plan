# v1.32 — Solo / Multi profile slots

## Persistence and ownership

- Solo keeps `profile.json` in the existing Dreamforge save directory. No content migration, merge, or schema-version change.
- Multi uses `profile.multi.json` in the same directory. First activation creates and saves `Profile.CreateNew` with an independent seed, before normal starter onboarding.
- Each slot has its own `ProfileStore`, `.tmp`, `.bak`, corrupt quarantine, reset-version check, and version archive. Multi archives use the `profile.multi.v…-archive-….json` prefix; Solo archives keep the existing prefix. Resetting one file does not reset the other.
- The active store and async writer are a pair. A writer is never rebound to another path. All ordinary saves, shutdown saves, and Builds use the active Profile. Relics, stash, per-traveler stars, codex, feats, bounties, awakening, materials, run state, and Lost & Found are entirely independent.
- `profile.slot` is small UTF-8 text: first line `solo` or `multi`, second line `auto=0` or `auto=1`. Manual choices serialize as `solo\nauto=0\n` / `multi\nauto=0\n`; AUTO as `solo\nauto=1\n`. The first line under AUTO is not an expedition checkpoint. Selection is recalculated from the current session.
- Missing settings mean AUTO. Invalid settings mean manual Solo with a visible load Note, preserving existing Solo progress rather than silently opening an empty Multi. Settings writes use a temporary file and atomic replacement.
- A newer unsupported profile version is not replaced with an empty editable profile. Load errors prevent the cutover; the previous active profile/store remain authoritative.

Decision order in `ClientSession.DetectProfileSession`:

1. A manager ending/ended gives Ambiguous.
2. `NetworkClient.active && !NetworkServer.active` gives Multi.
3. With a live session, before a server exists, `MultiplayerJoinLobby` or `MultiplayerJoinRestart` gives Multi.
4. In a live session, more than one `isHumanPlayer` in `allHumanPlayers` gives Multi; exactly one gives Solo; no initialized humans gives Ambiguous.
5. No current session gives Solo. Ambiguous deterministically selects Solo, but never authorizes an in-run switch.

The detector intentionally does not count `NetworkServer.connections`: authentication/loading connections are not a human roster. It does not use backend lobby capacity/member counts: those refresh asynchronously and are not the spawned game-player roster. A hosting lobby becomes Multi on the Update after its second human player registers, not simply when the co-op menu is selected. A remote join becomes Multi once its live manager/join intent is visible, before the local hero/run begins. Third-party AI players presented as human by the game's API are outside the documented roster contract.

## Exact switch moments and safety

- Startup: load Solo, then apply saved manual mode/AUTO if its saved `Profile.Run` is null. The existing Solo file is retained, not migrated.
- Menu controls queue selection changes for the next Update. Profile objects never change halfway through an IMGUI layout/repaint pair.
- Each `ClientSession.Tick` evaluates slots **before Wire and TrackRun**. In a stable title/lobby, an eligible changed selection switches in that Update.
- At the first observed Starting/InGame state or GameManager appearance, one final startup selection runs before `TrackRun`; that same Update latches the expedition. This also covers joining an already-running host before beginning the local profile run.
- Once latched, changes in roster, host/client role, hero state, room/scene loading, or result display only change the desired next slot. `Profile.Run != null` independently blocks Core switching, including saved unresolved runs after disconnect.
- The latch clears only when no GameManager/Starting/InGame state remains and a stable lobby/title boundary is identifiable. After results, switching therefore waits for the lobby/title, even if Rules has already cleared `Profile.Run`. An unresolved persisted run remains deferred until the existing run lifecycle settles it; disconnect alone never clears it.
- Pending trades, persisted salvage reservations, rewards, arrivals, and results must be settled before cutover. A runtime guard and debug assertion enforce this; clearing a queue is never used to discard unprocessed rewards.
- Cutover order: drain the old `AsyncProfileWriter` (timeout aborts), synchronously save the old Profile, load/create the target with its own store, replace the active Profile/store, retire the old writer, clear settled session ledger/RunChoice/host-ack state and visuals, invalidate Build/UI caches, run existing per-profile onboarding, and resend Build to the host when a local actor is available. A failed drain/save/load leaves old ownership intact. The host still decides run depth/waypoints; other players' profiles are untouched.

## Optional one-time copy

The header shows `ソロの進捗をコピー` / `Copy Solo progress` only for eligible first-use Multi, outside an expedition. A second `コピーを確定` / `Confirm copy` action confirms; Cancel is available. Copy clones serialized Solo progress rather than sharing objects. Neither profile may contain an unresolved run or salvage reservation.

`profile.multi.origin` records the initial Multi seed so exact untouched starter onboarding can still be recognized after restarting. Copy eligibility permits only empty state or that exact pristine starter-only state, including neutral UI-created traveler entries. Modified starter items, equipment allocations, earned progress, currencies, stars, codex, crafting, or run history deny copy. Existing progress never gets overwritten.

`profile.multi.copied` durably consumes the one-time copy before the copied profile is committed. A crash/failure after that marker conservatively consumes the attempt rather than risking a second overwrite. A successful copy then progresses independently. No general import/merge/reset UI is added.

## UI and protocol

The menu header always shows the active name, segmented `ソロ` / `マルチ` / `自動` (`Solo` / `Multi` / `Auto`) buttons, and a one-line explanation. Deferred changes show `遠征が終わったら切り替わります` / `The profile will switch after the expedition.` Save/switch errors remain visible. Records reads the active Profile as before; its cached lists are invalidated on cutover, including same-count codex/stash changes. Header-only identification is intentional; no additional HUD/secure-prompt row is required.

Protocol remains **12** (`NetMessages.cs:152-155`). Slots are local persistence/selection only. `CurrentBuild` computes from the active Profile and the existing multipart Build/ack messages are unchanged. There is no transmitted slot ID, remote-profile mutation, or new wire contract requiring a bump.
