# 起動時のパッチ適用の軽量化

2026-11-01。対象は v3.8.85 を元にした `perf/startup-patch-batch`。実機は未確認。

## 原因の見立て

利用者の Player.log では起動に 41,309〜45,268 ms、そのうちパッチ適用に 37,422〜38,017 ms かかっている。約390クラスに時間が分散している。

ゲーム同梱の Harmony を調べると、`Harmony.GetPatchedMethods()` は全所有者の全対象について `GetPatchInfo()` を呼び、所有者で絞っている。従来の `HasInstalledClass` はこの列挙の中でもパッチ情報を読み直していた。Infinity の導入判定などが呼ぶたびに、他 MOD を含むパッチ情報の直列化データを復元していた。対象が1メソッドのクラスにも全体の走査費用がかかる。

Harmony の `PatchClassProcessor` はクラス内では対象ごとにパッチをまとめるが、別クラスでは対象が同じでも置き換えを再生成する。ソースを単純検索した段階で388クラスを数えた。Prepare・Cleanup・動的な対象・Transpiler を持たない候補は212クラス。Actor.OnDisable、Actor.DealDamage、Actor.ApplyElemental などに重複がある。この数は静的な概数で、実際にまとめる数は連続するクラスと解決した対象によって決まる。

## 変更1 対象を絞った導入判定

通常のクラス属性だけで対象が決まる場合、`HasInstalledClass`、`EarlierCopyHookIsLive`、`RollBackClass` の探索をその対象だけに絞った。動的な対象、メソッドごとの対象指定、認識できない宣言は全対象を調べる従来の方法へ戻す。Prepare や TargetMethod(s) は呼び直さない。

所有者とクラスの完全名による所属判定は変えていない。再読み込みで別アセンブリの同名クラスへ解決される場合も従来の判定を使う。パッチ本体・導入順・初期化順は変わらない。

効果は推定。単一対象の判定が全対象数に比例する処理から対象1件の処理になる。利用者の環境で何秒短くなるかは未計測。

変更前の Release ビルドと NativeStartupTests 16件は成功。変更後は起動・再読み込みの既存テスト20件が成功し、既存のスキップが1件。最終の検証結果は作業完了時に追記する。

## 調査と未実行

Serena MCP は接続に失敗したため、検索と必要箇所の読み取りで調査した。ゲーム同梱 Harmony の実装はローカル DLL を逆コンパイルして確認した。逆コンパイルしたコードはリポジトリに保存していない。

実機のゲーム起動と13本の他 MOD を併用した時間計測は未実行。この環境ではゲームを動かせず、利用者の PC とゲームには触れていない。
