# Issue #779 記憶の発動ロックの検出と再同期

参加者側で残る発動ロックを、ホストの現在値で再同期する。実ゲームで頻発する症状の発生過程は未再現。既存の `tests/repro/issue779/Program.cs` で、製品の走査処理に対する検出漏れ4件を修正した。

## 検出と通信の条件

`ClientSession.SkillLock.cs` は1秒に1回、Q・W・E・R・Identity・Movementを調べる。停滞時間と診断の記録をスキル・現在設定ごとに保持する。死亡、画面切替、一時停止、キャラや接続先の変更で観測をやり直す。

- 非有限・負・600秒超のクールダウンや最低待ち時間は、従来どおり10秒続いたら再同期を要求する。
- クールダウンと最低待ち時間が終わったままチャージが0以下なら、詠唱フラグやチャネルの有無で走査を飛ばさない。
- 設定の発動ロック、マナとチャージが足りるのに予約できない状態、スタン、キャンセルできない行動制限を調べる。詠唱フラグだけが残る場合は、本体の詠唱予定時間を過ぎてから10秒待つ。
- 正常に減っているクールダウンや最低待ち時間は対象外。値が変わらないタイマーも調べるが、Ultimateの設定0と `lockCooldownUntilKilled` のクールダウンは停止が本来の動作なので除外する。
- 長い詠唱は予定時間内なら待つ。ゲストに生存中・期限前のチャネルがある場合も、発動ロックの確認を待つ。チャージ不足などの矛盾した数値は引き続き調べる。

要求は全スキルをまとめて最短10秒おき。正常な効果でも長い発動ロックはあり得るため、ロックや停止したタイマーの確認は同じ継続状態につき一度に限る。異常な数値とチャージ不足は回復まで10秒以上あけて再試行する。ホストはHello済みの依頼者とそのキャラだけを受け付け、同じ相手には8秒以上あける。両者の間隔には `Time.unscaledTime` を使う。

## 経路ごとの調査結果と対応

| 経路 | 調査結果 | 対応 |
| --- | --- | --- |
| チャージ不足 | 既存の検出はあるが、詠唱とチャネルによる早期returnで隠れていた | 早期returnを除き、ホストのチャージ・クールダウン・最低待ち時間を本体RPCで再送 |
| 詠唱フラグ | SyncVarなので値が変わらなければ従来の再同期では再送されなかった | スキルのSyncVarを再送。ホストで本体の `OnCastStart` と `OnStartChannel` を使い、チャネルが一つもないときだけ残存フラグを戻す。独自の詠唱処理を持つ派生型は変更しない |
| チャネル | `EntityControl.StartChannel` と `TickChannels` はサーバ専用。ゲストの一覧を走査除外の根拠にはできない | 一覧による全スキルの除外を撤去。行動制限のSyncVarをホストから再送。生存中のチャネルを停止・キャンセルせず、カウンターも推測で減らさない |
| 設定の発動ロック・能力の実体 | 本体 `AbilityTrigger.LogicUpdate` は無効な実体を取り除くまでロックを保持する。継続中の実体には一律の寿命がない | ロックを検出し、ホストでnullまたは非アクティブの実体だけを本体と同じ条件で整理してロックを再計算。生存中の実体を記録するが終了させない |
| 発動不可の状態異常 | `CanBeReserved` は `EntityAbility` のロックを参照。スタンやチャネルによる行動制限は別の同期状態 | 能力ロック・行動制限・状態のSyncVarを再送。状態異常を破棄せず、ロックハンドルも止めない。ホストに正当な制限が残ればそのまま保つ |
| 正常な長いクールダウン・詠唱 | 時間が減るクールダウンと予定時間内の詠唱は回復途中 | 再同期を要求しない。既存の対照テストで確認 |

## 再同期の順序と遅延

`Actor.CustomRpc_SendMessageToServer` はJSONをCommandのチャンネル0へ送る。本体のクールダウン・チャージ・最低待ち時間のRPCもチャンネル0を使う。Mirrorの `NetworkServer.BroadcastToConnection` によるSyncVar・SyncListの配信も既定の信頼チャンネルを使う。逆コンパイルしたコードで確認した範囲では、順序を逆転させる別チャンネルや遅延適用の経路は見つからなかった。

要求の到着時にホストの現在値を読み、同じ本体RPCを使って直ちに送る。再同期用の古いスナップショットをクライアントで後から適用する処理は追加しない。遅延中にローカル予測が0へ進んだあと、ホストの正当な残り時間が届けば表示が戻ることはある。これは通信の順序逆転とは区別する。

SyncVarは `SetDirty` で現在値を再送する。SyncListは同じ値を代入しても送信されないため、Mirrorの `AddOperation(OP_SET, ...)` で現在値の通常の更新を予約する。値を反転したり一覧を空にしたりせず、本体が続いている能力を一時的に解除しない。この内部APIが使えない場合は警告を一度記録し、その部分の再送だけを見送る。

処理落ちで走査が遅れても、経過時間を一度判定するだけで要求をまとめて送り直さない。ホストの間隔をゲーム内時間から実時間へそろえ、低速化時に8秒の制限が不必要に長くなる経路を修正した。実通信の遅延や順序逆転は再現していない。

## 診断

10秒続いた時点で、参加者側はスキルごとに一度だけ `Skill lock watchdog: guest snapshot` を出す。回復したあとに再発した場合は再び出す。クールダウン、最低待ち時間、チャージ数と最大数、設定の発動ロック、詠唱フラグ、マナ、チャネル数、行動制限、能力ロックのbitmap、スタン、状態異常の型と残り時間を記録する。設定と状態異常の詳細は各8件まで。

ゲストの実体一覧はサーバの実体を表さないため、同じ要求の `diagnosticSlots` に対応してホストも該当スキルの実体を記録する。型、一時的なnetId、生存状態、設定番号、ロックの種別、状態異常なら残り時間を各8件まで記録する。ホストのチャネルも経過時間、予定時間、行動制限を8件まで記録する。プレイヤー名やアカウントIDは追加しない。継続中の再試行には診断の印を付けない。

通信に診断用の任意フィールドを追加した。協力プレイでは全員が同じ版に更新する。旧いJSONにフィールドがなければ0として扱い、既存の要求version 1と本体RPCを維持する。
