# v1.31 cluster engine

## Scope and registration

Core remains pure C# 9 targeting netstandard2.0. Mod targets netstandard2.1 and includes `Game/**/*.cs`, including cluster tables, in its existing single assembly.

`StarClusters.All` is the registry. `StarClusters.Generate(definitions, existingTalents)` validates the complete registry before returning generated `TalentDef` nodes. `HeroSigils.All` appends them after the existing core, routes, and real outer anchors; `TreeFor(hero)` includes them. Existing core, trunk, and bridge IDs are unchanged; display coordinates are determined by the current layout.

The three working Cetus examples are in `src/SodRpg.Core/Game/StarClusters/Cetus.Example.cs`. The data team replaces this example table with approved tables; this engine does not supply the full 700-star design.

- Memory: `h.cetus.cluster.icy-veins`, Fan, anchor `h.cetus.route.icy-veins.7`.
- Bridge: `h.cetus.cluster.frozen-recall`, Chain, anchor `h.cetus.ring.force`.
- Outer: `h.cetus.cluster.abyssal-shell`, Ring, anchor `h.cetus.outer.abyssal-shell`.
- The outer anchor is a real one-rank +2% maximum-health star, registered in `StarClusters.OuterAnchors`, attached to the closest trunk tip.

## Data types and stable IDs

`StarClusterDef` has `Id`, `HeroKey`, `Region`, `Anchor`, `Shape`, and `Stars` (`IReadOnlyList<ClusterStarDef>`). Regions are `ClusterRegion.Memory(routeId)`, `ClusterRegion.Bridge(bridgeId)`, and `ClusterRegion.Outer`. Shapes are `Fan`, `Ring`, and `Chain`. Authored stars (`AuthoredStarDef.Shape`) carry their shape per star: one cluster may mix shapes as compound geometry, and the cluster-level `Shape` is then its entry star's segment.

Each generated ID is **`<clusterId>.<one-based list position>`**. `StarClusters.StarId(cluster, order)` returns that ID. Do not rename a registered cluster, reorder its stars, or insert before existing stars after saves use it. Append new stars or create a new cluster ID. Choice options use their parent star ID internally and are not additional graph nodes.

`ClusterStarDef` has `Kind`, bilingual `Name`, optional `Memory`, `Amount`, `Param`, `Gimmick`, `Power`, `Stat`, and `Options`. `MaxRank` and `RankCost` both default to 1. Choices require exactly one rank; their two options inherit the parent's cost.

This complete method constructs an Outer cluster using the existing real Cetus outer anchor. Its memory-bearing stars use Cetus memories. Radius and ExtraTargets have a meaningful recipient in the included Ricochet notable; Duration and Chance also have recipients in the existing icy-veins route. Register the returned definition in the registry to include it in the playable tree.

## Effect computation and limits

- MemoryDamage/Haste generate existing `LinkKind.MemoryDamage`/`MemoryHaste`, with exactly one `Requires` memory. Host equipment checks remain in force.
- GimmickBoost amounts add by memory across unlocked allocated stars and selected options. Both route gimmicks and cluster notables use `floor(baseValue × rank × (100 + totalBoost) / 100)`, bounded by the existing effect-value cap. It does not boost bridge pair-combo payoffs, global stats, or Power ranks.
- Parameters add by memory, affecting only supporting gimmicks. Duration and Radius scale their existing base by `1 + total/100`; ExtraTargets adds an integer; Chance adds percentage points to Element's extra-stack roll without changing guaranteed whole stacks.
- Duration and Radius totals cap at +300%; ExtraTargets caps at +16; Chance caps at +100 points and final roll probability at 100%. Internal cooldowns are not duration parameters. Existing effect-value caps, trigger attribution, no generated-damage chaining, and equipment restrictions remain.
- Duration supports Shield, Quicken, Empower, Expose (OnHit/OnCrit), Wound, Daze, Rampart, Primed, Crescendo, Sap, and Weakspot. Wound retains its per-tick damage rate for the extended lifetime. Daze's base value cap remains 0.8 seconds; duration scaling can extend it to 3.2 seconds. Crescendo scales the longer of 8 seconds or 1.5× memory cooldown.
- Radius supports Burst, Ricochet, Element (OnUse/OnKill), and Heal/Siphon with `Arg = 1` (allied recipients).
- ExtraTargets supports Ricochet (base `Arg`) and Rampart (base 5 distinct victims per cast). Rampart's shield limit grows with its target limit; it is not silently held at the old five-target total.
- Chance supports Element. Existing element stack limits still apply in the host.
- Gimmick notables use all supported existing effects, including G12–G22, with the same valid triggers, arguments, cooldown floors, and host paths as route gimmicks. Power notables use the existing Power rank path.
- Global Stat nodes are allowed **only in Outer**, including inside choice options. Outer can also contain all other kinds.

Descriptions are bilingual through `TalentDef.Describe()` and `Gimmicks.Describe()`. Parameter descriptions specify their units; computed gimmick descriptions include modified lifetimes, radii, targets, and probability.

## Fail-loud validation

Static initialization validates the example registry; generation validates against the entire provided existing tree before publishing any nodes. Failures throw `InvalidOperationException` with a cluster/star ID; initialization wraps failures in the CLR's `TypeInitializationException`.

Validation checks:

1. Unique valid cluster/generated/existing IDs; IDs use wire-safe letters, digits, `_`, `.`, `-`, at most 96 characters.
2. Known hero, supported shape/region/kind, nonempty star list, positive rank/cost, JA and EN names.
3. Existing anchor belonging to the same hero. Memory anchors belong to the specified trunk; Bridge anchors identify a real pair combo; Outer anchors are real positive stat talents marked `IsOuterAnchor`.
4. Region memory ownership: the trunk memory for Memory; either adjacent memory for Bridge; one of the hero's route memories for Outer.
5. Stat-only effects are restricted to Outer. Positive existing enum Power or valid Gimmick for a notable; modifiers do not carry an independent effect. Cluster gimmicks cannot be triggered by movement memories.
6. Exactly two non-choice options, both one-rank; each option passes all region/effect checks.
7. Every GimmickParam memory has at least one supporting gimmick in that hero's existing routes or supplied cluster notables/options, across the complete registry. Unsupported parameters are rejected, not substituted. `Gimmicks.SupportsParameter(def, param)` is the exact runtime predicate.

Q/R loadout compatibility is a **design-table review**, not inferred by this engine. Check all pre-expedition identity loadouts and mutually exclusive same-slot memories before registering tables. Stat share, balance/headroom, and the final 700-star count remain design-table responsibilities.

## Layout and connectivity

`HeroTreeLayout.Create` assembles the shipped topology before deciding final coordinates. Registration order, saved IDs, and edges are unchanged; legacy implicit outer access edges are resolved from their original angular slots, never rewired by new proximity. `PlaceSectors` assigns one wedge to each memory and exhaustively orders the six/seven wedges by weighted circular distance between bridged routes. Inner rings stay around the starting star, route stars occupy a clear boundary lane, Memory groups stay inside their own wedge, Bridge groups reserve boundary space first, and Outer groups occupy the band beyond their own memory's groups. Independent keystones sit beside their actual authored destination, with spacing of 160 between keystones.

Shape geometry comes from each star's authored `fan` / `ring` / `chain`; consecutive same-shape runs remain compound segments. Graph distance starts from every external entry, then authored prerequisites take precedence over undirected shortcuts. Fans use prerequisite layers, rings keep a circular contour ordered inward-to-outward, and chains use an outward curved sequence. Memory layers bend onto radial arcs so every internal prerequisite lies closer to the origin than its successor. Halo extents include the renderer's 37-unit padding, an additional radial-projection allowance for Memory groups, and a 16-unit gap between packed groups. Groups cannot leave their wedge or radial band during refinement. Equal-depth, same-shape swaps reduce internal crossings and star passes; bounded rigid translation/rotation candidates reduce external crossings, star passes, and squared edge lengths. Candidate order and ordinal tie-breaking are fixed; no random source or per-frame solver is used. Registered layouts and static fallback layouts are reused by `ForHero`.
After group refinement, route stars may bow within their boundary lane without changing their radius. Each fixed-order candidate must clear every halo and star, reduce affected edge/star occlusions, and add no affected edge crossings. Shape swaps with identical graph neighborhoods are skipped because they cannot improve the geometric score; this avoids repeatedly rescoring interchangeable leaves in large spoke fans.
Shape refinement also caps deterministic geometric comparisons per pass, rather than using a wall-clock deadline; oversized authoring groups retain their valid initial shape when further scoring would exceed that budget.
Compound segment spacing uses the realized far-edge coordinate, including the ring's prerequisite-depth offset, rather than its nominal diameter alone; the following fan or chain therefore retains the minimum star spacing.


For legacy non-authored groups, Chain connects consecutive nodes, Ring adds the closing edge, and Fan follows its entry sequence, branches into notables, and converges on choices. Authored groups use only explicit edges; shapes never infer or replace authored connections. The off-screen renderer uses identical final coordinates and edges, with an optional `--before` metrics table for per-hero comparison. Keystone catalogs do not get a single map-spanning halo: each independently anchored keystone already has its own purple ring. Halo separation and sector confinement can lengthen fixed inter-group edges, so the report includes CV and unmet targets rather than claiming an optimal crossing-free embedding.

Rules use the same graph for unlocks and refunds: every remaining allocated star must stay reachable from the start. `HeroTreeLayout.ForTalents(talents)` supports authoring/stress tooling after `Generate`; nine-hero tests exercise 90 clusters × 8 stars, all shapes, reachability, and pairwise spacing ≥90% of MinimumSpacing.

## Choice allocation, saves, and UI

```csharp
Rules.AddTalentRank(profile, "Hero_Cetus", "h.cetus.cluster.icy-veins.5", 0);
Rules.SetTalentChoice(profile, "Hero_Cetus", "h.cetus.cluster.icy-veins.5", 1);
```

Options are zero-based 0/1. Initial allocation requires an explicit option and normal connectivity/points. Switching requires allocation, costs no points, and is prohibited while `profile.Run != null`. Ordinary stars reject a supplied choice. Refunding the last rank removes its selection; respec clears talents, choices, and keystone. Cloning copies choices independently.

`HeroState.TalentChoices` is saved as each hero's `talentChoices` object. Profile format/version remains 3; old profiles without this field keep their existing allocations. A newly allocated choice with missing/invalid saved selection is refunded with a note rather than selecting an arbitrary effect; existing disconnected-save cleanup still applies.

The star-map tooltip shows both options and the chosen option. Clicking an unallocated choice opens two allocation buttons. Left-clicking an allocated choice switches it outside expeditions; right-click refunds normally. `choice` maps to the existing `link` artwork. MemoryDamage/Haste use `memory`; modifiers use `gimmick`; notables use the existing effect/power keys.

The map's “Show all” action fits the current coordinate bounds with a 64-UI-unit margin on each side. Zoom normally ranges from 0.15 to 3; larger layouts lower the minimum to their full-map fit zoom, and wheel zoom uses that same coordinate-derived minimum without jumping back to 0.15. Search and cluster navigation center the selected node at the current zoom. The choice panel is a canvas-relative overlay (8-unit margin, width at most 1000 units), not anchored to a star's historical coordinates; obscured stars cannot be clicked or zoomed, while panel backgrounds remain draggable. Dragging is measured in physical pixels and begins after movement exceeds 5 pixels. Runtime Unity visuals remain a separate verification requirement.

## Protocol and verification

**Protocol 10 → 11**: gimmick wire entries gain four integer fields:

`starId:memory:trigger:effect:value:arg:cooldown:durationPercent:radiusPercent:extraTargets:chancePercent`

The decoder also understands the old seven-field entries as zero modifiers. Host protocol gating requires matching mod versions. Choices themselves are not sent: Build sends the selected effective result. Links with identical canonical unordered requirements and kind are aggregated at existing equipped caps, removing the former 40-entry truncation. Gimmick capacity is 512 and the Build decoder accepts at most 131,072 characters; excess distinct gimmicks reject the payload/encoding instead of dropping effects. Duplicate IDs do not consume additional capacity.

Verification includes `StarClustersV131Tests.cs`, the entire xUnit suite, Release Mod build against game assemblies with deployment outside the game folder, and a separate executable smoke: allocation → Build encode/decode → GimmickRuntime hit → modified expiry → free choice switch → profile round trip. This is not a live-game UI/combat/co-op verification.

## Adding a cluster

1. Add an approved definition in `Game/StarClusters/<table>.cs` and include it in the registry's factory. Use immutable/read-only authored arrays and fixed IDs/list order.
2. Reuse an existing same-hero trunk/bridge anchor. For a new Outer attachment, register a real positive stat talent in `OuterAnchors` with a stable ID and `IsOuterAnchor = true`.
3. Review loadout compatibility and balance against the design table; choose supported effects/parameters, not substitute effects.
4. Call `Generate` on the full registry/tree and build `ForTalents` for layout inspection; validation must succeed without suppressing exceptions.
5. Exercise allocation, Build values, chosen options, encoding, refunds, save/load, descriptions, and layout before merging data.
