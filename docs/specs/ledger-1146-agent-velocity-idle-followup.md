# #1146 エージェント速度のゼロ再書き込み省略に関する改善案

2026-10-24、PR #1146 のレビュー指摘 F1（C-II 部分未達）を確認し、対応を決めた記録である。

## 指摘の内容

この節は指摘時点の状態の記録である。

[`NativeAgentVelocityIdlePerf.SetVelocity`](../../src/SodRpg.Mod/NativePerfPatches.cs) は、書く前にかならずネイティブの getter（`NavMeshAgent.velocity` の読み取り）を呼ぶ。速度がすでにゼロの実体では従来の setter 1回が getter 1回になり、速度がゼロでない状態が続く実体では getter と setter の両方が走って、従来よりネイティブ呼び出しが1回増える。動作の結果は変わらず、この増減は仕様書（[perf-loop/20261024-2030.md](perf-loop/20261024-2030.md)）と PR 本文に推定として明記してある。

## 対応したこと

レビューの裁定は「マージは止めない。実体ごとに『すでにゼロを書いた』ことを MOD 側で覚え、getter も呼ばずに判定する方式を改善案の台帳に残す。実機で計測できる機会があれば、移動中の実体での呼び出し回数を確かめる」である。これに従い、実装とテストは変えずにこのファイルへ記録した。

実装を見送る理由である。getter を呼ばない判定は、ゼロを書いたあとの格納値が管理コードの setter 呼び出し以外では変化しない、という実証されていない前提の上でだけ結果を本体と同じに保てる。いまの実装は毎フレーム getter で実際の格納値を読み、書く値と等しいときだけ setter を省く。このため、ネイティブ側が速度を書き換える実体がいても書き込みの省略は起きず、結果は本体と同じである（憲章II: 処理を軽くする変更は、結果が変わらないことを確かめる）。前提を確認しないまま getter も省くと、ネイティブ側が速度をゼロ以外に保つ実体では、本体が毎フレーム行うゼロへの書き込みを止めてしまい、結果が変わり得る。そのため、前提を実機で確認できるまで現行の形を維持する。

## 改善案の内容

実体（NavMeshAgent）ごとに「すでにゼロを書いた」ことを MOD 側で覚え、覚えている間は getter も setter も呼ばない。静止した実体の並びでは、毎フレームのネイティブ呼び出しを完全にゼロにできる。整えるべき点は次の3つである。

- 実体の破棄後に記憶が残らないこと。実体は生成と破棄を繰り返すため、`ConditionalWeakTable` のような弱い参照で持つ。
- ほかのコードによる velocity への書き込みでの無効化。`NavMeshAgent.velocity` の setter 自体に Harmony Patch を当てて記憶を落とす形が考えられるが、この場合、ゲーム全体の velocity 書き込みすべてに管理コードの呼び出しが乗る。
- ネイティブ側が速度を書き換える可能性。管理コード経由でない書き換えは上の無効化では拾えず、拾えないまま省略を続けると結果が変わる。

## 見直す条件

実機で計測できる機会があれば、次を確認する。

- 動き続ける実体で getter が非ゼロを返し続けるか（指摘の増分が実際に起きるか）。
- ゼロを書いたあと、管理コードが何も書かなければ getter がゼロを返し続けるか（改善案の前提）。
- velocity の setter に値の格納以外の副作用がないか（現行実装の前提）。

前提が確認できたら改善案を実装する。確認できるまでは、いまの実装（毎フレーム getter で読み、等しいときだけ setter を省く）を維持する。

## null・破棄済みエージェントと機能の無効化

2026-10-24 の修正ラウンドで、別の F1 として getter の例外後の動作が指摘された。`SetVelocity` は例外の種類を問わず static の `_disabled` を true にする。null または破棄済みの `NavMeshAgent` の getter が1回例外を出すだけで、すべての実体でゲーム終了まで最適化が無効になる。

catch のあとも元の `agent.velocity = value` は実行される。null・破棄済みエージェントでは setter も本体と同じように例外を出すため、移動結果は変わらない。失われるのは以後の軽量化の効果である。裁定は「影響は性能だけで、マージを妨げない」であり、CRITICAL / HIGH だけを修正する今回の指定に従って実装とテストは変更せず、未記録だった改善案をここに追加した。

改善案は null・破棄済みエージェントを getter で読まず、元の setter にそのまま渡すことである。この経路では `_disabled` と `_warned` を変更せず、setter の例外を呼び出し元へ返す。使用可能なエージェントの予期しない getter 例外では、現行どおりこの機能だけを無効化して警告を1回出し、元の書き込みへ戻す。

採用時には次の動作を確かめる。

- null・破棄済みエージェントへの書き込みが本体と同じ例外を返しても、続く正常な実体では同じ速度の再書き込みを省けること。
- null・破棄済みエージェントへの書き込みを成功扱いにせず、元の setter の例外を握りつぶさないこと。
- 使用可能なエージェントの予期しない getter 例外では、従来の機能単位の無効化と書き込みへの復帰を維持すること。

現行の既存テスト `GetterExceptionDisablesAndAlwaysWrites` は使用可能なエージェントの getter に `InvalidOperationException` を起こし、回復後も毎回書くことと警告が1回であることを確かめている。null・破棄済みエージェントを区別する検証ではない。今回、裁定と同じ `DOTNET_ROLL_FORWARD=Major dotnet test tests/Issue73.Native.Tests --filter FullyQualifiedName~AgentVelocityIdle` を実行し、このテストを含む6件の合格を確認した。
