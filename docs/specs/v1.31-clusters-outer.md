# v1.31 共有外周の星団 — 9旅人共通

設計日：2026-10-03。**8星団×20星＝160購入星**。どの旅人にも同じ160個を1回だけ生成する。うち全体能力値だけの `Stat` は32個、その他128個。選択肢・段数・中心の無料星を購入星数に足さない。実装完了報告ではなく、生成器と本体連動に渡す設計である。

## 参照と適用範囲

`v1.31-star-map-x10.md`、`v1.27-traveler-kits.md`、`v1.27-traveler-research.md`、`v1.28-memory-gimmicks.md`、同設計表、`v1.30-memory-pairs-table.md`、`v1.30-element-reactions-implementation.md`、`Gimmicks.cs` / `GimmicksV129.cs`、`HeroStarRoutes.cs`、`HeroSigils.cs`、`HeroTreeLayout.BranchOrder`、`Content.cs`、実際の列挙型を持つ `Ids.cs` を照合した。本体の `D:\app\stm\steamapps\common\Shape of Dreams\RawData\ja-JP\memories.json`・`travelers.json`・`stars.json` は読み取りのみ。

外周の記憶指定は、全9旅人が装備できる**共通記憶の実在ID**を使う。旅人のQ/Rを別の技に読み替える、装備していない記憶を仮想発動する、発動元を推測する仕組みは使わない。記憶を指定した星はその記憶を装備して使う構成のための選択肢であり、未装備時は条件を明示する。支援役以外も支援用の共通記憶を組み込める。召喚の星団には召喚記憶、味方限定の固有効果には味方が必要。どの条件も表示し、ソロ時に別効果へ置換しない。

旅人固有の核・幹・橋の全体 `Stat` / `Attune` / `Guard` は、各旅人の表でIDを保った記憶限定効果へ移行する。こちらへ古いノードを複製して星数を増やさない。本体の星座・装備の能力値は星図のノード数に数えない。9人中残り6人の移行完了は統合時に要確認。

コミュニティ資料では回復・障壁を攻撃に結び付ける構成、ナキアの召喚維持、ビスマスの記憶自動発動が強い構成として挙げられる。ただし順位や現在の最適解は確定しない。[回復記憶の構成議論](https://www.reddit.com/r/shapeofdreams/comments/1ntnwyo)、[召喚構成の議論](https://www.reddit.com/r/shapeofdreams/comments/1np7tsf/nachia_build_tips/) を参照し、効果の正確な条件は本体データとコードを優先した。

## 生成・接続・表記

- IDは `outer.<星団slug>.<接尾辞>`。全旅人で定義を共有し、取得状態は既存の旅人別保存領域に属する。以下の各表は `s1–s4,a1–a6,b1–b6,n1,n2,n3,c1` の**20個を全て**定義する。`c1` は1星で、A/Bのどちらか1つだけ有効。新星は全て最大1段、1ポイント。
- 形は二つの扇を輪でつなぐ。接続は外周入口→`s1`、`s1–s2–s3–s4–s1`、`s1–a1–a2`、`s3–b1–b2`。`a2` から `a3,a4,a5,a6`、`b2` から `b3,b4,b5,b6` に扇状分岐。`a6–n1–c1–n2–b6`、`c1–n3`。外周同士は `s2–次星団s4`。`a3/a4` 等の仕掛け修飾星は、該当する `a2/b2` も取得必須とする。逆側の接続から入ってもこの条件は省略しない。修飾先のない強化星は生成しない。
- `MD(M,x)`＝MemoryDamage、その記憶の本来のダメージ +x%。`MH(M,x)`＝MemoryHaste、現行 `LinkKind.MemoryHaste` と同じく**その記憶の使用完了で自己CDをx%短縮する連携**。本体の最大CD基準APIを使う現行意味を保持し、常時Hasteとは呼ばない。移動記憶へのMHはこの外周に存在しない。
- `GB(M,x)`＝GimmickBoost、取得中のMの全仕掛けの数値 +x%。`GP(M,Duration,x)` / `Radius,x` は有効な時間・半径 +x%、`Chance,x` は確率 +xパーセントポイント、`ExtraTargets,n` は対象数+n。Mは常に表の実在ID。複数星の修飾値は加算し、基礎値に一度だけ掛ける。記憶本体の持続・射程・投射物数・召喚上限には適用しない。
- `G(M,T,E,V,A,C)`＝Notableとして追加する完全な `GimmickDef { Trigger=T, Effect=E, Value=V, Arg=A, Cooldown=C }`。表中の `G(T,E,V,A,C)` はその列のMを使用。`P(Name,V)`＝Notableとして既存 `Power.Name` をVだけ加算。Choice内も同じ完全定義。`S(Name,V)`＝全体 `Stat.Name` をVだけ加算。
- この外周で参照する共通記憶のGB合計は同一記憶+160%、GPはDuration+100%、Radius+80%、Chance+30ポイントを星・装備込みの上限とする。旅人固有記憶の上限は各旅人表で定義する。Chanceの端数抽選は0–100%で、Elementだけは100%到達を確定1個に繰り上げる。ExtraTargetsとAlliedWardの半径・時間は効果別上限も適用。既存効果の値上限は `Gimmicks.Cap` を維持。低い整数Valueへ+10%してゼロ増加にならないよう、最終効果計算まで小数を保持する新集約が必要。表示も小数を省略しない。既存の完全回数 `Reload` と対象数はGBで増やさない。ElementはValue全体を倍率計算後、確定個数と追加1個の確率に再分解する（100に+10%なら110＝1個＋10%で1個）。実際に小数個の属性を付ける処理はない。
- GPは意味のあるフィールドだけを変える。Elementの確率は `Value % 100` の追加1個の確率だけに加算し、100ポイント到達は次の確定1個へ繰り上げる。ただし冷気の実スタックは1個上限。閾値・再発動間隔・Echoの0.3秒待ち・持続ダメージの総量を、Durationで増やさない。
- 同じ効果を最大値で扱う既存仕様は保持。`Sap` は各敵最大15%、ボス・ミニボスは半分、非加算。`Rampart` は各発動で異なる敵5体まで・総障壁最大HP10%まで・大きい方1枚。`Wound` は敵ごと1本、総量最大120%、延長後も総量一定。`Heal` は回復1回ごとに確定し蓄積しない。星図の`Shield`は同一星ID・所有者・受け手で最大の1枚を更新し、星図Shieldの合計追加残量は受け手最大HP20%まで。`AlliedWard`は同一所有者・受け手で最大の1枚を更新する。どちらも本体の障壁を削らない。
- 仕掛け・反応由来のダメージは無属性、攻撃効果0、記憶強化・仕掛け・反応・死亡時連鎖を再起動しない。追加回復・障壁は親を持たない `serverActor` 経由で、本体の団結を付与しない。属性は消費せず、闇5・光5・冷気1・火上限なし。回避・ダッシュ・テレポートイベントは購読しない。

約700星のツリーに対して32/700＝**4.57%**、絶対上限140個以内。今回の3旅人はそれぞれ旅人部分の全体能力値だけの星0、外周込み32個。残る6旅人も同じ移行を行えば、9人分は288個/6,300星以上＝4.57%以下。保存上同じ共有定義でも、各旅人の分母・分子へは1回ずつ数える。

設計レビュー後に必須の検査：160の一意IDとChoice各2案、仕掛け修飾の前提取得、各共通記憶の実装型の存在、支援記憶の無効MDが0、移動起点0、属性上限と非消費、GB端数、serverActor由来の団結非発火、召喚獣所有者の分離、Steam/Eclipse/Cinder/FrostCrystalの共存、報酬の重複受信拒否、300ポイント取得時の通信量。`Gimmicks.MaxEntries=32` に収まらない正当な取得を切り捨てない集約・通信設計が必要。上限到達済みの取得が値を増やせない場合は、購入前に上限と実効差分を示す。本書作成時点では新星のCore試験・Unity実戦確認は未実施。
