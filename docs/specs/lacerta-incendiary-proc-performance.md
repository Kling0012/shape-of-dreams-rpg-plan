# ラセルタの焼夷弾とエッセンス連鎖の軽量化

2026-10-18。対象ブランチは `perf/lacerta-incendiary-procs`。

## 原因と発生件数

本体の `Dew.Core.dll` と `Dew.Contents.dll` を静的に調べた。以下はコードから数えた件数であり、ゲーム内の測定値ではない。逆コンパイルした本体コードはリポジトリに含めていない。

`Se_Q_IncendiaryRounds_EmpowerAttacks.EntityEventOnAttackFired` は、通常攻撃の発射通知ごとに `Ai_Q_IncendiaryRounds_Attack` を1個作る。この Actor が元の弾の命中を受け、追加火ダメージを通知する。爆発弾薬の星 `Se_Star_Lacerta_F_IR_AoEDamage` があると、命中対象以外の範囲内の敵にも個別に火ダメージを与える。

範囲内の被弾対象数を主対象込みで N とすると、通常弾が1体に命中したときの増加は次のとおり。焼夷弾の強化が1つ付いた場合を数えている。

| 処理 | 範囲なし | 範囲あり |
|---|---:|---:|
| 焼夷弾用の追加 Actor | 1 | 1 |
| 焼夷弾の火ダメージ通知 | 1 | N |
| 焼夷弾の範囲検索 | 0 | 1 |
| 焼夷弾の命中演出送信 | 1 | 2（命中と範囲） |
| 元の通常弾のダメージ通知 | 1 | 1 |

これに命中先の被ダメージ通知、属性の適用・更新、星・装備の反応が加わる。重ね掛けや追加射撃があれば、それぞれの発射通知から同じ処理が始まる。弾帯の星は強化の弾数を2増やす。灼熱弾の星は元のダメージ補正・追加火スタックに加え、直前と異なる対象への命中で弾数を戻す。今回これらは変更していない。

エッセンスの増加経路は次のとおり。

| エッセンス | 反応と追加処理 |
|---|---|
| Ricochet | 対応するダメージ通知ごとに確率抽選。成功して別の候補がいれば、範囲検索1回と跳弾1本。MOD の確率上限は60% |
| Charcoal | 対応するダメージ通知から抽選・遅延を経て炭火弾1本。燃焼中の対象への命中には火属性ダメージと命中演出がある |
| Accuracy | 対応するダメージ通知で距離条件を満たすと追撃弾1本 |
| Blade | 対象別のクールダウンなどを満たすと、設定された回数の遅延攻撃。各攻撃にダメージと2種類の演出がある |
| Celestial | 発動元ごとの未処理対象に対し、既定では3回の遅延攻撃。毎ダメージに無条件で3回加わるわけではない |
| Fangs | 条件を満たす会心通常攻撃の命中から、2回の遅延射撃と各回の検索 |
| Void | キャスト後の対象となる通常攻撃効果から爆発1個。BasicAttackSub は除外される |
| Spiral | ダメージ通知ごとの反応ではなく、固有の射撃間隔ごとに検索して弾1本 |

Ricochet、Charcoal、Accuracy、Blade は `ReactionChain` で同じ個体の再反応を防ぐ。ただし、別のエッセンスへの反応や、反応順序の違う枝は残る。

例えば、焼夷弾由来の N 件だけを起点に、Ricochet と Charcoal を考える。別の標的が常に存在し、全弾が命中し、反応元が維持され、両エッセンスが発動可能な条件とする。各段階で同じ発動確率が続くと仮定し、跳弾確率を p、炭火の発動確率を q とすると、追加弾の期待数は `N × (p + q + 2pq)`。最後の項は「跳弾→炭火」と「炭火→跳弾」の別々の枝である。p=0.6、q=1、N=10 なら期待28本、元の火ダメージと合わせて期待38件のダメージ通知となる。元の通常弾、燃焼 DoT、ほかのエッセンス、星・装備はこの見積もりに含めない。途中の死亡、弾の未命中、候補不在、procCoefficient によって実際の件数は変わる。

火スタックは本体ですでに1つの `Se_Elm_Fire` に集約されている。通常の更新では約0.25秒ごとに DoT があり、生成時と終了時にも条件付きのダメージがある。火属性の個々の命中はスタック抽選か減衰タイマー更新を行うため、ダメージの合計値が同じでも、通知を1回にすると状態異常とエッセンスの発動結果が変わる。ダメージの合算は採用しなかった。

C# の逆コンパイルでは省略されていたイベント用デリゲートのキャッシュ代入を IL で確認した。焼夷弾の登録・解除は対応しており、購読漏れを原因とは扱わない。物理検索の戻りリストも本体ですでにプールされている。

## 変更内容

### 跳弾の候補と生成コールバック

`NativeRicochetAllocation.cs` はダメージ側の跳弾処理だけを最適化する。検索で借りたリストの先頭へ候補を元の順序で詰め、候補を別のリストへコピーする処理を省いた。候補数と `Random.Range` の各インデックスに対応する標的は元と同じになる。検索結果は処理の終了時に返す。

弾の生成前設定には再利用するオブジェクトとデリゲートを使う。本体の生成 API は設定コールバックを同期呼び出しする。生成完了まで借りた状態を保持し、途中で入れ子の生成が起きた場合は別の状態を使う。使用後は命中情報とエッセンスへの参照を外す。初回と入れ子の最大深度が増えたときには確保がある。

抽選、対象選択、生成の位置、`originDamage`、`ReactionChain.New`、`NotifyUse` の順序は維持する。回復側の重み付き跳弾には手を加えない。起動時にメソッド・フィールドと主要な呼び出しの形を確認し、違えば警告してこの最適化だけを外す。設定の読み出しに失敗した場合も、乱数抽選より前に本体へ戻す。抽選・生成後に本体を再実行する経路は設けない。

### 星・装備の追加ダメージ予約

`HostAuthority.NewPowers.cs` の `QueuePowerDamage` と暗属性継承の予約を、ラムダから `PowerCommand` の値へ置き換えた。`HostAuthority.PowerCommandQueue.cs` にデータと実行処理を分けた。

各予約は1件ずつ残り、FIFO、flush 開始時の件数、flush 中に追加された予約を次回に回す動き、対象の生存判定、生成ダメージの深度、例外を1件単位で扱う動きを維持する。ダメージ量・属性・対象数・乱数の処理は変えない。準備効果の既存コールバックも同じキューに入り、順序を保つ。準備効果側のラムダは今回の削減対象に含めない。リストは容量拡張時に確保するが、予約ごとのクロージャとデリゲートは不要になる。

### 命中演出の重複送信

`NativeProcImpactFx.cs` は、本体の `DewEffect.PlayNewNetworked` と `PlayNetworked` のうち、Entity に付ける3引数の呼び出しを対象にする。対象は次の具体型・フィールドに限定した。

- `Ai_Q_IncendiaryRounds_Attack` の `hitEffect` と `aoeEffect`
- `Ai_Gem_C_Charcoal_Projectile` の `fireHitEffect`
- `Ai_Gem_R_Blade` の `slashEffect` と `hitEffect`

通常時は、同一フレーム・同一発動者・同一対象・同一 assetId・同一演出種類の最初の1回を送る。低品質時は0.05秒、本体の負荷判定中は0.025秒の窓で同じ演出をまとめる。追跡は512種類までとし、超過した新しい種類は本体どおり送る。最初の演出はその場で送信し、次フレームへ待たせない。

演出の中身は初回に調べ、結果を弱参照のキャッシュに保持する。許可するのは列挙した描画用コンポーネントだけ。未知のスクリプト、欠落したコンポーネント、予告表示、UnityEvent、Entity の操作を含むものは省略しない。粒子の trigger・collision・subEmitter・stopAction が有効な場合も対象外とする。この条件は保守的なので、実際のプレハブが条件を満たさなければ、その演出の送信は減らない。ゲームの asset を使った適用率は未測定。

この処理は見た目の重複だけを省き、Actor の生成、命中、状態異常、星・装備の発動、ダメージ通知を省かない。既存の `NativeFxBudget` は残り、通した演出の粒子・ライトを引き続き制限する。例外時は警告を1回出し、この重複抑制だけを無効にする。

## 強さと互換性

発動率・ダメージ・攻撃速度・弾数・クールダウンの設定値は変更していない。Ricochet の60%上限と Crystal Circuit の0.5秒 ICD もそのまま。個々のダメージ通知、燃焼の抽選とタイマー更新、各エッセンスの反応枝を残している。範囲検索の結果を複数のダメージ間で共有すると、その間に起きた死亡・移動を見落とすため、検索回数をその方法では減らしていない。

通信は従来の本体パケットのまま。重複演出を送らず、最初の演出を従来の形式で送るため、新しい capability 交渉や受信側の変更は不要。旧版 MOD・MOD なしの参加者にも同じ本体形式で届く設計である。命中・属性・実績などに使われる本体のダメージ通知 RPC は削っていない。協力環境での実動作は未確認。

重いフレームで戦闘処理を新しく延期する処理は追加していない。今回は処理順序と寿命の条件を変えず、一時確保と重複した描画処理・通信を減らした。戦闘処理そのものが CPU の限界に達する場合の停止解消は、この変更だけでは確認できない。

