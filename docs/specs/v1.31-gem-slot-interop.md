# v1.31 エッセンス枠の相互運用 / Gem-slot interoperability

## 原因と証拠 / Cause and evidence

ライブプレイで、アイデンティティの追加枠の星（上限 +1）を取った後に枠が約11まで増えた。同時に DewGemSlotCount / SkillGemCount（Workshop 3618723919）を使用していた。

**確認できた不具合は、枠を書き込んだ本体より台帳の寿命が短いこと。** 修正前は `HeroRuntime` に基準値と `AddedGemIdentity` / `AddedGemMovement` を持っていた。`PruneAndApplyPending` は非アクティブなHeroを解除してruntimeを削除し、適用失敗後の再試行もruntimeを削除する。`UpdateGemSlot` は解除時の例外をログに残して戻るため、解除に失敗して本体に +1 が残っても、呼び出し元は台帳を捨てられた。次のruntimeは増えた現在値を初期値として取り込み、もう一度 +1 した。

修正前の製品アダプターを使った `Failed_cleanup_then_runtime_recreation_does_not_add_the_same_slot_again` は、解除の代入前に例外を起こすと期待値 `[3, 3]` に対して実測 `[4, 3]` で失敗した。基準2に初回 +1、その後8回この取り残しと再作成が起これば `2 + 1 + 8 = 11` になる。これは約11という報告を説明できる再現経路であり、ライブ時に8回の解除失敗が起きたという観測ではない。

以前の `TargetMax` の式は、代数的には `current + desired - previouslyAdded` だった。**同じ台帳を使う通常のBuild再適用だけでは累積しない。** Build更新やレート制限そのものを原因とは断定しない。台帳消失、または「実行中の加算を保持する」別MODとの相互増幅を伴う必要がある。

本体の逆コンパイルでは `HeroSkill.GetMaxGemCount`（1166行付近）が現在の枠を返し、`SetMaxGemCount`（1180行付近）は各 `maxGemCount*` のSyncVarに指定値を代入する。Identityの生成setterは `GeneratedSyncVarSetter(..., null)` を呼ぶ。ここには累積加算も非アクティブ判定もない。したがって「非アクティブならsetterが必ず失敗する」は確認できていない。Unityの破棄済み参照や外部パッチを含む実際の例外経路、ライブ時の相互増幅の有無は、現場のログがないため確定できない。

**Confirmed:** losing ownership after rejected cleanup causes double-addition. **Not established:** which cleanup or external rewrite sequence produced the reported live count of about 11. Stable-runtime reapplication alone cannot explain it.

## 台帳と決定 / Ledger and decisions

- `HostAuthority.GemSlots.cs` の静的 `ConditionalWeakTable<HeroSkill, NativeGemSlotLedger>` を使う。同じ本体について一度だけ捕捉し、runtimeとホスト接続層の再作成をまたいで保持する。netIdの再利用では別の本体を取り違えない。
- IdentityとMovementに、それぞれ純C#の `GemSlotLedger` を持つ。`OurContribution` は0〜1、`LastWritten` は直近に受理した目標値。外部変更後に書き込まない場合も、受理した現在値を比較基準に更新する。
- `Decide(current, desired, now)` は副作用のない提案を返す。外部の増加は保持する。外部の減少は、消された可能性がある自分の寄与を先に減らす。残った自分の寄与だけを現在値から除き、希望する0〜1を加える。`int.MaxValue` での飽和時には追加しない。
- `ShouldWrite` が偽なら `SetMaxGemCount` を呼ばない。初期値や外部差分を繰り返し加算する処理はない。
- `Commit` はsetterの後、またはsetterが例外を投げた後に実値を読む。実値が提案と一致したときだけ寄与を更新する。代入後のコールバック例外でも記録でき、エッセンスを外す途中の例外で二重減算しない。
- 枠を自分たちが縮めたときは、上限外のGemをインデックスの大きい順に足元へ落とす。装着数が少なくても穴の先にあるGemを処理する。通常の再適用では一時リストを確保しない。

## 競合停止 / Conflict latch

Build適用時と、ホストの1秒ごとの非スケール時間による確認時に現在値を読む。自分の書き込みを一度観測した後、同じ位置で直近の受理値と異なる外部変更が3回連続し、最初から3回目までが10秒以内なら競合とする。変更のない確認は連続回数をリセットし、10秒を超えた変更は新しい連続回数の先頭になる。10秒ちょうどは窓内。

一方の位置が競合すると、その `HeroSkill` 全体で追加を停止する。競合した位置はその決定で残っている自分の寄与を一度だけ取り除き、もう一方も現在値から自分の寄与だけを一度取り除く。解除に失敗しても以降の通常適用、振り直し、Detachから再びsetterを呼んで外部MODと争わない。競合ログは本体ごとに一度だけ出す。停止は同じ本体について解除しない。新しい `HeroSkill` は別の台帳を持つ。

ホストHUDはアクティブな本体のいずれかに競合があると表示する。所有者には任意の `DreamforgeGemSlotConflictMsg`（`heroNetId`, `protocol`, `disabled`）を送り、その本体のHUDだけに表示する。適用時・停止時に送り、5秒ごとに再同期する。クライアントはHero参照とnetIdの両方に状態を結び付け、本体やRPC接続が替わると消す。

- 日本語：ほかのMODがエッセンスの枠を変えているため、星図による枠の追加を止めました
- English: Another mod is changing essence slots, so the star map's extra slot is disabled.

Protocolは13のまま。既存メッセージのフィールドは変更しない。本体 `Actor.HandleRpc_Imp`（1872〜1903行付近）は登録された型名と一致しないメッセージをJSON復号前に無視するので、古いクライアントは新しい任意メッセージを無視する。古いホストから通知が来なくても新しいクライアントは初期値のままで動作する。

## 解除と寿命 / Removal and lifetime

`DecideRemoval(current)` は現在値から記録済みの自分の寄与だけを引く。記憶した絶対基準値へ戻すことはしない。アクティブな本体ではIdentityとMovementを独立して解除し、代入失敗後も台帳を失わない。Detachはruntimeから外れた本体も弱参照の一覧から処理する。

非アクティブまたは破棄済みのHeroには書き込まない。到達できる非アクティブ本体では寄与台帳を破棄し、弱いキーの退役印だけを残す。同じ本体が再びアクティブになっても、残った +1 を新しい基準として再捕捉しない。弱いキーなので本体の回収は妨げない。退役後の同じ本体には枠を再設定しない。新しい本体が次の適用の単位となる。

## 検証と限界 / Verification and limits

Core回帰は、反復適用、永続台帳、Chaosの外部 +1、絶対値の毎回上書きと3回目の停止、現在値からの解除、希望値0、連続回数と10秒境界、代入前後の失敗、0・負値・整数飽和を扱う。製品アダプターを直接コンパイルするライフサイクル回帰は、runtime再作成、解除失敗後のホスト再作成、本体交換、非アクティブ時の無書き込み、両位置の停止、上限外Gemの保存を扱う。

- `dotnet test tests/SodRpg.Core.Tests`：全2,441件成功、失敗0、スキップ0。修正前に失敗した解除失敗→runtime再作成の回帰も成功。
- 実ゲームDLLを参照するReleaseビルド：成功、エラー0。既存のUnity検索APIの非推奨警告2件。DLLとメタデータはゲーム外の指定配置先へ出力。

外部の一時的なsmoke runnerは製品の枠アダプター・送信側・クライアント状態処理をコンパイルし、狭い本体API代替で実行した。runtime再作成100回でもIdentityは3、setterは両位置の初回2回だけ。Chaos後は4、解除後は3。解除失敗とホスト再作成8回でも3を維持し、最後の解除で2。絶対値上書きは3回目で停止、ホストと所有者のフラグが立ち、以降は書き込まない。別Hero・古いnetId・異なるprotocolの通知を拒否し、切断で表示状態を消した。

これはUnity描画や実際のMirror配送の実機検証ではない。ゲーム起動もゲームフォルダーへの書き込みも行っていない。Releaseの配置先は `C:\Temp\DreamforgeRPG-build-gem\DreamforgeRPG`。

枠の合計値だけから変更元を完全に識別することはできない。外部減少では自分の枠から消えたとみなすため、外部の絶対値設定へ最大2回だけ再追加してから停止する。短時間に本体の正当な追加が3回連続しても保守的に停止し得る。確認周期より短い変更と元への復帰は観測できない。停止時の解除失敗は再試行せず、取り残しを許して増幅を防ぐ。assembly自体の入れ替えをまたぐ永続保存は行わない。

**SkillGemCountとの実プレイ確認が必要。** 設定済みの基準枠、両方の星、Chaos、振り直し、復帰・本体交換、別クライアントのHUDで確認する。合計値しかないため、既に11まで増えた過去の取り残しを推定して一括削除することはしない。

## 2026-10-07 他MODとの共存強化 / Coexistence hardening

DewGemSlotCount（精华槽数量|SkillGemCount）併用環境の報告（枠が増えすぎる／ゲーム中に増やした枠が消える）を受けて、Continue保留中の枠維持を「観測した現在値の再適用」から「台帳外の値としての保持」に変えた。保留中の走査は、他MODが上げた現在値の内側に既にはまっている保存Gemを数えず、現在値より上に出た保存Gemだけを上限1の自分枠として保護する（`GemSlotLedger.PreserveExternal`）。他MODによる変更を検出しても1回だけ警告し、機能は止めない。

DewGemSlotCountの公開ソースは見つかっていない（Steam Workshop 配布のみ）。Player.log 上は game settings start のたびに Gem 設定のスナップショットを再適用しており、書き込みの形（絶対値か差分か）は推定である。本MODのホスト側コードから再現できる二重加算経路は今回確定できなかった。回帰テストは、他MODが先に枠を上げた状態での Continue 保留と再開、絶対値での書き戻しへの再補填、振り直しと解除で他MOD分を保持することを固定する。
