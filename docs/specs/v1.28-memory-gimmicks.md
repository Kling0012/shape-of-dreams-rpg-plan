# v1.28「記憶の仕掛け」：ルートを記憶の動きに合わせる

利用者の指摘（2026-10-03）：
- 元のルート分けは旅人の記憶やアイデンティティに合わせたはずだが、シナジー感が薄い。
- 多くのルートは能力値を伸ばすだけで、その動きに合わせた仕掛けを用意できていない。プレイヤーは新しい仕掛けを期待するはず。

調べた結果：ルートの星の約3分の1（157個）が「その記憶を装着している間、攻撃力・魔力%（同調）／最大HP%（守り）」で、記憶の動きと関係しない汎用の値だった。

## 1. 新しい連携「記憶の冴え」（`LinkKind.MemoryDamage = 5`、定義は済み）
- その記憶で与えるダメージ +X%。アイデンティティ記憶の受け身で出るダメージ（例：サラマンダーパウダーの4発目の爆発、エキゾチック物質の爆発、群れの心臓の光の爆発）も含む。
- 上限は記憶加速などと同じ考え方（1つ 40、2つ 1.6倍、3つ 2.2倍。覚醒Ⅲまで含めた上限は `Links.EquippedCap`）。
- ルートの「同調」は、ほとんどをこれに置き換える（守りは盾役の記憶だけ残す）。

## 2. 記憶の仕掛け（新しい仕組み）
ルートの星に「仕掛け」を持たせる。仕掛けは、その星のルートの記憶（`RouteMemory`）に反応する。

```csharp
public enum GimmickTrigger { None = 0, OnUse = 1, OnHit = 2, OnKill = 3, OnCrit = 4 }
public enum GimmickEffect
{
    None = 0,
    Element = 1,    // 命中は当てた敵、OnUse は自分の周り4m、OnKill は倒した敵の周り4mに属性を付ける。Arg: 0 火 1 冷気 2 光 3 闇。Value: 100 ごとに1つ、残りは%の確率でもう1つ
    Burst = 2,      // 当てた敵の周り（OnUse は自分の周り）4m に、攻撃力か魔力の高い方の Value% の追加ダメージ（魔力の方が高ければ魔法）
    Shield = 3,     // 自分に最大HPの Value% の障壁（4秒）
    Heal = 4,       // 自分を最大HPの Value% 回復。Arg=1 なら近くの味方（10m）も
    Recharge = 5,   // その記憶の残りクールダウンを Value% 縮める
    Quicken = 6,    // 4秒間、攻撃速度 +Value%（重ならず時間を延長）
    Empower = 7,    // 4秒間、攻撃力・魔力 +Value%（重ならず時間を延長）
    Expose = 8,     // 当てた敵は4秒間、自分から受けるダメージが Value% 増える（重ならず時間を延長）
    Echo = 9,       // 当てたダメージの Value% を、0.3秒後にもう一度与える
    Reload = 10,    // その記憶の使用回数を1回戻す。最大1回の記憶はクールダウンを全回復
    RechargeOther = 11, // 装備中のほかの通常記憶の残りクールダウンを Value% 縮める。移動・Ultimate・Identity は除外
}
public sealed class GimmickDef
{
    public GimmickTrigger Trigger; public GimmickEffect Effect;
    public int Value;       // 1段あたりの値（段を振るほど伸びる。頂点は1段）
    public int Arg;         // 効果の補足（属性の種類、味方も回復するか）
    public float Cooldown;  // 内部の間隔（秒）。0 なら制限なし。OnHit は同じ敵ごとではなく、その星ごと
}
```
- `TalentDef.Gimmick`（`GimmickDef`、なければ null）。説明文は `Gimmicks.Describe(def, memory, ranks)` で自動で作る（「『ハンドキャノン』が当たると、敵に火を1つ付ける（1秒に1回）」のように。上限・間隔を必ず書く）。
- 1つのルートに2つ：**4番目の星**（いまの固有効果の星。3段）と、**頂点**（7番目。1段）。頂点は「記憶の冴え」と仕掛けの両方を持ってよい。
- 回避（移動の枠の記憶）のルートには、回避で発動する仕掛け（OnUse など）は置かない（v1.28 の方針）。移動の記憶のルートは OnHit／OnKill／OnCrit のある記憶だけ、ないものは常時の効果で。
- つり合い：仕掛けの強さの目安（間隔は基本0。継続・多段の制限が必要な星だけ設計表の値を使う）
  - Element：1〜2つ（Value 100〜200）
  - Burst：40〜120%
  - Shield／Heal：3〜8%
  - Recharge：10〜30%、Reload：1回、RechargeOther：10〜15%
  - Quicken／Empower：8〜20%
  - Expose：8〜15%
  - Echo：15〜40%

## 3. 記憶の判定（ホスト）
- 与えたダメージがどの記憶から出たかを、本体の型でたどる（`DamageData` の actor → `AbilityInstance` → その発生元の `SkillTrigger` の型名、アイデンティティの受け身も含む）。判定の対応表は調べて文書に残す。
- OnUse：`OnSkillUse` の `info.skill` の型名。OnHit：記憶のダメージが敵に当たったとき。OnKill：記憶のダメージでとどめを刺したとき。OnCrit：記憶のダメージが会心したとき。
- 仕掛けで出たダメージ（Burst・Echo）からは、仕掛けを起こさない（連鎖させない）。

## 5. 方針（利用者の指示、2026-10-03）
**ステータスをただ高く伸ばすのではなく、遊び方を横に広く広げることが重要。**
- 仕掛けは、その記憶の使い方・判断・組み合わせを変えるものを中心にする（倒すとクールダウンが戻る、属性でほかの記憶や四元の共鳴につなぐ、弱らせて仲間や別の記憶の起点にする、残響で手数を変える、仲間を回復・守る）。
- 一時的な能力値の上昇（攻撃力・魔力、攻撃速度）はルート全体の2割以下。
- 「記憶の冴え」（ダメージ+X%）はルートの中で数を減らし、仕掛けの比重を上げる（各ルートで2〜3つ以内）。
- 9種類で表せない仕掛けは、新しい効果として足すことを検討する（本体の仕組みを確かめてから）。

## 6. 方針：今の戦い方の邪魔をしない（利用者の指示、2026-10-03）
**そのキャラをよく調べて考えて、今ある戦闘系統に対して違和感がないようにする。新しく入れたものが邪魔になったらダメ。**
- 仕掛けごとに、その旅人の今の戦い方（アイデンティティ記憶・旅人記憶・固有星座・コミュニティの構成）と食い違わないかを確かめ、設計表に「邪魔にならない理由」を書く。
- してはいけない例：距離を取って戦う旅人（Lacerta・Yubar）に敵を引き寄せる。自分で通常攻撃しない Bismuth に通常攻撃の条件。攻撃速度を攻撃力に変える Husk に攻撃速度の効果（意味が変わる）。HP を捧げる Aurena に HP を高く保つ前提の効果。本体の仕組み（Vesper の4発目、Cetus の氷の血脈のスタックなど）を上書きしたり勝手に動かしたりする。プレイヤーの操作を奪う（勝手に移動・向きを変える）。
- 設計表ができたら、別のレビューで「邪魔になっていないか」を旅人ごとに確かめてから実装に入れる。
- **アイデンティティ記憶は付け替えられる**（利用者の指摘）。上の例の多くはアイデンティティ由来（Husk の一歩一殺、Bismuth のプリズムの視界）なので、旅人ごとに決めつけない。
  - アイデンティティ記憶のルートの仕掛けは、そのアイデンティティを着けているときだけ効く。そのアイデンティティの性質に合わせてよい。
  - 旅人記憶（Q・R・移動）のルートの仕掛けは、その旅人が**遠征の前に選べる**アイデンティティ（自分の2つ）のどちらと組んでも成り立つ（少なくとも害にならない）ようにする。遠征中に拾う共通のアイデンティティは考えない（利用者の指示）。
  - Bismuth はアイデンティティを変えられない（プリズムの視界で固定）。Bismuth のルートはすべて「自分では通常攻撃せず、本が自動で攻撃する」前提でよい。共通のアイデンティティ「華麗なる芸術家」のルートは使われないので外し、Bismuth は6ルートに戻す。

## 7. レビューで決めたこと（2026-10-03）
- **OnCrit** は、その記憶のダメージが確実に会心するもの（例：4発目の会心、ダッシュ後の確定会心の通常攻撃）だけ。分からないものは OnHit にする。
- **間隔**（利用者の指示で訂正）：組み合わせ次第で記憶を連打できるのは仕様。**「何秒に1回」の制限は、どうしても必要な場合だけ**にする。クールダウンを戻す（Recharge）・使用回数を戻す（Reload）・別の記憶を縮める（RechargeOther）には間隔を付けない。間隔を付けるのは、1回の技で何十回も当たる技や継続ダメージの1回ごとに発動して、障壁・回復・追加の爆発・属性が際限なく出る場合だけで、表にその理由を書く。
- **仕掛けで出るダメージ**（Burst・Echo）は属性なし。本体のスタック（氷の血脈・チャージされたアンギリアンなど）や、ほかの仕掛け・記憶の冴えを増やさない。
- **仕掛けの回復・障壁**が本体の付与条件（Nachia の団結など）を自動で回さないこと。避けられない場合は、その記憶のルートに回復・障壁の仕掛けを置かない。
- **召喚獣・味方の攻撃**を「その記憶のダメージ」と数えられるかは、判定の実装で確かめる。数えられない場合は、旅人自身の命中か OnUse に置き換える。
- **新しい効果**：Reload（その記憶の使用回数を1回戻す）と RechargeOther（装備中のほかの記憶のクールダウンを縮める。回避・Ultimate・アイデンティティは対象外）を足す。Spread と Brand は既存の効果で表せるので足さない。

### 効果の API と制限

- 属性は `Actor.ApplyElemental`。OnUse は自分の周り4m、OnKill は撃破イベント時に保存した倒した敵の位置の周り4mにいる生存敵へ付ける（倒した敵自身は除く）。Core の発動要求が範囲と中心の種類を指定し、ホストは死体の生存状態に依存せず処理する。味方回復は10m内の生存する味方旅人を含む。
- Burst は既存の `DamageAround` を使い、4m、攻撃力／魔力の高い方で計算する。魔力が高いときだけ `MagicDamage`、同値なら `PhysicalDamage`。
- Echo は命中の最終ダメージ量を保存し、0.3秒後に割合分を `PureDamage` で繰り返す。既に防御で減った値を二重に減らさない。死亡・非アクティブになった対象には与えない。
- Recharge は `Actor.ApplyCooldownReductionByRatio`。`.ref/dump/AbilityTrigger.txt` と `AbilityTrigger.ApplyCooldownReductionByRatio_Imp` で、API の比率が最大クールダウン基準であることを確認した。現在の設定の残り時間／最大時間で比率を換算して渡す。本体が持つ複数設定へはこの同じ比率が適用され、設定ごとの残り時間が異なる場合に全設定を個別の割合で縮めるものではない。本体のクールダウン短縮不可設定も尊重する。
- Reload は現在の設定の `TriggerConfig.maxCharges` と `AbilityTrigger.currentConfigCurrentCharge` で分岐する。複数回なら `SetCharge(currentConfigIndex, 現在+1)` を上限まで戻し、進行中の次のチャージのクールダウンは変えない（満タンなら本体更新でタイマーが消える）。最大1回なら `Actor.ResetCooldown(skill)` で全回復を要求する。本体の短縮不可設定と短縮プロセッサを尊重するため、無条件の時間代入ではない。最大0回の設定は対象外。Value は段数によらず1回が上限。宣言は `.ref/dump/AbilityTrigger.txt`、`.ref/dump/SkillTrigger.txt`、実装は `Dew.Core.dll` の `AbilityTrigger.SetCharge`／`TriggerConfig`／`Actor.ResetCooldown`。SetChargeの範囲補正・同期は `C:/Temp/memory-v128-types/AbilityTrigger.decompiled.cs:1410-1424` でも確認した。
- RechargeOther は `HeroSkill.GetSkill` で装備中の全枠を調べ、自身・Movement・Identity を除外し、実際の `SkillTrigger.type == SkillType.Normal` の記憶だけに Recharge と同じ残り時間割合を適用する。R枠の通常記憶は含むが、`SkillType.Ultimate` はどの枠でも含まない。宣言は `.ref/dump/HeroSkill.txt`、`SkillTrigger.txt`、`SkillType.txt`。間隔0は同時刻の複数発動も許可し、正の間隔だけ星ごとに共有する。
- Quicken／Empower／Expose は Core の4秒窓。各星の期限を延長し、同じ効果は有効な最大値1つだけを使う。Expose は旅人ごと・敵の Instance ID ごとで、負の Instance ID も有効。
- Burst／Echo は `DamageData.SetAmountModifiedBy(typeof(GimmickRuntime))` で識別し、同期 Dispatch の間も発動禁止フラグを保持する。記憶の冴え・Expose の再増幅と、命中／会心／とどめの仕掛けを抑止する。`Actor.DealDamage` の同期順序を確認したため、ダメージのない Kill イベントにも禁止を適用できる。
- 本体の送り手・受け手のダメージプロセッサは属性を後から足し得るため、マーカー付きのBurst／Echoだけを `Entity.ProcessReceivedDamage` の末尾で無属性・攻撃効果強度0に戻す。`Actor.DealDamage` はこの後に `FinalDamageData` を作り、属性付与・命中通知を行う。通常の記憶ダメージは変更しない。確認先は `.ref/dump/DamageData.txt`／`Entity.txt` と `Dew.Core.dll` の `Actor.DealDamage`。
- `Dew.Contents.dll` の `St_D_IcyVeins.ActorEventOnDealDamage` と `Se_D_ChargedAnguillian.ActorEventOnDealDamage` は最終ダメージのCold属性でスタックを付け、procCoefficientや仕掛けマーカーは検査しない。したがってproc0だけでは不十分。`Se_D_IcyVeins` は攻撃効果通知で蓄積を消費するため、攻撃効果強度も0に固定する。無属性化で送り手の両スタック付与を、攻撃効果除去で氷の血脈の勝手な消費を防ぐ。Charged Anguillianの被ダメージによる蓄積は別条件であり、敵だけを狙うBurst／Echoから所有者へは発生しない。確認先：両DLLの同名メンバーと `C:/Temp/sod-movement-api/contents-il/Dew.Contents.il:109480-109620,110270-110373,110478-110633`。
- 追加効果の作用は命中イベント内ではなく次のホスト更新で行う。これにより Burst が元の命中の `lastAttacker` を横取りして、とどめの記憶を変えることを避ける。Echo の待ち時間は元のイベント時刻から数える。

### 判定の境界と通信

- 親鎖に記憶の `SkillTrigger` が残る場合を対象にする。Actor を旅人へ直接付け直したダメージ、親が失われた効果、既知の記憶一覧にない型は推測せず対象外。
- Gem 自身と Gem が生成した `AbilityInstance.gem != null` の効果は対象外。エッセンスは記憶を親に借りることがあるため、記憶ダメージへの誤帰属を防ぐ（`HeroSkill.EquipSkill`／`EquipGem`、`Gem.CreateAbilityInstanceWithSource` を確認）。
- OnUse は既存の旅人の使用通知と同じ経路を使う。ゲームを動かした戦闘確認はこの実装記録には含めない。
- Build に `g:星ID:記憶:きっかけ:効果:値:Arg:間隔` を追加する。各星は1回、最大32件。既知の記憶・列挙値・Arg・区切りを含まない星ID・有限な間隔を検証する。値は効果別上限、間隔は60秒で切る。値の上限は属性6つ、Burst／Echo 1000%、Empower 200%、Reload 1回、その他（RechargeOtherを含む）100%。Reload／RechargeOther の Arg は0だけ。
- 通信版は **6**。旧版の Decode は未知の非空セクションを能力値の形式として読もうとして失敗するため、版5のまま追加しない。記憶の冴えは従来の `l` セクションを使い、覚醒込みの `Links.EquippedCap` を引き続き適用する。

### 回復・障壁と「団結」

- `Dew.Contents.dll` の `St_D_HeartOfThePack.OnEquip` は所有者の `ActorEvent_OnDoHeal`／`ActorEvent_OnGiveShield`／`ClientActorEvent_OnCreate` に購読する。回復・障壁は敵でも中立でもない対象、生成通知は有益な状態効果（Bond自身を除く）なら `TryApplyCharge` を呼ぶ。回復が全快で捨てられても発動し、マーカーや効果量では除外しない。
- `Dew.Core.dll` の `Actor.DoHeal`／`InvokeOnDoHeal`、`Actor.GiveShield`／`CreateStatusEffect`／`InvokeOnCreate`、`StatusEffect.DoShield`／`InvokeOnGiveShield` は生成元の親鎖へ通知する。普通に旅人から実行すると、自分への障壁でも団結を付け得る。
- 仕掛けだけは既存の `ActorManager.instance.serverActor` から `Heal(...).Dispatch`／`GiveShield` を呼ぶ。`ActorManager.OnStartServer` は親なしの `ServerActor` を生成し、`ServerActor` は旅人へ付け直さない。このため回復と障壁の生成・付与通知は旅人に届かず、団結を自動で付けない。本体の回復・障壁・バフは変更しない。
- この経路も受け手の回復・障壁プロセッサ、HP上限、受けた通知、障壁の4秒タイマーを使う。送り手の旅人の回復・障壁補正と「支援した」条件は通さない。味方回復の範囲は旅人のみで、召喚獣は含まない。
- 宣言の確認先：`.ref/dump/ActorManager.txt`、`Actor.txt`、`Entity.txt`、`HealData.txt`。上記の順序・購読条件は両DLLの同名メンバーを読み取り専用で逆コンパイルして確認した。Unity内の実戦確認は未実施。
