# perf-loop/20261019-1543

## 対象

`native Dew.Core/Actor.cs`（2698行全体）。毎フレームの `LogicUpdate`・`FrameUpdate`、被弾ごとの `DealDamage`・`DoHeal`・`DoBasicAttackHit`、撃破後の破棄まわり、そして協力プレイの MOD 間通信の受け口 `HandleRpc_Imp` とその下流（`SafeAction`、`DewPersistence.ToJson/FromJson`、`DamageData.HasAttr`）を呼び出す側と一緒に読んだ。

## 直した内容

MOD 間通信を1通受けるたびに走る `Actor.HandleRpc_Imp` の型探しを、Harmony の Prefix（`NativeCustomRpcDispatchPerf`、`src/SodRpg.Mod/NativePerfPatches.cs`）で辞書引きに置き換えた。

本体の実装は、登録済みハンドラの辞書を最初から最後まで列挙し、各エントリで `Type.Name` と電文の型名を文字列比較して、一致した型で JSON を復元する。MOD はセッション用の Actor に数十種類のメッセージ型を登録するため、ホストも参加者も、撃破・モンスター・取引・選択肢など通信1通ごとに同じ全走査を払っていた。この Prefix は型名から型への対応を Actor ごとに一度だけ決めて覚え、以後は辞書の `TryGetValue` で1回引きする。JSON の復元は本体と同じ `DewPersistence.FromJson` を同じ型で呼び、設定は `DreamforgeConfig.nativeCustomRpcDispatch`（既定は有効）で切れる。

## 結果が変わらない理由

電文の内容も配達の結果も変えない。覚えた対応は、毎通その Actor の辞書で `TryGetValue` し直して確かめる。型の登録が解除されていれば引きが外れるので、その通は本体の全走査に戻る。リストの中身（ハンドラの追加・解除）は辞書が持っている生の List 参照越しに見えるので、覚えた対応が古くなる経路はない。

同じ単純名を持つ別々の型が同じ Actor に2つ以上登録されていた場合は覚えず、本体の列挙に任せる。本体は一致する型が複数あると順に復元を試し、復元に失敗した型は飛ばして次へ進むが、この挙動ごと本体側に残る。復元は本体と同じ `DewPersistence.FromJson` で、復元に失敗した電文を捨てるのも本体と同じだ。ハンドラは辞書が返すリストの並びどおりに呼び、例外は1個ずつ `Debug.LogException` する。本体が先に代入している `_serverRpcCaller` も同じ位置で代入する。

送信側は一切触らないので、電文の形式は変わらず、古いバージョンや MOD なしの相手との組み合わせも今のままで動く。

本体側の形が違って更新で壊れたときは、`Prepare` が対象メソッドや private メンバー（`_serverRpcCaller`・2つの辞書・`RpcHandler.wrappedAction`）の有無を確かめて、そのパッチだけ外れて1回警告を出す。実行中の想定外の例外でも同じく1回警告して本体の処理に戻す。

## 効果の見込み

通信1通あたり、登録済みメッセージ型の数（MOD だけで36か所の登録がある）に比例していた文字列比較と辞書列挙が、1回の辞書引きになる。支配的なコストは JSON の復元なので全体としての縮みは数パーセント程度の推定だが、協力プレイで最も頻繁に走る受信経路の1つなので、通信が増える終盤の戦闘ほど効く。毎フレームではないため GC への影響はない（本体も Prefix も電文ごとの確保を増やさない）。

`python3 tools/balance/gen_cs.py --check` と Mod の `dotnet build`（Release）を通し、テストは `tests/Issue73.Native.Tests`（460件すべて合格）と `tests/SodRpg.Mod.Startup.Tests`（225件合格・既存のスキップ1件）で確かめた。実機での通信動作は未実行（この環境ではゲームを動かせないため）。
