対象は `src/SodRpg.Mod/HostAuthority.BossInk.cs` である。直した内容は、白夜（boss_white_night）の蓮の領域などで最も近い味方の英雄を探す処理 `InkNearestAlly` に、位置だけの事前確認を足したことである。この処理は `DewPhysics.OverlapCircleAllEntities` で物理エンジンの円オーバーラップ判定を行い、返ってきたエンティティから味方の英雄を選んでいた。呼び出し元の `InkDomainShields` は、領域が成熟してから消えるまでの間、ホストのティック（毎フレーム）で走り、味方の盾を配り終えるまで（一人用なら永久に）毎フレームこの物理クエリを繰り返す。変更後は、まず `ActorManager.allHeroes`（登録中の英雄の一覧、協力プレイでは少数）を走査して、物理クエリの絞り込みと同じ条件（自分以外、領域の中心から半径以内、敵・中立でない）を位置だけで満たす英雄が1人もいなければ、物理クエリを丸ごと省いて null を返す。条件を満たす英雄がいるときは、これまでどおり物理クエリを実行してその結果を使う。

結果が変わらない理由は次のとおりである。物理クエリの結果から有効な候補が返るためには、その英雄のコライダーが円に重なることに加えて、絞り込みの条件（自分以外・`InkInside` による中心からの距離が半径以内・敵中立でない）を満たす必要がある。位置が半径内の英雄が1人もいないなら、コライダーの重なり如何にかかわらず有効な候補は存在しないので、クエリを省いて null を返すのは元どおりの結果である。逆に位置条件を満たす英雄が1人でもいれば、元のクエリをそのまま実行するので、コライダーの重なり・無敵状態・生存の各判定はすべて元の経路に任せたまま変わらない。事前確認で使う述語は元の絞り込みと同じ式で、読み取りだけの処理（`InkInside` は位置の計算、`CheckEnemyOrNeutral` は関係の取得）であり、副作用はない。`ActorManager.allHeroes` は本体が `OnCreate` の直後に全英雄を登録する一覧で、本体自身も一覧が必要な場面で使っているものである。`_am` が未接続のときは事前確認を飛ばして元どおりクエリを実行する。

効果の見込みは推定である。白夜の蓮の領域（stage2、盾の対象数2）は成熟後およそ2秒間存続し、その間 `TickInkBoss` と `InkWhiteAfterFields` の2箇所から毎フレーム `InkDomainShields` が呼ばれる。味方が領域の半径3mに入っていない間（一人用では常に）、この2回のそれぞれが物理クエリ1回だったのが、英雄一覧の数要素の線形走査になる。60fps 換算で1つの領域あたり最大約240回、戦闘中は領域が繰り返し作られるので、そのつど同規模のネイティブな物理クエリ（広域フェーズの走査と返ってきたコライダー1つ1つの処理）が減る。獲得はホスト側の CPU で、割り当ては元からプールされているので GC への影響は変わらず、通信には触れない（`PublishBossVisual` の呼び出し回数と内容は変わらない）。なお、このファイルから参加者への見た目の送信を調べたが、値が変わらない再送は `PublishBossVisual` 側の重複排除と kind 7・9 の間引きですでに抑えられており、今回の変更はその層に触れていない。実機（ゲーム内）での確認は未実行である（この環境ではゲームを動かせないため）。
