# perf-loop/20261024-0259

対象は `src/SodRpg.Mod/HostAuthority.AlliedWard.cs` である。直した内容は、`DispatchAdmittedWard` が発動のたびに毎回やり直していた有効域の変換（`MechanismPayload` の組立 → `TransformAuthoredPayload` の刻印適用 → `AlliedWardDefinition` の組み直し）を、定義ごとのキャッシュに置き換えた点である。`ConditionalWeakTable<AlliedWardDefinition, ConditionalWeakTable<Hero, WardTransformCache>>` を足し、刻印の世代（`binding.Epoch`）・発動元ヒーロー・刻印適用前のペイロードを決める `authored`・発動元の記憶・発動種別をキーにした辞書で前と同じ値を返す。キャッシュは定義×発動元ヒーローごとに持ち、世代が動いたときだけそのヒーローの辞書を空にして計算し直す。刻印を持たないヒーローはすべて同じ世代 0 を返すため、発動元ヒーローを鍵に含めないと同じ定義インスタンスを共有したときに結果が混ざる恐れがあり、世代をヒーロー別に持たないと世代の食い違いのたびに辞書が空になる。変換の結果が無効（Value が 0 以下か対象数が 1 未満）のときは、その否決も覚えて従来どおり 0 を返す。

従来のしくみは次のとおりである。ホストは許可済みの防壁（オールワード）の発動ごとに `DispatchAdmittedWard` を呼び、そのつど `KeystonePayload` と `KeystoneCaps` を新しく作り、`KeystoneContext` と `KeystoneResult` も新しく作り、刻印の適用処理（`ScopedKeystoneModifiers.Apply`）の検査と変換の走査を全部通し、最後に `AlliedWardDefinition` を検査つきで組み直していた。つまり発動ごとに確保4個と変換の走査1回で、入力が同じなら結果は毎回同じだった。

結果が変わらない理由は次のとおりである。変換の結果は刻印ランタイムの状態と発動元だけで決まり、時間・乱数・現在の HP は読まない。刻印ランタイムは `RefreshAuthoredKeystone` の `Configure` でしか書き換わらず、`Configure` は必ず `binding.Epoch = checked(++_authoredKeystoneEpoch)` と対で走る。`binding.Equipment` も世代の更新と同時にだけ差し替わる。`StarDamageScaling.ScaleResult` は Shield 効果・AlliedWard 種別・ModEffect 層のペイロードに倍率 1（恒等）を返すので、`ConfigureAuthoredKeystone` が世代を進めずに行う `existing.Build = build` の差し替えにも結果は影響されない。入力の `AlliedWardDefinition` は getter しかない不変のクラスで、設定し直しのたびに新しいインスタンスが作られる（`AuthoredMechanisms.Key(spec)` が仕様全体の符号化なので、内容が変われば別のチャンネル状態になる）。ブリッジ経路でも `state.Wards` の仕様は `payload.Ward` と同じインスタンスを共有する。そのため、インスタンスを鍵にすれば内容の変化を取りこぼさない。刻印が付いたり外れたりすれば世代は必ず進むので、古い値が残ることはない。`AuthoredKeystoneEpoch`（内部で `RefreshAuthoredKeystone` を呼ぶ）をキャッシュの確認のたびに通すので、刻印の再設定と機材の再検査のタイミングも変更前と同じ位置で動く。前段のガード（生存・記憶の所持・装備エポックの一致）と後段の対象選択・配布・回数枠の消化は触っていない。後段の `AlliedWard.Select` は静的な純関数、`AwardModShield` は定義から値だけを受け取り、バッファは発動ごとに借りて返すため、同じ世代で同じ定義インスタンスを使い回しても後段の動きは変わらない。変換が例外を投げる設定は、計算し直しのたびに同じ例外になる（キャッシュには入らない）。

効果の見込みは推定だが、発動1回ごとの確保4個と刻印適用の走査1回がなくなり、世代が同じあいだは辞書1回の参照になる。オールワードの発動は記憶の発動イベントに続くので、マルチヒットや召喚が多い戦闘ほど、イベントの数に比例して減る。この経路は `NetworkServer.active` のガードのとおりホストだけで走り、参加者側の処理・通信は変わらない。実機（ゲーム内）での確認は未実行である（この環境ではゲームを動かせないため）。
