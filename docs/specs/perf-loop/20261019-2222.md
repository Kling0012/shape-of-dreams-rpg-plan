# perf-loop/20261019-2222

## 対象

native Dew.Core/Gem.cs（装飾品「宝石」の Actor。装備中はホストの `LogicUpdate` が毎ロジックフレームで走る）。

## 直した内容

宝石のクールダウン減算の同期を、毎ロジックフレームから 0.5 秒間隔に間引いた。`Gem.LogicUpdate`（Gem.cs:769）のサーバー経路は、クールダウンが進んでいる間 `Network_currentCooldown = Mathf.MoveTowards(...)`（Gem.cs:774）を毎フレーム書き、Mirror は値が動くたびに SyncVar の差分（8バイトの dirty マスク＋4バイトの float）を全参加者へ配る。戦闘中は複数の宝石が同時にクールダウンに入るため、参加者は宝石1個あたり毎フレーム1回の差分を受信してデシリアライズしていた。

NativePerfPatches.cs に `NativeGemCooldownPerf`（`Gem.LogicUpdate` の該当1呼び出し点を Transpiler で `WriteCooldown` へ置き換え）と `NativeGemCooldownPublication`（SyncVar セッターの Prefix/Postfix で出版時刻を記録）を追加した。20261019-2119 の状態効果の残り時間と同じ方式で、前回の送信から 0.5 秒以内の周期減算はサーバー側のローカル値だけ進めて送信を省く。MOD 設定 `nativeGemCooldownSync`（既定有効）で切れる。

## 結果が変わらない理由

間引くのは `LogicUpdate` の周期減算の1呼び出し点だけ。`StartCooldown`・`ApplyCooldownReduction(ByRatio)`・`ResetCooldown` の明示的な書き込みと、0 に届いた書き込み（最後の値）はネイティブのセッターを通るので即時に送る。サーバー側のローカル値は抑制中も正確に進むので、クールダウンの長さ・判定・準備完了のタイミングは変わらない。`InvokeOnCooldownReady` など準備完了の RPC もネイティブのままで、発火時刻は1フレームもずれない。

参加者側でこの値を読むのは `UI_InGame_GemSlot`（Dew.UI/UI_InGame_GemSlot.cs:280）の表示だけで、`IsReady()` を使う判定は `Gem_C_Charcoal` と MOD の NativeDreamContent（どちらもサーバー側のみ）なので、参加者の見え方はクールダウンバーの更新が最大 0.5 秒の段階になるだけ。状態効果の残り時間の同期間引き（v3.7.0）と同種の、表示の粒度の変更であり、遊び方・強さ・判定は変わらない。

## 効果の見込み（推定）

戦闘中に同時にクールダウンが進む宝石を4個として、ホストから各参加者への差分が毎秒約240回（60fps 換算）から約8回（0.5秒間隔）に減る。スナップショット1回あたりの dirty マスクと float のペイロード（約12バイト＋バッチ処理）と、参加者側の `DeserializeSyncVars` の呼び出しが同量減る（推定）。ホスト側の送信前の SyncVar 書き込みと dirty 管理も減る。
