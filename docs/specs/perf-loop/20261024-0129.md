# perf-loop/20261024-0129

## 対象

mod src/SodRpg.Mod/HostAuthority.BossLight.cs（Light ボス装備＝boss_light_elemental のホスト側処理）。被弾・メモリ使用・移動完了・被ダメの各アクティベーションごとに `DispatchLightBoss` が呼ばれ、装備がある間は毎ティック `TickLightBoss` が走る。参加者への通信はボス演出メッセージの送信だけで、こちらはこのファイルの中で変化検出と 0.1 秒間隔の間引き（`PublishBossVisual` の coalesce）が済んでいるので、3（毎フレーム・アクティベーションごとの経路の無駄）の観点で見た。

## 直した内容

`TickLightBoss` は、Light の状態が存在する間ずっと毎ティック 9 種一括の `BossFind`（`Build.BossMoves` の全走査）を繰り返していた。1 つは装備が減ったら状態を捨てるため、もう 1 つは `state.Mask` の更新のためである。また `DispatchLightBoss` は受理されたイベント 1 件ごとに 6 種の在確認を個別の `BossFind` でやり直し、`LightChargeInput` でも stage2・stage3・stage6 の 3 回、`LightStartPhase` と `LightTickBeam` でも在確認のためにそれぞれ 1 回の全走査をしていた。

そこで、9 種の在確認と `(entry, profile)` の判定を `LightCombat` に覚える `LightScan` を新設した。走査を行うのは状態の作成時と、装備エポック（`rt.ShieldEquipmentEpoch`）が変わった最初の 1 回（`TickLightBoss` 内）だけで、以後のイベント処理・チャージ処理・位相処理・ビーム処理は覚えた判定を流用する。在確認が null のときの早期 return は従来どおり残し、判定が null の区分は以前と同じく何もしない。

## 結果が変わらない理由

`BossFind` の結果は `rt.Powers.Build.BossMoves` の内容と静的な `BossProfiles` だけで決まり、`BossMoves` は Build の生成後にどこからも変更されない。装備の付け替えは必ず別インスタンスの Build か装備エポックの前進になり、`BossEnsure` は Build の差し替え・装備エポック・部屋・走・所有者の寿命のいずれかが変わるたびに `ClearBossEffects` → `ClearLightBoss` で状態を一度捨てるので、`LightCombat` が生きている間は覚えた判定が古くなる窓がない。生きている間にエポックだけが変わる経路が万一あっても、`TickLightBoss` の変更パスが 9 種を走査し直して `Mask` を付け直し、消えた区分があれば従来どおり `LightCancelProfile` で撤去する。攻撃の流れは以前と同じく判定の有無と `state.Mask` のビットでしか分岐しないので、走査をやめたことで新しい区分が動き出すこともない。クールダウン・ダメージ・演出・送信の内容と回数は何も変わらず、この処理はホストだけで走る。

## 効果の見込み（推定）

`Build.BossMoves` は最大 64 件で、走査 1 回ごとに最大 64 回の文字列比較と `BossProfiles.TryGetMove` の辞書引きを行う。以前は Light 装備の状態がある間、ティックごとに 9 回、受理されたイベントごとに 9 回（6 種ループ＋チャージ 3 種）の全走査が続いた。60fps 換算で Light 装備 1 人分の状態があるだけで毎秒 540 回、攻撃 1 回ごとに最大 9 回の全走査がなくなる（推定。1 回は数百ナノ秒だが、戦闘中ずっと走る経路の固定費である）。参加者の PC には届かない処理だが、ビームの sweep 中はティックごとに物理判定と円探索も走るので、ホストのフレーム時間の裾を下げる。
