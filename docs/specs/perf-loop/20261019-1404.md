# perf-loop/20261019-1404

対象: native Dew.Core/Se_Shrine_Chaos_StatBonus.cs。混沌の神殿（Chaos Shrine）の帰属を表す永続ステータス効果で、実 DLL（`Shape of Dreams_Data/Managed/Dew.Core.dll`）から ilspycmd で再取り出しし、空白正規化 diff で照合した。差分は逆コンパイラの表現差（`base.` 修飾・ラムダ形式）のみでロジック差なし。プレイ中に反復して走る経路は1本だけだ。`OnCreate_Corrupted` がホスト側で購読する `ActorEventOnDealDamage` で、混沌の神殿を持つ英雄がダメージを与えるたびに、相手の光・闇の属性状態の最大スタックを corrupted 報酬の分だけ引き上げる。残りの経路はどれも報酬を選んだときや効果の生成・破壊などイベント時だけだ。`NotifyUpdate` が送る SyncVar は Mirror の同値チェックで変化したときだけ送られるので、通信で無駄な送信は見つからなかった。

直した内容: `ActorEventOnDealDamage` に Prefix（`NativeChaosShrineHitScanPerf`、`NativePerfPatches.cs` 末尾）を差し込み、`currentAddedLightMaxStack` と `currentAddedDarkMaxStack` が両方 0 のときだけ本体のハンドラを飛ばす。2つのフィールドは式木でコンパイルした読み取りデリゲートで1回ずつ読むだけなので、Prefix 自体は確保なしで2つの int 比較をする。本体の型は MOD の他の場所から参照していないため、テストハーネスの模倣型を足す必要がないよう `AccessTools.TypeByName` で解決する。対象の型やメソッド、フィールドが見つからないときは警告を1回出してこの修正だけ外れる。設定は `DreamforgeConfig.nativeChaosShrineHitScan`（既定は有効）。テスト側の模倣 `DreamforgeConfig`（`tests/Issue73.Native.Tests/NativeEmbracePositionBoundary.cs`）に同じ名前のフィールドを足した。

結果が変わらない理由: ボーナスが両方 0 のとき、本体の書き込みは `Mathf.Max(maxStack, 5)` になる。`StackedStatusEffect.maxStack` の既定値は 5 で、逆コンパイルした全アセンブリ（Dew.Core・sod-contents）を検索してもこの2行以外に書き手はなく、書くときも Max で上げるだけだ。ボーナスは `AddCorruptedBonus` が正の定数を足すだけでしか増えないので、どちらのボーナスも 0 のままの効果インスタンスでは maxStack は常に 5 であり、`Max(5, 5)` は同じ値を書き込むのと同じだ。その前提で飛ばされる `TryGetStatusEffect` の走査は読み取りだけで副作用がない。ハンドラは `isServer` のときだけ購読されるので、参加者側はそもそもこの処理を走らせておらず、通信や見えるものは何も変わらない。残る仮定は、サードパーティの MOD が属性状態の maxStack を 5 未満に下げている場合で、そのとき本体は次の該当被弾で 5 に戻すが、この省略では戻らない。本体とこの MOD にはそのような書き手がないことを確かめたうえで、従来の unchanged-write スキップ系のパッチと同じ扱いとして残した。

効果の見込み（推定）: 光か闇の攻撃1回ごとに、相手のステータス一覧を端から調べる走査が丸ごとなくなる。報酬で光・闇の最大スタックを取っていない間の話なので、混沌の神殿のランで光・闇ビルドに寄らない序盤ほど効く。判定はホストだけで走るので、ホストの被弾処理の負担がその分減る。ネットワークの送信量と回数は変わらない。
