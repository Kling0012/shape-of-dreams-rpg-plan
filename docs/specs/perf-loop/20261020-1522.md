# perf-loop/20261020-1522

対象は mod `src/SodRpg.Mod/BountyReportBatching.cs` である。ホストが数えた依頼（バウンティ）の進捗カウント（支援シールド・他旅人の回復・元素状態つき撃破）をゲストへまとめて届ける経路と、ゲストの受信処理 `OnBountyCounts` を担うファイルである。

見えた構造は次のとおりである。`QueueBountyReport` は被弾・回復・被弾シールド・元素撃破のイベントごとに `HeroRuntime` のカウンタを進めるだけの軽い処理で、確保はない。`FlushBountyReports()` はホストティックの工程（`BuildTickStages` の "bounty reports"）として登録されており、ホストティックは `DreamforgeMod.Update` から毎フレーム呼ばれる。そのため、どれかの旅人に未送信のカウントが1つでもあるフレームでは、その旅人の相手（ capability を広告するゲスト、またはローカルプレイヤーへのループバック）へ `DreamforgeBountyCountsMsg` が毎フレーム1通ずつ送られていた。支援ビルドがシールドや回復を毎秒数回適用する戦闘では、この送信が連続する。決着・保存・セッション再起動・プリムス結末の前には `BountyReportsBeforeBoundary`（Priority.First）が即時のフラッシュを挟む。

直した内容は、ティック工程の入口を新しい `TickBountyReports` に差し替え、`_nextBountyFlush`（`BountyFlushSeconds` = 1秒。`StageAreaScan` の `_nextAreaScan` と同じ `_tickNow` による間引きの型）でフラッシュを1秒に1回へ間引いたことである。境界フラッシュと、旅人削除時の `FlushBountyReports(rt)` は間引かず即時のままである。テスト側は、`HostAuthority.cs` をリンクしていない `tests/Issue73.Native.Tests/NativeBoundary.cs` の部分クラスに `_nextBountyFlush` の宣言を足して合わせた。

結果が変わらない理由は次のとおりである。送るメッセージは「前回のフラッシュからの合計」なので、フレーム単位の送信を1秒単位に併せても届く合計値は同じである。最後の値は、決着・保存・再起動・プリムス結末の前の境界フラッシュと旅人削除時のフラッシュが保証する。capability を持たない相手への従来形式の個別報告（フォールバック）は、同じ件数のメッセージが1秒ごとのフラッシュに束ねられるだけで、件数は増えない。戦闘の状態（敵の出現・撃破・スキル）を運ぶ電文は別経路のままで、触っていない。変わるのは依頼の進捗の計上が最大1秒遅れることと、ゲストが突然切断されたときに未送信分として最大1秒ぶん（変更前は最大1フレームぶん）失われる可能性があることだけである。

効果の見込み（推定）は、支援ビルドが戦闘中にカウントを流し続けているときのゲスト宛てのカウント送信が、毎フレームから最大毎秒1通になることである。ホストの直列化と送信、各ゲストの受信・逆直列化・ハンドラ・`Emit` がその回数だけ減る。未送信カウントが無いフレームの負荷は、間引きの判定1回だけでほぼ変わらない。

検証は次のとおりである。`python3 tools/balance/gen_cs.py --check` を通した。`dotnet build src/SodRpg.Mod -c Release -p:GameDir=... -p:ModDeployDir=/tmp/perfloop-x` を通した（エラー0、警告6件は既存分）。`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release` は 612 件すべて通過した。`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Mod.Startup.Tests -c Release` は 225 件通過・1件スキップで失敗はなかった。実機（ゲーム内）での確認は未実行である。この環境ではゲームを動かせないためである。
