# perf-loop/20261018-1707

対象: mod src/SodRpg.Mod/ClientSession.Infinity.cs（と、そこから毎フレーム呼ばれる経路）。

直した内容: `AdvanceInfinityIdentity`（ClientSession.Infinity.cs:240）は `RunChoiceProgress.TryAdvance` に `Emit` をメソッドグループ引数として渡しており、プロジェクトは LangVersion 9.0 でメソッドグループからデリゲートへの変換のキャッシュは C# 11 からのため、この呼び出しは毎フレーム `Action<IEnumerable<GameEvent>>` を新しく確保していた。同じ `TickRunChoices` の毎フレーム経路にある `FlushPendingRunRewards`（ClientSession.RunChoices.cs:236）と `TryFinishSecureArrival`（同:259）も同型で、後者は `PublishRunChoicesForZone` の確保も伴う。3箇所の引数を、初回のみ束縛する遅延キャッシュ（`EmitEvents` / `PublishZoneChoices`）に置き換えた。コンストラクタでの初期化にしなかったのは、ネイティブ境界テストが実物の `ClientSession` コンストラクタを経由せず部分クラスを差し替えて組み立てるためで、ctor 初期化ではテスト側で null のまま null 参照になる。

結果が変わらない理由: デリゲートは同じインスタンスの同じ非仮想メソッドを指し、`RunChoiceProgress` は受け取った `emit` / `reward` / `finalized` を呼び出すだけで等値比較も保持もしない。毎回新しいデリゲートと1回だけ作ったデリゲートは、呼ばれる側から区別できない。キャッシュを `ClientSession` 自身のフィールドが持つため、参照の寿命も延びない。

効果の見込み（推定）: インフィニティ遠征中はホスト・参加者とも毎フレーム1件（`TryAdvance`）、通常モードの遠征中は毎フレーム最大3件（`FlushRewards` 1件と `TryFinishSecureArrival` 2件）のデリゲート確保（各64バイト程度）がなくなり、60fps では毎秒数KB規模の GC 確保の削減と推定する。ゲーム内の数値・判定には影響しない。

検証: `python3 tools/balance/gen_cs.py --check` 合格、`dotnet build src/SodRpg.Mod -c Release` 合格（警告は既存のもの）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release` 278件合格、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Mod.Startup.Tests -c Release` 149件合格・1件は既存のスキップ。ビルド済み DLL を ilspycmd で逆コンパイルし、3呼び出し箇所がキャッシュ経由になったことを確認した。実機での動作確認は未実行。
