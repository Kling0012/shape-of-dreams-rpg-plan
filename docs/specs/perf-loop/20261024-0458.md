# perf-loop/20261024-0458

対象は `src/SodRpg.Mod/CulinaryIngredientCap.cs` である。直した内容は、料理ポットのそばで毎フレーム走る素材数の後処理（`Shrine_CookingPot.GetIngredientCount` への postfix である `AfterIngredientCount`）から、結果に関係しない作業を2か所で省いた点である。1つ目は、数えた素材が 0 以下のときに何もせず返る早期リターン。2つ目は、ドメイン共有の弱い辞書（`ConditionalWeakTable`）を、読み込みごとのコピーが最初の1回だけ `AppDomain.GetData` で取り出して静的フィールドに覚え、2回目以降はその参照を返すようにした点である。従来は postfix のたびに、ネイティブが直前に終えたばかりのステータス効果の全走査（`Ingredients` が `GetStatusEffect` でやり直す）と、`AppDomain` の鍵つき探索とそのロックを、毎フレームやり直していた。

この経路が参加者側で走る根拠は次のとおりである。ポットの `CanInteract` は `GetIngredientCount` を呼び、それを `ControlManager.GetNearbyInteractable`（半径6m の `OverlapSphereNonAlloc` のあとの候補ごとの判定）と、フォーカス中の対象を確かめ直す `GetCharInputOfInteractByButtonPress` が、操作入力を作るたびに呼ぶ。これはホストでも参加者でも、その場のローカルプレイヤーの PC で走る。素材スタックを持たない英雄がポットのそばに立つだけの状態（ふつうの状況）では、native の戻り値は 0 で、MOD の postfix は走査と辞書仕事のすべてを無駄に繰り返していた。

結果が変わらない理由は次のとおりである。素材数 0 のときは、効果が存在しない場合とスタックが空の場合のどちらも native が 0 を返し、上限の `Math.Min(0, 調理分量)` も 0 のままなので、戻り値は変わらない。`TryCapacity` を省いたときに失われる副作用は「元の上限の記録」と「`maxStack` の引き上げ」だけだが、どちらも変異の経路（`OnCreate`・`SetStack`・`AddStack`・`RemoveStack`・`ConsumeIngredients` の各 prefix）が自分のクランプの前に必ず初期化するので、後から必要になることはない。`maxStack` が読まれる残りの場所（`ActiveLogicUpdate` の `numberDisplay`）も、スタック 0 では引き上げの前後で同じ値になる。ネイティブの上限が安全でないと判定されたスタックへの警告については、`OnCreate` の prefix が効果の生成時に必ず先に走るので、表示上の変わる余地はゲーム内にない。辞書のキャッシュについては、共有ストアはドメインに1回だけ作られ、以後このコード自身は置き換えない（`Stop` やアセンブリ再読み込みのあとも渡し続けるのがこの実装の目的である）。再読み込み後の新しいコピーは静的フィールドが空のまま最初の1回を取り直すので、複数コピーの共有と同時実行時の原子な記録（並行テストが確かめる性質）は保たれる。互換しないストアが入っていた場合の検査と、そのときのこの機能だけの停止も初回アクセスで従来どおり動く。参加者側では `maxStack` は SyncVar ではないので、同期で来るのはスタック数だけで、参加者のローカルで上がった上限とプレハブの値の食い違いも起きない。

効果の見込みは推定だが、ポットのそばに立つあいだの毎フレームで、素材を持たない英雄はステータス効果の全走査1回と `AppDomain` 探索とそのロックが丸ごと消え（整数比較1回になる）、素材を持つ英雄でも `AppDomain` 探索とドメイン全体へのロックが消えて辞書1回の参照になる。通信は1バイトも変えず、送受信の回数も変えない。実機（ゲーム内）での計測は未実行である（この環境ではゲームを動かせないため）。
