# perf-loop/20261019-1948

## 対象

mod src/SodRpg.Mod/ClientSession.RunChoices.cs（参加者が受け取るたびに走る `ReceiveRunChoices`）。

## 直した内容

参加者は同じ選択状態の文字列を繰り返し受け取る。ホストは内容が変わらなくても5秒（状態の簡素化が有効な相手は30秒）ごとに再送する経路が2本ある（`DreamforgeRunChoicesMsg` の定期再送と、`DreamforgePressureMsg` に載せて送る `runChoices`）。これまでは受信のたびに `RunChoiceSnapshot.TryDecode` が全文を解析していた。解析は `Split('|')` による配列と部分文字列の確保、9個の数値変換、Base64 と UTF-8 の復号、新しい `RunChoiceSnapshot` と `Offers` のリストの確保で、インフィニティの遠征ではさらに JSON の解析と `InfinityRunState` の組み立てまで行う。解析が終わっても、内容は前と同じなので `RunChoiceProgress.Receive` が同一 Revision として棄て、どこにも反映されない。

そこで `ReceiveRunChoices` に、検査を通過して処理まで終えた文字列を記憶する `_processedChoicesPayload` を追加し、同じ文字列を結果の通知なしで受けたら解析の前に読み捨てるようにした。記憶する位置は、RunId とゲーム内の遠征の一致、権威世代の確認、空 RunId の保留確認をすべて通った直後。ここを通った文字列は、再送されても適用済みか同一 Revision での棄却かのどちらかになるため、読み捨てても動作は変わらない。authority や Revision が変われば文字列自体が変わるので、新しい内容は必ず解析される。同期状態を作り直す2箇所（`ResetRunChoiceConnection` と `RestoreRunDurability`）では記憶を解除し、復元後に届く同じ文字列がもう一度処理されるようにした。

## 結果が変わらない理由

読み捨ての条件は「結果の通知（terminal・帰還）を伴わない」かつ「記憶した文字列と完全一致」の2つ。結果の通知を伴う受信と、帰還の受付から来る受信は、これまでどおり最後まで処理する。完全一致の再送は、記憶時点で検査を全部通っているので、RunId の不一致や権威の遅延で落とされることはなく、`Receive` に入っても同一 Revision で棄てられるだけ（`TryAccept` の同一内容での棄却は状態を変えない）。解析の前に落とすことで省くのは、棄却が確定している後続の処理だけである。進行の復元（`Snapshots.Reset` を伴う `Restore`）と接続のやり直しでは記憶を解除するので、同じ文字列が再び意味を持つ場面でも処理される。

## 効果の見込み（推定）

参加者の PC で、選択状態の再送1回ごとに上記の解析一式がなくなる。再送は2経路合わせて1分に最大24回（変更時は即時なので戦闘中はもう少し増える）。1回あたりの確保は通常の遠征で1KB前後、インフィニティでは JSON 分も含めてさらに増える（推定）。頻度は高くないが、受信側の完全に無駄な処理で、ホスト側の送信は何も変えていない。判定・通信量・見た目は変わらない。
