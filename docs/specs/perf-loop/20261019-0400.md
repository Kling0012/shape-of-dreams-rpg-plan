# perf-loop/20261019-0400

## 対象

native Dew.Core/EntityControl.cs（位置同期 `PositionSyncData` を送るかどうかの判定 `HasMeaningfulSyncDataChange` と、その呼び出し元3箇所）。

## 直した内容

エンティティの位置・速度・向きを同期する値（`PositionSyncData`）には、送るかどうかを決める判定式がある。本体の式は「タイムスタンプが前回から1秒以上新しい」「位置が動いた」「速度が変わった」「向きが0.1度以上変わった」のどれか一つでも当てはまれば送る。このうち「1秒以上新しい」は心拍として働いていて、動いていないエンティティでも1秒に1回、位置・速度・向きの差が本体の閾値を超えない更新を送り続ける。参加者の操作する英雄では送信（Cmd）→サーバー受信→全オブザバーへの再配信という1往復、モンスターなどサーバー管理のエンティティでは SyncVar の dirty 化→全オブザバーへの配信が、動いていない間ずっと1秒に1回続く。

MOD では、この判定の呼び出し元3箇所（`UpdatePositionSyncData` 内2箇所＝所有クライアントが送るかどうかの判定と、サーバー管理エンティティの SyncVar を dirty にするかどうかの判定、`UserCode_CmdPositionSyncData` 内1箇所＝サーバーが所有クライアントのCmdを受け入れるかどうかの判定）を Harmony の Transpiler で書き換え、判定の計算を「更新の持つ速度がほぼ0（二乗距離0.0001以下）のときだけタイムスタンプの条件を除いた同じ式」に置き換える。本体の閾値（1秒・0.0001平方・0.1度）とフィールド読み出しの形は IL の指紋で固定して確かめ、形が変わっていればこの修正だけが外れて警告を1回出す。MOD 設定の「動いていない実体の位置同期の同じ再送を省く」（`nativePositionSyncIdle`、既定ON）で切れる。

## 送信条件と表示への影響

再送を省くのは、位置・速度・向きの差がすべて本体の閾値以下で、かつ更新の持つ速度がほぼ0（二乗距離0.0001以下）の更新だけに限る。位置差の二乗距離が0.0001を超えるとき・速度差の二乗距離が0.0001を超えるとき・向きが0.1度を超えて変わるときは、今までどおり即座に送る。閾値以下の速度変化では、停止時の速度0も必ず送られるとは限らない。更新の持つ速度が1cm/sを超える場合は心拍も省かない（理由は次の段落と「レビュー指摘 F1 への対応」）。60Hzの送信上限も変えていない。テレポートは `EntityControl.Teleport` が新しいタイムスタンプ付きの同期をこの判定を通さず直接配信するので、参加者に遅れて届くことはない。変位・転移の終了時に参加者側で立てられるタイムスタンプの下限は、テレポートの直接配信か次の実際の移動で必ず上回られる。

速度がほぼ0の静止実体では、参加者側の「最終受信時刻」が更新されなくなる。受信側の実装（本体 EntityControl の SyncVar フック `OnMovementSyncDataReceived` と毎フレームの `DoMovementObserverFrameUpdate`、r1.4.1.2 の逆コンパイルで確認。定数は同 static コンストラクタによる）は、最終受信から0.5秒（`SyncFixSnapshotLifetime`）の間だけ最終位置へ速度を外挿した目標（外挿は `SyncExtrapolateMaxTime` 0.15秒で上限）へ SmoothDamp で寄せ、0.5秒を過ぎると補正を打ち切って速度ぶんの単純移動だけを続け、1秒（`SyncAgentVelocityLifetime`）を過ぎると保持している速度を0に落とし、停止判定の早期リターンで表示を凍結する。受信側が保持する速度も0の静止実体では、外挿も単純移動も動かないため表示は変わらない。ただし、省いた更新の速度と最後に受理した速度には最大1cm/sの差があり得る。更新の速度が1cm/s以下でも、受信側は最大約2cm/sを保持し得るため、最長1秒の外挿で最大約2cmのずれが残り、次の意味のある更新まで表示が戻らない場合がある。例えば1.5cm/sを受理したあとに実速度が0.8cm/sになり、位置・速度・向きの差も閾値以下なら、心拍だけの更新が省かれて受信側は1.5cm/sのまま外挿する。1cm以内に収まるという以前の説明は、この保持速度との差を考慮していなかった。

速度が0でないのに位置が止まっている実体（行き先が壁やほかの実体で塞がっている場合など）では、受信側の表示は最終受信時刻に依存する。素の心拍は毎秒この受信時計をリセットしていたため、これを省くと最終受信から速度×1秒程度まで一度進んだ位置で凍結し、軽量化の前後で表示が変わってしまう。そのため、更新の持つ速度の二乗距離が0.0001（1cm/s）を超えるときは心拍を省かず、本体と同じ毎秒の引き戻しを続ける。この状況の見た目の確認は実機では行っていない（本体コードと定数からの確認のみ）。

メッセージの形式は1バイトも変えていないので、MOD が片側だけ（ホストか参加者かどちらか）でも今までどおり動く。

## レビュー指摘 F1 への対応（2026-10-19）

- 境界値のテスト `EnabledKeepsTheHeartbeatForUpdatesThatStillCarryVelocity` を追加した。速度0.5のまま塞がれている実体の心拍だけの更新を ON でも本体と同じく通すこと、速度の二乗距離がちょうど0.0001（1cm/s）の更新は心拍を落とすこと、速度0の静止実体の心拍だけの更新は落とすことを確かめる。
