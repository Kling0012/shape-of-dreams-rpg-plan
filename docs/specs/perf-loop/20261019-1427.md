# perf-loop/20261019-1427

## 対象

native Dew.Core/ControlManager.cs。プレイ中に走る入力まわり全体を見て、その中のキャストプレビューの送信（`ProcessCastInfoSampling` から `DewPlayer.DispatchSample_Update` への0.05秒ごとの Command）を軽くした。対象ファイル自体は変更せず、MOD から Harmony の Prefix で送信を省く。

## 直した内容

プレイヤーがチャージ系スキルを溜めている間、クライアントは0.05秒ごと（最大毎秒20回）に狙いの CastInfo（caster・target・point・angle・animSelectValue の5字段）を Command でホストへ送り続ける（`DewPlayer.DispatchSample_Update`。この送信メソッドを呼ぶのはゲーム全体で ControlManager の1箇所だけ）。受信側（`UserCode_DispatchSample_Update`）の作用は、受け取った構造体を文脈に代入して `updateCallback` を呼び直すことだけで、`updateCallback` を登録している箇所はゲーム全体で `ChargingChannel` の1箇所（`HandleInfoUpdate`）しかない。その本体は `castInfo = info;` と、一度 true になったら戻らないフラグの再設定だけで、同じ値をもう一度代入しても何も変わらない。それでも本体は狙いが止まっている間も同じ値を送り続け、ホストは毎回逆直列化と代入をしていた。

MOD では `DispatchSample_Update` に Prefix（`NativeSampleUpdateIdlePerf`、NativePerfPatches.cs 末尾）を差し込み、この DewPlayer が前に実際に送った CastInfo と `CastInfo.Equals`（本体の IEquatable で、weaver が直列化するのと同じ5字段の比較）で等しいときだけ送信を飛ばす。等しくない値は次の0.05秒の枠で今までどおり送るので、変化がホストに届くまでの遅れの上限は本体と同じ。最終的な値は発動の `DispatchSample_Cast` で必ずホストに届く（こちらは触らない）。実機にこのメソッドが見つからない・形が違うときは警告を1回出してこの修正だけ外れる。設定は `DreamforgeConfig.nativeSampleUpdateIdle`（既定は有効）。

## 結果が変わらない理由

省く対象は、ホスト側で同じ値の再代入と既に true のフラグの再設定しかしないメッセージに限る。`ChargingChannel` の回転（`RotateForward`）はチャンネルのティックごとに保持している `castInfo` を読むだけで、更新の受信回数に依存しないので、同じ値の更新を落としても回転の速さも向きも変わらない。`HandleInfoUpdate` が立てるフラグ（`_didReceiveAnyUpdates`）は一度 true になったら戻らないので、更新の取りこぼしで処理が止まる箇所もない。送る・省くの判定は本体が直列化するのと同じ5字段の等値で、等しいときの再送はホスト側の状態を1つも書き換えないため、省いたメッセージは元々作用を持っていなかった。独自に `updateCallback` を登録するサードパーティ MOD から見ると呼び出し回数が減るので、設定で切れるようにした（NativeProjectileIdleRpcPerf の省略と同じ扱い）。メッセージの形式は1バイトも変えていないので、MOD が片側だけでも今までどおり動く。

## 効果の見込み（推定）

チャージ系スキルを溜めている各プレイヤーから、狙いが変わっていない時間の分だけ毎秒最大20回の Command が消える（1メッセージは Mirror のヘッダと CastInfo の5字段で約25〜40バイトの推定）。ホスト側では毎回の逆直列化と代入がなくなり、ホスト自身が溜めているときはループバックの直列化も減る。数値はすべて推定。チャージ系スキルを使っていない間の通信は何も変わらない。
