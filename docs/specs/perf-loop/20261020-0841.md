# perf-loop/20261020-0841

対象は MOD `src/SodRpg.Mod/EnemyOwnershipNative.cs`（185行）と、そこから敵のスポーンごと・AI の思考ごと・敵対化（Aggro）ごとに呼ばれる処理である。呼び先は `HostAuthority.EnemyOwnership.cs` と `HostAuthority.SummonOwnership.cs`、下流の本体側は `Dew.Core/EntityAI.cs`（722行）まで確認した。まず全体の見取りとして、このファイルの5つの Harmony パッチはすべて `NetworkServer.active` の1比較でゲスト側は即 return であり、`EntityAI.UpdateAIContext` と `EntityAI.Aggro` は本体側で `[Server]` かつ `LogicUpdate` の `isServer` 比較で守られているため、**このファイルにゲスト側で走る経路はない**。そのため指示どおり観点 3（AI の思考ごとの経路の無駄）で見た。

見えた構造は次のとおりである。`UpdateAIContext` はモンスターで 0.5〜1 秒間隔、ボスと召喚獣で 0.25 秒間隔、ヒーローで 0.15 秒間隔の AI 思考ごとに走り、MOD 側は Prefix の候補判定（辞書1回の参照）だけですむ。`Aggro` は本体の探索・再ターゲット・被弾・召喚獣の伝播、MOD の `RetargetOwnership` から呼ばれ、百単位の敵がいる部屋では毎秒数百回の呼び出しになりうる。この `Aggro` の Prefix は無条件に `SelectSummonOwnershipAggro` を呼び、その先頭で `OwnershipRunning()`（ GameManager と ZoneManager の取得、runId とゾーンの確認、`DewPlayer.gamePlayers` の走査と参加人数ごとの `Contains`）が、Summon 型の判定より先に走っていた。この関数が実際に動く対象はプレイヤーの召喚獣だけで、モンスターが大多数を占める Aggro 呼び出しのたびに、答えに関係しないプレイヤー一覧の走査を毎回払っていた（ソロでも同じ）。

直した内容は、`HostAuthority.SummonOwnership.cs` の `SelectSummonOwnershipAggro` の先頭ガードの並べ替えである。`!(ai?.entity is Summon summon)` と召喚獣・主人の確認を先にし、`OwnershipRunning()` を最後に移した。これでモンスターなど召喚獣でないエンティティの Aggro 呼び出しは、型の判定だけでこの関数を抜ける。

結果が変わらない理由は次のとおりである。並べ替えたのは短絡評価の OR 条件の順序だけで、5つの条件はどれも副作用のない読み取りである（`Summon.hero` は自動プロパティ、`owner` は Mirror の SyncVar のキャッシュ付き getter、`isHumanPlayer` は参照比較2つ、`OwnershipRunning()` は状態の読み取りだけで書き込みがないことを、本体の逆コンパイル `NetworkedManagerBase.cs`・`DewPlayer.cs`・`Summon.cs`・`Entity.cs` で確認した）。順序を変えても真偽は1つも変わらず、呼び出し側も `EnemyOwnershipNative.cs:96` の1箇所だけである。

効果の見込み（推定）は、Aggro の呼び出しごとに、マネージャの取得2回・runId とゾーンの確認・プレイヤー人数ぶんの走査と `Contains`（人数を N とすると O(N²) の参照比較）が、召喚獣以外では丸ごとなくなることである。重い部屋で毎秒数百回の Aggro を想定すると 1 回あたり数十操作なので、合計では毎秒数十マイクロ秒程度の推定で、効果は小さい。ただしゲーム内で最も頻度の高い AI 経路に乗る純粋な無駄であり、結果が変わる箇所はない。数値は推定で、実機での計測は行っていない。

見送った候補は次の3つである。(1) `OwnershipRunning()` のフレーム単位のキャッシュ。効果はこの並べ替えより大きいが、プレイヤーの切断やゾーン遷移が1フレームの途中で起きたときに前フレームの値を使うことになり、同値性を証明できない。(2) `RetargetOwnership` が呼ぶ `ai.Aggro` の後でもう一度 `TryOwnership` と `OwnershipCanTarget` が走る重複。呼び出し経路によって前段の判定の有無が違うため、経路ごとに結果を変えずに外せない。(3) Retarget Prefix の `CanAggroTo` の省略。本体がターゲットを落とすのと同じ思考の回に MOD 側のリターゲット判定が変わるため、リターゲットのタイミングが半〜1思考ぶんずれる可能性があり、不可。
