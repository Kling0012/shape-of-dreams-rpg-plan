# perf-loop/20261019-0431

対象: mod src/SodRpg.Mod/ClientSession.RunChoices.cs（と、そこから毎フレーム呼ばれる経路）。

直した内容: `TickRunChoices`（ClientSession.RunChoices.cs:207）は毎フレーム `PublishCurrentRunChoices`（同:160）を呼び、その末尾で `PublishRunChoiceHistory`（ClientSession.RunReplay.cs:31）が走る。履歴配信の送信自体は 0.1 秒ごとに 4 メッセージ・8KB のバジェットで間引かれているのに、送信前の走査（履歴ピアの離脱掃除、gamePlayers と lobbyPlayers の全走査と `_choiceHistoryTargets` の組み直し、履歴改訂・確定状態・接続の変化検知、`Profile.LobbyReturnedRunIds` の検索）は毎フレーム実行されていた。変化検知と離脱掃除と送信を、既存の送信バジェットと同じ 0.1 秒周期 (`_nextChoiceHistoryBatch`) に揃えて 1 回にまとめ、バジェット未満のフレームでは関数の冒頭で抜けるようにした。

結果が変わらない理由: 履歴は後追いで届けばよい情報で、受信側の見え方はカーソル管理で送る内容と順序にだけ依存する。走査を 0.1 秒に間引いても、離脱・参加・履歴の変化の検知が最大 0.1 秒遅れるだけで、送るエントリ・順序・カーソルの進み方は変わらない。遅れる量は既存の送信バジェット（0.1 秒）と同じなので、参加者が受け取る時刻も実質変わらない。共有選択情報（`DreamforgeRunChoicesMsg` の `choices`）は別の経路で、ホストは変化を検知した時点でそのまま送信する（ClientSession.RunChoices.cs:221 の `current != before`）。こちらは今回の変更に含まれないため、参加者が選択情報を受け取るタイミングは従来どおりである。

効果の見込み（推定）: ホスト（1 名）で毎フレーム走っていた O(プレイヤー数²) 程度の比較と辞書列挙、`Time.unscaledTime`・`Time.frameCount` のネイティブ呼び出しが、1/6 の頻度になる。アロケーションは元からないため削減は CPU の僅かな節約で、無視できる規模と推定する（推定）。通信量・送信回数・見た目・判定は変わらない。
