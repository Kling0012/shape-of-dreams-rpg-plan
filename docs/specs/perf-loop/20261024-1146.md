# perf-loop/20261024-1146

対象: `Dew.Core/InputManager.cs`（入力管理。ホスト・参加者を問わず各端末で毎フレーム動く）

## 直した内容

`InputManager.FrameUpdate` は毎フレーム `DoRumbleFrameUpdate` を呼びます。この中身は、
被弾シェイクのリスト（`_shakes`）を畳んで期限切れを捨てたあと、**必ず**
`Gamepad.current.SetMotorSpeeds` を呼ぶ作りです。呼ぶ値は、シェイクが1つも
働いていなければ `(0, 0)` で、これは「振動を止めろ」という指示です。入力モードが
ゲームパッドでないときも値は `(0, 0)` に強制されるので、キーボードとマウスで
遊んでいる人でも、コントローラーがつながっていれば毎フレームこの呼び出しが走ります。

ゲームに同梱されている Unity.InputSystem の実装を見ると
（`Gamepad.SetMotorSpeeds` → `DualMotorRumble.SetMotorSpeeds`）、この呼び出しには
「前と同じ値なら送らない」という仕組みがありません。毎回 `DualMotorRumbleCommand`
を作り、`device.ExecuteCommand` で入力バックエンドへのネイティブ呼び出しを1回
行います。止まっている振動に向けて毎フレーム「止まっていろ」と送り続けている状態です。

MOD 側に `NativeGamepadRumbleIdlePerf` パッチ（`NativePerfPatches.cs`）を追加し、
`DoRumbleFrameUpdate` の Prefix で「シェイクのリストが空で、前回の本体実行が確実に
`(0, 0)` を送ったフレーム」に限って本体を飛ばします。Postfix は、本体が送った値を
本体と同じ条件から導き直して記録します。リストが空・モードがゲームパッド以外・
timeScale が 0.001 未満のときは必ず `(0, 0)` が送られたと分かるので、それ以外
（ゲームパッドモードで止まっていないシェイクが残っているフレーム）だけフラグを
消して次のフレームから本体に戻します。Postfix の冒頭は設定（`nativeGamepadRumbleIdle`）
も見て、無効な間は毎フレームの読み出しと導出そのものを行いません。無効な間にフラグが
古くなっても害はなく、Prefix が設定を先に見て必ず本体を走らせるためで、再有効化後の
最初の Postfix が生きた状態から導き直します。この2つの判定（`ShouldSkip`・`DeriveSentZero`）は
引数だけから決まる純粋な静的関数として切り出してあり、Prefix/Postfix は状態を読んで
渡すだけです。テスト（`GamepadRumbleIdlePerfTests`）から直接駆動して、(1) リスト空+
前回 `(0, 0)` 送信のときだけ飛ばす、(2) ゲームパッドモードかつ timeScale 0.001 以上で
シェイクが残るときフラグを立てない、(3) 最後のシェイクが消えたフレームに本体を実行
する、の3つと、シェイク発生 → 減衰 → 消滅 → 待機のフレーム列で実行/飛ばしの順序が
本体どおりの送信列になること（非ゼロの送信は全て同じフレーム、消滅フレームに最後の
`(0, 0)` が1回、以後の待機フレームは何も送らない）を確かめています。
設定（DreamforgeConfig の `nativeGamepadRumbleIdle`、既定は有効）で切れます。本体の
メソッドや `_shakes` フィールドが見つからない形のときは1回だけ警告を出して何もしません。
Prefix 内で例外が出たときも警告1回でパッチを無効化し、本体どおりに戻します（fail-soft）。

本体の形は実 DLL の逆コンパイル（`decompiled/sod-decomp/Dew.Core/InputManager.cs` の
`DoRumbleFrameUpdate`）と突き合わせて確認しています。転写の結果: 期限切れの除去は
モードや一時停止に関係なく畳み込みの中で起き（期限は超過の厳密比較、振動強度 1 未満
では経過時間を 0.5 + 強度 * 0.5 で割って早まる）、エンベロープは attack 中も sustain
中も全力値 1 で decay で線形に下がり（attack へのランプは無い）、低周波モーターに
振幅 * 0.1 * エンベロープ * (2.5 * 強度) が足り、高周波モーターは振幅 * 0f で常に 0、
モードがゲームパッド以外なら両値を 0 に強制し、`Gamepad.current` が null なら何も
送りません。このうちスキップ判定（ゼロか非ゼロか）に関わるのは リスト空・非ゲーム
パッド・一時停止の3条件だけで、エンベロープの形・強度の係数・期限の厳密比較は
フラグの意味を変えません（強度や厳密比較は待機へ入るタイミングをずらすだけで、
フラグは本体実行後にしか立たないため保守側に倒れる）。

Prefix/Postfix/Prepare の配線も `GamepadRumbleIdlePerfWiringTests`（境界スタブの
`InputManager.DoRumbleFrameUpdate` を本体に見立てて reflection で直接呼ぶ）で確かめて
います: 空リスト + フラグ true のときだけ Prefix が false を返すこと、Postfix が
`DewInput.currentMode` と `Time.timeScale` を正しく渡すこと、例外で `_disabled` に
なり警告1回で本体へ戻ること（Prefix と Postfix の両方）、設定が無効のとき Prefix は
常に本体を走らせ Postfix はフラグを書かないこと。

## 結果が変わらない理由

- 飛ばすのは「止まっている振動にもう1回止まっていろと送る」フレームだけです。
  モーターの状態は既に止まっているので、コントローラーの挙動は何も変わりません。
- シェイクが働いているフレーム、および最後にシェイクが消えた直後の1フレームは、
  本体とまったく同じ呼び出しが行われます。振動の強さ・タイミングは変わりません。
- 振動を直接書くのは `InputManager` だけです（逆コンパイル全体で確認）。
  他の MOD が `Gamepad.SetMotorSpeeds` を直接叩いて振動させている場合、本体は
  毎フレーム `(0, 0)` で上書きして消しますが、このパッチの待機状態ではそれを
  上書きしません。ゲーム本体の挙動には依存していないため、本体の動きとしては
  変わりません。この点は「外部の書き手」の前提としてコメントに書いてあります。

## 効果の見込み（推定）

コントローラーをつないだ環境で、毎フレーム1回の入力バックエンドへのネイティブ
呼び出し（`DualMotorRumbleCommand` のデバイスコマンド）が、待機中はなくなり
ます。バックエンドがドライバーへ振動の書き込みを流す実装ではその回数も減ります。
1回あたりは小さいですが、ホスト・参加者を問わず全員の毎フレーム経路なので、
待機状態のフレーム時間のごく一部を確実に減らします（推定: 数十µs/フレーム未満の
規模）。シェイクが連続する戦闘中は本体どおりに戻るため、効果は待機時に集中します。
