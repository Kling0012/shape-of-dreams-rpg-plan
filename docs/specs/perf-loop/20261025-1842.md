# perf-loop/20261025-1842

対象: `Dew.Core/Se_HeroKnockedOut.cs`（英雄の撃倒状態の処理）

## 直した内容

英雄が撃倒されると、`Se_HeroKnockedOut` はホストの毎ロジックtickで
`SetHealth(0.01f)` を呼んで体力を0.01に固定します。ところが本体の
`EntityStatus.LogicUpdate`（優先度 -300、効果のtickは優先度 -200 の次のバケツ）
は撃倒中も体力自然回復を整数チャンクで適用するため、チャンクが乗るtickでは
`_currentHealth`（Mirror の SyncVar、dirty bit 0x80）を1tickに2回書きます。
Mirror の送信はtickとtickの間に走るので、送られる値は常に固定後の 0.01f です。
つまり回復が乗る限り、参加者全員がすでに持っている 0.01f を、送信ごとに
繰り返し受けていました。tick内に味方の回復が乗ったときも、その回復は次の
固定で打ち消されるので、通信に残るのは同じ 0.01f だけです。

MOD 側に `NativeHeroKnockoutHealthIdlePerf`（NativePerfPatches.cs）を追加し、
効果の `ActiveLogicUpdate` への Harmony Prefix／Postfix で、条件がそろったときだけ
0x80 の dirty bit を下げます。設定での切り替えは DreamforgeConfig の
nativeHeroKnockoutHealthIdle（既定は有効）。dirty bit の定数は
`Network_currentHealth` セッターの IL から読み、Mirror内部の書き換えは
`syncVarDirtyBits` プロパティ経由にしたので、他の SyncVar や SyncList の bit は
触りません。`lastSyncTime` は送信の有無の判定のために読みますが、書きません。
パッチ先が見つからない・形が違うときは
警告1回でこの機能だけ外れます。

bit を下げてよい条件は4つです。

1. 参加者が 0.01f をすでに受け取ったあと。この「配達済み」の印は、効果のtick
   開始時に bit が立っておらず（＝それまでの立てが実際の送信で消えた）、かつ
   開始時の体力が固定値の 0.01f と一致する tick でのだけ付け直します。
   開始時の値こそ参加者が今持っている値なので、0.01f 以外の値（tick 順序の外で
   乗った回復など）が届いた直後は印が付かず、作成直後と同じく送るまで残します。
   途中参加の参加者の初期値はフルスナップショットから来るので、
   このパッチは関わりません。
2. 配達済みの印が新しい。Mirror の送信（ClearAllDirtyBits）は bit を消すと同時に
   NetworkBehaviour.lastSyncTime を進めるため、tick 開始時に bit が立っていても、
   lastSyncTime がこのパッチが前回のtickで見た値より進んでいれば「その送信の
   あとに乗った新しい書き込み」だと分かります（効果より前のバケツの回復チャンクや
   tickの間に乗った回復。送信は health の bit も一緒に消すため、後に残っている
   bit は必ずその送信より後の立てです）。その送信が参加者へ何を届けたかは
   分からないため印を落とし、そのtickは bit を下げず、次に開始時 bit が立って
   いない tick で印を付け直します。この判定がないと、tickの間に 0.01f 以外の
   値 X が届いた直後の回復チャンク（X+回復）で立った bit を古い印で下げて
   しまい、参加者は 0.01f へ戻る唯一の送信を失って撃倒が終わるまで X のままに
   なります。
3. 固定の書き戻しによる収束待ちの bit がない。Mirror の送信は syncInterval で
   間引かれるため、tick 開始時に bit が立っていても、それが前のtickの書き戻しで
   まだ送られていないとは限りません。Postfix が「開始時に立っていなかった bit が
   終了時に立っている」のを見たら、その効果に「収束待ち」の印を付け、以後は
   Prefix が bit の消失（＝実際の送信）を確認するまで bit を下げません。
   tick 順序の外で 0.01f 以外の値が参加者へ届いたあとの 0.01f へ戻る送信は
   この経路だけなので、間引かれた tick が連続しても本体どおり届きます。
4. 体力がまだ固定値の 0.01f と一致する。復帰・死亡・それ以外の意外な値の
   ときは、bit も値も本体が置いたままにします。

## 結果が変わらない理由

- このパッチはホスト側の値を1つも書き換えません。体力の計算、回復、
  死亡判定（自然回復がマイナスで0に達したときの `Kill()`）は、
  これまでどおり本体がそのまま計算します。変わるのは「すでに参加者全員が
  持っている値の再送」だけです。
- 送信はtickの間に走り、固定の書き込みが毎tickの最後なので、チャンクや
  tick内の回復がそのまま送られることは本体でもありません。したがって
  参加者が受け取る値の列は、条件1〜4を満たす送信を省いても1つも変わりません。
- 印の判定は、効果のtick開始時の bit と値を毎回読んでやり直します。
  送信が走ったこと（lastSyncTime の前進）も毎tick確かめるため、tickの間に
  0.01f 以外の値が届いても次のtickで印が外れます。予想と違う書き込みがあれば
  次のtickで条件が外れ、本体どおり送られます。
  設定を無効にしている間は何も観察しないため、印も捨てて、有効化し直した
  ときには最初の上げを送信の確認まで残します。
- 送らないことで `lastSyncTime` は進まないので、次に本当に変わった値は
  本体より早く遅れることなく届きます（間引きは送信を遅らせません）。

## 効果の見込み

撃倒中の英雄が体力自然回復を持っている間、ホストは送信のたびに
`currentHealth` の float（dirty mask 8バイト＋値4バイト）を全員へ送っていました。
回復量が大きいほどチャンクは毎tick乗るので、送信間隔ごとの無駄な送信になります。
効果量は状況推定です。撃倒は複数人プレイで定期的に起き、待機時間は
仲間が駆けつけるまでの数十秒に及ぶことがあります。回復を積んだ英雄ほど
効果が大きく、回復が0の英雄では何も変わりません（bit が立たないので
パッチは何もしません）。ホストの直前の軽量化と同じく、
「参加者の受信処理の回数を減らす」種類の削減です。
