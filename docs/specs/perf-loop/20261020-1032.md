対象は MOD `src/SodRpg.Mod/HostAuthority.EnemyOwnership.cs`（959行）である。まず参加者（ゲスト）側の経路の有無から確認した。担当制（敵の担当割り当て）はホストだけの機能で、ファイル内の入口はすべて `NetworkServer.active` の確認か `OwnershipRunning()` のガードで始まる。毎被弾ごとに走る `ApplyOwnershipReceivedDamage` も `Entity.ProcessReceivedDamage` の Postfix（`Patches.cs:168`）から呼ばれるが、最初の行でゲストを弾く。AI の `RetargetOwnership` や `SelectOwnershipAggro` に至るフック（`EnemyOwnershipNative.cs`）も同様である。つまり**このファイルにゲスト側で走る経路はない**。ゲストに関係する送信（`SendMonsterClassification`、`AssignDynamicEnemy`）は隣接ファイル（`HostAuthority.KillSync.cs`、`HostAuthority.DynamicDifficulty.cs`）にあり、送信自体は値が変わらないときに送らないよう既に絞られていた。そのため指示どおり観点 3・4（毎フレーム・毎被弾・定期掃除の経路の無駄）で見た。

見えた構造は次のとおりである。ホストの定期掃除 `ScanEnemyOwnership` は `ScanArea` 経由で 0.25 秒ごと（`CoopBalance.ScanSeconds = 0.25f`）に走り、担当を持つ敵1体ごとに（1）`RefreshSharedObjectiveOwnership`、（2）`ScanBossShares`、（3）再割り当ての確認、（4）体力の期待値の確認、を順に実行する。（4）の `ExpectedOwnershipHealth` は `OverrideOwnershipHealth` → `TryOwnership` を通る。`TryOwnership` は担当割り当ての成功条件を毎回そっくり確認し直す。具体的には、辞書の再検索、`OwnershipRunning()`（`DewPlayer.gamePlayers` の全列挙と接続確認、`GameManager`／`ZoneManager` の取得、`runId` の文字列確認）、`CoopOmens.IsSharedObjective`（`IsCoopOmenWard` の守護者枠の走査と `HumanOmenPlayers()` によるプレイヤー列挙）、`IsAnyBoss`、`OwnershipConnected` である。しかし同じ巡回路の中で、これらの答えは直前の処理がすでに確定させていた。走行状態は掃除の冒頭の `running` に、共有目標かどうかは同じ反復の先頭の `RefreshSharedObjectiveOwnership` が `state.SharedObjective` に書き込んだばかりであり、除外とボス判定は（3）のブロックが直後に扱い、担当者の接続は（3）でも確認済みである。つまり担当を持つ通常の敵1体ごとに、0.25 秒ごとに、答えが分かりきっている確認をもう1回払っていたことになる。

直した内容は、（4）の健康ブロックに確定済みの事実を使う速い経路を追加したことである。`ExpectedOwnershipHealth` に掃除開始時の `running` を引数で渡し、`running` かつ `Strength` の失敗フラグが立っておらず、`state.Enemy` が null でなく、辞書の現在の値がその `state` と同一で、`state` の除外・共有目標・担当者の各条件とボス判定・担当者の接続が `TryOwnership` の成功条件と厳密に同じになるときは、`OverrideOwnershipHealth` を経由せず `OwnershipEnemyPressure(state).HealthMultiplier` を直接返す。1つでも満たせない項目があれば、種となる初期値を保持したまま従来どおり `OverrideOwnershipHealth`（全確認つき）に落ちる。

結果が変わらない理由は次のとおりである。速い経路の条件式は `TryOwnership` の成功条件（`enemy != null`、辞書の存在、`!Excluded`、`!SharedObjective`、`Owner != null`、`OwnershipAvailable(Strength)`、`!IsSharedObjective`、`!IsAnyBoss`、`OwnershipConnected`）を1つ残らず並べ直したもので、評価の順序が違うだけで判定内容は同じである。`enemy != null` には `state.Enemy != null`（Unity の破棄済み判定を含む null 比較）が対応し、辞書の存在には `_enemyOwnership.TryGetValue(state.Enemy, out var liveState) && ReferenceEquals(liveState, state)` が対応する。辞書の確認を残すのは、同じ反復の（2）（3）や entity-removed フックが反復の途中で辞書からその敵を外したり別の state に差し替えたりする余地があるためで、その場合は従来と同じく全確認へ落ちる。`running` は掃除の冒頭で `OwnershipRunning()` を評価した値をそのまま使うが、掃除の1回の実行の中で走行状態を変える要素（設定の切替、サーバーの停止、ランやゾーンの遷移、プレイヤーの接続・切断）は動かない。`state.SharedObjective` については、同じ反復の先頭の `RefreshSharedObjectiveOwnership` が例外の有無に関わらず `CoopOmens.IsSharedObjective` の評価結果を書き込むことを確認した（`IsCoopOmenWard` は内部で例外を握り、`IsSharedObjective` 自体に投げる箇所がないため、書き込みより前の脱出はない）。掃除の途中で `ScanBossShares` や `ChangeOwnership` が走っても、速い経路は `state` の各フィールドと失敗フラグをその時点の値で読み直すので、事実が変わっていれば自然に従来の全確認へ落ちる。成功時の計算は `OverrideOwnershipHealth` の成功側の分岐（`(float)OwnershipEnemyPressure(state).HealthMultiplier`）と同一の式であり、浮動小数点の演算順序も変わらない。`ExpectedOwnershipHealth` の呼び出し箇所はこの健康ブロックの1箇所だけなので、ほかの経路への影響はない。

効果の見込み（推定）は、担当を持つ通常の敵1体ごと・0.25 秒ごとに、`OwnershipRunning()` のプレイヤー全列挙（1人あたり2回のリスト走査を含む）と `IsSharedObjective` の守護者枠・プレイヤー列挙が丸ごとなくなることである（辞書の検索は全確認との一致のために残す）。1回あたり百〜数百ナノ秒の見込みで、協力プレイで敵が多い部屋（Infinity の圧がかかる部屋で担当敵が100体を超えることもある）では掃除1回あたり数十マイクロ秒、毎秒では0.1〜0.3ミリ秒程度の推定である。効果は小さいが、戦闘が静かなときも含めて 4Hz で必ず走る経路の純粋な無駄であり、ホスト側の負荷（参加者全員の通信の元になるホストの刻み）を減らす。数値は推定で、実機での計測は行っていない。

見送った候補は次のとおりである。（1）被弾ごとの `ApplyOwnershipReceivedDamage` の担当外の分岐で、被害者が英雄でないときに計算して捨てられる `OwnershipSource` の祖先走査の省略。純粋関数なので安全だが、効果が数ナノ秒単位で小さすぎる。（2）`OwnershipRunning()` や `IsSharedObjective` のフレーム単位のキャッシュ。プレイヤーの切断は Mirror の通信処理と同じ枠で来るため、同じフレーム内でも値が変わる可能性を排除できず、同値性を証明できない。（3）担当敵の表示同期（`RefreshMonsterOwnership`、隣接ファイル）が掃除の各反復と同じ `TryOwnership` と `OwnershipProtected` をもう1回払っている重複。効果は今回の分より大きいが、直すには同期側ファイルの変更が必要で、対象ファイルの外に手が広がるため今回は見送った。（4）`ExpectedOwnershipHealth` の入力（道標・深層・無限の段階・所持ビルド・動的係数）のメモ化。入力の列挙に漏れがあると敵の体力が古い倍率のまま残るので、同値性を証明できない。
