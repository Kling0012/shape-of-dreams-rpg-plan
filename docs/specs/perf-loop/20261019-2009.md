# perf-loop/20261019-2009

## 対象

native Dew.Core/EntityControl.cs（向きの滑らかな追従 `DoRotateTowardsDesiredAngleTick`）。

## 直した内容

`EntityControl.DoRotateTowardsDesiredAngleTick(float)` に Prefix パッチ（`NativeEntityRotationIdlePerf`）を足し、向きが止まっているときはメソッド全体を飛ばすようにした。このメソッドは、自分で動きを計算しない実体（協力プレイの参加者なら、ホストが処理するモンスター・召喚体・ほかのプレイヤーの英雄のすべて）に対して描画フレームごとに呼ばれ、中身は `Mathf.SmoothDampAngle` の1ステップと `transform.rotation` への書き込みだけである。スキップの条件は「現在の向きと目標角度の差が0.05度未満」「ダンパーの内部速度が0.05未満」の2つで、どちらも呼び出しごとに読み直す。

設定は `nativeEntityRotationIdle`（既定有効）で切れる。パッチ先のメソッドや `_desiredAngleCv` フィールドが見つからないときは、その修正だけ外れて1回警告を出す。テスト側では、リンクされる `NativePerfPatches.cs` が参照する本体 API の受け口として、既存の境界ファイルに `EntityControl.transform` と `Quaternion.eulerAngles`（記録した角度をそのまま返す）の模倣を足した。この受け口と `_desiredAngleCv` は、Prefix の判定を直接動かす検証（`EntityRotationIdlePerfTests`）からも使う。

## 結果が変わらない理由

SmoothDampAngle の1ステップの動きは、現在との角度差と内部速度の両方に比例し、0.05〜0.1秒の smoothTime では係数が1以下に収まる。差と速度がどちらも0.05未満なら、本来書き込まれる回転は現在の回転から0.1度以内である（`EntityRotationIdlePerfTests` が本体と同じ式の模倣 SmoothDampAngle で、差・速度を0.007刻みに総当たりして確かめる）。厳密に言えば結果は同じではない: スキップが続く間、向きは目標との差が0.05度未満の位置で止まり、内部速度も止まった時点の値のまま残る。本来の処理はこの最後の0.05度未満を収束させていくが、見た目に残る差はこの0.05度未満に収まる。ダンパーの状態は動かさないので、次のフレームは同じ状態から同じ判定になる。差と速度は毎回読み直すので、目標が動けば、回転の即時指定（`RpcRotateImmediately`）やテレポートで差が開けば、次のフレームから本来の処理に戻って追従する。どちらかが NaN なら比較が成立せず本来の処理が走る（NaN からの回復も元のままである）。呼び出し側が渡すのは見た目向けの角度で、攻撃・移動・同期の判定は `desiredAngle` や速度を使っており、滑らかにした transform を判定に使う箇所はない（`OnStartClient` の初期角度の1回だけ）。書き込みを飛ばすことで、全実体が持つキネマティックな Rigidbody の transform 同期を汚さずに済む面もある。

## 効果の見込み（推定）

参加者の PC では、向きが止まっている実体1つごとに毎フレームの SmoothDampAngle の計算と `transform.rotation` へのネイティブ書き込みがなくなる。向きが止まっている実体は戦闘中でも常に一定数あり、60fps・80体が止まっている場面で毎秒約4800回の書き込み減（推定）。ホスト側でも、自分で処理する実体の向きが止まっている間に同じ効果がある。逆に動いている・回っている実体では、現在角度を読むネイティブ呼び出しが元の本体と合わせて2回になる（増分は小さい）。
