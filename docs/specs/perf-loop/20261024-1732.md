# perf-loop/20261024-1732

## 対象

`mod src/SodRpg.Mod/HostAuthority.SacrificeShield.cs`（と、そこから毎ホストティックで呼ばれる `src/SodRpg.Core/Game/Mechanisms/SacrificeShield.cs` の `SacrificeShieldRuntime`）。

## 直した内容

`UpdateSacrificeShields()` はホストの全ティックで走る（`HostAuthority.cs` の `_tickStages` の先頭）が、その中で毎ティック `_sacrificeShields.TakePendingForHostUpdate()` を呼んでいた。このメソッドは処理する授与が空のときでも、戻り値用の `List<SacrificeShieldAward>` を毎回新しく確保する。授与は犠牲（シールド発動の支払い）の直後にしか溜まらないので、ほとんどのティックでは空のリストを作っては捨てていた。

`SacrificeShieldRuntime.PendingCount`（既存プロパティ）で予約が 0 のティックは呼ばないようにガードを足した。対象ファイル内の変更のみで、ランタイム側の契約は変えていない。

## 参加者側の経路について

このファイルの参加者（ゲスト）側の経路は、ネイティブの自己犠牲 Dispatch を置き換える `DispatchPayment` だけで、ゲストでは `host` が null になるため数命令の検証のみで犠牲は発生頻度も低い。ゲスト側で省ける処理は見つからなかった。そのため毎フレーム経路の確保の無駄（探すもの 3）としてこの修正を行った。ホスト側の改善だが、ゲストには影響しない分類。

## 結果が変わらない理由

`TakePendingForHostUpdate()` は `_pending` キューを空にするまで取り出すので、`PendingCount == 0` のときの戻り値は必ず空で、foreach 本体は実行されない。ガードを入れても実行される処理は完全に同じ。予約が 1 件以上あるティックは以前と同一の経路を通る。

## 効果の見込み（推定）

空リスト 1 件と列挙子 1 件の確保を毎ホストティックから消す（推定: ティックレート 30 前後として毎秒 60 前後の小さな確保の削減）。GC 圧力の低減が目的で、体感できる変化を狙うものではない。
