# perf-loop/20261024-1421

対象: `src/SodRpg.Mod/HostAuthority.PilingLuckV129.cs`（Piling Luck の会心確定・会心確率の上乗せ）

## 直した内容

`PilingLuckForgetPooledCast`（本体 `AbilityInstance.OnDisable` の Harmony Prefix）は、
能力インスタンスがプールへ返されるたびに `PilingLuckGuarantees.Forget` で
`ConditionalWeakTable` からエントリを削除していました。この Prefix には
`NetworkServer.active` の条件がなく、協力プレイの参加者（ゲスト）側でも
全スキル・全攻撃インスタンスの返却ごとに表の参照（ハッシュ計算とバケット走査）が
走っていました。

一方、キャスト表 `Casts` への書き込み（`Capture`。`PilingLuckCaptureCast.Prefix` で
`NetworkServer.active` 条件付き）と読み取り（`TryRead`／`TryReadChance`。呼び出し元は
`BasicAttackContext.Prefix` と `TryWeakspotBasic` の `NetworkServer.active` 分岐の内側）は、
どちらもホスト側でしか起こりません。つまりゲスト側では表が常に空で、
`Forget` の削除は確実に何もしない操作です。

そこで Prefix の先頭に `if (!NetworkServer.active) return;` を足し、ゲスト側では
表の参照を丸ごと省くようにしました。ホスト側の後片付けは従来どおり行われます。

## 結果が変わらない理由

- `Casts` の読み書きはすべて `NetworkServer.active` 下でしか起こらないため、
  ゲスト側では表は常に空です。ゲスト側で `Forget` を呼ばなくても、
  表の内容と読み取りの結果は変わりません。
- ホスト側では条件が true のままなので、削除のタイミングも回数も従来どおりです。
- `NetworkServer.active` はセッションの間に true から false へ転じて、
  削除されないエントリが残っても誤読される経路はありません。読み取り側も
  `NetworkServer.active` 下でしか呼ばれず、セッションが変われば新しい
  AbilityInstance（新しいキー）を使うためです。表は弱参照テーブルなので、
  残ったエントリはキーの回収とともに消えます。

## 効果の見込み（推定）

ゲスト側で、戦闘中に走る全能力インスタンス（プレイヤーとモンスターの全スキル・
全攻撃、バフ系インスタンスを含む）のプール返却ごとに、Prefix 内の表参照
（メソッド呼び出し1回と `ConditionalWeakTable.Remove` のハッシュ計算・バケット走査。
推定数十ナノ秒）がなくなります。返却の頻度は波によって秒間数十〜数百回の
オーダーなので、毎秒数マイクロ秒程度の削減を見込みます（推定）。
Harmony の Prefix 呼び出し自体はゲスト側でも残ります。
