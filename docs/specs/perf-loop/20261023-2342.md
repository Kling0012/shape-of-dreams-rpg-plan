# perf-loop/20261023-2342

## 対象

mod src/SodRpg.Mod/HostAuthority.BossSeeker.cs（幻彩の追装＝Seeker ボス装備のホスト側処理）。

## 直した内容

ホストの毎フレーム処理 `TickSeekerBoss` が、状態が存在する間ずっと `BossFind` で `Build.BossMoves` の全走査を2か所で繰り返していたのをやめた。1つ目は「stage2 が装備から消えたら位相を0に戻す」ための走査で、2つ目は「分身のコピー元プロファイルがまだ装備にあるか」の確認である。どちらの結果も、`Build` のインスタンスが差し替わらない限り変わり得ない（`BossMoves` は `Build` の生成時に確定し、以後はどこからも変更されない）。そこで `SeekerState` に判定済みの `Build` 参照を覚え、`ReferenceEquals` で同じなら走査を飛ばし、差し替わった最初の1フレームだけ `BossFind` を行う。分身のほうは `SeekerDouble` の呼び出し元がどちらも現行 `Build` の `BossMoves` からプロファイルを見つけた直後なので、作成時点で存在判定が確定しており、その `Build` を記録して流用する。

## 結果が変わらない理由

`BossFind` の結果は `rt.Powers.Build.BossMoves` の内容と静的な `BossProfiles` だけで決まる。`BossMoves` への追加は `Build` の生成経路（`Build.Compute` 系と `Decode`）だけにあり、適用後の `Build` はどのメソッドも変更しない。`PowerRuntime.SetBuild` は参照の差し替えなので、装備の付け替えは必ず別インスタンスになり、`ReferenceEquals` の比較で見逃しようがない。位相の前進は `DispatchSeekerBoss` が毎回 `BossFind` を通して stage2 の在確認をしてから進めるため、stage2 のない `Build` のもとで位相が進むことはなく、「同じ `Build` で判定済みの不在」の間に位相を0へ戻し直す必要も生じない。分身の消去判定も同じで、`Build` が同じなら存在判定は作成時のまま正しく、差し替わった直後のフレームで再判定して消すか残すかを決める。見えるもの・判定・タイミングは元のままである。この処理はホストだけで走り、通信の量や回数は変わらない。

## 効果の見込み（推定）

`Build.BossMoves` は最大64件で、走査1回ごとに最大64回の文字列比較と `BossProfiles.TryGetMove` の辞書引きを行う。状態は Seeker 装備の初回 dispatch 以降ずっと残るので、以前は1フレームごとに最大2回の全走査が続いていた。60fps で走査1回を数百ナノ秒と見積もると、ホスト1人分で毎秒最大120回の全走査がなくなる（推定。1回は小さいが、常に走る経路の固定費である）。分身のほうは移動のたびに3秒・クールダウン5秒で張り付くことが多く、移動中は常時近い。参加者の PC には届かない処理だが、ホストのフレーム時間の裾を下げる。
