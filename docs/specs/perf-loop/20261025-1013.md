# perf-loop/20261025-1013

対象は本体 `Dew.Core/Monster.cs`（358行）である。実 DLL から ilspycmd で再取り出しし、空白正規化の差分で照合した。差分はバッキング識別子のエスケープ表記、`base.` 修飾の有無、switch 文と switch 式の書き方だけで、ロジックは同じである。

まず参加者側の経路を全部点検した。毎ティックの `AIUpdate` と `PoolAIUpdate` は、呼び出し元 `EntityAI.LogicUpdate`（`Dew.Core/EntityAI.cs:225`）が `!base.isServer` で即座に帰るのでホスト専用であり、参加者は走らせない。`GetStaggerSettings` は `Entity.OnStartServer`（`Dew.Core/Entity.cs:471`）でスポーン時に1回だけ呼ばれ、switch で静的な `StaggerSettings` を返すだけである。通信ごとに走る `SerializeSyncVars`／`DeserializeSyncVars` は Mirror の生成コードで、dirty bits を見てから書く形になっている。SyncVar の hook `OnPopulationChanged` は `isServer` で即座に帰る。スポーン時の `OnPrepare` もホストの生成フローからしか呼ばれない。この範囲で、参加者側の経路に省ける処理はなかった。

そこでホスト側のスポーン経路を見ると、`SelectAbilityPool` に1つ無駄があった。BossMonster のときだけ、本体はログ1件のために `string[7]` の配列を確保し、`String.Format` を2回呼び、`String.Join` で `hardVariantBossZoneIndices` を列挙し（`IEnumerable<int>` なので要素ごとに boxing する）、`String.Concat` でつなげてから `Debug.Log` に渡す。`Debug.Log` はスタックトレースの取得を伴う。ボスが出るたびにこの一式が走り、同一フレームにボスが複数湧くスポーンの集中では回数が重なる。

直した内容は、`Monster.SelectAbilityPool` への Transpiler パッチである（`NativeMonsterBossPoolLogPerf`）。本体の命令列は `ldarg.0 / isinst BossMonster / brfalse <ログの直後>` の分岐の中にログ全体を抱えているので、この `isinst` を `ldc.i4.0` に置き換えて分岐を常に通す。命令は削らないので分岐先は動かず、`AssignTriggerInstancesToCurrentPool` は従来どおり呼ばれ、ログの文字列は組み立たなくなる。パッチは `NativePerfOptions.BossPoolSpawnLog`（`DreamforgeConfig.nativeBossPoolSpawnLog`、既定は有効）で切れる。失敗時の扱いは、`Debug.Log(object)` と直前の `String.Concat(string[])` が1件ずつ無い、`isinst BossMonster` と `brfalse` の形が違う、`brfalse` の飛び先がログの直後でない、ログの中に外から飛び込むラベルや外を指す分岐がある、のどれかに当たったときは命令を1つも変えずに警告を1回出して帰る。この形状検証と置き換えは、実 IL の形を写した `CodeInstruction` 列で直接動かして確かめた（正常形で `isinst` が `ldc.i4.0` になり、分岐先が保たれ、分岐後の処理に届くこと、形が違う5種では何も変わらないこと、設定を切ったときに変わらないこと）。

結果が変わらない理由は次のとおりである。変えるのは BossMonster かどうかの判定結果だけで、プールの選択（hard variant の判定と `Mathf.Min` による `currentPoolIndex` の決定）はログより前にあり変更しない。非ボスは元々ログを通らないので動作は同じままである。削るのは観測用の出力だけで、ゲーム内の状態・判定・同期・見た目には何も触れない。発動側のホスト・受信側の参加者とも、処理の順序とタイミングは変わらない。

効果の見込み（推定）は、ボスのスポーン1件ごとに、`string[7]` と boxing 2件、`String.Join` の要素ごとの boxing と連結文字列群の確保、そしてスタックトレース取得を伴う `Debug.Log` 呼び出しがなくなることである。ボスが多数湧く無限モードのスポーンの集中で、スポーン処理に乗る遅れを減らす。ログはホストだけで出るものなので、参加者の受信処理には影響しない。数値は推定で、実機での計測は行っていない。
