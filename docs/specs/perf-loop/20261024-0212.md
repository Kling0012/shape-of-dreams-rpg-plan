# perf-loop/20261024-0212

対象は `src/SodRpg.Mod/HostAuthority.BossAzurak.cs` である。`DispatchAzurakBoss` の冒頭にイベント種の絞り込みを足し、Azurak のどの区分も購読しないイベント（`NativeDamageDealt`、`ModeTransition` など）では `BossMoves` の全走査を纏めて省くようにした。最終の実装では、`BossProfiles.Moves` の Azurak 区分の全 Action の Event と `MainHit` から起動時に1回だけ求めた静的な `bool[]`（`AzurakEventGate`）を使う。既存の早期 return の後に `if (!AzurakEventGate[(int)kind]) return;` で判定する。以下の「無駄のしくみ」から検証結果までの段落は、手書きの4種で絞り込んだ初版の記録である。レジストリ起点への切り替えとテストは末尾の2段落に記す。

無駄のしくみは次のとおりである。`DispatchAzurakBoss` はボス装備のイベント1件ごとに呼ばれ、最後の for ループで `rt.Powers.Build.BossMoves` を先頭から走査する。Azurak の区分（武器・防具・装飾・頭・手・足と3つのセット段階）が `Actions[0]` で購読するイベントは、`MainHit`・`NativeDamageTaken`・`MemoryUse`・`MovementCompleted` の4種だけである。それ以外の種で呼ばれても、各エントリは `SetId` 一致 → `BossProfiles.TryGetMove`（文字列キーの辞書引き）→ 段階プロファイルの除外 → `action.Event != kind` で continue し、1行も実行するものがない。代表が `NativeDamageDealt` で、主人公が与えるダメージ1件（基本攻撃・スキル・発火など、活性IDごとに1回）で毎回この全走査と `agentPosition` の読み取りだけをして終わっていた。

結果が変わらない理由は次のとおりである。`BossProfiles.Moves` は起動時に確定する静的な辞書で、実行時の追加はなく、`AzurakSetId` のエントリが解決され得るプロファイルは `CreateAzurakMoves()` の9つに限る。装備の解決側（`Build.cs` と `BossBuildCodec`）も `TryGetMove` で検証するので、レジストリ外のプロファイルが `BossMoves` に入ることはない。よって4種以外のイベントでは、変更前からループが何もしないことが確定しており、省いても何も変わらない。4種のイベントでは条件がすべて真になり、既存の処理は1行も変わらない。`agentPosition` の読み取りを4種以外で省いてよいのは、その値を MainHit 判定と no-op のループが変更前から使っていなかったからである。

効果の見込みは推定だが、Azurak を装備した主人公が戦闘中にダメージを与えるたびに走っていた全走査（6件装備なら最大9エントリ、各エントリは `SetId` の比較、最長19文字の文字列ハッシュと辞書引き、最大3回の文字列比較）を、列挙型の整数比較1回で省く。ホスト側の削減であり、この変更は送信を出さないので、参加者の受信処理と通信量は変わらない。

このファイルの参加者側の経路は `PublishBossVisual` 経路のみである。印表示（`AzurakPublishHits`）は呼び出しごとにヒット数の増減か削除で内容が必ず変わるため、Nyx で直したような無変化の再送にはなっておらず、間引きの余地はなかった。MainHit ごとの `BossFind` による stage2 の全走査は Primus（#1068）と同種の装備確定時キャッシュで省けるが、Azurak は stage2 を持たない2件装備など状態が作られない構成があるため、Polaris（#1070）形式の状態の導入が必要で、1回の変更として大きいので見送った（次回以降の候補）。`TickAzurakBurrow` の毎ティック走査は、潜行が無い間はリストの `Clear` だけで実質 no-op のため見送った。

検証は `python3 tools/balance/gen_cs.py --check`（通過）、`dotnet build src/SodRpg.Mod -c Release -p:GameDir="$HOME/dev/sod-gamedata/Shape of Dreams" -p:ModDeployDir=/tmp/perfloop-x`（0エラー、警告6件は既存のもの）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release`（728件通過）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Mod.Startup.Tests -c Release`（237件通過、1件スキップは既存のもの）を行った。実機（ゲーム内）での確認は未実行（この環境ではゲームを動かせないため）。

レビュー（PR #1078 の F1・F2）を受けて、絞り込みを手書きの列挙からレジストリ起点に切り替え、性質をテストで確かめた。`DispatchAzurakBoss` の絞り込みは、`BossProfiles.Moves` の Azurak 区分（`CreateAzurakMoves()` の出力）の全 Action（`Actions[1]` 以降を含む）の Event から起動時に1回だけ求めた静的なフラグ（`AzurakEventGate`、`bool[]` の添字参照）に変えた。区分に Action を足したりイベントを変えたりすると自動的にフラグに反映されるため、購読しているイベントがこの早期 return で黙って落ちることがなくなる。`MainHit` は `Actions` とは別に stage2 の命中カウンター分岐が直に鍵として使うため常に含める。`BossBuildCodec.Validate` が entry と profile の `SetId` の一致を強制するため、走査が dispatch に使うプロファイルは `SetId` が AzurakSetId のものに限り、フラグの元と一致する。

テスト（`tests/Issue73.Native.Tests/AzurakEventGateTests.cs`、抽出は `NativePersistence.targets` の `CompileAzurakEventGate`）は、生成の実ソース（`BuildAzurakEventGate` と `AzurakEventGate`）を抽出して、(1) フラグがレジストリの Azurak 区分の全 Action の購読イベントと `MainHit` に過不足なく一致すること、(2) `CreateAzurakMoves()` の全プロファイルについても同じこと（Azurak の区分を `CreateAzurakMoves()` 以外から登録すると名前の集合の比較で失敗する）、(3) Azurak が購読しない種（被害ごとに飛ぶ `NativeDamageDealt`・`ModeTransition`・`RewardInstance`）はフラグが通さず、走査ごと省かれたままであること、を確かめる。追加後の `DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release` は731件通過（既存の728件に今回の3件を加えたもの）。
