# perf-loop/20261025-0202

## 対象

`src/SodRpg.Mod/ClientSession.PressureDividend.cs`（MOD 側。夢の圧の配当（未確保の欠片）の受領通知を参加者が受け取り、保留しておいた分を精算するファイル）。

参加者側の経路を2つ確かめた。1つは受信処理 `OnPressureDividend`（ホストからの受領通知ごと。対象の英雄・実行中の遠征・プロトコル・欠片数を確かめてから `PendingPressureDividends.AddAuthenticated` で重複を除いて保留に置く）、もう1つは精算 `FlushPendingPressureDividends`（毎フレームの `TickRunChoices` → `FlushPendingRunRewards` から呼ばれる）。精算は最初の `Count == 0` で抜けるので、保留が無いときのコストは `Queue.Count` の1読みだけで、通知用のデリゲートもすでにキャッシュしてある。受信側の検査は安く（`Protocol.WarnMismatch` の警告は HashSet で1回限定）、精算が通ると `Rules.ApplyPressureDividend`（`GameEvent` の生成は通知そのものなので固有のコスト）から `Emit` へ進む。呼び出し先も確認した。`PendingPressureDividends` の `AddAuthenticated`・`Drain` は受領と精算のたび、`RetireBeforeGraph` は `ClientSession.KillSync.cs` の tick から graph 変更の1回物で呼ばれる。

## 直した内容

精算時の通知デリゲート `e => Emit(new[] { e })` を、メソッドグループ `Emit` を直接割り当てる形に替えた。旧実装は精算1件ごとに `GameEvent[1]` を確保し、`Emit(IEnumerable<GameEvent>)` の foreach を1段余計に通っていた。単体の `Emit(GameEvent)` が public にあるので、デリゲートをそのメソッドに結び付ければ配列の確保と foreach が消える。

## 結果が変わらない理由

`Drain` は `result != null` を確かめてから notify を呼ぶので、渡されるのは null でない `GameEvent` 1件である。旧実装はそれを1要素の配列に包んで `Emit(IEnumerable<GameEvent>)` の foreach で `Emit(GameEvent)` へ渡すだけで、`Emit(GameEvent)` の中身（`_dirty` の設定、Drop の自動分解候補への追加、Delved・LevelUp・Fused の `MarkDirty`、`_notify` への伝播、`AdditionalEvents` の再帰）は同じ順で同じ回数走る。新しい割り当ても同じ `Emit(GameEvent)` に結び付く。`GameEvent` は `IEnumerable<GameEvent>` を実装しないため、オーバーロードの解決が曖昧になることはない。デリゲートの生成が初回の1回であることも変わらず、`Drain` の呼び出しと `DeferKillSave` の条件は触っていない。

## 効果の見込み（推定）

精算1件（参加者の英雄がとどめを刺した追跡対象の撃破ごとに届く受領がたまった分）ごとに、32バイト程度の配列確保1回と foreach 1段が消える。夢の圧が効いている戦闘で撃破が続き受領が連なる間、参加者側の GC への細かな圧力がその分減る（実測はしていない推定）。

## 見送った候補

- `AddAuthenticated` の受領ごとの `"n:"+nonce`・`"d:"+key` の文字列連結（2件の確保）。受領は撃破1件ごとで、精算本体の `GameEvent` 生成や辞書操作に比べて小さい。
- `OnPressureDividend` の受領ごとの `hero.netId.ToString(...)`（1件の確保）。キャッシュには接続ごとの無効化が必要で、頻度に対して効果が見合わない。
- 毎フレームの `FlushPendingPressureDividends` の見直し。最初の `Count == 0` で抜け、保留があるときも文字列比較と `Peek` だけで確保がない。以前の回で整理済みである。
