# perf-loop/20261018-2311

対象: mod src/SodRpg.Mod/CoopOmens.cs（と、そこからティックごと・通信ごとに呼ばれる経路）。

直した内容: ホストのティックは `TickRoomOmens`（0.25秒間引き、HostAuthority.RoomOmens.cs:69）から `TickCoopOmen` を呼ぶ。共鳴の盾の部屋では、その末尾の `Time.unscaledTime >= _nextCoopSync`（1秒）の条件が、盾がすべて倒れて枠が retire した後も部屋が終わるまで毎秒 `SendRoomOmen` を送り続けていた。この1通ごとに `DreamforgeRoomOmenMsg` を新規に確保し、ホスト自身のクライアント状態（`ClientSession.SetHostCoopOmen`）を更新し、`Actor.CustomRpc_SendMessageToClient` で参加者それぞれへ送信する。しかし盾が残っていない間のメッセージの内容（omen・runId・room・zone・node と空の盾欄）は、以後二度と変わらない。また人間が1人に減ったときの枝（`HumanOmenPlayers() < 2`）は、完了条件を持たないため `ClearCoopOmen` と `SendRoomOmen` をティックごとに繰り返していた。前者は Ward ループの中で「生きた盾が1つでもある」を追跡する `anyWardLive` を送信条件に加え、後者は `_coopWardLimit > 0` のときだけ解除・送信するようにした。`ClearCoopOmen` は `_coopWardLimit` を0に戻す。共鳴の盾の部屋は `RoomOmens.RollCoop` が人間2人以上のときしか引かれないため、`BeginCoopOmen` は `_coopWardLimit` を必ず2以上に初期化し、`_coopWardLimit` が0で始まる部屋はない。したがって `_coopWardLimit > 0` のガードは、人間が1人になった枝の解除・送信を各部屋でちょうど1回に限る。部屋の中で `_coopWardLimit` が0のままこの枝に来るのは、既に同じ枝で解除・送信が1回済んでいるときだけである（`ClearRoomOmen` と `DisableCoopWards` 経由の解除は `CoopWardRoomActive` を偽にするため、この枝には到達しない）。

結果が変わらない理由: 受け側の `ReceiveCoopOmen`（ClientSession.RoomOmens.cs:84）は盾のスナップショットを受け取ってから4秒で失効させ、`CoopWardId` は失効後は0を返す。盾が残っていない間のメッセージの盾欄は最初からすべて0で、失効しても `CoopWardId` と `CoopResonanceRemaining` の値は変わらない。つまり生きた盾がない間の再送は、受け側のどの状態も動かしていなかった。生きた盾がある間は、共鳴の残り秒の更新とスナップショットの維持に毎秒の送信が要るため、今までどおり送る。内容が変わったときの `_coopSyncDirty` による送信もそのまま残してあり、減るのは同じ内容の再送だけである。人間が1人になった枝でも、最初の1通で盾欄が空になり、以後の内容は変わらない。部屋や遠征の移り変わりは `RefreshRoomOmen` が独自に publish・送信する経路があり、途中参加の相手には Hello の `SendRoomOmenPeer`（HostAuthority.Hello.cs:172）が個別に送るため、この間引きの影響を受けない。

効果の見込み（推定）: 盾の部屋で最後の盾が倒れてから部屋が終わるまで、参加者1人あたり毎秒1通のメッセージ確保と Mirror の書き込み・配送がなくなる（推定。部屋の残り時間は盾を倒す順番による）。人間が1人に減った部屋では毎秒4通が最初の1通だけになる（推定。ティックが0.25秒間引きのため）。通常の部屋（共鳴の盾でない部屋）の経路は最初の分岐で変わらず、処理はほとんど変わらない。
