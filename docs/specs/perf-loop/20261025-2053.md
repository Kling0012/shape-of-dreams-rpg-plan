# perf-loop/20261025-2053

## 対象

`src/SodRpg.Mod/HostAuthority.DirectedRecharge.cs`（機構の冷却短縮の振り分け）。ファイル内に参加者（ゲスト）側の経路はない（全経路が最初に `NetworkServer.active` を見る）。そのためゲストではなく、被弾・撃破・使用ごとの経路の無駄（探すものの3）を減らした。

## 直した内容

`DispatchDirectedRechargeEvent` が通知の種類に関係なく毎回 `HasOwnSummons` を呼んでいたのを、基本攻撃発火（`OwnedBasicAttackFired` かつ `MainBasicAttack`）の通知のときだけに絞った。`HasOwnSummons` は英雄の召喚一覧を走査し、各召喚で祖先チェーンの照合（`FindFirstAncestorOfType`）まで行う。

絞り込みの判定は `MemoryActivationEvent.IsMainBasicAttackFired` にまとめた。`ResolveEventSource` の `St_D_CircleOfLife` 特例（`Admits` と `DirectedRechargeRequest.RequiresOwnedSummon` を含む）も同じ定義を使い、条件が各自に書き写されないようにしている。

## 結果が変わらない理由

召喚の有無（`summons`）の唯一の消費先は `MechanismEquipment.ResolveEventSource` で、そこが `hasOwnedSummon` を読むのは `St_D_CircleOfLife` 特例（基本攻撃発火の通知）のときだけ。それ以外の通知（被弾・クリティカル・撃破・使用・召喚攻撃）では `Admits` の条件により発火元が必ず名前付き記憶になり、`summons` の値は戻り値に影響しない。`DirectedRechargeRuntime.Notify` 内でも `HasOwnedSummon` は `ResolveEventSource` への受け渡しにしか使われず、チャネルの条件判定には使われない。乱数（`roll`）を引く回数も変わらない。

`tests/SodRpg.Core.Tests` の DirectedRecharge 系に回帰テストを足した。1) 召喚がいる構成で、被弾（`Hit`・`CriticalHit`）・撃破（`Kill`）・使用（`ConfirmedUse`）・召喚攻撃（`SummonAttack`）の通知では `summons` の真偽に関係なく同じ発火元と同じ要求が出ること。2) 基本攻撃発火（`MainBasicAttack`）の `St_D_CircleOfLife` 特例では、従来どおり召喚がいるときに `St_D_CircleOfLife` が発火元になること（召喚がいなければ発火元なし）。

## 効果の見込み（推定）

召喚を伴う構成（特に召喚体が多い場合）で、被弾・撃破・使用ごとに走っていた召喚一覧の走査（召喚体ごとの祖先チェーン照合を含む）が消える。通知は戦闘中、攻撃・被弾・撃破のたびに届くため、召喚体の数が多いほど削減量が増える。基本攻撃発火の通知では従来どおり計算する。
