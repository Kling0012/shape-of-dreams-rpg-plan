# perf-loop/20261018-1841

対象: native Dew.Core/CastIndicatorManager.cs（と、そこから毎フレーム呼ばれる経路）。

直した内容: 照準インジケーターの円（`DTT.AreaOfEffectRegions.CircleRegion.UpdateProperties`）は、`CastIndicatorManager` の描画メソッドと領域自身の `Update` の両方から毎フレーム呼ばれ、子トランスフォームのスケール・オフセットとマテリアル float を `Radius`・`Offset`・`FillProgress` から毎回書き直している。`NativePerfPatches.cs` に Prefix/Postfix を追加し、この3入力とレンダラーのマテリアル実体が前回から変わっていないときは本体の再書き込みを省く。MOD設定 `nativeCastIndicatorCircle`（既定は有効）で切り替えられる。本体側の IL 形状を `Prepare` で検証し、形が違えば警告1回だけでパッチを入れない。検証は2段で、(1) `get_Radius` 1回・`get_Offset` 2回・`Material.SetFloat` 1回・`_fillProgress` 読み出し 1回の回数、(2) 本体が参照するメンバー一式（`ExpectedMembers`。実DLLから採取した21件。call と callvirt は同じ呼び出しとして扱う）の照合である。回数だけでは、将来の更新で追跡していない入力が紛れ込んでも回数が同じなら受理されてしまうため、一式の照合で拾う。前回値の確定は Postfix で行う（Harmony は本体が例外で中断したとき Postfix を実行しないため、書きかけの入力が「反映済み」と記録されない）。確定候補（`CircleInputs`）は Prefix がスレッド静的な pool 欄から取り出して `__state` に載せ、Postfix が確定後に返却して使い回す。本体が例外で中断したフレームは Postfix が走らないため、例外経路でも Harmony が実行する Finalizer が候補を pool 欄へ返す（void 返しなので本体の例外はそのまま伝わり、飲み込まない）。例外が連続するフレームでも毎フレームの新規確保は起きない。Prefix が本体を通す全経路（入力の変化・null マテリアル・設定無効）では、通す前に前回の確定値を無効化する。無効化は `ConditionalWeakTable.TryGetValue` と既存レコードへのフラグ書き込みで行い、新規確保は増えない。Prefix は fill を `FillProgress` プロパティでなく本体と同じ `_fillProgress` フィールドから直接読む（逆コンパイルで getter が `ldfld _fillProgress; ret` の純粋パススルーであることも確認済み。読み取り経路を本体と同一にしたためこの事実には依存しない）。`SodRpg.Mod.csproj` は `DTT.AreaOfEffectRegions.Runtime` を参照に追加した。型名は完全修飾で書き、テストの抽出生成物（`NativePersistence.targets` が using 行ごと持ち込む）が DTT 参照のないテストプロジェクトで壊れないようにした。スキップ判定は DTT に依存しない純粋関数 `ShouldSkip` として切り出し、`Offset` は成分ごとの厳密な float 比較に揃えた（`Radius`・`Fill` と同じ。Unity の `Vector2==` が持つ約1e-5 の許容は使わない）。

結果が変わらない理由: このメソッドは入力から出力を決める書き直しで、入力が同じなら既に書き込んであるのと同じ値をもう一度格納するだけである。書き込み先の子トランスフォーム `_circle` とマテリアルの `_FillProgress` を書くのはこのメソッドだけで、射程超出時の縮小アニメ（DOTween）が動かすのは領域ルート側のトランスフォームである。円の位置追従（`playerOrigin` への書き込みと対象の位置の指定）はこのメソッドの外にあり、毎フレームそのまま動く。マテリアルは `CastIndicatorManager.Awake` がレンダラーごとに実体化したもので、実体が差し替えられた場合は比較で検知して必ず再実行する。入力が変化したフレームは必ず通るため、1フレームの遅れも生じない。本体が途中で例外を投げた場合も動きは変わらない: Prefix は本体を通すときに前回の確定値を無効化し、Harmony は例外時に Postfix を実行しないため確定し直されない。よって例外で書きかけに終わったフレームのあと、入力が前回の確定値へ戻っても省かずに本体を再実行し、パッチなしと同じ書き直しが起きる。null マテリアルで本体へ回すフレームと、設定を無効にしている間も同じ扱いで、確定値を捨てながら本体だけを通す（再び有効にしたフレームが古い確定値と同じ入力でも省かない）。fill の読み取りは本体と同じ `_fillProgress` フィールドへの直接参照で行うため、`FillProgress` プロパティの実装が将来変わっても判定と本体の読む値がずれない。ゲーム内でこの領域クラスを使うのは `CastIndicatorManager` だけである（逆コンパイル全体を検索して確認）。

効果の見込み（推定）: 照準円が表示されている間、円1つあたり毎フレーム2回の `UpdateProperties`（ローカルスケールとローカル位置の読み書き、`sharedMaterial` の取得と `SetFloat`、合わせて5回ほどのネイティブ呼び出し）を、半径・進行度が動かないフレームは省く。対象指定の照準では二重円で2つ、射程はめったにフレーム間で変わらないため、照準中のほぼ全フレームで省ける推定である。判定・数値・通信には関わりがない。
