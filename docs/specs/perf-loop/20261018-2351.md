# perf-loop/20261018-2351

対象: native Dew.Core/CursorManager.cs（と、そこから毎フレーム・毎ロジックTick呼ばれる経路）。

直した内容: `FrameUpdate` は毎フレーム `ApplyCursor` を呼ぶ。ソフトウェアカーソルが無効な間（プラットフォーム設定 `DewSave.platformSettings.gameplay.disableSoftwareCursor`、または CinematicCameraHelper の切り替えによる `disableSoftwareCursor`）、`ApplyCursor` は呼ばれるたびに `Cursor.SetCursor(null, Vector2.zero, CursorMode.Auto)` を実行して既定のOSカーソルへ戻す（CursorManager.cs:64-68）。この要求は前のフレームと同じであり、値は1度も変わらない。NativeCursorIdlePerf を追加し、`ApplyCursor` の Prefix で無効状態の繰り返しを検知して本体の呼び出しを省く。最初の1回と、有効経路を通ったあとの最初の無効呼び出しは本体をそのまま実行して反映する。Postfix は本体が完走したときだけ「適用済み」を確定する。MOD設定は `nativeCursorIdle`（既定で有効）。

結果が変わらない理由: `Cursor.SetCursor` を呼ぶのは逆コンパイル全体で CursorManager だけで、ほかにカーソル画像を変える経路はない。Unity は要求を誰かが変えるまで保持し、シーンの読み込みでも `Cursor.lockState` / `Cursor.visible` の書き換えでもカーソル画像は戻らないため、同じ要求の繰り返しは観察され得ない。無効の1回目は本体が実行されて要求が反映され、以後の省略は同じ状態を保つだけである。有効経路の呼び出しのたびに印を落とすため、無効→有効→無効と戻したときも、無効の最初のフレームで本体が再び実行され、パッチなしの動作と同じ順で同じ要求が出る。本体が例外で中断した場合と、ほかのMODの Prefix に差し替えられた場合（`__runOriginal` が false）は印を確定しないため、次のフレームは本体へ戻り、パッチなしの毎フレーム再試行と同じ動作になる。設定を切れば以後の呼び出しはすべて本体へ流れる。

効果の見込み（推定）: ソフトウェアカーソル無効中の全利用者で、毎描画フレーム1回のネイティブ呼び出し（推定0.5〜2マイクロ秒/回、60fpsで推定30〜120マイクロ秒/秒）が消える。有効な通常のPC環境ではPrefixの読み取り数回が増えるだけで、結果と負荷はほとんど変わらない。ゲーム内の数値・判定・見た目には影響しない。

見送った候補: `LogicUpdate`（30Hz）が毎Tick `Cursor.lockState` へ同じ値を書き込んでいる箇所。WindowsのConfinedでは毎回ClipCursor相当の処理が走る可能性があり、全利用者で無駄になるが、OS側の状態がズレたとき（ alt-tab で拘束が外れた直後など）に毎Tickの再設定が実質の再適用として働いている可能性を排除できない。Unity内部の早期リターンの有無をこの環境では確かめられず、結果が変わらないと証明できないため触らない。

修正ラウンド（レビュー所指摘、2026-10-19）: 2点を直した。1つ目は、Prefix の判定と本体 ApplyCursor の早期リターン条件の一致を、実行時にも確かける仕組みを足した。出荷時の Dew.Core.dll（2026-10-19 に ilspycmd で確認）の無効分岐は、ガードが ldarg / ldfld CursorManager::disableSoftwareCursor / brtrue / ldsfld DewSave::platformSettings / ldfld gameplay / ldfld disableSoftwareCursor / brfalse の順で2つの入力を読み、リセットが ldnull / Vector2::get_zero / ldc.i4.0（CursorMode.Auto）/ Cursor::SetCursor / ret だけである。NativeCursorIdlePerf に ValidateBody を追加し、Prepare でこの命令並びと両分岐の飛び先を照合する。形が違えば（引数 index への分岐が増える、読み出しが1つ欠ける、順が入れ替わる、無効分岐にほかの書き込みが増える）警告1回でパッチを入れず、本体の毎フレーム再試行のままにする。2つ目は、設定 `nativeCursorIdle` が無効の呼び出しでも印 `_defaultCursorApplied` を解除するようにした。従来は無効の呼び出しを印を残したまま本体へ流していたため、無効の間に本体が有効経路でカーソル画像を設定しても印が true のまま残り、再有効化後の最初の無効呼び出しが印で省かれて `SetCursor(null)` が発行されない状態が起きた。解除は Prefix の早期 return の前で行えば足りる。CursorManager.ApplyCursor はカーソル画像を変える唯一の経路で、その呼び出しはすべてこの Prefix を通るため、設定の再適用時に別途キャッシュを無効化する処理は要らない。あわせて Issue73.Native.Tests に検証を9件足した。ValidateBody には、本体 ApplyCursor の無効分岐と同じ命令並びに書いた見本（CursorIlShapes）を PatchProcessor.GetOriginalInstructions で読んで渡し、前述の4種の変わった形を拒否することを確かめる。Prefix/Postfix は実ソースから抽出したものをそのまま使い、無効状態で続けて呼ぶと本体が1回だけ動くこと、有効状態を1回はさむと次の無効呼び出しで本体が再び動くこと、`__runOriginal=false` と Postfix が走らない例外フレームでは印が立たないこと、設定を無効にした間に本体がカーソル画像を設定してから再有効化する遷移で最初の無効呼び出しが必ず本体へ戻ること（起動不要の再現）を確かめる。検証: `DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release` 343件（従来334件＋追加9件）合格、mod の Release ビルドを通した（警告は既存の6件）。Startup.Tests はこの変更で触ったファイルをコンパイルしないため未実行。実機での動作は引き続き未実行。
