# perf-loop/20261018-2351

対象: native Dew.Core/CursorManager.cs（と、そこから毎フレーム・毎ロジックTick呼ばれる経路）。

直した内容: `FrameUpdate` は毎フレーム `ApplyCursor` を呼ぶ。ソフトウェアカーソルが無効な間（プラットフォーム設定 `DewSave.platformSettings.gameplay.disableSoftwareCursor`、または CinematicCameraHelper の切り替えによる `disableSoftwareCursor`）、`ApplyCursor` は呼ばれるたびに `Cursor.SetCursor(null, Vector2.zero, CursorMode.Auto)` を実行して既定のOSカーソルへ戻す（CursorManager.cs:64-68）。この要求は前のフレームと同じであり、値は1度も変わらない。NativeCursorIdlePerf を追加し、`ApplyCursor` の Prefix で無効状態の繰り返しを検知して本体の呼び出しを省く。最初の1回と、有効経路を通ったあとの最初の無効呼び出しは本体をそのまま実行して反映する。Postfix は本体が完走したときだけ「適用済み」を確定する。MOD設定は `nativeCursorIdle`（既定で有効）。

結果が変わらない理由: `Cursor.SetCursor` を呼ぶのは逆コンパイル全体で CursorManager だけで、ほかにカーソル画像を変える経路はない。Unity は要求を誰かが変えるまで保持し、シーンの読み込みでも `Cursor.lockState` / `Cursor.visible` の書き換えでもカーソル画像は戻らないため、同じ要求の繰り返しは観察され得ない。無効の1回目は本体が実行されて要求が反映され、以後の省略は同じ状態を保つだけである。有効経路の呼び出しのたびに印を落とすため、無効→有効→無効と戻したときも、無効の最初のフレームで本体が再び実行され、パッチなしの動作と同じ順で同じ要求が出る。本体が例外で中断した場合と、ほかのMODの Prefix に差し替えられた場合（`__runOriginal` が false）は印を確定しないため、次のフレームは本体へ戻り、パッチなしの毎フレーム再試行と同じ動作になる。設定を切れば以後の呼び出しはすべて本体へ流れる。

効果の見込み（推定）: ソフトウェアカーソル無効中の全利用者で、毎描画フレーム1回のネイティブ呼び出し（推定0.5〜2マイクロ秒/回、60fpsで推定30〜120マイクロ秒/秒）が消える。有効な通常のPC環境ではPrefixの読み取り数回が増えるだけで、結果と負荷はほとんど変わらない。ゲーム内の数値・判定・見た目には影響しない。

見送った候補: `LogicUpdate`（30Hz）が毎Tick `Cursor.lockState` へ同じ値を書き込んでいる箇所。WindowsのConfinedでは毎回ClipCursor相当の処理が走る可能性があり、全利用者で無駄になるが、OS側の状態がズレたとき（ alt-tab で拘束が外れた直後など）に毎Tickの再設定が実質の再適用として働いている可能性を排除できない。Unity内部の早期リターンの有無をこの環境では確かめられず、結果が変わらないと証明できないため触らない。
