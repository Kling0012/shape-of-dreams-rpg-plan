# perf-loop/20261018-2027

対象: mod src/SodRpg.Mod/ClientSession.RunReplay.cs（と、そこから毎フレーム呼ばれる経路）。

直した内容: `ClientSession.Tick` → `TickRunChoices`（ClientSession.RunChoices.cs:195）→ `PublishCurrentRunChoices` はホストで毎フレーム走り、末尾で `PublishRunChoiceHistory` を呼ぶ。この中の `PublishChoiceHistoryTo`（ClientSession.RunReplay.cs:117）は `DewPlayer.gamePlayers` と `lobbyPlayers` を渡り歩いて相手側の遊び手ごとの送信状態を作るが、ホスト自身の遊び手（`DewPlayer.local`）も例外なく対象にしていた。この相手には参加時の最新枠、確定での追いかけ送信、30秒ごとの全履歴の再送と、ほかの相手と同じだけの送信が行われる。それぞれ `Actor.CustomRpc_SendMessageToClient`（Actor.cs:1820）経由で `DewPersistence.ToJson` による全体の JSON 文字列化と Mirror の書き込み、ローカル回りの配送まで払ったうえで、受け側の処理で必ず捨てられていた。`PublishChoiceHistoryTo` の走査で `DewPlayer.local` を最初から対象から外し、この無駄な一本化された往復と送信枠の占有をなくした。1行の条件追加と `using Mirror;` の追加のみで、送信の中身と相手側の処理は変えていない。

結果が変わらない理由: `DreamforgeRunChoicesMsg` の受け側ハンドラは `ClientSession.cs:567` に登録された `OnRunChoices` 1つだけである。ホストでは `NetworkServer.active` が真のため、その両分岐（`ReceiveLobbyReturn` と `ReceiveRunChoices`、ClientSession.Continue.cs:474 と ClientSession.RunChoices.cs:331）は冒頭で何も変更せずに返る。ホスト自身への送信はどれもここで捨てられ、送り先のプロセスは送り元と同じ1つなので、どこの機械の状態も今まで動いていない。変更後はその送信自体がなくなるだけで、受け取らないことの効果は同じである。遠隔の参加者へのメッセージの内容は1バイトも変わらず、変わるのは輪番の順番だけで、全履歴の追いかけに使う0.1秒あたり4通・8192バイトの枠がホスト自身と分け合わなくなる分だけ早く回る。網に流れる通信量も変わらない（ホスト自身への配送はローカル接続のみ）。`DewPlayer.local` は null になり得るが、その場合は誰も対象から外れない。

効果の見込み（推定）: ソロのホストでは選択履歴の送信がまるごとなくなる。これまでも履歴の確定ごとの追いかけと30秒ごとの全再送で、1通につき最大8KBのchoices文字列のJSON化・書き込み・復号と破棄を繰り返していた（推定。エントリ数は走ったゾーン数に比例する）。参加者のいるホストでは、追いかけ枠をホスト自身に取られなくなるため、ゾーン確定後の履歴の追い付けが参加者数ぶん速くなる（推定）。毎フレームの走査自体は1つの静的プロパティ読み出しと比較が増えるだけで、ほとんど変わらない。
