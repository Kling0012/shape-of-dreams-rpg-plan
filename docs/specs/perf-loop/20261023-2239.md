# perf-loop/20261023-2239

## 対象

native Dew.Core/FlavourManager.cs（被弾シェイク `OnClientTakeDamage`）。

## 直した内容

`FlavourManager.OnClientTakeDamage(EventInfoDamage)` に Prefix パッチ（`NativeDamageShakeIdlePerf`）を足し、シェイクが成立しない被弾でのみ本体の呼び出しを飛ばすようにした。このメソッドは、ホストが `ClientEventManager` 経由で全端末に中継するすべてのダメージイベントの受信側で、協力プレイの参加者も自分の英雄への被弾に限らず戦闘中の全被弾（全プレイヤーがモンスターに与える攻撃を含む）ごとに呼ぶ。

本体は、しきい値未満の弱い被弾でも次の準備をすべて行ってから捨てる。プールから `Ad_DamageShake` を取り出し、victim の `EntityVisual` から全項目ゼロの `EntityTransformModifier` を確保して `AddData` で登録した直後に、残り時間が 0 以下だと分かった時点で `RemoveData`・`modifier.Stop()`・プール返却を行う。この経路のうち「既存のシェイクが無く、評価したシェイク時間が 0 以下」の場合だけを Prefix で省く。判定には本体と同じ式で算出した時間（`shakeDuration.Evaluate`）と同じ比較（`<= 0f`）を使い、victim のデータ辞書（`Actor._dataByType`）に既存シェイクがあるかを `Ad_DamageShake` の型キーで先に確かめる。毒などの DoT（`ElementalStatusEffect`）は本体が最初の早期リターンで排除する経路なので、Prefix も同じ判定を先に置いて追加コストをかけない。

設定は `nativeDamageShakeIdle`（既定有効）で切れる。パッチ先のメソッド、入れ子型 `Ad_DamageShake`、`_dataByType` フィールドのどれかが見つからないときは、その修正だけ外れて1回警告を出す。Prefix 内の例外でも同様に無効化して本体に任せる。テスト側では、リンクされる `NativePerfPatches.cs` が参照する本体 API の受け口として、既存の `NativeBoundary.cs` に `AnimationCurve`（評価器を差し替えられる）、`FlavourManager`（`OnClientTakeDamage` と入れ子の `Ad_DamageShake` を含む形）、`DamageData.discardedAmount` を足し、`Actor` に本体どおりの `_dataByType` を、`NativeEmbracePositionBoundary.cs` の `DreamforgeConfig` の模倣に `nativeDamageShakeIdle` を足した。Prefix の分岐の検証は `DamageShakeIdlePerfTests.cs`（修正ラウンドで追加）が担う。

## 本体の処理の流れ（Dew.Core r1.4.1.2 逆コンパイル、2026-10-23 確認）

実DLL（`Shape of Dreams_Data/Managed/Dew.Core.dll`、r1.4.1.2）を ilspycmd で逆コンパイルした `FlavourManager.cs:145-188`・`Actor.cs:164,1949-2000`・`EntityVisual.cs:2383-2399`・`EntityTransformModifier.cs` で、`OnClientTakeDamage` の本体の流れを確認した。

1. 早期リターンは2つ。最初は `info.actor is ElementalStatusEffect`（DoT）で、何もせず戻る。もう1つは既存シェイクの置換判定の中にある。num・num2・num3 を算出した後で `info.victim.TryGetData<Ad_DamageShake>(out var data)` が当たり、`data.intensity >= num2`（新しい被弾が既存シェイクより強くない）なら何もせず戻り、上回るときは古いシェイクを `isStale`・`modifier.Stop()`・`RemoveData` で止めてから作り直す。
2. num の算出に Clamp は無い。`float num = (info.damage.amount + info.damage.discardedAmount) / (info.victim.maxHealth + info.victim.Status.currentShield); num = (num - shakeDamageRatioRange.x) / (shakeDamageRatioRange.y - shakeDamageRatioRange.x);` の2行だけで、`Mathf.Clamp01` などの正規化は入っていない。範囲外の値（1 超・0 未満・除算での Inf/NaN）もそのまま `shakeIntensity.Evaluate(num)`・`shakeDuration.Evaluate(num)` に渡る。
3. 作成と即時破棄。プールから `Ad_DamageShake` を Pop（空なら new）して字段へ num2・num3 を写し、`info.victim.Visual.GetNewTransformModifier()` で修飾子を確保し（プールから取り出して `ResetForReuse`（全オフセットゼロ・倍率1・回転恒等）をかけ、`_transformModifiers` へ追加して `_parent` を設定する。この追加では dirty フラグは立たない）、`AddData` で登録する。`remaining = num3` が `<= 0f` なら `RemoveData`・`modifier.Stop()`（`EntityVisual.RemoveTransformModifier`: リストから除外・`_isTransformModifiersDirty = true`・`ResetForReuse`・プール返却）・`ReturnShake`（`_shakePool` へ Push）で即時破棄する。正なら `_activeShakes` へ追加して `StepShake` へ進む。
4. シェイク以外の副作用は無い。このメソッドの本体に被弾フラッシュ・音・カメラ揺れ・UI の類は一切なく、触る状態はシェイクの管理（`_activeShakes`・`_shakePool`・`_dataByType`・`_data`・`_transformModifiers`・`_isTransformModifiersDirty`）だけである。ヒットストップ（`hitStopDealDamage`）は `OnStartServer` の `OnEntityAdd` が各モンスターの `EntityEvent_OnTakeDamage` へ登録するサーバ側ハンドラで別のイベント経路、キルフィードバックは `OnDeath`/`ClientHeroEvent_OnKillOrAssist` 系の購読にあり、どちらもこの Prefix の影響を受けない。
5. 辞書の形。`Actor.TryGetData<T>` は `_dataByType.TryGetValue(typeof(T))` そのもので、`AddData<T>`・`RemoveData<T>` も同じ `typeof(T)` をキーに使う。Prefix の `_dataByType(victim).ContainsKey(_shakeDataType)`（`_shakeDataType` は `AccessTools.Inner` で解決した同じ入れ子型）は、本体の `TryGetData<Ad_DamageShake>` の判定と同じである。

Prefix の条件と式はこの流れと一致する（早期リターンの順序・num の式と Clamp の有無・`<= 0f` 比較・型キー）。スキップする「既存シェイクが無く、評価した時間が 0 以下」の被弾では、本体は上の 3 の作成と即時破棄だけを行い、状態は元へ戻る（dirty フラグの1回の再計算を除く）。

## 結果が変わらない理由

スキップする条件では、本体が作るシェイクは残り時間 0 で、登録した直後に取り消される。確保される `EntityTransformModifier` は作られた時点でオフセットがゼロ・倍率が 1・回転が恒等（`ResetForReuse`）なので、それを付けても外しても各実体の変位の合計値は1ビットも変わらず、見た目・判定・通信に現れる差はない。なくなるのは、変更結果が空のままのリスト・辞書操作（うち2つは要素数に比例する走査）と、dirty フラグによる1回の不要な再計算だけである。

既存のシェイクが動いている victim は本体にそのまま通す。強い被弾が古いシェイクを打ち切る置換判定は本体が担当しており、これを飛ばすと古いシェイクが本来より長く残るためである。評価した時間が正の被弾も本体に通すので、実際にシェイクが動く被弾は元どおりである。時間が負になるような異常データでも本体と同じ値を同じ比較にかけ、本体が破棄するものだけを飛ばす。NaN は比較が成立せず本体が走るので、元の挙動のままである。

## 効果の見込み（推定）

参加者は戦闘中のすべてのダメージイベントを受けるので、しきい値未満の弱い被弾が大半の場面では、1イベントごとにプール・辞書・リストの操作6種と不要な再計算1回がなくなる（推定）。スキップが効く頻度はカーブの実値しだいで、実機のアセットからは確認できないため、効果の大きさは推定にとどまる。逆に実際にシェイクが動く被弾では、Prefix の判定のために曲線評価1回と辞書参照1回が増える（増分は小さい）。
