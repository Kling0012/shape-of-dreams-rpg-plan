# perf-loop/20261023-2239

## 対象

native Dew.Core/FlavourManager.cs（被弾シェイク `OnClientTakeDamage`）。

## 直した内容

`FlavourManager.OnClientTakeDamage(EventInfoDamage)` に Prefix パッチ（`NativeDamageShakeIdlePerf`）を足し、シェイクが成立しない被弾でのみ本体の呼び出しを飛ばすようにした。このメソッドは、ホストが `ClientEventManager` 経由で全端末に中継するすべてのダメージイベントの受信側で、協力プレイの参加者も自分の英雄への被弾に限らず戦闘中の全被弾（全プレイヤーがモンスターに与える攻撃を含む）ごとに呼ぶ。

本体は、しきい値未満の弱い被弾でも次の準備をすべて行ってから捨てる。プールから `Ad_DamageShake` を取り出し、victim の `EntityVisual` から全項目ゼロの `EntityTransformModifier` を確保して `AddData` で登録した直後に、残り時間が 0 以下だと分かった時点で `RemoveData`・`modifier.Stop()`・プール返却を行う。この経路のうち「既存のシェイクが無く、評価したシェイク時間が 0 以下」の場合だけを Prefix で省く。判定には本体と同じ式で算出した時間（`shakeDuration.Evaluate`）と同じ比較（`<= 0f`）を使い、victim のデータ辞書（`Actor._dataByType`）に既存シェイクがあるかを `Ad_DamageShake` の型キーで先に確かめる。毒などの DoT（`ElementalStatusEffect`）は本体が最初の早期リターンで排除する経路なので、Prefix も同じ判定を先に置いて追加コストをかけない。

設定は `nativeDamageShakeIdle`（既定有効）で切れる。パッチ先のメソッド、入れ子型 `Ad_DamageShake`、`_dataByType` フィールドのどれかが見つからないときは、その修正だけ外れて1回警告を出す。Prefix 内の例外でも同様に無効化して本体に任せる。テスト側では、リンクされる `NativePerfPatches.cs` が参照する本体 API の受け口として、既存の `NativeBoundary.cs` に `AnimationCurve`（評価器を差し替えられる）、`FlavourManager`（公開字段のみ）、`DamageData.discardedAmount` を足し、`NativeEmbracePositionBoundary.cs` の `DreamforgeConfig` の模倣に `nativeDamageShakeIdle` を足した。新しいテストファイルは作っていない。

## 結果が変わらない理由

スキップする条件では、本体が作るシェイクは残り時間 0 で、登録した直後に取り消される。確保される `EntityTransformModifier` は作られた時点でオフセットがゼロ・倍率が 1・回転が恒等（`ResetForReuse`）なので、それを付けても外しても各実体の変位の合計値は1ビットも変わらず、見た目・判定・通信に現れる差はない。なくなるのは、変更結果が空のままのリスト・辞書操作（うち2つは要素数に比例する走査）と、dirty フラグによる1回の不要な再計算だけである。

既存のシェイクが動いている victim は本体にそのまま通す。強い被弾が古いシェイクを打ち切る置換判定は本体が担当しており、これを飛ばすと古いシェイクが本来より長く残るためである。評価した時間が正の被弾も本体に通すので、実際にシェイクが動く被弾は元どおりである。時間が負になるような異常データでも本体と同じ値を同じ比較にかけ、本体が破棄するものだけを飛ばす。NaN は比較が成立せず本体が走るので、元の挙動のままである。

## 効果の見込み（推定）

参加者は戦闘中のすべてのダメージイベントを受けるので、しきい値未満の弱い被弾が大半の場面では、1イベントごとにプール・辞書・リストの操作6種と不要な再計算1回がなくなる（推定）。スキップが効く頻度はカーブの実値しだいで、実機のアセットからは確認できないため、効果の大きさは推定にとどまる。逆に実際にシェイクが動く被弾では、Prefix の判定のために曲線評価1回と辞書参照1回が増える（増分は小さい）。
