# perf-loop/20261024-1221

対象: `src/SodRpg.Mod/HostAuthority.BossShares.cs`（共有ボスの持ち分制）

## 直した内容

このファイルの経路はすべてホスト側で、参加者端末では動きません（持ち分の入口になる
`Actor.DealDamage` は本体で `[Server]` ガード付き）。そのため被弾ごとの経路の無駄を
探しました。`PrepareBossShares` の冷経路（持ち分を持たない敵の被弾と、0.25秒ごとの
定期点検 `ScanEnemyOwnership` の敵ごとの確認）で、ガードの並びが安価な判定より先に
稼働確認（`OwnershipRunning`）を評価していました。稼働確認はマネージャの静的参照、
runId の文字列検査、最大4人に対する接続確認（内側にリストの線形探索）からなり、
通常モンスターはその直後の型とボスの判定（`is Monster` と `IsAnyBoss`、
本体 `EntityCheck.cs:21` の型・フラグ判定）で落ちるので、稼働確認は毎回無駄でした。

ガードを「型・ボス判定 → 稼働確認 → 静的フラグ → ボス固有の確認」の順に並べ替え、
稼働確認の値を呼び出し元から渡す形にしました。定期点検（`ScanBossShares`）は走査の
先頭で計算済みの値をそのまま渡します。点検では生存敵ごとに再評価していたのを
走査全体で1回に減らします。

被弾の冷経路（`TryBossShares`）は、`PrepareBossShares(state, OwnershipRunning())` の
引数が呼び出しの前に評価されるため、並べ替えだけでは通常モンスターへの被弾でも
稼働確認が毎回評価されたままでした。そのため `TryBossShares` の側にも同じ純粋判定
（`is Monster` と `IsAnyBoss`）を先に入れ、通常モンスターと `Enemy` が null の状態は
稼働確認を評価せずに落とすようにしました。ボスの被弾は1回評価して渡します
（回数は変わらない）。

## 結果が変わらない理由

- 並べ替えた判定と `TryBossShares` に追加した純粋判定はすべて副作用のない読み取りです
  （`||` の短絡評価の順序を変えても結果の集合は同じ）。`state.Enemy` が null のときの
  扱いも同じです（`null is Monster` で落ちる）。従来 `PrepareBossShares` が持ち分を
  作れたのはボスだけで、通常モンスターは必ず null だったため、返り値と
  `state.Shares` は変わりません。
- 点検に渡す `running` は、走査の先頭で1回評価した値です。走査は単一の同期処理で、
  呼び出し元の走査ループ（`ScanEnemyOwnership`）の内容は所有権の帳簿更新と通知の
  送信だけです。稼働確認の入力（有効フラグ・サーバ状態・マネージャ・runId・ゾーン・
  プレイヤーの接続）は変えないため、敵ごとの再評価と同じ値になります。仮に走査中に
  稼働が false へ転じても、被弾ごとの `TryBossShares` の再評価と次回点検の先頭ガード
  （`if (!running) { state.Shares = null; return; }`）で1ティック以内に掃除されます。
- 被弾の冷経路でボス（`Monster` かつ `IsAnyBoss`）は `TryBossShares` 内で1回評価して
  渡すので、評価回数は変わりません。速経路（持ち分済みボスへの被弾）は変更していません。
- `PrepareBossShares` は private で、呼び出し元は `TryBossShares` と `ScanBossShares`
  の2か所だけです。通常モンスター・`Enemy` が null の状態・未稼働のボス・親を持つボスが
  両入口で null を返し `state.Shares` を null のまま変えないことと、通常モンスターと
  null が稼働確認より前で落とされること（稼働確認が例外を出す状態でも例外にならない）を
  `BossSharesTests` に直接確かめるテストとして足しました。

## 効果の見込み（推定）

持ち分を持たない敵＝通常モンスターへの被弾が戦闘中に数百件/秒に達する場面で、
被弾1件あたりの稼働確認（マネージャ参照・runId の文字列検査・最大4人の接続確認。
推定数十ナノ秒）と静的フラグ2件の読み取りがなくなり、型とボスの判定だけになります。
定期点検は生存敵の数（多い部屋で数十）×4回/秒分の再評価が走査全体で1回にまとまります。
合計で毎秒数十マイクロ秒程度の見込み（推定）です。ホスト側の経路なので、
参加者端末の負荷は直接は下がりません。
