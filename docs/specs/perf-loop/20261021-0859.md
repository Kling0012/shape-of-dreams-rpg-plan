# perf-loop/20261021-0859

対象は `src/SodRpg.Mod/HostAuthority.BossLastStarlight.cs` である。直した内容は、`ReconcileLastStarlight` が退避済み（`Retired`）の状態を呼ばれるたびに再計算し続けていたのを、差し引きが済んだ退避済み状態では早期に返すようにした点である。追加したのは条件1つと、それを説明するコメントだけで、変更は数行にとどめた。

LastStarlight の黒穴（`Ai_Gem_U_LastStarlight`）は出現から消滅まで数秒続く。その間、`ActiveLogicUpdate` の接辞（`RefreshLastStarlight`）と待機条件（`WaitFinished`）が毎フレーム `ReconcileLastStarlight` を呼ぶ。通常の状態は同一フレームの2回目以降を `LastReconcile==now` で落とすが、この重複除去の最初の条件が `!state.Retired` になっているため、退避済みの状態は重複除去が働かず、呼ばれるたびに本体を全部実行していた。本体は `LastStarlightCurrent`（正規装着の確認など十数項目）に加え、`BossEnsure`（機器エポック・部屋・ランの確認）と `BossRewardStage`（記憶の検索とエッセンス走査）まで実行する。

退避は英雄の戦闘不能、装備の組み直し（`ClearLastStarlight`）、宝石の装備解除、部屋遷移で起きる。退避しても黒穴の本体側の処理は宝石かスキルが無効になるまで続くため、退避後も消滅までの数秒間、待機中は毎フレーム2回の本体再計算が続いていた。退避済みの状態は二度と段階を取り戻せない（`LastStarlightCurrent` は最初に `!Retired` を見る）ので、差し引きの1回（段階0・差分0に揃える1回）以降の再計算は同じ答えを出すだけだった。

結果が変わらない理由は、早期リターンで飛ばす本体が退避済み状態では観測可能な副作用を持たないためである。`LastStarlightCurrent` は偽に固定され、`stage` は0、4つの差分はすべて0、`changed` は偽になる。フィールドへの書き込み（`+= 0-0`）は値を動かさず、演出の更新（`changed && Waiting` が偽）も呼ばれない。本体が書き換える他の値（`LastReconcile`・`Build`・`Epoch`）は退避済み状態ではどこにも読まれない（重複除去の条件は退避済み状態で `!Retired` の時点で短絡する）。待ち時間の計算（`WaitFinished` の `seconds`）はこの関数の外で行われ、差分が0になってからは値が動かないので、退避の反映（差分の引き戻しで待ちが本来の長さに戻る）も待ちの残り時間も従来どおりである。差し引きの1回自体は、退避の理由がどれでも従来どおり実行される。

効果の見込みは推定だが、ホスト側の CPU の削減である。このファイルの MOD 側の経路は5本のパッチすべて `NetworkServer.active` で保護されており、参加者の PC では接辞がブール判定1つで返るため、参加者側の負荷は変わらない。参加者側の経路がないため、規則の3・4（毎フレーム経路の重複計算）の観点で選んだ。削れるのは1つの黒穴あたり退避から消滅までの数秒間、毎フレーム最大2回分の辞書引き十数回と装着・エッセンスの走査である。黒穴は同時に少数（報酬持ちの英雄ごとに1つ）なので削減量の絶対値は小さいが、退避のきっかけ（戦闘不能・装備変更）は戦闘中に頻繁に起きる。参加者への通信（ボス演出のメッセージ）は送信条件も内容も変えていない。
