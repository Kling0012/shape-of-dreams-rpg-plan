# perf-loop/20261024-1950

## 対象

native `Dew.Core/DewPlayer.cs`（4828行）。本体は直接変えられないため、MOD から Harmony のパッチで軽くする。

## 見た範囲

`DewPlayer.cs` 全体。プレイ中に走る経路は `LogicUpdate` 配下の4つ（`LogicUpdate_InGame`、`LogicUpdate_InGame_NetworkedOnScreenTimer`、`LogicUpdate_MidJoin`、`LogicUpdate_Lobby`）と、通信ごとの受信処理（SyncVar の hook 群、`UserCode_CmdNotifyClientStatus`、`UserCode_TpcSetNetworkedOnScreenTimerValue` などの TargetRpc 受信側）。実 DLL は前回（20261019-1924）すでに取り出して照合済みで、今回も逆コンパイルを確認した。

`LogicUpdate_InGame` はカーソルの地面位置を毎フレーム計算し、値が変わったときか 0.05 秒ごとに `CmdNotifyClientStatus` を送る。ホストはこの値で参加者のヒーローの狙いを動かすので、送る間隔や粒度を変えるとホスト側の見え方・判定が変わる。触れない。`LogicUpdate_InGame_NetworkedOnScreenTimer` の同値再送は、すでにマージ済みの `NativePlayerTimerIdlePerf`（20261019-1924）が押さえている。金・ドリームダストなどの SyncVar hook と `GetTeamRelation`（List 3つの小さな `Contains`）は受信ごと・呼び出しごとに見たが、確保も全走査もなく無駄がない。

## 直した内容

`LogicUpdate_MidJoin` の末尾である。ここは「ゲーム進行中・途中参加許可（既定で許可）・ロビーに待機する参加者に再参加データがある」ときに毎ロジックフレームで走り、最後の1文で毎フレーム `new HeroLoadoutData()` を作っては SyncVar `Network_<selectedLoadout>k__BackingField` に代入し直している。`HeroLoadoutData` は普通のクラスなので Mirror の生成セッターは参照等値で比べ、新しく作った空のインスタンスは前のフレームのものと等しくならない。その結果、待機している間ずっと（ボス戦の前・最中・後は `BossMonster` が `midJoinWaitType` を自動で変えるので、ボス戦の窓全体がこれに当たる）、毎フレーム SyncVar が dirty になり、Mirror が中身の変わらない空のロードアウトを全観測者へ再送し、ホストでは毎フレーム、各クライアントでは受信のたびに `OnLoadoutChanged` → `ClientEvent_OnSelectedLoadoutChanged` が発火し続ける。

そこで `NativeMidJoinLoadoutIdlePerf` を追加した。weaver 生成のセッター `Network_003CselectedLoadout_003Ek__BackingField` に Harmony の Prefix を掛け、「入ってくる値も現在値も内容が空」（スキル4つの int が 0 で、星のリスト4つが null か空）のときだけセッターを飛ばす。空でない値どうし、null が絡む代入、1回目の本当のクリア（空でない → 空）はそのまま本体に通る。MOD 設定 `nativeMidJoinLoadoutIdle`（既定は有効）で切れる。対象が見つからない・形が変わっているときは警告を1回出して何もしない。Prefix の中で例外が出たときも、その機能だけを恒久で止めて同じ警告を1回出す。

Prepare はセッターの解決に加えて、`HeroLoadoutData` の公開字段が空判定の8項目（スキル4 int と星リスト4つ）と数・名前まで一致するかも確かめる（実 DLL の逆コンパイル 2026-10-24 で、公開字段はこの8つだけであることを確認済み）。ゲーム更新で字段が増える・名前が変わると「空」の判定が同期対象の一部だけを見ることになり、内容の変わる代入まで飛ばし得るため、その場合は警告1回で無効にする。

## 結果が変わらない理由

飛ばすのは「空 → 空」の代入だけである。どちらも内容が同じ空なので、同期・hook・UI の更新がどれだけ発火しても見える状態は変わらず、発火しなくても各端末の持つ値は変わらない。ゲーム内にこの SyncVar の書き手は `LogicUpdate_MidJoin`、`CmdSetHeroType_Imp`（無効なロードアウトのクリア）、`CmdSetHeroLoadoutData_Imp` の3か所しかなく、どこも「空 → 空」のときの発火は同じ内容の再送・再描画だけなので、飛ばしてよい。ロビーのロードアウト UI は `ClientEvent_OnSelectedLoadoutChanged` で値を読み直すだけの作りで、同じ値での再描画は見た目を変えない。新しい観測者が途中で加わるときは Mirror が初期状態を字段から作るので、飛ばした分が欠落することはない。

空判定の列挙（8項目）が実機の字段構成から外れる将来の失敗筋（ゲーム更新で字段が増え、追加字段だけが変わる代入を誤って「空 → 空」と飛ばす）は、Prepare の字段照合が塞ぐ。不一致なら警告1回で無効化するので、列挙が同期対象の一部だけを見ている状態でパッチが動き続けることはない。

## 効果の見込み

推定: 途中参加・再参加の待機中（ボス戦の窓など）に限り、(1) 毎フレームの SyncVar dirty と、Mirror の送信間隔ごとの空ロードアウトの全員への再送、(2) ホストで毎フレーム・各クライアントで受信ごとの `ClientEvent_OnSelectedLoadoutChanged` の発火、をなくす。待機者がいなければ元から走らないので、通常の単独プレイでは効果はゼロで、待機者がいる協力プレイでホストの送信量と全員の受信処理を減らす。呼び出し側の `new HeroLoadoutData()` 自体は残る（Gen0 に落ちる小さな1個）。体感できる規模ではないが、待機が長いほど効く。

## 見送った候補

- `CmdNotifyClientStatus`（参加者からホストへの毎フレームに近い状態通知）: 送る間隔・動きのしきい値を変えるとホストが動かす参加者の狙いの精度とタイミングが変わるため触れない。
- `OnStateChanged` の `Sort` 用ラムダ、`TeamRelationChanged` の全実体走査: 状態遷移・チーム変更のたびにしか走らず、呼ばれる頻度が無視できる。
- `LogicUpdate_MidJoin` の wait 分岐の全体を Prefix で作り直す案: private メソッドの再実装になり、`TpcPrepareSceneBeforeMidJoin` やログの再現まで抱える割に、セッターの Prefix で同じ無駄が消えるため見送った。
- `LogicUpdate_MidJoin` の wait 分岐で毎フレーム回る `playerRejoinData` の二重引き（`ContainsKey` + インデクサ）: セッターの Prefix だけでは消えないが、辞書引き1回の差であり、見送った。

## 検証

完了条件の4つをこのセッションで実行した（結果は報告文のとおり）。実機（ゲーム内）では未確認。ハーネス（Issue73.Native.Tests の NativeBoundary）には本体の weaver 生成セッターがなく、当初は Prepare が警告1回で無効になり Prefix の判定は一度も動かなかった。そこで境界の `DewPlayer` に weaver 生成セッターの模倣（`Network_003CselectedLoadout_003Ek__BackingField`。クラス既定の参照等値で比べ、参照が変わるときだけ字段へ代入し書いた回数を数える）を置き、`MidJoinLoadoutIdlePerfTests` でパッチを有効なまま確かめた: (1) 空の現在値への新しい空の代入は何フレーム繰り返してもセッターまで届かない（星リストが null の空も両側で同じ扱い）、(2) 空 → 非空（int だけ・星リストだけの両方）・非空 → 空・空 → null・null → 空はすべて本体のセッターに通る、(3) 設定無効時は「空 → 空」も通る、(4) 字段照合は実機と同じ8項目の形で通り、字段が増えた・名前が変わった・減えた型では false を返す。コンパイルを通すため NativeBoundary に `HeroLoadoutData`・`LoadoutStarItem`・`DewPlayer.selectedLoadout` の形を、DreamforgeConfig の模倣（NativeEmbracePositionBoundary.cs）に `nativeMidJoinLoadoutIdle` の字段を追加した。

ゲーム本体を更新するときは、逆コンパイルで `HeroLoadoutData` の字段一覧を空判定の列挙（8項目）と突き合わせる。追加字段があれば Prepare の字段照合が警告1回でパッチを無効化するので、その警告を見たら新しい字段を空判定に含めるかどうかを決めて追随する。
