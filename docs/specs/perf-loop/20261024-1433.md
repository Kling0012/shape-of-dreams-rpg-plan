# perf-loop/20261024-1433

対象は `src/SodRpg.Mod/HostAuthority.GimmicksV129.cs` である。直した内容は、Weakspot（急所）の会心付与を damage に適用する `ApplyGimmickDamageV129` で、記憶元を特定する `MemorySource` の親連鎖走査を、対象外の damage には行わないようにしたことである。この処理は `Entity.ProcessReceivedDamage` の Postfix（`Patches.cs` の `GimmickDamageIsolation`）から呼ばれ、戦闘中の被弾1回ごと（通常攻撃・スキル・継続ダメージ・元素反応のすべて）に走る。変更前は、呼び出し側の `ApplyFinalGimmickDamageV129` が`MemorySource`（`damage.actor` から親を最大128段階たどる走査）を実行してから、呼ばれる側で会心済みの damage や自分の英雄の基本攻撃を門で除外していた。つまり会心ダメージのように確実に対象外の damage まで、毎回親連鎖をたどっていた。変更後は、`MemorySource` の計算を呼ばれる側に移し、副作用のない安価な門（会心属性の確認、攻撃種別の確認、`IsAmountModifiedBy` の確認）を先に評価し、すべてを通った damage だけを走査するようにした。合わせて、基本攻撃の門の中で `firstEntity`（`FindFirstOfType<Entity>()` で親連鎖をたどる）の前に攻撃種別の確認を置き、基本攻撃以外の damage ではこの走査も省くようにした。変更はこの1つの経路だけで、呼び出し側と呼ばれる側の引数の受け渡し（`string memory` を `Actor memorySource` に変える）を含めて十数行である。

結果が変わらない理由は次のとおりである。門の条件式（会心属性・攻撃種別・`firstEntity` との一致・生成ダメージの属性）は、どれも状態を書き換えない読み取りであり、評価の順序を入れ替えても受理する damage の集合は同じである。門で除外される damage は `MemorySource` を実行しなくなるが、`MemorySource` の戻り値で状態が変わるのは型ごとの記憶名の覚え書き（`_memorySourceTypes` のキャッシュ）だけで、damage の結果には影響しない。乱数は門をすべて通った場合にだけ `_rng.NextDouble()` を引く仕組みのままで、門が乱数を消費しないため、出目の並びも変更前と同じである。`WeakspotPercent` の呼び出し位置と、記憶元の算出に使う Actor（`damage.actor` を優先し null なら呼び出し側の `actor`）も変更前と同じである。なお `HostAuthority` は `NetworkServer.active` が偽のときは何もしないので、この経路はホスト側だけで走り、参加者への通信には一切触れない。

効果の見込みは推定である。戦闘中の被弾1回ごとに、変更前は少なくとも親連鎖の走査1回（`MemorySource`、連鎖の深さ分の型確認と辞書参照。飛び道具や継続ダメージでは深さが数十段階になることがある）、会心済みでなければさらに `firstEntity` の親連鎖走査1回がかかっていた。会心はこのゲームの戦闘で頻繁に発生し、自分の英雄の基本攻撃も戦闘全体を通して最も多い damage の1つなので、これらの大多数で走査2回が攻撃種別や属性の確認のような定数時間の確認に置き換わる。獲得はホスト側の CPU と GC 負荷の削減であり（走査そのものは新しい割り当てを行わないが、除外が早まることで1被弾あたりの処理時間が減る）、通信量と参加者の受信処理は変わらない。検証は `tools/balance/gen_cs.py --check`、`src/SodRpg.Mod` の Release ビルド、`tests/Issue73.Native.Tests`（796件全件合格）、`tests/SodRpg.Mod.Startup.Tests`（238件合格・1件は既存のスキップ）で確認した。実機（ゲーム内）での確認は未実行である（この環境ではゲームを動かせないため）。
