# perf-loop/20261024-0145

## 対象

mod src/SodRpg.Mod/HostAuthority.BossEternalFlame.cs（Infernus ボス装備＝Gem_U_EternalFlame のホスト側処理）。Harmony パッチが乗るのは呪いの生成・タイマー・被弾・宝石の処理で、どれも本体の判別（`HostAuthority.NativeInstance?.` と `NetworkServer.active`）が先に来る。`NativeInstance` はホストの `Tick` の間だけ入り、参加者の環境では null のままなので、このファイルの処理は参加者側では型確認だけしか走らない。そのため通信ではなく、3（毎フレーム・被弾ごとの経路の無駄）の観点で見た。

## 直した内容

`TickEternalFlame` は Infernus セットの装備がある間、ホストの毎フレーム（`DreamforgeMod.Update` → `HostAuthority.Tick` → `StageBossEffects`）に呼ばれ、所有者の状態にある呪いを1件ずつ処理する。このループでは `EternalFlameCurseCurrent(capture)` で期限切れを判定した直後、同じ呪いに対して `capture.Curse.parentActor != capture.Gem`、`capture.Curse.info.caster != rt.Hero`、`capture.Gem.owner != rt.Hero`、`!EternalFlameEquipped(capture.Gem, out _)` の4項目をもう一度検査してから、タイマーを戻すか延長するかを分けていた。

この再検査は直前の `EternalFlameCurseCurrent` が済ませた内容と同じなので、やめた。残る分岐は `stage == 0` かどうかだけで、stage が 0 のときはタイマーを戻し、stage が 0 より大きく延長が未適用（`AddedMaximum == 0`）のときは `CaptureEternalFlameCurse` で付け直す。この流れは以前と同じである。

## 結果が変わらない理由

`EternalFlameCurseCurrent` は、1 回の呼び出しの中で呪いの親（`capture.Curse.parentActor == capture.Gem`）、キャスター（`capture.Curse.info.caster == capture.Runtime.Hero`）、装備（`EternalFlameEquipped(capture.Gem, out var rt)` と `rt == capture.Runtime`）まで確認し、true を返す。true が返った直後の再検査は同じ同期処理の中にあり、その間にゲームの状態は変わらないので、結果は必ず同じになる。

`capture.Runtime == rt` も成り立つ。呪いは `CaptureEternalFlameCurse` が所有者自身（`EternalFlameEquipped` が返したランタイム）の状態にしか追加せず、`TickEternalFlame` の `state` はその鍵である rt 自身の状態だからである。すると `EternalFlameEquipped` の戻り値のランタイムが `capture.Runtime == rt` と等しいことから、`capture.Gem.owner == rt.Hero` と `capture.Curse.info.caster == rt.Hero` も従う。4 項目すべてが分岐に影響しなくなるので、タイマーの延長・復元、火の付与、演出メッセージの送信の内容と回数は何も変わらない。この処理はホストだけで走る。

## 効果の見込み（推定）

削ったのは、呪い 1 件あたり毎フレーム 1 回の `EternalFlameEquipped`（`_runtimes` の辞書引き、生存・戦闘不能の確認、gem 棚の辞書引き、連携 6 枠の `GetSkill` 全走査）と比較 3 回である。火の呪いは Fire ダメージを受けた敵 1 体ごとに付くので、敵を引き寄せたあとの部屋では数十件になる。60fps 換算で呪い 30 件なら、毎秒およそ 1800 回の再検査がなくなる（推定。1 回は数十〜百ナノ秒程度だが、戦闘中ずっと走る経路の固定費である）。参加者の PC には届かない処理で、ホストのフレーム時間の裾を下げる。

## 検証

`python3 tools/balance/gen_cs.py --check` は合格。`dotnet build src/SodRpg.Mod -c Release -p:GameDir=... -p:ModDeployDir=/tmp/perfloop-x` は合格（警告 6 件は既存の CS0618/CS0649）。`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release` は 723 件すべて合格。`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Mod.Startup.Tests -c Release` は 237 件合格・1 件スキップ（元から `Skip` 指定の ModReloadTests）。

軽量化後の `TickEternalFlame` の分岐が変更前と同じ結果になることは、`tests/SodRpg.Core.Tests/BossEternalFlameNativeTests.cs`（#1077 レビューで追加）で固定した。実API相当の double で `HostAuthority.BossEternalFlame.cs` を駆動し、(1) 段階が 0→2 に上がった最初のティックで付け直しの延長が入ること、(2) 所有者状態の段階が 0 のまま延長が入ったあとのティックで、ループの `stage==0` 分岐が延長分だけ戻して呪い自体は解除しないこと、(3) 段階 2→0 の下がりで延長分だけ戻ること、(4) 削除した再検査の4条件（親・キャスター・gem.owner・装備）のどれが崩れても `EternalFlameCurseCurrent` が false になり復元＋解除が選ばれること、を確認する（7 件合格）。テストは `NetworkServer.active`・`Time.time`・`HostAuthority.NativeInstance` などプロセス全体で共有する静的状態を書き換えるため、他のテストと並列に走らない Collection（`DisableParallelization`）に入れてある。延長の秒数の一致は小数第3位までで確認する。ゲーム内での動作確認は未実行。
