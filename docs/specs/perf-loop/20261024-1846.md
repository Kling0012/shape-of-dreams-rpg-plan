# perf-loop/20261024-1846

## 対象

`src/SodRpg.Mod/HostAuthority.AuthoredKeystones.cs`。HostAuthority はホスト専用（`Tick` が `NetworkServer.active` を見てゲストでは即 return する）で、このファイルのうち参加者側で走るのは `Actor.DealDamage` への Transpiler 差し替え（`ProcessReceived`）だけ。ゲストでは `NetworkServer.active` の1読みで終わるので、参加者側の経路には無駄がない。そのため指示の観点3（被弾・発動ごとの無駄）で見た。

## 見た範囲

ファイル全体（273行）。ホットな入口は3つ。`ProcessReceived`（被弾ごと、ホストでは `ApplyAuthoredFinalNativeDamage` へ）、`TransformAuthoredPayload` とその薄いラッパー3種（記憶ダメージ・生成ダメージ・ギミックの変換ごと）、`AuthoredKeystoneActive`／`AuthoredKeystoneEpoch`（発動判定ごと）である。呼ばれる先も確認した。`EnsureMemoryAttributionEquipment`（エポック一致で即return、中身は `GetInstanceID` 1回と辞書引き1回）、`MemoryActivationAttribution.EquipmentEpoch`（辞書引きのみ）、`DamageData.IsAmountModifiedBy`／`SetAmountModifiedBy`（`_modifyFlags` の HashSet）、`StarDamageScaling.ScaleResult`（確保なし）、`ScopedKeystoneModifiers.IsKeystoneActive`（選択刻印の数だけの線形走査）。呼び出し側には既存のキャッシュがある（`AuthoredChannelEveryN` と `WardTransformCache` はエポックが動いたときだけ変換し直す）。`ConfigureAuthoredKeystone` は署名一致のとき再構成を省く速い道がある。

## 直した内容

`TransformAuthoredMemoryDamage`、`ApplyAuthoredFinalNativeDamage`、`TransformAuthoredGeneratedDamage` の3経路が、被弾・発動ごとの変換で毎回 `new KeystoneCaps(decimal.MaxValue)` を作っていた。`KeystoneCaps` は全プロパティが get のみの不変型で、消費側（`ScopedKeystoneModifiers.Apply` の上限適用）も `Math.Min` で読むだけなので、静的な1インスタンス（`UnlimitedKeystoneCaps`）を共有するようにした。

## 結果が変わらない理由

`KeystoneCaps` には setter がなく、参照の同一性で比較する箇所も src と tests のどこにもない（確認済み）。静的初期化で作る1個は従来の1個と同一の引数・同一の検証を通るので、`payload.Caps` を読むすべての計算の入力値が変わらない。`KeystonePayload` 自体は発動ごとに値（ダメージ量など）が違うため、引き続き作る。

## 効果の見込み

推定: 記憶ダメージ・ネイティブダメージ・生成ダメージの変換1回ごとに、小さなヒープ確保1個（decimal 5フィールド分）を減らす。ホスト側だけの効果で、刻印を持つヒーローの戦闘中に数百回/秒になり得る経路なので Gen0 への圧力を少し下げる。体感できる規模ではない。

## 見送った候補

`KeystoneContext`／`KeystonePayload`／`KeystoneResult` の発動ごとの確保は、SodRpg.Core 側の検証つき API の設計そのもので、対象ファイル内では変えられず、変えるなら大きな作り替えになるため見送った。`RefreshAuthoredKeystone` の遅い道（許可ベクトルの辞書と文字列構築、LINQ）は装備エポックが動いたときしか通らないため無駄がない。`ValidateAuthoredSacrificeBinding` のループ内 `CollectMechanismEquipment` は、ループが回るのはビルド適用時1回で、犠牲シールドの刻印は `h.aurena.key2` 以外が禁じられているため実質1個だけである。
