# perf-loop/20261021-0459

対象は `src/SodRpg.Mod/HostAuthority.Monsters.cs` の、被弾のたびに走るダメージプロセッサ3本である。直した内容は、プロセッサが計算した値を実際に読む接辞・タグがモンスターに付いているときだけ計算するようにした点である。

1本目は悪夢の挙動の被ダメージ処理（`ApplyMonsterBehavior` の `Damage`）である。Veiled・Hollow・Facing のどれも付いていないモンスターでは、攻撃者の位置を辿る処理（`actor.firstEntity` と `position` の読み）と、距離（`magnitude` の sqrt）・向き（四元数の積と内積）の計算を飛ばす。2本目は変種タグの被ダメージ処理（`ApplyVariantTags` の `TagDamage`）で、`MemorySource(actor)`（親の Actor 鎖を最大128段までたどり、型ごとの辞書引きも行う）、`actor.FindFirstOfType<Summon>()`、`AttackerShielded(actor)`（同じく親鎖の走査）を、その戻り値を読むタグ（それぞれ Armored|Spellward、SummonHunter、ShieldBreaker）があるときだけ計算する。3本目は変種タグの与ダメージ処理（`TagDealt`）で、`currentShield` の読みと `FindFirstAncestorOfType<Summon>()` の祖先走査を、ShieldBreaker・SummonHunter のビットがあるときだけ行う。

結果が変わらない理由は、`MonsterBehavior.IncomingMultiplier`・`WeaknessIncomingMultiplier`・`WeaknessDealtMultiplier` の3関数が、どれも対応するフラグのビットがあるときしか該当の引数を読まないためである。条件を同じビットで入れたので、ビットがあるときは従来どおり計算した値が渡り、ないときは読まれない値が渡るだけである。分岐の評価順で副作用が変わる箇所もない（追加した条件はビット判定のみ）。

この「引数を読まない」ことの確認を、レビュー（PR #1000 の修正ラウンド）を受けてテストに移した。まず省略の判定を `MonsterBehavior` の純粋関数へ切り出した（`ReadsHitGeometry`・`WeaknessReadsMemory`・`WeaknessReadsShield`・`WeaknessReadsSummon`。#904 が `ShouldSendMonsterBehaviorCue` を純粋関数に寄せたのと同じ方針で、ネイティブテストのハーネスは `HostAuthority.Monsters.cs` をコンパイルしないため）。次に `MonstersV129Tests` と `VariantWeaknessV129Tests` に、全接辞・全タグのビット組み合わせ（接辞21種・タグ9種の全組み合わせ）について、(a) 判定が偽のとき、省いた引数（距離・向きは境界値を含む8×4の組、記憶・召喚・障壁は真偽両方）をどんな値に変えても倍率が同じであること、(b) 判定が自分のビット（Veiled・Hollow・Facing／Armored・Spellward／ShieldBreaker／SummonHunter）でのみ真になること、を確かめるテストを追加した。倍率関数が将来ビットなしで引数を読むように変わるか、判定が誤って狭くなると、これらのテストは落ちる。

プロセッサのラムダ式そのもの（`takenDamageProcessor` の発火、actor が null のとき、親鎖に Summon があるときの実体の走査）はゲーム実行がないと動かせないため、テストで確かめるのは呼び出し地点の省略判定までである。actor が null でも親鎖に Summon がいても、プロセッサから倍率関数へ渡る引数の値が変わるだけであり、その値の全域（真偽の両方、距離と向きの境界値）について同値性は上のテストが保証している。ビットがあるときの計算本体は従来のコードから1文字も動かしていない。

効果の見込みは推定だが、被弾のたびの処理なので敵の数が多い波・深い階で効く。特に効くのは変種や Veiled 系の接辞を持たないモンスターへの攻撃で、モンスター1体あたり毎ヒットの親鎖の走査と位置・向きの計算が丸ごと省れる。削れるのはホスト側の CPU であり、この経路は `HostAuthority.Tick` が `NetworkServer.active` を見て参加者では早期に返すため、参加者の PC では動かない。参加者への通信（モンスターの合図・分類のメッセージ）は量も内容も変えていない。通信経路は別途確認し、合図は状態が変わったときだけ送られる dedupe（`SendMonsterBehaviorCue` の `cue == state.Cue` 判定）と、分類は5秒ごとの再同期が `ClassificationQueued` 等の比較で間引かれていることを確かめたため、今回触れる余地はなかった。
