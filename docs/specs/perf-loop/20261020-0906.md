対象は本体 `Dew.Core/Shrine_Chaos.cs`（525行）である。メンバー一覧は `reflection-dump/Shrine_Chaos.txt`（33項目）と突き合わせて一致した。そこから呼び出し側と下流を両方向で確認した。呼び出し側は `EditSkillShrine`（基底クラス、`GetCustomData` と `CmdActivateEditSkillAction` の本体）、`UI_InGame_EditSkillShrineText`（`LogicUpdate` で毎フレーム `GetEditSkillIndicatorRawText`／`GetEditSkillIndicatorColor`）、`UI_InGame_SkillButton_EditSkill`（`FrameUpdate` と `LogicUpdate`→`UpdateCostDisplayStatus` で毎フレーム `GetTargetTypes`、`GetTargetInfo`）、`EditSkillManager`（`IsSlotSelectable`／`IsSlotHighlighted`）、`UI_InGame_FloatingWindow_Chaos`、作成側の `RoomRewards.DropChaosReward` と `Ai_RandomGemUpgrade` である。

ゲスト側の毎フレーム経路は、混沌の神殿で報酬を選ぶ編集モードUIを開いている間に限って存在する。本体は報酬の選択を `rewards[guid]` の辞書引き → `GetCustomData(guid)` の辞書引き → `int.Parse` → 配列の添字、という連鎖で解決するが、この連鎖を `GetEditSkillIndicatorRawText`・`GetEditSkillIndicatorColor`・`GetTargetTypes`・`GetTargetInfo`（スキルとジェムの2つ）の5メソッドのそれぞれが毎回やり直す。編集モード中はスキルボタン1つにつき毎フレーム3〜5回（`FrameUpdate`・`UpdateCostDisplayStatus`・`IsSlotHighlighted` の内部）、さらに神殿テキストで2回だから、報酬を選んでいる参加者の画面では1フレームあたり十数回の辞書引きと文字列解析が重複して走る。ホストでも `CmdActivateEditSkillAction` の処理内で同じ連鎖が走る。そのほかの経路は軽かった。`OnStartClient` は出現時の1回、`rarity` の SyncVar は変化時だけ、`rewards` の SyncDictionary は生成時と使用時だけ動く。`CanInteract` は周回走査から毎フレーム呼ばれるが中身は `ContainsKey` の1辞書引きで、被弾ごと・撃破ごとの経路はない。送信系は利用者の操作が起点で、値が変わらないのに繰り返す送信はなかった。

直した内容は、この解決連鎖の結果を `(プレイヤー, rewards 配列の参照, customData 文字列の参照)` が同じ間だけ使い回す小さなキャッシュである。`src/SodRpg.Mod/NativePerfPatches.cs` に `ShrineChaosChoiceCache` と5つの Prefix（`NativeShrineChaosIndicatorTextPerf`・`NativeShrineChaosIndicatorColorPerf`・`NativeShrineChaosTargetTypesPerf`・`NativeShrineChaosSkillTargetInfoPerf`・`NativeShrineChaosGemTargetInfoPerf`）として追加した。Prefix はキャッシュが当たったときだけ本体を省いて結果を返し、外れたときは何もせず本体に任せる。MOD 設定 `nativeChaosShrineChoiceCache`（既定は有効）で切れる。対象メソッドが見つからない・形が違うときは `NativePerfPatch.Find` が警告を1回出して、その修正だけ外れる。

結果が変わらない理由は次のとおりである。キャッシュが当たるのは、`rewards` から取り出した配列、`GetCustomData` が返す文字列、プレイヤーの3つの参照が前回と同じときだけだ。`rewards` の配列は `OnLateStartServer` で作ったあとは中身の書き換えがなく（逆コンパイル一式と MOD ソースを grep して確認）、使用後は `RemovePlayerAndCheckEmpty` が鍵ごと外すだけである。`ChaosReward` は構造体で、`rarity` の書き込みは配列を辞書に入れる前だ。customData の文字列は `EnterEditSkill` で差し替えられ、文字列は不変なので、参照が同じなら中身も同じになる。だから参照が同じなら、キャッシュした報酬は本体の連鎖が返すものと同一になる。外れたときは本体がそのまま動くので、鍵がないとき・解析できないとき・範囲外のときの例外も本体と同じ型で同じ箇所から起きる。`GetTargetInfo` の2つの本体実装は `player` 引数を使わず `target.owner.owner` で解決するため、Prefix も同じ所有者で解決する。Prefix は `target?.owner?.owner` が null なら本体に任せる。これにより、一時的な null で catch に入り、その Prefix がセッション中ずっと無効になって警告を出すことを防ぐ。本体が同じ入力で出す例外は変えない。`DewLocalization.GetUIValue` は本体と同じく毎回呼ぶ（言語変更への追従を保つ）。この同一性は境界テストでも確かめた。テスト境界（`tests/Issue73.Native.Tests/ChaosShrineHitScanPerfBoundary.cs`）の `Shrine_Chaos` に本体5メソッドを転写し（報酬の解決連鎖と例外の型まで本体と同じ）、等価性テスト（`ChaosShrineChoiceCachePerfTests.cs`）で Prefix を経由した結果と転写本体の結果が一致することを、報酬型ごと・customData と報酬配列の差し替え・プレイヤーの切り替え・解析できない値と範囲外と鍵の消失（本体に任せること）・`GetTargetInfo` の2つの多重定義（`isLevelUpEnabled` が false のときと端数の切り捨てを含む）・設定 OFF・owner が null のときは本体に戻り、軽量化を無効にせず、その後の有効な呼び出しでキャッシュを使えることについて確かめている。

効果の見込み（推定）は報酬を選んでいる参加者の画面で、編集モードを開いている間の1フレームあたり十数回の呼び出しで、キャッシュが当たると `int.Parse` と配列の添字の解決（合計で1フレーム数μsの推定）を省けることである。文字列キーの辞書引き2回は配列と文字列の参照を比較するために残る。編集モードは神殿を使う数秒間だけなので効果は小さいが、このファイルのゲスト側に残っていた唯一の毎フレームの重複計算であり、結果が変わる箇所はない。数値は推定で、実機での計測は行っていない。
