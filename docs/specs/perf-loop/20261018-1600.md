# perf-loop/20261018-1600

対象は native Dew.Core/ActorManager.cs（アクター・エンティティ・ヒーローの一覧管理と、サーバー側の睡眠・スタック判定）。改善あり。

直した箇所: CanEntitySleep のヒーロー距離ループ。DoSleepTick が毎秒1回、CalculateWakeImmediately がヒーローの5mを超えるテレポートのたびに、アクティブな全エンティティに対してこの判定を呼ぶ。本体はループの内側で、調べる対象エンティティ自身の position（transform.position のネイティブ読み出し）を英雄の人数ぶん毎回読み直していた。MOD 側の Harmony パッチ（NativeSleepPositionPerf、設定 nativeSleepPositionReuse、既定ON）で、この読み出しを判定1回につき1回にまとめた。型判定・CanSleep・距離しきい値・try/catch は本体のまま残し、該当する読み出し箇所だけを差し替えている。

結果が変わらない理由: 読み出し位置は最初のループ回で、本体が最初に読む時点と同じである。判定は単一スレッドの同期処理で、ループの途中（列挙子の Current と transform.position の読み出ししかない）で対象エンティティは動かないため、2人目以降の比較に使い回しても同じ Vector2 になる。キャッシュの突き合わせは ReferenceEquals で行う（Entity の == は破棄済みオブジェクト同士を等しく返すUnityの演算子のため、参照そのものだけを信用する）。破棄済みエンティティの transform 読み出しで出る例外は、本体の catch へ変わらず伝わる。 Prefix が判定のたびにキャッシュを空にするため、例外で抜けた後の古い値が再利用されることもない。

効果の見込み（推定）: ホスト（サーバー）側のみの効果で、エンティティ数 ×（英雄の人数 − 1）回ぶんの transform.position 読み出しと ToXY 変換が毎秒減る。たとえば4人プレイでエンティティ300体なら毎秒900回程度（推定）。1回あたり数十〜数百ナノ秒の桁のネイティブ呼び出しのため、削減は毎秒数十〜数百マイクロ秒程度と見込む（推定）。ソロでは英雄が1人のため効果はない。

検証: python3 tools/balance/gen_cs.py --check、mod の Release ビルド、Issue73.Native.Tests 278件、SodRpg.Mod.Startup.Tests 149件（1件は環境による既存のスキップ）を通った。ゲーム内での動作は未実行（この環境ではゲームを動かせないため）。
