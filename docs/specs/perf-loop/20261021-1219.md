# perf-loop/20261021-1219

対象は `src/SodRpg.Mod/BossSharesNative.cs` である。直した内容は、このファイルが被弾ごとに呼ぶ `HasBossShares` の内側（`HostAuthority.BossShares.cs` の `TryBossShares`）で、冷経路では外側と `PrepareBossShares` の先頭で2回評価されていた `OwnershipRunning()` を、全ての被弾で1回に整えた点である。変更は `TryBossShares` の数行だけで、呼び出し側の契約（偽のときは `shares` が null）は保った。

`BossSharesNative.cs` 自体には参加者側の経路がない。パッチ先の `Monster.OnStartServer` はサーバーだけで、`Actor.DealDamage` は `[Server]` 付きで `NetworkServer.active` を確認してから本体に入るため、ゲストでは走らない。そのため規則3（被弾ごとの経路での重複した計算）の観点で、ホストとはいえ毎被弾の経路を見た。`HasBossShares` は `Actor.DealDamage` の接辞が全ダメージイベントごとに呼ぶ。敵はほぼすべて `_enemyOwnership` に登録されるので、変更前は敵への被弾ごとに `TryBossShares` → `OwnershipRunning()` → `PrepareBossShares` と進み、`PrepareBossShares` の冷経路の先頭でもう一度 `OwnershipRunning()` を評価してから保持判定に入っていた。`OwnershipRunning()` は安価なフラグではなく、`GameManager`・`ZoneManager` の静的インスタンス読み2つ、`runId` の文字列検査、参加者ループ（各人ごとに `gamePlayers.Contains` の線形走査がある O( participant 数^2) 相当）を毎回行う。

結果が変わらない理由は、削ったのは同一呼び出し内の同一条件の再評価だけだからである。`TryBossShares` は経路を分けた。速経路（`Shares` 済み）は `TryBossShares` の中で稼働確認を1回行い、冷経路は `PrepareBossShares` の先頭の稼働確認に任せる。`PrepareBossShares` は冷経路の先頭が `!OwnershipRunning()` なので、稼働していないときは保持の初期化も `FailBossShares` も副作用なく null を返す。どちらの経路でも成立条件の集合は同じで、「プレイヤーが2人未満に戻ったら共有を当てない」という現行の判定を保つ。`TryBossShares` の呼び出し元4か所（`HasBossShares`、`OverrideBossShareHealth`、`ApplyBossShareReceivedDamage`、`CommitBossShareHealth`）はいずれも戻り値が偽のとき `shares` を捨てるので、真のときのみ非 null の `shares` を返す契約は変わらない。`PrepareBossShares` を直接呼ぶ `ScanBossShares` は経路外で、内部の稼働確認はそのために残してある。例外時の振る舞いも同じで、冷経路の先頭の `OwnershipRunning()` は try ブロックの外にあるため、そこで例外が出れば変更前と同じく呼び出し元へ伝わる。try の内側（保持の初期化）の例外は引き続き `FailBossShares` で捕捉される。

効果の見込みは推定だが、冷経路に入る被弾（従来は外側と内側の2回）から `OwnershipRunning()` 1回分（静的読み2つと文字列検査と参加者ループ）が消え、全ての被弾で評価は1回に揃う。速経路は従来から1回で変わらない。1回あたりは数十ナノ秒程度の規模で、戦闘の密な場面で毎秒数百件のダメージイベントが起きても削減量は毎秒数十マイクロ秒程度と小さい。ホットな経路の定常コストを減らす地味な削減で、参加者側の負荷はこの変更では変わらない。
