# perf-loop/20261020-1112

対象は MOD の `src/SodRpg.Mod/HostAuthority.GemSlots.cs` である。このファイルの処理はホスト側だけで走る（`HostAuthority.Tick` は `NetworkServer.active` でなければ抜ける）。ゲスト側の負荷につながる出口は、`skill.SetMaxGemCount` の SyncVar 書き込み（値が変わったときだけ）、`skill.UnequipGem`（枠のはみ出しがあるときだけ）、そして `ClearGemSlotConflict` が送る `DreamforgeGemSlotConflictMsg` の3つである。

直した内容は、`TickGemSlots` が5秒ごとに行っていた `DreamforgeGemSlotConflictMsg` の再送をやめたことである。これまでは5秒ごとの周期でロード済みのヒーロー1人ずつを数え、そのヒーローの持ち主（owner）へ `disabled = false` のメッセージを送り続けていた。この周期送信を外し、メッセージはイベント時（`ApplyGemSlots` から、つまりヒーロー登録の直後とビルド適用のたび）にだけ送る形にした。周期用の `_nextGemSlotNotice` フィールドと `DetachGemSlots` でのリセットも削除した。`ClearGemSlotConflict` とメッセージ型自体は残す。

結果が変わらない理由は、このメッセージが運ぶ値が定数だからである。リポジトリ内の送信元は `ClearGemSlotConflict` の1箇所だけで、常に `disabled = false` を送る。`disabled = true` を送るコードはどこにもない。現行クライアントの受信処理（`ClientSession.OnGemSlotConflict`）は値を読み捨てるので、届く回数を減らしても受信側の状態は変わらない。GemSlotConflict プロパティが生きていた過去のクライアントでも、`_gemSlotConflict` が true になるのは `disabled = true` の受信だけなので、届いた `disabled = false` は初期値 false のフラグへの代入であり、何も変えなかった。プロトコル不一致の古いクライアントはこのメッセージを無視するので、届かないことと同じである。イベント時の送信は残るため、メッセージを受け取る可能性のある古いクライアントにも、ヒーロー登録とビルド適用の時点で従来どおり1度届く。枠の数の書き込み（`SetMaxGemCount`）とは無関係のメッセージなので、枠の見え方・判定・タイミングも変わらない。

効果の見込み（推定）は、4人協力で毎秒0.6〜0.8通（ヒーローごとに5秒に1通）の MOD メッセージをなくすことである。各1通につき、ホスト側でメッセージオブジェクトの確保と直列化と送信、ゲスト側で Mirror の受信パイプラインの通過とハンドラ呼び出しが1回ずつ減る。1通が小さい（uint と int と bool）ので、帯域としての絶対量は小さい。値が変わらない定数送信をゼロにするのが目的である。数値は推定で、実機での計測は行っていない。

検証は `python3 tools/balance/gen_cs.py --check`（変化なし）、`dotnet build src/SodRpg.Mod -c Release -p:GameDir=... -p:ModDeployDir=/tmp/perfloop-x`（0 エラー、警告6件は既存のもの）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release`（573件全通）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Mod.Startup.Tests -c Release`（225件通過・1件スキップは既存のもの）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Core.Tests -c Release`（3050件通過・7件スキップは既存のもの。`EssenceSlotLifecycleTests` が `TickGemSlots` を直接動かすため併せて実行した）を実行してすべて通した。実機（ゲーム内）での確認は未実行であり、コードとテストで理論上正しいことを確かめた段階である。
