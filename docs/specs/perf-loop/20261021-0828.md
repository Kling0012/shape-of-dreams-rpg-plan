# perf-loop/20261021-0828

## 対象

mod src/SodRpg.Mod/HostAuthority.BossBurrow.cs（Azurak の St_U_Burrow と Ai_U_Burrow_Emerge まわりの Harmony パッチと、ホスト側の補正の記録）。

## 見た範囲

本体側の Se_U_Burrow.Emerge と Ai_U_Burrow_Emerge.OnCreate/OnHit を ilspycmd で取り出して確認した。Emerge は isServer の内側からしか呼ばれず、OnCreate/OnHit に差し込まれた AdjustDaze/AdjustStun は HostAuthority.NativeInstance をホストの Tick でしか設定しないため、ゲストでは null 判定だけで終わる。Actor.OnDisable への Prefix も静的フラグと型判定のみで、ゲスト側の経路は既に軽く、改善の余地がなかった。

## 直した内容

ホスト側の被弾ごと経路 AzurakBurrowStun で判定の順序を入れ替えた。生存、NaN/Inf、敵対関係、ボス、CC無効といった安い判定を先に評価し、高価な AzurakBurrowStage（AzurakBurrowCurrent の整合チェックと BossEnsure、BossRewardStage。FindMemory を2回含む）を最後に移す。ボスやCC無効の敵へのヒットでは、これまでこのチェーンを毎回評価してから棄却していた。

## 結果が変わらない理由

&& の各判定は対象の状態を読むだけで、順序を入れ替えても真偽は変わらない。AzurakBurrowStage の一部として走る BossEnsure は、同じ emerge の OnHit より先に OnCreate の AdjustDaze が同じ判定を通すため、OnHit 側で省いても状態の更新は保たれる。返す stun の値はどの入力でも変わらない。順序入れ替え前の判定順をそのまま写したオラクル（BossBurrowStunReorderTests.AzurakBurrowStunPreReorder）と実装を同じ条件の rig で呼び比べ、ボス・CC無効・死亡・非敵対・NaN/Inf・stage==0 の各棄却とスタン加算の正常系（0/0.3/0.95/1.5秒）で返り値の一致を確かめた（原則 II）。

## 効果の見込み（推定）

burrow の攻撃が対象に当たるたび、棄却される対象（ボス、CC無効、死亡、非敵対）のヒットで FindMemory 2回と辞書引き数回を含むチェーンを省く。毎フレームではなく被弾ごとの経路なので、絶対量は小さい（推定）。
