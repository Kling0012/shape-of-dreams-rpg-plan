# perf-loop/20261024-0808

## 対象

native Dew.Contents/Shrine_CorruptedChaos.cs。堕落した混沌の神殿（`Shrine_CorruptedChaos : EditSkillShrine`）と、その花びらを揺らす `Shrine_CorruptedChaos_PetalAnimator`（同じ Dew.Contents の型で、神殿のモデルに同居する）。逆コンパイル置き場には `Shrine_CorruptedChaos.cs` のファイルが無かったので、実 DLL（`Shape of Dreams_Data/Managed/Dew.Contents.dll`）から ilspycmd で取り出して読み、reflection-dump の `_alltypes.txt`（5085〜5089行）で型の存在も確かめた。

ゲスト（参加者）側で走る経路を確かめた。毎フレームは花びらアニメの `Shrine_CorruptedChaos_PetalAnimator.FrameUpdate` だけ（`LogicBehaviour` が OnEnable で登録し、`LogicUpdateManager.Update` が距離・画面内外の間引きなしで全端末に配る）。神殿の近くでは `CanInteract` が焦点判定ごとに走るが、辞書の `ContainsKey` 1回で済む。UI を開いている間は `GetTargetInfo` と `GetEditSkillIndicatorRawText` が毎フレーム走る（`GetTargetInfo` には MOD 側の既存 Postfix がある。`GetEditSkillIndicatorRawText` は `string.Format` 1回で、神殿の前で UI を開いている短い間だけの小さな確保）。通信は `rewards` SyncDictionary の初期同期と、誰かが報酬を選ぶたびの1操作だけだった。本体側の重い処理は見当たらなかったので、3（毎フレームの経路の無駄）の観点で `FrameUpdate` を扱う。

## 直した内容

`Shrine_CorruptedChaos_PetalAnimator.FrameUpdate` は、Start で一度取っておいた花びらごとの基準スケール（`_originalLocalScales`、private）に対して、毎フレーム子ごとに `transform.GetChild(i)` を呼んで正弦波のスケールを書き戻す。花びらの階層は Start で確定したあと変わらないのに、子 Transform の解決だけを毎フレーム繰り返していた。そこで NativeChaosPetalIdlePerf を新設した。`FrameUpdate` への Prefix で、インスタンスごとの `ConditionalWeakTable` に花びらの Transform の配列を覚えておき、元の本体と同じ式・同じ順序でスケールを計算して書き、本体を飛ばす。基準スケールは本体の `_originalLocalScales` を FieldRefAccess で読むので、Start の値をそのまま受け継ぐ。`Time.time` はフレーム内で一定なので、2つの積（`Time.time * sin0Time`・`Time.time * sin1Time`）をループの外へ出しても値は1ビットも変わらない。子の数が Start の把握と合わなくなったときは現れる階層から作り直し（本体の `GetChild` が読むのと同じ並び）、Start の把握より子が減ったときはそのフレームを本体に返す。元の本体の残りの文は空の `base.FrameUpdate()` 呼び出しなので、飛ばしても何も起こらない。対象の `FrameUpdate` か `_originalLocalScales` が見つからない・形が違う・例外のときは警告を1回出してこの修正だけ外れる（fail-soft）。設定は DreamforgeConfig.nativeChaosPetalIdle（既定は有効）。

テスト側は、リンクされた NativePerfPatches.cs がコンパイルに必要とする本体 API の境界に、`Mathf.Sin`、`Transform` の部分宣言への `childCount`・`GetChild`（子の一覧を持たせ、`GetChild(i)` が i 番目の子を返す）、`Shrine_CorruptedChaos_PetalAnimator` の模倣（NativeBoundary.cs。`Start`・`FrameUpdate` は実 DLL 逆コンパイルと同じ式の転写）、`DreamforgeConfig.nativeChaosPetalIdle`（NativeEmbracePositionBoundary.cs）を足した。ChaosPetalIdlePerfTests（4件）で模倣に対して確かめる: Prefix の書き込みが本体の式と全部の子でビット単位で一致して false を返すこと、子の一覧が変わってキャッシュを作り直す場面でも一致すること、子が Start の把握より減ったフレームは true を返して何も書かないこと、設定が無効のときは true を返すこと。このテストを書いた過程で、キャッシュの作り直し条件が配列長（初回以降不変）を見ていて子の増加を検出できない（本体の `GetChild` が読む並びと変わる）のに気づいたので、キャッシュ構築時の子の数を覚えて増減で作り直すように直した。

## 結果が変わらない理由

書き込む値の式は本体と1語1句同じで、読む Transform も `GetChild(i)` が返すのと同じオブジェクト（子の並びが変わっていないとき。変わったときは本体と同じ並びの作り直しか、本体への返送）。`Mathf.Sin` への入力も同じ積と和の順なので、スケールは毎フレーム本体と同じ値になる。飛ばした `base.FrameUpdate()` は `LogicBehaviour.FrameUpdate` の空の本体で、副作用がない。花びらの階層は Start 以後変わらないのが本体の前提でもある（基準スケールを Start で一度だけ取る）ので、キャッシュの前提は本体と同じものを共有する。見た目（花びらの揺れ）・判定・数値・同期には触れていない。

## 効果の見込み（推定）

神殿の部屋が読み込まれている間、ホスト・ゲストの全端末で毎フレーム、花びらの数（prefab にしか書かれておらず、実測はできないので推定）だけあった `Transform.GetChild` のネイティブ呼び出しが、テーブル参照1回と `childCount` の確認1回に減る。花びらの数を n として、フレームあたりのネイティブ相互運用呼び出しが n 回から 2 回に減る（推定）。`GetChild` 1回は 0.1 マイクロ秒程度の小さな呼び出しなので、効果は神殿1つあたり微小だが、待ち時間のない毎フレームの経路で、神殿が画面の外でも動き続けていた分が減る。
