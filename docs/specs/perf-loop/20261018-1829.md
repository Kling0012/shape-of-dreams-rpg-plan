# perf-loop/20261018-1829

対象: mod src/SodRpg.Mod/ClientSession.KillSync.cs（と、そこから毎フレーム呼ばれる経路）。

直した内容: `ClientSession.Tick` → `TickKillSync`（ClientSession.KillSync.cs:423）は、差分送信対応のホスト（`_hostKillReceiptDelta`）と接続している間、`TickKillReceiptDelta`（同:495）を毎フレーム実行する。その中の受領状況（receipt）の汚れ検査は `_nextKillAck` が汚れありのときしか進まず、受領状況が変わらない静止状態でも毎フレーム `acknowledged` 全件に対する辞書引き（streamId の文字列ハッシュを伴う `_killSentReceipts.TryGetValue`）を繰り返していた。検査の入力が前回と同じであることを、`KillReceiptsForProgress` の戻り値の参照比較（`_killReceiptScanSource`）で確かめ、同じ間は検査を0.25秒間隔に間引き、`ResetKillReceiptSchedule` で参照のキャッシュも無効化するようにした。

結果が変わらない理由: 検査結果を変えうる入力は `KillReceiptsForProgress` の戻り値と `_killSentReceipts` の2つに限られる。前者は `Profile.KillClassification.Receipts`・`_killDurableReceipts`・静的な空配列のいずれかで、いずれも Capture・保存完了による昇格・復元でのリスト差し替えを通じてのみ変わる（`AcknowledgedThrough` への書き込みは Clone と読み込み時の初期化にのみ存在し、公開後の書き換えはない）。参照が同一なら内容も同一のため、検査結果は前回と同じ0（汚れなし）になる。後者は送信後に送った内容と同期し、クリアは `ResetKillReceiptSchedule` のみで、そこでは `_nextKillAck` も0に戻し参照キャッシュも無効化するため、次のフレームで必ず再検査する。欠落ファクトの再送（0.5秒枠）と心跳（30秒枠）は独立した門で変わらない。参照が同じ静止状態では、送信の判断・内容・時刻は従来と同じになる。門が閉じている間にリストが差し替えられたときだけ違いがあり、従来は次の門（最大0.25秒後）まで送信が遅れたのに対し、参照の変化で同じフレームに検査して送るため受領の報告が最大0.25秒早まる。内容は同じで、ホストは受領状況を累積的に受け取るため扱いは変わらない。

効果の見込み（推定）: 接続中のクライアントセッションごとに、毎フレームの受領状況1〜3件程度の辞書引きと文字列ハッシュ計算が、変化があるたびと0.25秒ごとにだけ行われる形に減る。1フレームあたりの削減は小さい（数百ナノ秒程度と推定）が、接続中は常時動く経路である。通信量・ゲーム内の数値・判定には影響しない。
