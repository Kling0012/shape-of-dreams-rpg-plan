# perf-loop/20261018-1729

対象: native Dew.Core/AttachToFace.cs（と、そこから毎フレーム呼ばれる `Update` → `TryGetWorldPositionAndRotation` → `Dew.GetBakedMeshOptimized` の経路）。

直した内容: `AttachToFace` は毎フレーム `TryGetWorldPositionAndRotation` で共有の焼きメッシュのキャッシュ（`Dew.GetBakedMeshOptimized`）へ問い合わせるが、実際に焼き直しが起きるのはレンダラーごとに `Dew.BakeMeshInterval`（0.1秒）ごとで、それ以外のフレームでは問い合わせは必ず「新しくない」を返す。そこを、`Dew.GetBakedMeshOptimized` の Postfix でレンダラーごとの最終焼き直し時刻を記録し、`TryGetWorldPositionAndRotation` の Prefix で「前のフレーム以降に焼き直しがなく、まだ間隔内」と確実に言えるときだけ本体の問い合わせを飛ばして偽を返すようにした。MOD 設定 `nativeAttachFaceIdle`（既定ON）で切れる。

結果が変わらない理由: 飛ばすのは、本体の問い合わせが同じく偽を返すと証明できる場合だけ。キャッシュの項目は間隔が切れるまでは削除も置き換えもされず、焼き直し時刻がこのフレームなら（ほかの装飾品や `FxMeshTrail` が焼いた場合も Postfix で記録する）問い合わせを実行して本来の処理を行う。省いたのはプールの貸し借りと辞書の読み書き・参照カウントの一時的な増減で、これらは外部から観察できない。装飾品の位置・回転の補間計算と、焼き直しフレームでの頂点読み出しは本体のまま。

効果の見込み（推定）: 装飾品1つにつき毎フレーム約6回の辞書操作と2回のプール操作が、フレームの約9割からなくなる（60fps なら0.1秒あたり6フレーム中5フレーム）。英雄1人に数個の装飾品が付いている想定で、CPU を秒あたり数十〜数百マイクロ秒程度減らす見込み。数値は推定。

## 修正ラウンド（レビュー F1/F2）

ネイティブ側の時刻基準: 逆コンパイルした Dew.Core/Dew.cs の `GetBakedMeshOptimized` を確かめた。再焼き込みの判定は `Time.unscaledTime - bakeUnscaledTime > BakeMeshInterval`、isNew の判定は `bakeUnscaledTime == Time.unscaledTime` で、どちらも `Time.unscaledTime` を使う。MOD の記録と判定も同じ時刻なので、`Time.timeScale` が 1 以外でも本体との基準はずれない。この根拠を `NativePerfPatches.cs` のコメントに記した。

記録表の掃除: `LastNewBake` が 64 項目を超えたときの全消去は、焼き直し対象のレンダラーが 64 を超える場面（敵が多い、`FxMeshTrail` が多い）で新しい記録まで消して、省略の効果を長期間失わせていた。間隔（`Dew.BakeMeshInterval`）を過ぎて省略判定に使えなくなった項目だけを `PruneStale` で除く方式に変えた。間隔を過ぎた項目は Prefix が本体に戻す対象なので、除いても結果は変わらない。破壊されたスキンの項目も間隔を過ぎれば次の掃除で除かれる。

テスト: 省略判定を時刻と間隔を引数に取る純関数 `ShouldSkipLookup(baked, now, interval)` に切り出した。tests/Issue73.Native.Tests に6件のテストを追加した（`AttachFaceIdlePerfTests`。抽出は `NativePersistence.targets` の既存の仕組み、境界は `AttachFaceIdlePerfBoundary.cs`）。確かめるのは、同一フレーム・間隔ちょうど・間隔超過・記録なし・設定 OFF の各境界での本体呼び出しの有無、焼き直し後の間隔内の照会だけが偽で省略されること、Postfix が isNew のときだけ記録すること、しきい値超過時に間隔を過ぎた項目だけが掃除され省略が続くこと。

検証（修正後）: `python3 tools/balance/gen_cs.py --check` 合格、`dotnet build src/SodRpg.Mod -c Release`（`-p:GameDir` と `-p:ModDeployDir` を指定）合格・警告は既存、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release` 293件合格（追加6件を含む）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Mod.Startup.Tests -c Release` 149件合格・1件スキップ（既存）。実機での動作確認は未実行。

## 修正ラウンド（F1: 本体キャッシュの消去経路の監査）

レビュー F1 が前提として確かめるように求めた「間隔内のキャッシュ項目は削除も置き換えもされない」を、逆コンパイルした Dew.Core の全経路で調べた。`Dew._skinInstanceIdToNewestMeshId`（スキン→最新の焼きメッシュ）から項目を除く経路は次の4つだけで、セッションの途中で表を消す Clear 系の処理は本体側にない。

1. `Dew.GetBakedMeshOptimized` の維持走査（1秒に多くとも1回）: 参照カウントが0で、かつ `Time.unscaledTime - bakeUnscaledTime > BakeMeshInterval` の項目だけを除く。
2. 同メソッドの焼き直し分岐: 前の項目が `BakeMeshInterval` を過ぎていたときだけ、前の項目を除いて焼き直す。
3. `Dew.BakedMeshHandle.Return()`: 参照カウントが0になり、かつ `BakeMeshInterval` を過ぎた項目だけを除く。
4. `Dew.OnInitBakeMesh`（`RuntimeInitializeOnLoadMethod`）: 表全体を作り直すが、プレイヤーの起動時に一度だけ動く。

1〜3はいずれも間隔を過ぎた項目しか除かない。間隔を過ぎた項目は MOD 側の省略判定（`ShouldSkipLookup`）も本体へ戻す対象なので、除かれても省略と本体の結果は一致する。4は起動時の一度だけで、その時点では MOD の記録表は空（プレイ中の焼き直しはまだ起きていない）。部屋の読み込み（`OnRoomLoadedBakeMesh`）は遊休メッシュのプールを破棄するだけで、スキンから焼きメッシュへの表は触らない。以上から、`LastNewBake` を Clear する Postfix を足す必要はなく、この監査結果を `NativePerfPatches.cs` のコメントに記録した。この変更はコメントと文書だけで、動作は変えない。

残る前提: 将来のゲーム更新でセッション中の全消去が加わった場合や、Unity が破棄したスキンで使っていたインスタンス ID を新しいスキンに再利用した場合、省略が1回の焼き直しを最大 `BakeMeshInterval`（0.1秒）のあいだ隠せる。影響は装飾品の追従が一時的に遅れるだけで、次の焼き直しで直り、設定 `nativeAttachFaceIdle` で無効化できる。シグネチャの変更は `Prepare` の引数検証が、実行時の失敗は Prefix/Postfix の try-catch＋Warn が検知してこの機能を止める。ただし新たな消去経路の追加のような意味の変化は検知できないため、この前提は将来に残す指摘として PR 本文にも記録する。
