# perf-loop/20261021-0258

対象は `src/SodRpg.Mod/HostAuthority.SupportOverheal.cs` である。このファイルは、回復の経路に割り込む Harmony パッチ3本（`Actor.InvokeOnDoHeal`・`Actor.DoHeal`・`Actor.InvokeOnGiveShield`）と、溢れ回復の障壁（SupportOverhealWard）の管理を持つ。3本のパッチはいずれも `NetworkServer.active` を見て参加者の PC では抜ける。本体の `Actor.DoHeal` 自体も `[Server]` 属性と `NetworkServer.active` のガードを持つため、このファイルの処理はホストでしか走らない。参加者側の経路がなかったため、指示の3の観点（被弾・回復ごとの経路の無駄）で見て、ホスト側の1箇所を直した。

見つけた無駄は、`Actor.DoHeal` へのパッチ（NativeSupportHealScope）が、呼び出しごとの状態を Harmony の `__state`（構造体）で持っていたことである。Harmony 2 は `__state` を object 型の局所変数として受け渡すため、値型の状態は呼び出しごとにボックス化されてヒープに確保される（ゲームに同梱の Harmony は 2.3.6）。この構造体は EventInfoHeal に bool と int を足した64バイト強のものである。`Actor.DoHeal` はホスト上のすべての回復（`HealData.Dispatch` の経路、時間経過で回復するステータス `Se_GenericHealOverTime` の各ティック、回復オーブ `Pickup_HealthOrb` など）で呼ばれ、本体の `DoHeal` の本体は FinalHealData も EventInfoHeal も構造体で、呼び出しごとのヒープ確保を行わない。そのため、MOD がこの経路に足している呼び出しごとの確保は、このボックス1つである。

直した内容は、`__state` をやめて、深さを添え字にした静的配列2本（EventInfoHeal と bool）へ退避先を変えたことである。Prefix は退避する値を `Depth` の位置に書いてから `Depth++` と `Active = false` を行い、Finalizer は `Depth--` して同じ位置から戻す。配列は最初8段で、入れ子がそれを超えたときだけ倍に伸ばす。外部から読まれる `NativeSupportHeal.Current` と `Active`（`HostAuthority.OnHealTaken` が `DoHeal` の内側で読む）と `Depth`（NativeSupportHeal.Prefix のガードが読む）の意味は変えていない。このクラスを参照するテストはない。

結果が変わらない理由は、保存と復元の対応が元の `__state` と同じだからである。Harmony の Finalizer は、メソッドが正常終了したときも例外で抜けたときも1回必ず走る。そのため Prefix で書いた位置は、Finalizer の `Depth--` で必ず読み返される。`Depth` の書き手はこのクラスの Prefix と Finalizer だけで、入れ子は必ず入れ子の順に抜けるため、後入れ先出しの対応は崩れない。復元する値と復元のタイミングも同じで、入れ子の各段が自分の段の位置だけを書く点も、呼び出しごとに `State` が積まれていた元の形と同じである。追加した `Depth <= 0` のガードは、Prefix が配列の確保に失敗したときに深さが負へ抜けるのを防ぐためだけのもので、通常の経路では常に偽になる。

効果の見込み（推定）は、ホストの回復1回ごとの構造体1個分のボックス化がなくなることである。回復は戦闘中に秒間数十回に達しうる（時間回復のステータスが複数の対象に付き、オーブの取得も重なる）ため、毎秒数百バイトから数KB程度のごみの発生が消えると推定する。数値は推定であり、実機での計測は行っていない。ホスト側のみの変更で、参加者の PC の負荷は変わらない。
