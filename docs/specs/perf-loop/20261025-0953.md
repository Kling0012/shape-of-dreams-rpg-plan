# perf-loop/20261025-0953

対象は MOD `src/SodRpg.Mod/HostAuthority.GemSlots.cs`（278行）である。ゲスト（参加者）に関係する経路から先に見た。このファイルがゲストに届けるものは、枠の数の SyncVar 書き込み（`SetMaxGemCount`、値が変わるときだけ `decision.ShouldWrite` で書くので定常状態では送信ゼロ）、はみ出したエッセンスを落とす `UnequipGem`（はみ出しが見つかったときのイベント）、そして前回のループで定期的な再送が止められた競合解除メッセージ（イベント駆動のみ）である。本体の `Network_<maxGemCount*>k__BackingField` のセッタ（`Dew.Core/HeroSkill.cs:315`）は値が同じなら同期を汚さないので、このファイルのゲスト側の通信はすでに太っていなかった。そのため視点を3・4に移し、ホストで1秒ごとに走る経路を見た。

見えた構造は次のとおりである。`TickGemSlots`（1秒ごと）は各英雄につき `UpdateGemSlot` を2回（Identity・Movement）呼び、同じく1秒ごとの `TickLevelGemSlots`（`HostAuthority.LevelGemSlots.cs`、Q・W・E・R）がさらに4回呼ぶ。`UpdateGemSlot` は呼ばれるたびに、はみ出したエッセンスを探す全走査をする（`HostAuthority.GemSlots.cs:239`）。この走査は省けない。本体の `HeroSkill.EquipGem`（`HeroSkill.cs:927`）は枠の数を確認せず、保存データの復元（`DewPersistence.cs:1342`）と再参加（`DewPlayer.cs:4369`）は保存済みの場所（任意のインデックス）にそのまま装備するので、プレイ中のいつはみ出しが生まれてもおかしくない。だから走る回数は変えられず、1回の走査の中身を見た。

走査の `foreach (var kv in skill.gems)` は、本体の `NetworkBehaviourDictionaryWrapper`（`Dew.Core/NetworkBehaviourDictionaryWrapper.cs:52`）の列挙子を通る。この実装は `Enumerable.Select(...)` の遅延評価なので、走査1回ごとに LINQ の反復子を1個と、インターフェース越しごとに箱詰めした辞書の列挙子を1個確保し、要素1個ごとに委譲の呼び出しと `(Gem)(NetworkBehaviour)` のキャストとペアの複製が乗る。英雄1人あたり毎秒6回の走査がこれを繰り返していた。

直した内容は、走査を鍵だけの列挙に替えることである。`skill.gems.Keys` はラッパの `Keys` から本体の `SyncIDictionary.Keys`（`Mirror/SyncIDictionary.cs:66`）を素通りして生の辞書の鍵並びに届くので、LINQ の反復子も要素ごとの委譲呼び出しもなくなる。鍵が一致した項目だけ `TryGetValue` で値を読み直し、null の項目は今どおり外す。

結果が変わらない理由は次のとおりである。辞書の鍵は一意で、鍵の列挙順はペアの列挙順と同じなので、集まる項目の集合も `_gemOverflow.Sort` のあとの並びも同じであり、`UnequipGem` を呼ぶ順序と回数は1つも変わらない。走査の実行回数と実行時点も変わらない。値が変わらない限り SyncVar を書かない構造も、ゲストへの送信も、そのまま保留してある。

効果の見込み（推定）は、英雄1人あたり毎秒12個（走査6回×確保2個）だった小さな確保が毎秒6個になり、要素の移動も委譲呼び出しから直接の列挙に変わることである。プレイヤー4人の無限モードでは毎秒約48個が約24個になる計算で、大きさはGCの churn の削減にとどまるが、定常的に乗っていたものだけに確実に減る。数値は推定で、実機での計測は行っていない。
