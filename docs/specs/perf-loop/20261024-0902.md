# perf-loop/20261024-0902

対象は `src/SodRpg.Mod/HostAuthority.BossWorldCracker.cs` である。直した内容は、光の報酬6個（WorldCracker の拍動）の判定が走る被弾ごとの経路で、同じ検証を1回余分に繰り返していた点である。`WorldCrackerDamage` は `WorldCrackerCurrent(state)` で束縛の有効性を確認した直後に `RefreshWorldCracker` を呼んでおり、`RefreshWorldCracker` の入り口でも同じ述語をもう1回評価していた。この2つの呼び出しの間には何も走らないため、入り口の再検証は結果が同じになることが確実な重複計算である。そこで `RefreshWorldCracker` を、入り口の検証をする本体と、検証済みの束縛を受け取って先へ進む `RefreshWorldCrackerValidated` に分け、被弾ごとの経路からは後者だけを呼ぶようにした。本体の `Tick`（0.1秒ごと）と `ActiveLogicUpdate` の Prefix から呼ぶ従来の `RefreshWorldCracker` は、入り口の検証を保ったまま何も変わっていない。

結果が変わらない理由は次のとおりである。`WorldCrackerCurrent` はフィールドと本体側の状態（`isActive`・`creationTime`・装備辞書）を読むだけの述語で、単一スレッドの Unity で、その間に何も実行されない2回の呼び出しは必ず同じ値を返す。述語の中の `FindMemory` が装備エポックの変化時に辞書を作り直す場合も、作り直しは1回目の呼び出しの中で完結し、2回目は作り直し後の同じ辞書を読むので、1回目の結果に揃う。`RefreshWorldCrackerValidated` が `BossEnsure` の後で行う再検証（辞書の載し替えと同一性確認）は残しており、`BossEnsure` が `ClearBossEffects` 経由でこの束縛を止めたときの動作は従来どおりである。拍動の予約・段階の再設定・束縛の終了のどれも、起こる条件と順序が変わっていない。

効果の見込みは推定だが、ビームが敵に当てるダメージ1回ごとに `WorldCrackerCurrent` の1回分がなくなる。この述語1回は、装備エポックの辞書引き2回、`parentActor` の祖先走査（`FindFirstAncestorOfType`）、作成時刻の同一確認4回、部屋と走行の一致確認を含む数十操作であり、ビームは `damageInterval` ごとに範囲内の敵全員に当てるため、敵の数だけこの削減が乗る。ホスト側の被弾ごとの経路の削減であり、参加者側の処理・通信は変わらない（本体の `ActiveLogicUpdate` はダメージ部分の直前で `isServer` の確認で抜けることを逆コンパイルで確認しており、このファイルの参加者側の経路はガード付きの Prefix と辞書の空引きだけである）。実機（ゲーム内）での確認は未実行である（この環境ではゲームを動かせないため）。
