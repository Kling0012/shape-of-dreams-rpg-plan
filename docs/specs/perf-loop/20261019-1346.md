# perf-loop/20261019-1346

## 対象

`src/SodRpg.Mod/HostAuthority.MemoryActivationAttribution.cs`。ホスト側の被弾ごとの記憶帰属、とりわけ `Actor.DealDamage` のすべての呼び出しで走る `NativeAttributedDamagePacket` の前置処理を見た。このファイル自体は通信を直接扱わない（発行した `MemoryActivationPublished` はホスト側の機構処理に渡るだけなので）、被弾ごとの経路の観点で確認した。

## 直した内容

`BeginAttributedDamagePacket` の承認条件から、被弾ごとの2度目の祖先走査 `!IsPairReactionSource(actor)` を外した（1行削除とコメント）。

`IsPairReactionSource` が評価されるのは、`&&` の左から順に、`TryGetMemoryActivation` が true を返したときだけだが、true は祖先走査が根まで完了したときにしか返らない。その走査は途中に Gem・要素状態効果・gem 付き AbilityInstance があれば false を返す。`IsPairReactionSource` は同じ連鎖を同じ述語（Gem・要素状態効果・gem 付き AbilityInstance）で探すだけの2度目の走査なので、この経路では常に false になる。サイクル検出も、true が返る経路では本体側の例外が出て到達しないため、走査長の上限（128）との違いは影響しない。

## 結果が変わらない理由

上のとおり、評価されうる経路で `IsPairReactionSource` の戻り値は常に false なので、`packet.Admitted` は変わらない。2つの走査の間に外部コードは入らず（辞書引きだけ）、`EnsureMemoryAttributionEquipment` は1回目の走査の内側で既に走っているので、今日のコードが持つ再入の余地は変わらない。`IsPairReactionSource` 自体はギミックやキルアシストなど別の経路で引き続き使うため、削除はしていない。

なお本体（r1.4.1.2）の `AbilityInstance.gem` の getter は遅延検索になっており、gem の付いていないインスタンスでは読むたびに `FindFirstOfType<Gem>()` が祖先を根までたどる。被弾ごとの2度目の走査はこの検索を gem なしインスタンスについてもう1回繰り返していたので、省略の効果は gem なしの投射体・通常攻撃が多い場面で大きい。

## 効果の見込み

承認された被弾（記憶の帰属対象になる攻撃）ごとに、祖先連鎖の長さ（ふつう2〜5ノード、gem なし AbilityInstance では本体の遅延検索の分も含めて実質2倍）ぶんの走査が1回減る。被弾が集中する戦闘でホストの被弾経路の所要を数パーセント下げる見込み（推定は推定。実測はしていない）。
