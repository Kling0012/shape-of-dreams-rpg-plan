# perf-loop/20261019-2119

## 対象

native Dew.Core/EntityStatus.cs（ゲーム本体の逆コンパイル。ステータス管理。SyncVar 26個と、再計算のたびに全員へ飛ぶ空の ClientRpc を持つ）。

## 直した内容

`EntityStatus.CalculateStats`（HostAuthority.MpFixes.cs や本体の DamageData 処理など、あらゆるステータス変化のたびにホストで走る再計算）は、末尾で体力とマナを「入口で取った比率 × 新しい最大値」で書き直す（`currentHealth = num * data.maxHealth`）。最大値が動いていない再計算では、この書き換えは float32 の「割ってから掛ける」の往復計算で、2000万サンプルの実測で約9.5%が1 ulp だけ異なる値になる。Mirror の SyncVar セッターは値が違うと dirty ビットを立てるため、次の同期間隔で、全参加者がすでに持っているのと同じ float が全員に再送される。

減衰する基本効果（スローなど）を持つ実体は `UpdateStatusEffectInfo` が毎ロジックフレーム再計算を要求し、効果の追加・除去・StatBonus の出入りもそのたびに再計算するため、戦闘中はこの無意味な再送が絶えず発生する。

MOD 側に `EntityStatus.CalculateStats` への Prefix/Postfix を足した（`NativeStatsRatioIdlePerf`）。Prefix は入口の体力・マナ・最大値を記録し、Postfix は最大値がビット単位で不変だった場合に限り、入口の値を weaver 生成の `Network_currentHealth`/`Network_currentMana` セッターで書き戻してから、入口で立っていなかった dirty ビット（体力 0x80・マナ 0x100。セッターの IL から定数を読んで照合する）を落とす。設定 `nativeStatsRatioIdle`（既定有効）で切れる。

## 結果が変わらない理由

窓の外での書き込み（ regen・SetHealth・ダメージ）は対象外で、窓の中で他のコードが書いた値は本体自身の比率書き換えが上書きする（プロセッサは書き換えの前に走り、finalStats のイベントは後に走るが、どちらも最終値は比率計算の結果が勝つ）。最大値が動いた再計算は何もせず本体どおりで、比率維持はそのまま生きる。書き戻し後のホストの値は入口の値と同一で、参加者側の値とも一致するため、落としたビットの分は「全員がすでに持っている値の再送」だけを消している。電話の代わりになる通知（RpcInvokeStatsCalculated、SyncVar フック）はすべて元どおり鳴る。

 guard を2か所入れた。入口の体力が正で書き換え後が0以下になるケース（非正規化数のアンダーフロー。本体なら `LogicUpdate` の死亡判定で倒れる）は書き戻さず本体どおりに倒れる。最大値が異常な0になっている場合は本体なら NaN が入るが、書き戻しで最後の有限値を保つ（実害より狭い偏差）。ゲストは窓の中の値を一切受け取らないので、参加者から見た状態は本体と同一。

## 効果の見込み（推定）

ホストでの再計算9.5%（最大値不変かつ比率の往復が1 ulp ずれた場合）について、体力・マナ各4バイト+マスク8バイト×全オブザーバー分の送信と、参加者側の受信・代入がなくなる。減衰効果の多い戦闘で、実体あたり毎秒数回〜数十回の無駄な同期が消える見込み（推定）。ホスト側の体力の 1 ulp ドリフトもなくなる。判定・見た目・通信の届き方は変わらない。
