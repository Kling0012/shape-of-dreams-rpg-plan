# perf-loop/20261025-1358

対象: `native Dew.Core/StandardProjectile.cs`（標的追尾の弾が毎ロジックティックごとに通る、本体 `Projectile` の標的解決）。MOD から Harmony の Prefix で `Projectile.Network_targetEntity` の getter を軽くする。

## 直した内容

`Projectile`（`StandardProjectile` の基底クラス）の `Network_targetEntity` getter は Mirror 生成の SyncVar 参照で、中で `GetSyncVarNetworkBehaviour(____targetEntityNetId, ref _targetEntity)` を呼びます。この Mirror の実装はホスト（isServer）では設定時に書き込まれた `_targetEntity` をそのまま返す O(1) ですが、純クライアント（協力プレイの参加者）では `NetworkClient.spawned` の辞書引き、`NetworkBehaviours[componentIndex]` の配列アクセスとキャストを呼び出しごとにやり直します。結果を `_targetEntity` に書き戻すだけで、読み取りがキャッシュから返ることはありません（Mirror.dll の逆コンパイルで確認）。

MOD 側に `NativeProjectileTargetSyncVarPerf` パッチ（`NativePerfPatches.cs`）を追加しました。純クライアントのときだけ、解決済みの `_targetEntity` が今の `____targetEntityNetId` と一致するならそれをそのまま返します。一致の判定は (netId, componentIndex) の比較です。設定（DreamforgeConfig の `nativeProjectileTargetClientFast`、既定は有効）で切れます。getter やフィールドの形が違うときは Prepare で1回だけ警告を出してこの修正だけ外れます（fail-soft）。

参加者側で走る経路は次のとおりです。追尾弾（entity mode、`Projectile.OnPrepare` で標的のあるときに設定される）は、`LogicUpdateManager` のロジックティック（約30Hz）ごとに `Projectile.LogicUpdate` → `StandardProjectile.PositionSolver` → `GetTargetWorldPosition()` → `targetEntity` を読み、`rotationType` が `Target` の弾は `RotationSolver` でもう1回読みます。追尾弾は基本攻撃のほとんど（標的のある `AttackProjectile`）と魔物の射撃に当たるため、魔物が多い戦闘では参加者で常に数十発が飛んでいます。値は OnPrepare で1回設定され、OnDisable で解除されるだけで、飛行中に変わることはありません。つまり参加者は、前のティックと同じ答えになる辞書引きを毎秒数百〜数千回やり直していました。

## 結果が変わらない理由

- 一致の判定は (netId, componentIndex) の比較です。netId は生きている NetworkIdentity の間だけ一意で、Mirror はクライアント側の削除で必ず GameObject の破壊（Unity-null 化）か `Reset()` による netId=0 化のどちらかを行います（Mirror.dll の `NetworkClient.DestroyObject` を逆コンパイルで確認。unspawn handler 経路は Reset、生成プレハブ経路は Object.Destroy、シーン配置経路は非アクティブ化+Reset）。破壊なしの除外はホストクライアントの `OnHostClientObjectDestroy` だけで、これは isServer の除外により対象外です。componentIndex は `InitializeNetworkBehaviours` が `NetworkBehaviours` の添字と同じ値を入れるため、判定が通るとき元の実装が返すオブジェクトと同じ参照を返します。
- 標的の despawn 後は、破壊されたときは Unity-null で判定を通らず本体が解決します（辞書にないので null。本体と同じ）。Reset されたときは netId=0 で不一致になり、同じく本体に任せます。同期での標的の変更（再設定）も netId か componentIndex が変わるので不一致になり、本体が解決します。ミスのときは常に本体経路そのものです。

ホストと、netIdentity がない状態は対象外で、本体どおりに動きます。ホストの本体経路はすでに O(1) なので、速くなる余地も遅くなる余地もありません。飛行の計算（`PositionSolver` の数値）、判定、通信の内容は何も変えません。読み取りの結果が同じであるだけです。

## 効果の見込み（推定）

参加者で、飛行中の追尾弾1つあたりティックごとに1〜2回の辞書引きと配列アクセスとキャストが、等値比較2〜3回に置き換わります。ロジックティックは約30Hzで、魔物の多い戦闘で同時追尾弾が数十とすると、毎秒数百〜数千回の置き換えになります。1回あたりの節約は辞書引きと配列アクセスとキャストを等値比較に置き換える数十ナノ秒程度（推定）で、効果は小さいものの、参加者側の毎ティックの経路に乗る純粋な無駄です。ホスト側の経路と送信量は変わりません。実測はできていません。

なお、対象ファイルの残りも確認しました。`PositionSolver` の毎ティックの計算は確保がなく、`Adaptive_ShouldPlayEffects` による演出の間引きは本体の仕様の一部なので触れていません（処理の前倒しは、負荷が揮発するときの再開後の速度が変わるため見送りました）。SyncVar は作成時に1回設定されるだけで送り過ぎはなく、RPC は命中・完了・消散の演出の通知で、送るべきものなので間引いていません。
