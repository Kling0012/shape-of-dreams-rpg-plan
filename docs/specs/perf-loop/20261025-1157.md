# perf-loop/20261025-1157

対象は本体 `Dew.Core/RoomMonsters.cs`（2478行）である。reflection-dump の `RoomMonsters.txt`（公開メンバー）と逆コンパイルの照合を済ませた。まず参加者側で走る経路を全部点検した。毎フレームの `ActiveLogicUpdate` は `DoEnvSpawnLogicUpdate` を呼ぶが、中身は `base.isServer` の確認で即座に帰り、キャンプ（`Camp.DoCampTick`）も `_camps` の構築ごと `OnRoomStartServerRoutine` からなのでホスト専用である。ウェーブのスポーン（`SpawnMonstersRoutine`・`WaitForPopulationRoutine`・`GetSpawnMonsterPosRot`）も呼び出し元がホストの生成フローに限られる。参加者が受け取る通信は、ミニボス出現時の `CallOnCreateAsMiniBoss`（出現1件ごとで中身は仮想呼び出し1つ）と、部屋のプリウォーム一覧である `RpcPrewarm`（部屋開始時）と `TpcReplayPrewarm`（途中参加の参加者の英雄が用意できた後）の3つだった。このうち毎回の無駄があったのは `RpcPrewarm`／`TpcReplayPrewarm` の両方から呼ばれる `ApplyPrewarm` である。

`ApplyPrewarm` は項目（`PrewarmEntry`）ごとの `ResolveClientPrewarmPrefab(assetId, ownerNetId)` を、keep set を作るためと `SpawnManager.Prewarm` の個数を数えるための2つのループで、**同一の引数で2回**呼んでいる。1回の解決は `DewResources` の辞書引き数回、Mirror の `Utils.GetSpawnedInServerOrClient` の辞書引き、`GetSuggestedVarDef` による `VariantDef` の計算、`ResourceLoadSettings` の組み立てで、その種の variant が初めてのときは Addressables の同期ロードと prefab 全体の `Instantiate` まで走る。2回目は1回目でキャッシュが温まっているとはいえ、同じ値を返すだけの引き直しである。

直した内容は、`RoomMonsters.ApplyPrewarm` への Prefix 置き換えである（`NativeRoomPrewarmResolveOncePerf`）。1つのループで keep set と個数の辞書を両方埋め、以降は元のコードと同じ順序で `ReleaseInactivePoolsExcept(keep)` → `AgeAndDropInactivePools()` → 項目ごとの `SpawnManager.Prewarm(prefab, count)` を呼ぶ。本体クラスへの参照は名前引き（`AccessTools.TypeByName`）と delegate にして、この MOD がコンパイル時に型を知らなくても済む形にした。パッチは `NativePerfOptions.RoomPrewarmResolveOnce`（`DreamforgeConfig.nativeRoomPrewarmResolveOnce`、既定は有効）で切れる。失敗時の扱いは、`Prepare` で型・メソッド・ネストした struct・フィールドのどれかが取れないときは警告を1回出してパッチごと外れる。実行時の例外も警告を1回出す。解決ループ中の例外では `true` を返して本体の元の2回解決に処理を戻す。プールの解放・経過処理・プリウォームの副作用を始めた後の例外では、二重実行を避けるため `false` を返して今回の暖機を終了する。テスト側は、既存の `DreamforgeConfig` の模倣（`tests/Issue73.Native.Tests/NativeEmbracePositionBoundary.cs`）に同じ名前のフィールドを1つ足した。あわせて本体 API の模倣（`RoomPrewarmResolveOncePerfBoundary.cs`）と等価性テスト（`RoomPrewarmResolveOncePerfTests`）を足した。模倣は `ApplyPrewarm` の2ループ版の逆コンパイル転写と、`PrewarmEntry`・`ResolveClientPrewarmPrefab`・`SpawnManager.ReleaseInactivePoolsExcept`／`Prewarm<T>`・`DewEffect.AgeAndDropInactivePools` で、実機と同じグローバル名前空間に置いて `Prepare` が同じ名前解決を通るところから再現する（static・private の別も含む。`Prewarm<T>` の `where T : UnityEngine.Object` 制約だけは、テスト用アセンブリの `UnityEngine.Object` が静的クラスの模倣で制約に使えないため、`Prepare` が見ない範囲として省略した）。テストは同じ入力（同じ assetId の重複、別 owner から同じ prefab への解決、解決結果が null、count 0）で2ループ版と Prefix 版を動かし、keep set の中身・`Prewarm` に渡す (prefab, count) の列と順序・`ReleaseInactivePoolsExcept` → `AgeAndDropInactivePools` → `Prewarm` の呼び出し順が一致することと、解決の呼び出し回数が項目数（2ループ版の半分）になることを確かめる。

結果が変わらない理由は次のとおりである。`ResolveClientPrewarmPrefab` は引数が同じなら結果が決まる。`DewResources` の `LoadRaw` は guid ごとに同じオブジェクトを返し、`GetVariant` は (guid, `VariantDef`) ごとに同じ variant を返す。間に挟まる `ReleaseInactivePoolsExcept` と `AgeAndDropInactivePools` は SpawnManager のプール instances、Fx のプール、各種キャッシュだけを触り、DewResources の variant prefab（DontDestroyOnLoad の非アクティブな親の下にある）には届かない。だから解決を解放前に1回にまとめても keep set の中身は同じで、個数の合計も同じである。`Prewarm` の呼び出し順も、どちらの版も辞書への挿入順（削除なし）なので同じになる。呼び出し側（`UserCode_RpcPrewarm`・`UserCode_TpcReplayPrewarm` のコルーチン）と送信側は一切変えていないので、通信の量・回数・タイミングも変わらない。

効果の見込み（推定）は、ゲストが部屋ごとに受けるプリウォーム適用で、項目数ぶんの解決が半分になることである。`BuildPrewarmEntries` が作る項目はモンスター種・能力・pickup・ミラージュや条件付きの追加を合わせて数十件になり得るので、解決1件あたり約20回の辞書引きとして、部屋1回あたり数百〜千強の辞書引きが減る計算になる。部屋開始のRPCと、途中参加ではプレイ中に届く `TpcReplayPrewarm` の両方で効く。ただし1回限りの部屋単位の処理なので、毎フレーム系の修正と比べると絶対量は小さい（推定）。実機での計測は行っていない。
