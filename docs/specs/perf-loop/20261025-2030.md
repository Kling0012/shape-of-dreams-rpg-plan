# perf-loop/20261025-2030

## 対象

`src/SodRpg.Mod/HostAuthority.Monsters.cs`（MOD 側・ホスト authority のモンスター挙動）。

## 直した内容

`TickMonsterBehaviors`（0.1秒ごとのホストティック）で、群れ（Packbound）の味方キャッシュの更新 `PackboundAllyNear` を呼ぶ位置を、睡眠・ゾーン遷移のスキップ branch の後ろへ移しました。以前は眠っているモンスター（戦闘が起きていない部屋のモンスター）やゾーン遷移中のモンスターに対しても、0.2秒ごと（キャッシュ窓 0.15秒 × ティック 0.1秒）に `_monsters` 辞書全体の走査（`FindBehaviorAlly`）を回していました。

## 結果が変わらない理由

眠っている間は更新結果を読む経路がありません。合図の送信（`SendMonsterBehaviorCue`）は睡眠 branch の `continue` で止まり、被弾処理は `isSleeping` で先に抜けます。キャッシュは時間ベース（`MonsterBehavior.AllyCacheSeconds`＝0.15秒で無効化）なので、窓が切れた後の最初の読み、つまり起床後の最初の被弾・合図・リプレイが同じ計算をその場で行い、同じ値を返します。どの読みの時点でも、返る値は最大 0.15秒前の値という性質は変更前後で同じです。

読み出し側の確認。すべて `PackboundAllyNear` を経由し、窓が切れていれば `FindBehaviorAlly` で計算し直します。

- 被弾処理（damage closure）: `HostAuthority.Monsters.cs:77` が `PackboundAllyNear(rt)` を呼ぶ。眠っている被弾は `HostAuthority.Monsters.cs:54` の `m.isSleeping` で先に return し、読み取り自体が走らない。
- 合図の送信: `HostAuthority.Monsters.cs:267`（`SendMonsterBehaviorCue` 内）が `PackboundAllyNear(rt)` を呼ぶ。呼び出し元は、起きているときのティック送信（`HostAuthority.Monsters.cs:218`、睡眠 branch の後ろ）、生成直後の初回送信（`HostAuthority.Monsters.cs:105`）、再同期（`HostAuthority.KillSync.cs:866`）、キルリプレイの再送（`HostAuthority.KillSync.cs:964`）。
- 窓の判定は `MonsterBehavior.AllyCacheStale`（`SodRpg.Core/Game/MonsterBehavior.cs`）に純粋関数として切り出してあり、`HostAuthority.Monsters.cs:141` が使う。キャッシュ欄（`HasAlly`・`AllyCheckedAt`）を読むのはこの関数だけで、直接読む箇所は他にない。
- `FindBehaviorAlly` の直接呼び出しは残り2箇所（キャッシュ更新 `HostAuthority.Monsters.cs:143` と、Beacon の盾相手選び `HostAuthority.Monsters.cs:186`）。後者は起きているモンスターのティック内だけで走る、この変更の対象外の全走査です。

## 効果の見込み

眠っている Packbound モンスター1体ごとに、0.2秒ごとの `_monsters` 全走査（対象はゾーン内の全モンスター）が止まります。ゾーン遷移中は全モンスターがこの対象になります。効果はホスト側の CPU で、辞書の規模 N と眠っている Packbound 数 P に対して毎秒 5×P×N 回だった候補チェックが減ります（推定: N=80・P=15 で毎秒約6,000回の候補チェック減。推定値です）。ゲスト側への通信は変更前後で変わりません。このファイルからゲストへ出る合図は値が変わったときだけで、今回の変更は送信に触れないためです。
