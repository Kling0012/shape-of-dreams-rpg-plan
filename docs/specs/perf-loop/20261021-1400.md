# perf-loop/20261021-1400

対象は `src/SodRpg.Mod/HostAuthority.PairCombos.cs` である。直した内容は、被弾ごとに走る `StrongestExposePercent` から、装備が変わって記憶を収集し直したときだけ `PairComboRuntime.RefreshEquipment`（連携の全状態の走査）を呼ぶようにした点である。そのために `CollectPairMemories` に「装備の変化で収集し直したか」を戻り値で報じるようにした。変更はこの2か所の数行で、他の呼び出し元は戻り値を無視するだけである。このファイルは参加者側の経路を持たない（`HostAuthority` はホストでしか走らず、パッチの接辞も `NetworkServer.active` を確認する）ため、規則3（被弾ごとの経路で重複した計算を省く）の観点で見た。

`RefreshEquipment` は、装備していない組の印（Expose）と窓（Window）を消す処理で、その要否は `rt.PairMemories` の内容だけから決まる純関数である。一方 `rt.PairMemories` と `rt.MemoryEquipmentEpoch` を書き込むのは `CollectPairMemories` だけで、装備エポックが不変の間は前回の収集結果をそのまま使う。だからエポックが変わらないのに呼ばれた `RefreshEquipment` は、前回の呼び出しで何も消す対象がなかったのと同じ条件で走る冪等な走査であり、被弾ごとに繰り返す意味がない。そこで「収集し直したときだけ再判定」に変えた。装備が変わったあと最初の被弾では収集し直しが起きて再判定が走るので、消える印と窓の集合は変更前と同じである。残りの再収集の経路も寿命は変わらない。`QueueGimmicks` と `OnAttackFired`（と `HostAuthority.cs` の撃破経路）は `PairComboRuntime.Fire` を通るので、`Fire` の内部で状態ごとの装備再判定が必ず先に走る。装備を外した直後の経路は `OnPairMemoryUnequipped` が今どおり明示的に再判定するので、そのまま残した。

結果が変わらないことの根拠はもう一つある。印は `Fire` の内部でしか作られず、`Fire` は常にはじめに装備再判定をするので、装備していない組に印が新しくできる道はもとからない。`StrongestExposePercent` の読み（`PairCombos.ExposePercent`）は期限切れを自分で落とすので、消し忘れをこの再判定に頼ってはいない。テストの期待値は変えていない。

効果の見込みは推定だが、連携を持つビルドの被弾1回につき連携状態の全走査（橋7本までの状態それぞれに装備2つのメンバーシップ判定）が1回消える。ホスト側だけで、1被弾あたり数百ナノ秒程度の規模で、毎秒数百件のダメージイベントが起きる密な戦闘でも削減は毎秒0.1ミリ秒前後と小さい。参加者側の負荷はこの変更では直接変わらない。
