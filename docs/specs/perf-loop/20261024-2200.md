# perf-loop/20261024-2200

## 対象

`native Dew.Core/Gem.cs`（本体 r1.4.1.2。`OnStartClient` の IL を実 DLL `Dew.Core.dll` から ilspycmd で取り出して照合し、逆コンパイル結果と同じ本体であることを確認済み）。

参加者側で走る経路を先に確認した。`LogicUpdate` は毎ロジックフレームで呼ばれるが、中身は `isServer` の 3 分岐だけで参加者側では実質何もしない。SyncVar のフック（`OnOwnerChanged` など）と RPC の受け口は発生ごとで、本体の処理はイベント呼び出し程度。`CanInteract`・`priority` は操作対象の走査（`ControlManager.GetNearbyInteractable` の近傍 6m の `OverlapSphereNonAlloc`）から呼ばれるが、対象は近くの宝石に限られる。その結果、参加者側で繰り返し走るのは宝石のネットワーク出現ごとの `OnStartClient` だった。

`Gem.OnStartClient` は出現のたびに `Resources.Load<GameObject>("WorldModels/Gem World Model")` を呼んでから `Instantiate` する。この呼び出しは参加者を含む全クライアントで、宝石 1 個の出現ごとに走る。宝石のクールダウン同期は既存の `NativeGemCooldownPerf` が 0.5 秒間隔に間引く済みなので、今回は触っていない。

## 直した内容

`Gem.OnStartClient` の中の `Resources.Load` の呼び出し点（`ldstr "WorldModels/Gem World Model"` と `call Resources::Load<GameObject>(string)` の組。実 DLL の IL で 1 組だけあることを確認）を、最初の 1 回の結果を静的に覚えて返す `LoadCachedGemWorldModel` へ差し替える Transpiler を `NativePerfPatches.cs` に足した（`NativeGemWorldModelLoadPerf`）。2 回目以降はネイティブのアセット検索を通らず、覚えたインスタンスをそのまま返す。

`Prepare` が本体 IL の呼び出し点の形（パス文字列の直後に GameObject を型引数にする 1 引数の `Load` が来ること、その組が 1 組だけであること）を確かめ、形が変わっていればこの修正だけを外して 1 回警告する。MOD 設定は `nativeGemWorldModelCache`（既定は有効）。設定を無効にしたときは毎回 `Resources.Load` を呼ぶ本体と同じ動作に戻る。

Prefix での丸ごと置き換えは、`base.OnStartClient()` の先の `Actor.OnStartClient` と `DewNetworkBehaviour.OnStartClient`（子の登録、`OnCreate` の起動、遅延開始キュー）まで再実装することになるため使わず、呼び出し点 1 つだけの差し替えにした。

## 結果が変わらない理由

Unity の `Resources.Load` は同じパスへの 2 回目以降も同じアセットの同一インスタンスを返す。キャッシュはその戻り値をそのまま覚えるだけなので、`Instantiate` に渡る参照が元から等しく、複製されるワールドモデルの中身も変わらない。`Instantiate`・`GetComponent<GemWorldModel>`・`_worldModel` への代入は本体の IL がそのまま残る。読み込みが null のときはキャッシュせず素通しするので、アセットが無い場合も本体と同じく後続の `Instantiate` が同じ例外を出す。出現のタイミング、見た目、同期の内容はどれも変わらない。

## 効果の見込み（推定）

宝石 1 個の出現ごとに、全クライアントで 1 回のネイティブのアセット検索がなくなる。敵の連続撃破や報酬のまとめ出しなど、1 フレームに宝石が数十個出る場面では、参加者ごとにその分の検索が同じフレームから消える（1 回の検索は数十マイクロ秒程度の推定）。定常的に毎フレーム走る経路ではないので、効果は出現の固まりに集中する。ホスト側でも同じ数だけ減る。

## 見送った候補

- `UserCode_RpcSetPositionAndRotation` の `Physics.SyncTransforms()`（ドロップごとに参加者で走る）。物理の同期は増分処理なので 1 回ごとの増しは小さく、呼び出すタイミングをずらすと同フレーム内の当たり判定の問い合わせ結果が変わり得るため触らない。
- `LogicUpdate` のレート制限ブロックで `GetValue` を毎フレーム呼ぶ箇所。ホストだけで走り、レート制限を持つ宝石は数が少ないため後回し。
- `DoDismantleLogicUpdate` が装備済みの宝石に対して毎フレーム 0 を再書き込みする箇所。Mirror の `GeneratedSyncVarSetter` が等価なら早期リターンするので送信も確保も発生していない。
- `IInteractable.priority`・`CanInteract` の `GetSyncVarNetworkBehaviour` の辞書引き。走査が近傍 6m に限られ対象が少ないのに加え、`tempOwner` の参照を自分でキャッシュすると、本体が同期変数の受信後に出現を遅らせて解決する場合と食い違い得るため触らない。
