# perf-loop/20261025-0700

対象: `Dew.Core/Entity.cs`（MOD から Harmony の Prefix で `Entity.owner` の getter を軽くする）

## 直した内容

`Entity.owner` の getter は Mirror 生成の SyncVar 参照で、中で `GetSyncVarNetworkBehaviour(____ownerNetId, ref _owner)` を呼びます。この Mirror の実装は、ホスト（isServer）では設定時に書き込まれた `_owner` をそのまま返す O(1) ですが、純クライアント（協力プレイの参加者）では `NetworkClient.spawned` の辞書引き、`NetworkBehaviours[componentIndex]` の配列アクセスとキャストを呼び出しごとにやり直します。結果を `_owner` に書き戻すだけで、読み取りがキャッシュから返ることはありません。

MOD 側に `NativeEntityOwnerSyncVarPerf` パッチ（`NativePerfPatches.cs`）を追加しました。純クライアントのときだけ、解決済みの `_owner` が今の `____ownerNetId` と一致するならそれをそのまま返します。設定（DreamforgeConfig の `nativeEntityOwnerClientFast`、既定は有効）で切れます。フィールドや getter の形が違うときは、Prepare で1回だけ警告を出してこの修正だけ外れます（fail-soft）。

## 結果が変わらない理由

- 一致の判定は `(netId, componentIndex)` の比較です。netId はスポーン中の NetworkIdentity の間だけ一意で、Mirror は所有者の despawn のときに必ず GameObject の破壊（Unity-null 化）か `Reset()` による netId=0 化のどちらかを行います（Mirror.dll の `NetworkClient.DestroyObject` と `NetworkIdentity.OnDestroy` で確認）。componentIndex は `InitializeNetworkBehaviours` が `NetworkBehaviours` の添字と同じ値を入れます。そのため判定が通るとき、元の実装が返すオブジェクトと同じ参照を返します。
- 未解決・所有者の despawn 後・同期での所有者変更のときは判定が偽になり、本体の解決に任せます。netId が 0 のときも本体に任せます（本体は辞書に見つからず null を返し、getter は `defaultOwner` に落ちます）。
- ホストと、netIdentity がない状態は対象外で、本体どおりに動きます。ホストの本体経路はすでに O(1) なので、速くなる余地も遅くなる余地もありません。
- 違いとして残るのは、所有者 DewPlayer の破壊処理（OnDestroy）が走っている同じフレームの中だけで、破壊されたオブジェクトを返す窓がある点です。DewPlayer が壊れるのはマッチの解散時などで、戦闘中の毎フレームの経路ではありません。

## 効果の見込み（推定）

`owner` はゲストでも次の経路から読まれます。`UI_HealthBar_Simple.LateUpdate` は表示中の簡易ヘルスバーごとに `DewPlayer.local.GetTeamRelation(target)` → `target.owner` を読み、ミニマップの項目（`UI_InGame_Map_Item_Entity.OnSetup`）と画面外インジケータの定期処理（0.1秒ごと）も `GetTeamRelation` 経由で同じ参照を見ます。MOD 側の撃破ごとの `GetRelation` も通ります。エンティティが百を超える部屋では、参加者で毎フレーム数十〜百回超の辞書引きになると推定します。1回あたりの節約は辞書引きと配列アクセスとキャストを等値比較に置き換える数十ナノ秒程度（推定）で、効果は小さいものの、ゲスト側の毎フレームの経路に乗る純粋な無駄です。ホスト側の経路と通信の内容は変わりません。
