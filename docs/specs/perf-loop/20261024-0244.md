# perf-loop/20261024-0244

対象は `src/SodRpg.Mod/HostAuthority.AuthoredMechanisms.cs` である。直した内容は、`DispatchAuthoredChannel` が発動のたびに毎回計算していた EveryN（N回に1回の間引き数）の変換を、チャンネルごとのキャッシュに置き換えた点である。`AuthoredChannelState` に刻印の世代（`binding.Epoch`）と発動元の記憶・発動種別をキーにした辞書を1つ足し、世代が同じあいちは前と同じ値を返す。世代が動いたときだけ辞書を空にして計算し直す。

従来のしくみは次のとおりである。ホストは記憶に反応する被弾・撃破のイベントごとに `OnAuthoredMechanismEvent` を通り、条件の合うチャンネルごとに `DispatchAuthoredChannel` を呼ぶ。そこではトリガーが一致したチャンネルについて、DirectedRecharge 以外は必ず `TransformAuthoredEveryN` を呼んでいた。この1回の呼び出しの内側では、仕様ごとに `KeystonePayload` と `KeystoneCaps` を新しく作り、`KeystoneContext` と `KeystoneResult` も新しく作り、刻印の適用処理（`ScopedKeystoneModifiers.Apply`）の検査と変換の走査を全部通していた。つまり被弾ごと・チャンネルごとに最大4個のインスタンスを確保し、結果の EveryN はほとんどの場合 base のままで捨てていた。

結果が変わらない理由は次のとおりである。EveryN の値は刻印ランタイムの状態と発動元だけで決まる。刻印ランタイム（`ScopedKeystoneModifiers`）は `RefreshAuthoredKeystone` の `Configure` でしか書き換わらず、`Configure` は必ず `binding.Epoch = checked(++_authoredKeystoneEpoch)` と対で走る（バインディングの作成時も新しい世代を割り振る）。`binding.Equipment` も世代の更新と同時にだけ差し替わる。`StarDamageScaling.ScaleResult` は Value だけを変えて EveryN には触れないので、Build の付け替え（`ConfigureAuthoredKeystone` が世代を進めずに行う `existing.Build = build`）も EveryN には影響しない。刻印が付いたり外れたりすれば世代は必ず進むので、古い値が残ることはない。`AuthoredKeystoneEpoch`（内部で `RefreshAuthoredKeystone` を呼ぶ）をキャッシュの確認のたびに通すので、刻印の再設定と機材の再検査のタイミングも変更前と同じ位置で動く。チャンネルの再利用は `AuthoredMechanisms.Key(spec)`（仕様全体の符号化）が同じときに限るので、仕様が変われば別の値として計算し直る。

効果の見込みは推定だが、条件の合うチャンネル1つにつき被弾ごとの確保4個と刻印適用の走査1回がなくなる。マルチヒットの構成や召喚が多い戦闘ほど、イベントの数と当てはまるチャンネルの数に比例して減る。キャッシュは最初の1回と世代が動いた1回だけ計算するので、以降は辞書1回の参照になる。実機（ゲーム内）での確認は未実行である（この環境ではゲームを動かせないため）。

結果が変わらないことは `tests/SodRpg.Core.Tests/AuthoredMechanismNativeTests.cs` の `Cached_every_n_matches_the_uncached_transform_and_recomputes_when_the_keystone_epoch_moves` で確かめる（原則 II）。基本 EveryN=4 の回復チャンネルを刻印が 2 に縮める構成で、（1）同じ世代ではキャッシュ経由の発動間引きが毎回の `TransformAuthoredEveryN` と同じ 2 で動くこと、（2）世代を進めない Build の差し替え（星の数の変更）でも 2 のままであること、（3）刻印を外して世代が進めば基本の 4 を計算し直すこと、（4）刻印を戻せば再度 2 に戻ることを、回復量で数えて確かめる。世代が進んでも辞書を空にしない作り（古い値を使い続ける障害）には失敗することも確認済みである。
