# perf-loop/20261024-1511

対象: `src/SodRpg.Mod/HostAuthority.MeleeCoop.cs`（近接協力4機能のホスト側）。
このファイルの実行時の経路はホストでだけ走ります（`HostAuthority` の処理は
`NetworkServer.active` のときに動く）ので、参加者側の経路はなく、命中ごとの
経路（探索の観点3）で見ました。

## 直した内容

近接の「崩し」の付与判定が、ダメージイベント1回ごとに
`TravelerCombatNative.IsMelee(rt.Hero)` で近接種別を読み直していました
（`HostAuthority.cs` の `OnMemoryDamage`）。この1回は、基本攻撃の現在構成
（`currentConfig`）をたどってアセットの型を確かめるもので、アセットが
Component のときは `GetComponent<MeleeAttackInstance>()`（エンジンとの
相互運用）を呼びます。近接の旅人は通常攻撃の頻度が高いので、ドットのtickや
範囲攻撃を含む戦闘中に、この読み直しがダメージイベントのたびに繰り返されて
いました。

一方、同じ近接判定は 0.25 秒ごとの走査（`ScanMeleeCoop`）でも行われていて、
近接防御（MeleeGuard）は走査の結果を命中時に使い回す（最大 ScanSeconds 古い）
契約で動いています。そこで判定結果を `HeroRuntime.IsMeleeTraveler` に保存し、
`OnMemoryDamage` は走査が更新した値を見るようにしました。走査では従来どおり
毎回 `TravelerCombatNative.IsMelee` を呼ぶので、判定の源（旅人の型名と
基本攻撃のアセット）は毎走査で確かります。

テストは、`HostAuthority.MeleeCoop.cs` を単独でコンパイルする2つの既存
ハーネス（`tests/SodRpg.Core.Tests/MeleeCoopNativeTests.cs` と
`tests/repro/issue522/NativeApi.cs`）のスタブに、新しいフィールドの1行を
足しただけです（新しいテストファイルは作っていません）。

## 結果が変わらない理由

- 走査（`ScanMeleeCoop`）が毎回 `TravelerCombatNative.IsMelee` を呼んで
  `IsMeleeTraveler` を更新するので、攻撃の近接・遠距離の差し替えは次の走査
  （0.25秒以内）で反映されます。これは近接防御がすでに持っている反映の
  間隔と同じです（既存のコメント「Hits reuse this result (up to ScanSeconds
  old) instead of re-checking the attack per hit」の契約に、崩しの判定を
  そろえた形です）。
- `OnMemoryDamage` は冒頭で `Alive(rt.Hero)` を確認していて、走査での保存は
  `alive` を含めずに行うので、生きている旅人の `IsMeleeTraveler` は従来の
  読み直しと同じ値になります。死亡中も走査は判定を更新し続けるため、
  復活直後の窓も生じません。
- `MeleeGuard`・射程→攻撃速度変換・崩しの倍率・対象の関係判定は、
  `melee = alive && rt.IsMeleeTraveler` で従来と同じ値を作るので、
  どれも変わりません。
- `MarkMeleeBreak` の `Debug.Assert` はリリースビルドでは呼びごと消えるので、
  実行時のふるまいに影響しません。

## 効果の見込み（推定）

近接種別の旅人（指定4旅人）が出すダメージイベント1回ごとに、基本攻撃構成の
読み直しと `GetComponent` 相当の相互運用が1回ずつ減ります。1回あたりは
マイクロ秒程度の見込みで、敵が多くドットや範囲攻撃のtickが重なる場面ほど
イベント数が増えるため、そのぶんホスト側の負荷が下がります。毎秒数百
イベントの想定で毎秒1ミリ秒以下程度の削減を見込みます（数値は推定で、
実測はしていません）。遠距離の旅人は保存値が false のため、従来の
型名の文字列比較より速いか同等で、悪化はありません。
