# perf-loop/20261023-2303

## 対象

mod src/SodRpg.Mod/HostAuthority.BridgeSuccessEffects.cs（記憶の連携が成功したときの効果の配布。`MemoryActivationPublished` の発動ごと・被弾ごとに走る `OnBridgeSuccessEvent` と、その取引ごとの `ApplyBridgeSuccess`）。

## 直した内容

`ApplyBridgeSuccess` のペイロード ループから、ダメージ payload の直前にある2回目の `transaction.IsCurrent(...)` 判定と `CollectMechanismEquipment(...)` の呼び出しを外した（1行削除）。ループの先頭で payload ごとに同じ判定をしていて、ダメージ payload の場合はその判定から種別比較を挟むだけで2回目に届く。間にあるのはローカルの enum 比較だけで、装備・前提・状態を変える処理はない。

## 結果が変わらない理由

2回目の判定は1回目と引数が同じで、結果も必ず同じになる。`IsCurrent` が呼ぶ `RefreshSuccessPrerequisites` は装備のオーナーと世代が同じなら早期リターン、ランク表は変更検出でコピーしない、使えなくなった連携の無効化も1回目で済んだあとの2回目は何もしない、という冪等な作りである。`MechanismEquipment.Admits` と `Find` は読み取りだけの純粋な処理で、`IsSuccessCurrent` は状態の一覧を走査して一致を見るだけである。1回目の判定で偽ならそこで return しており、2回目まで届かない。残る判定（ペイロードごとの先頭の再判定、被弾直前の `BridgeDamageTargetReady`）は変わっていない。ゲストの視界・判定・タイミングに触れる変更ではなく、ホスト側の計算を1回減らすだけである。

## 効果の見込み（推定）

連携の成功1回ごとに、ダメージ payload 1つにつき装備スナップショットの取得2回（辞書引き）と `IsCurrent` 全体（`RefreshSuccessPrerequisites` 2回・`Admits`・`Find` 2回・状態走査）が減る。連携はクールダウンで発火が抑えられるとはいえ、爆発系の記憶が敵の集団を一度に殴る場面では発動ごとの被弾で繰り返し走る。1回あたりは辞書操作数十個の規模で、体感できるものではない（推定）。
