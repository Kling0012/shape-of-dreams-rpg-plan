# perf-loop/20261021-0623

対象は mod src/SodRpg.Mod/CulinaryMagnet.cs（料理のエッセンスの食材を持ち主へ吸い寄せる MOD 側の経路）。改善あり。

直した箇所: 食材の生成ごとに呼ばれる Harmony postfix の AfterCreate が、本体 PickupInstance の float フィールド5本（attractionRange、pickupDelay、maxVelocity、velocityAccelerationMin、velocityAccelerationMax）へ、FieldInfo.SetValue のリフレクション呼び出しで値を書き込んでいた。この postfix はホストと各参加者のどちらでも、食材1個の生成ごとに走る。Install のときに式木から Action<object, float> のデリゲートを1回だけ組み立てるようにして、生成ごとのリフレクション呼び出しと float のボックス化（1回の SetValue につき1個）をなくした。Setter の組み立ては Install の既存の try/catch の内側にあり、失敗したときは従来どおりこの機能だけが外れて警告を1回出す。

結果が変わらない理由: 書き込むフィールド、値（500、0、120、150、300）、書き込むタイミング（本体の OnCreate の後）は変更していない。デリゲートは同じ FieldInfo への代入をそのまま実行するもので、ボックス化の有無以外に読み取り側から見える差はない。RequireField による検証（float、非 static、非 readonly）もそのままで、デリゲートが代入する型は同じ検証を通った宣言型（PickupInstance）を使う。SnapToOwners（ホストの Tick 専用）と Tracked の扱いは触れていない。通信も触れていない。MOD は食材の位置を同期せず、ホストの snap が参加者へ届かないことは、PickupInstance・Actor・AbilityInstance の逆コンパイルで同期変数と位置同期コンポーネントがないことを確かめたうえでの既知の動作で、今回も変えていない。

効果の見込み（推定）: 食材1個の生成につき、ホストと各参加者で5回のリフレクション呼び出しと5個のボックス化がなくなる。手元の .NET 8 での計測では、SetValue 100万回で約24MB（1回あたり float 1個のボックス化）を確保したのに対し、デリゲートでは確保がほぼゼロだった。Unity の Mono での値ではないので実際の大きさは推定だが、食材が続けて生まれる戦闘では、生成のたびの CPU と GC の細かな負荷が参加者側で減る見込み（推定）。

テスト: 新しいテストファイルは作っていない。CulinaryMagnet.cs はテストプロジェクトにリンクされていない（Startup テストは同名のスタブを持ち、Culinary テストは CulinaryIngredientCap.cs だけをコンパイルする）ため、既存テストの変更もない。
