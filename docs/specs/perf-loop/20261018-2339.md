# perf-loop/20261018-2339

## 対象

mod src/SodRpg.Mod/CoopTradeTransport.cs（`CoopTradeSendQueue.TryPeek`）。クライアント（`ClientSession.Tick` → `TickCoopTrade` → `FlushCoopPayloads`）とホスト（`HostAuthority.TickCoopTrade` → 各接続の `FlushCoopPayloads`）の両方から、転送の滞留中は毎フレーム呼ばれる。

## 直した内容

`TryPeek` は、チャンクの JSON（`transfer.Json`）を組み立てた後に、送信レート制限（フレーム上限64KB・秒間128KBのトークンバケット）の判定へ `System.Text.Encoding.UTF8.GetByteCount(transfer.Json)` を使う。この JSON は次のチャンクへ進むまで（`Sent()` で消えるまで）同じ文字列のままキャッシュされるが、バイト数のほうは毎回の呼び出しで約11KBの文字列を再スキャンしていた。バイト数を `Transfer` のフィールド（`JsonBytes`）に保持し、JSON を組み立てた時点で1回だけ数えて、判定ではその値を読むようにした。

## 結果が変わらない理由

`transfer.Json` が書き換わる場所は組み立ての1箇所だけで、そこで同時に `JsonBytes` も更新する。JSON が `null` に戻るのは `Sent()`（チャンク完走）と `Retry()`（送信失敗のやり直し）の後だけで、次の組み立てで両方が作り直される。このため判定に使う値は常に「今の JSON のバイト数」と一致し、レート制限の動作・送信の順番・中身は1ビットも変わらない。キャッシュされるのは既に文字列として保持している同じデータの長さだけで、追加の確保もない。この一致は `tests/Issue73.Native.Tests/CoopTradeSendQueueRateTests.cs` が保証する。このテストは、判定のたびに `GetByteCount` を数える変更前の意味論の影のモデルと実装を同じタイムラインで突き合わせ、保留・送信の判定と送られる JSON がフレーム単位で一致すること（トークン枯渇による複数フレーム保留と `Retry` 後の組み立て直しを含む）を確かめる。

## 効果の見込み（推定）

協力取引で倉庫サイズのプロフィール（最大4MB、チャンク約11KB×数百個）を送っている間、持続レート128KB/sに対してチャンク1個は約5〜6フレーム待つ。待っている間の毎フレームの約11KBのスキャンがなくなり、送るチャンク1個あたり約50〜60KBぶんの走査が減る（推定。実際の削減量はプロフィールの大きさとフレームレートに依存）。待ちのない転送中のフレームと、転送がない間（`Pending` の1回の比較で return）の挙動は変わらない。
