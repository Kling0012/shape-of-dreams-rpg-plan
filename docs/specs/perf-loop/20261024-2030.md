# perf-loop/20261024-2030

## 対象

native Dew.Core/EntityControl.cs（自分で移動を処理する実体の毎フレーム経路 `DoMovementProcessorFrameUpdate` と、その中の NavMeshAgent の速度への書き込み1か所）。

## 直した内容

`EntityControl.DoMovementProcessorFrameUpdate` は、この端末が移動を自分で処理するすべての実体（ホストならモンスター・召喚体・NPC のすべて、参加者なら自分の英雄）に対して描画フレームごとに走る移動の積分である。この中の `_agent.velocity = Vector3.zero` という NavMeshAgent の速度への書き込みが、条件なしで実体1つにつき毎フレーム1回行われる。この書き込みはエージェントの自律移動を止めて、このメソッドが `nextPosition` で手動移動できるようにするためのものだが、エージェント自身が速度を書くことはない（OnStart から `updatePosition`・`updateRotation` は false。実 DLL の IL でも EntityControl 全体で NavMeshAgent の `set_velocity` はこの呼び出し箇所の1か所だけ）。そのため一度ゼロになった速度は誰かが意図的に書くまでゼロのままで、動いていない実体では同じ値をネイティブの setter で毎フレーム書き直している。

MOD では、この1か所の呼び出しを Harmony の Transpiler で置き換え関数（`NativeAgentVelocityIdlePerf.SetVelocity`）につなぎ替えた。置き換え関数はエージェントの現在の速度を成分ごとに読み、書くべき値とまったく同じなら何もせずに返る。違う値のときはネイティブの setter が従来どおり走る。実 DLL の IL で `set_velocity` がこのメソッド内にちょうど1か所あることを確かめ、数が合わなければ何も置き換えずに警告を1回出す。読み取りで例外が出たときは、この修正だけを外して従来どおり書く。設定は `nativeAgentVelocityIdle`（既定ON）で切れる。

## 結果が変わらない理由

スキップの条件は「格納されている速度と書こうとする値が成分ごとに == で等しい」のときだけである（実装どおりの float の == であり、ビット比較ではない。書く値は常に Vector3.zero なので、== とビット比較が食い違う +0/-0 と NaN はここでは起こらない）。そのとき本体の代入は、値を変えない同じ値の再書き込みであり、この値の読み手（次フレームの同じ getter と、エージェントの内部状態）は書く前と同じ値を見る。値が違う間（動き始め・止まりかけ・回避や他システムが速度を変えた直後）は setter が必ず走るので、動き・衝突・回避・同期される状態は1行も変わらない。IL の指紋（`set_velocity` が1か所）が変わったときは、この修正だけが外れて警告を1回出す。

前提として、NavMeshAgent.velocity の setter には値を格納する以外の副作用（crowd 側の速度上書き指定など）がないと仮定している。同一値の再書き込みを省く変更が結果を変えないのはこの仮定の上であり、実機での確認はまだ行えていない（実機計測の機会があれば、動作中実体の getter/setter の呼び出し回数とあわせて確認する）。

## 効果の見込み（推定）

この変更は、毎フレームのネイティブ setter 呼び出しを getter 呼び出しに置き換える。速度がすでにゼロの間（静止・待機中の実体）は、従来の setter 1回が getter 1回になり、削減量は setter と getter のコスト差に限られる。速度がゼロでない間（updatePosition=false でも内部シミュレーションが進み getter が非ゼロを返し続ける能動的に経路を追う実体など）は getter と setter の両方が走り、従来の setter 1回に対してネイティブ呼び出しが1回増える。つまり静止実体の並びで効き、動き続ける実体ではごく微小な増加になり得る（通信は変わらない。送信の量も間隔も触れていない）。

## 将来の改善案（見送り）

- MOD 側で実体ごとに「すでにゼロを書いた」ことを覚え、ネイティブの getter も呼ばずに判定する形にすれば、静止中の呼び出しを完全にゼロにできる。実体の生成・破棄や外部からの速度書き込みとの整合をどう保つかが課題で、今回は複雑化を避けて見送った。
- 実機計測の機会があれば、動作中実体の getter/setter の呼び出し回数（本項の増減の見込み）と、velocity setter に格納以外の副作用がないことを確認する。
- これらの見送りの理由と見直す条件は、改善案の台帳 [ledger-1146-agent-velocity-idle-followup.md](../ledger-1146-agent-velocity-idle-followup.md) に記録した（2026-10-24 レビュー F1 の裁定による）。
- null・破棄済みエージェントの getter 例外でも static の `_disabled` が true になり、全実体でゲーム終了まで最適化が無効になる。元の setter は実行されるため移動結果は変わらず、影響は性能だけでマージを妨げないという裁定である。null・破棄済みエージェントを元の setter にそのまま渡し、正常な実体の最適化を維持する改善案と受け入れ条件を、同じ記録の「null・破棄済みエージェントと機能の無効化」に追加した。今回の実装とテストは変更していない。
