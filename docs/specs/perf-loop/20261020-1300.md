# perf-loop/20261020-1300

対象は本体の `Dew.Core/TimescaleManager.cs`（逆コンパイル）である。このクラスは SyncVar を2本持つ（`_finalTimescale` と `effectTimescale`）。`FrameUpdate` は最初に `NetworkServer.active` でなければ抜けるので、本体の処理はホスト側だけで、ゲスト側の経路は SyncVar のフック（`Time.timeScale` への代入）と `DeserializeSyncVars` だけである。ホストからゲストへの出口はこの2本の SyncVar の差分送信である。

見つけた無駄は、`FrameUpdate` の effectTimescale の扱い方である。冒頭で `effectTimescale` を 1 に戻し、続くループで進行中のスロー変更の最小値を改めて適用する。スロー効果（`FxStopTime` の 0.1 倍。duration の既定は 0.3 秒。特殊メニュー開いている間の 0.025 倍も同じ）が生きている間、この2つの書き込みが毎フレーム 0.1→1→0.1 と値を往復させ、Mirror の weaver セッターが dirty ビット2を毎フレーム立て直す。Mirror はビットが立っている限り serialize のたびにその float（とマスク）を全参加者へ送り、serialize の後にビットをクリアするので、次のフレームですぐまた立つ。つまりスロー効果が続く間ずっと、値が変わっていない差分メッセージが送り続けられる。この Mirror の `syncInterval` は既定 0（フィールド初期化なし。逆コンパイルで確認。プレハブ側で上書きされている可能性はある）なので、実際にはサーバの送信レートごとに流れる。

直した内容は、`NativePerfPatches.cs` に `TimescaleManager` への Postfix を2本足したことである。`SerializeSyncVars` の後で、最後に参加者へ配信した値を基線として記録する。`FrameUpdate` の後で、フレーム末の値がその基線と同じとき、dirty ビット2だけを落とす（クリアするビットは、weaver セッターの IL から読んだビット定数に束ねるので、SyncVar の並び替えがあっても別のビットを落とさない）。ビット1（`_finalTimescale`）とほかのビットには触れない。基線が進むのは差分の serialize が値を実際に運んだときだけで、途中参加への初期状態では進めない（進めると、参加の直前に立った変更ビットが古い基線との同値比較で落ち、既存参加者へ届かなくなる）。設定が OFF の間・サーバが active でない間は両 Postfix とも基線を未知に戻し、管理対象（owner）への参照も null に戻す。この間は素通しで配信が起きて基線が追従しないため、ON へ戻った直後や同じインスタンスでのサーバ再開の直後に、古い基線が新しい変更のビットを落とすのを防ぐ（値は次の差分で配信されてから基線が結ばれる）。本体の名前や形が変わっていれば警告を1回出してこの修正だけを外れる。MOD 設定 `nativeTimescaleIdle`（既定ON）で切れる。テスト側のスタブとして、`NativeBoundary.cs` に `TimescaleManager` を、`NativeEmbracePositionBoundary.cs` の `DreamforgeConfig` に同名の設定フィールドを足した。

結果が変わらない理由は、落とすのが「参加者がすでに持っている値」の再送だけだからである。基線が進むのは、effectTimescale のビットが立ったまま走った差分の serialize（値を実際に運んだ配信）だけで、ビットが落ちた差分や初期状態の serialize では進まない。だから値が変わったフレームはビットが残り、次の差分の serialize で必ず送られる。途中参加者には、初期状態の serialize がビットと無関係に全フィールドを送るため、初期状態の経路で値が届かないこともない。weaver セッターは `FrameUpdate` の中でしかこのフィールドを書かないため、クリアと直後の serialize の間に値が変わることはない。参加者が読む値（`effectTimescale`・`_finalTimescale`・`Time.timeScale`・フックの呼ばれ方）はすべて本体どおりで、削れるのは同値の再送の回数だけである。ホスト側では値もビット以外の状態も変わらず、単人プレイの見た目も変わらない。

効果の見込み（推定）は、スロー効果1回（既定0.3秒）につき、参加者1人あたり送信レート分の同値差分メッセージをなくすことである。1通は小さい（マスク1バイトと float 4バイトに Mirror のヘッダが付く）が、ホストは接続ごとの `SerializeSyncVars`、参加者は受信パイプラインの通過と `DeserializeSyncVars` を1回ずつ減らせる。停止系の演出が頻発する戦闘ほど回数が増える。数値は推定で、実機での計測は行っていない。
