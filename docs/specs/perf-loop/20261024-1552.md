## 直した内容

`OnMemoryPrimedRelayNotification` は、通知ごとに `WithPreparationEpoch(notification, state)` でエポック付きイベント `source` を組み立てていたが、この変数を使うのは「オーサード機構を持たないヒーローへのフォールバック配信（`state.Primed.OnSourceEvent` と `state.Relay.OnSourceEvent`）」のなかだけだった。オーサード機構のヒーロー（リレー状態を持つのは実質このケース）では、`AuthoredMechanisms` 側のチャンネル付き配信が同じ `OnSourceEvent` を担うため、ここで組み立てた `source` は捨てられていた。組み立てを `if` ブロックの中へ移し、通知ごとの `state.Epochs` の辞書引きと10フィールド構造体のコピーを、使われない場合には行わないようにした。

## 結果が変わらない理由

`WithPreparationEpoch` は `state.Epochs` を読んで構造体を返すだけで副作用がなく、移動しても読む状態と呼び出し順序は変わらない。ブロック内で使う `source` の値は従来と同一で、ブロックの外（プロック経路の `TryConsume` や `Pending` への予約）では `source` を使っていない。ブロック自体の実行条件（`_authoredMechanisms` の有無）も触っていないので、`OnSourceEvent` の呼ばれ方も従来と同一である。

## 効果の見込み

推定: 記憶の活性化イベント1回ごと（基本攻撃の命中で2〜3回、スキル使用・撃破でも1回）に、辞書引き1回と構造体コピー1回が減る。確保は元々なかったので GC への影響はなく、CPU 数百ナノ秒程度/イベントの削減を見込む。体感できる規模ではないが、通知が最も多い攻撃spamの戦闘でHOST側の定常コストを少し下げる。
