# perf-loop/20261024-1529

対象は本体の `Dew.Contents/Gem_C_Responsibility.cs`（「責任」の宝石）である。reflection-dump の型の一覧にこの型が無いため、実 DLL（`Shape of Dreams_Data/Managed/Dew.Contents.dll`）から ilspycmd で型を取り出して確認した。この宝石は詠唱が終わると `initDelay` の間に自分の攻撃が当たった敵を集め、その1体ずつに `RpcPlayHit`（ClientRpc）を送る。この RPC の受け口 `UserCode_RpcPlayHit__Entity__Single` は、ホストが送るたびに、それを受け取った全クライアント（ホスト自身のローカルクライアントと各参加者）で走り、3つの曲線（音程・音量・揺れ）を評価した後、被弾演出のプレハブ `fxHit` の子孫を `GetComponentsInChildrenNonAlloc` で2回（`DewAudioSource` と `FxCameraShake`）全走査してプールのリストを出し入れし、その結果の各コンポーネントへ値を書き、`localScale` を1回書いてから `FxPlayNew` で演出を再生する。参加者はこの宝石を使う味方の詠唱が敵に当たるたび、被害者の数だけこの受信処理を受け取る。

直した内容は、この受け口を `NativePerfPatches.cs` の `NativeGemResponsibilityHitPerf`（Harmony の Prefix）で置き換え、子孫の全走査をキャッシュに置き換えたことである。`fxHit` はシーンに置かれないプレハブアセットで、実行中に子の構成を変える処理は本体にもこの MOD にも無いため、走査は毎回同じ配列を返すだけである。Prefix は `fxHit` の参照が変わった最初の1回だけ本体と同じ走査（`includeInactive=false`）で配列を作り、以後はその配列へ同じ値を同じ順で書く。走査が毎回なくなるほか、プールのリストの出し入れ2回もなくなる。設定には `nativeGemResponsibilityHitCache`（既定有効）を足し、本体側の失敗に備えて `Prepare` で本体 IL の形（`Evaluate` 3回、子走査 2回、`pitchMultiplier`・`volumeMultiplier`・`amplitude` への書き込み各1回、`set_localScale` 1回、`FxPlayNew(GameObject, Entity)` 1回）を数え、形が変わっていればこの修正だけを外して警告を1回出す。Prefix 内の例外でも同じく無効化して本体経路へ戻す。

結果が変わらない理由は次のとおりである。書き込み先のコンポーネントは、プレハブアセットの子構成が不変であるため、毎回の走査が返すものと最初の1回の走査が返すもので同一である。書き込む値は3つの曲線の評価結果で、式と評価の引数（`strength`）は本体と同じだ。書き込む順序も、各音源への `pitchMultiplier`・`volumeMultiplier`、各 `FxCameraShake` への `amplitude`、`localScale`、最後の `FxPlayNew` まで本体と同じである。コンポーネントへの個別の書き込みは互いに依存しないため、走査と曲線評価の前後関係を入れ替えても結果は同じである。送信側（ホストのコルーチン、RPC の間隔と宛先）は一切変えていないので、通信の量とタイミングも変わらない。

効果の見込みは推定である。被弾演出 RPC を受けるたびに、子孫の全走査2回（`fxHit` の階層の深さに比例）とプールのリストの出し入れ2回が、プレハブごとに最初の1回だけのコストに置き換わる。残るのは曲線の評価3回、配列の走査と値の書き込み、`localScale` への書き込み、`FxPlayNew` の呼び出しで、いずれも本体も行う処理である。獲得はホストと各参加者の受信ごとの CPU 負荷の削減であり、通信量は変わらない。この宝石は詠唱が多発する戦闘で被弾者の数だけ RPC を送るため、参加者の負荷が高い場面（多数の敵を巻き込む詠唱）ほど差が開く。検証は `tools/balance/gen_cs.py --check`、`src/SodRpg.Mod` の Release ビルド、`tests/Issue73.Native.Tests`（803件全件合格）、`tests/SodRpg.Mod.Startup.Tests`（238件合格・1件は既存のスキップ）で確認した。実機（ゲーム内）での確認は未実行である（この環境ではゲームを動かせないため）。なお本体が数えていない種類の文を将来追加した場合は指紋で検出できないため、ゲーム更新のときはこの指紋の見直しが必要である。
