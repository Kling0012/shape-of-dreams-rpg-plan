# perf-loop/20261024-1529

対象は本体の `Dew.Contents/Gem_C_Responsibility.cs`（「責任」の宝石）である。reflection-dump の型の一覧にこの型が無いため、実 DLL（`Shape of Dreams_Data/Managed/Dew.Contents.dll`）から ilspycmd で型を取り出して確認した。この宝石は詠唱が終わると `initDelay` の間に自分の攻撃が当たった敵を集め、その1体ずつに `RpcPlayHit`（ClientRpc）を送る。この RPC の受け口 `UserCode_RpcPlayHit__Entity__Single` は、ホストが送るたびに、それを受け取った全クライアント（ホスト自身のローカルクライアントと各参加者）で走り、3つの曲線（音程・音量・揺れ）を評価した後、被弾演出のプレハブ `fxHit` の子孫を `GetComponentsInChildrenNonAlloc` で2回（`DewAudioSource` と `FxCameraShake`）全走査してプールのリストを出し入れし、その結果の各コンポーネントへ値を書き、`localScale` を1回書いてから `FxPlayNew` で演出を再生する。参加者はこの宝石を使う味方の詠唱が敵に当たるたび、被害者の数だけこの受信処理を受け取る。

直した内容は、この受け口を `NativePerfPatches.cs` の `NativeGemResponsibilityHitPerf`（Harmony の Prefix）で置き換え、子孫の全走査をキャッシュに置き換えたことである。`fxHit` はシーンに置かれないプレハブアセットである。根拠は ilspycmd の逆コンパイルで、この受け口は `fxHit` を読んで値を書き込み `FxPlayNew`（`DewEffect.PlayNew` へ渡して池から新しい演出として再生する）に渡すだけで、`fxHit` をシーンへ置いたり子を増減する命令は本体に無い。したがって実行中に子の構成を変える処理は本体にもこの MOD にも無いため、走査は毎回同じ配列を返すだけである。Prefix は `fxHit` の参照が変わった最初の1回だけ本体と同じ走査（`includeInactive=false`）で配列を作り、以後はその配列へ同じ値を同じ順で書く。走査が毎回なくなるほか、プールのリストの出し入れ2回もなくなる。設定には `nativeGemResponsibilityHitCache`（既定有効）を足し、本体側の失敗に備えて `Prepare` で本体 IL を検査して、形が変わっていればこの修正だけを外して警告を1回出す。検査は出現回数（`Evaluate` 3回、子走査 2回、`pitchMultiplier`・`volumeMultiplier`・`amplitude` への書き込み各1回、`set_localScale` 1回、`FxPlayNew(GameObject, Entity)` 1回）に加えて値の流れまで見る。すなわち、3つの曲線が `strength` だけで評価されてそれぞれのローカルに入り、その結果が対応するフィールドの書き込みと `localScale`（`Vector3.one * volumeCurve` の結果）へ渡ること、子走査2回が bool を取らない2引数の `GetComponentsInChildrenNonAlloc`（`includeInactive=false` の意味）で `DewAudioSource`・`FxCameraShake` それぞれに `fxHit` を渡して呼ばれること、`FxPlayNew(fxHit, e)` が `fxHit` と被害者 `e` を引数に取ることを確かめる。Prefix 内の例外でも同じく無効化して本体経路へ戻す。ただし `FxPlayNew` の呼び出しだけは try の外にある。書き込みが済んだ後の `FxPlayNew` の中で例外が出たときに本体へ戻すと演出がもう1つ入る（または同じ例外がもう1回出る）ため、そこは戻さず例外をそのまま伝播させ、本体が `FxPlayNew` の中で例外を出す場合と同じ挙動にする（レビュー指摘 F2 への対応）。

結果が変わらない理由は次のとおりである。書き込み先のコンポーネントは、プレハブアセットの子構成が不変であるため、毎回の走査が返すものと最初の1回の走査が返すもので同一である。書き込む値は3つの曲線の評価結果で、式と評価の引数（`strength`）は本体と同じだ。書き込む順序も、各音源への `pitchMultiplier`・`volumeMultiplier`、各 `FxCameraShake` への `amplitude`、`localScale`、最後の `FxPlayNew` まで本体と同じである。コンポーネントへの個別の書き込みは互いに依存しないため、走査と曲線評価の前後関係を入れ替えても結果は同じである。送信側（ホストのコルーチン、RPC の間隔と宛先）は一切変えていないので、通信の量とタイミングも変わらない。

この等価性は境界テスト（`tests/Issue73.Native.Tests/GemResponsibilityHitPerfTests.cs`）でも確かめた。境界の `Gem_C_Responsibility`・`DewAudioSource`・`FxCameraShake`・曲線のスタブに記録できる子と評価器を置き、Prefix を直接呼び出して、`strength` から `pitchMultiplier`・`volumeMultiplier`・`amplitude`・`localScale` への書き込み値と `FxPlayNew(fx, e)` の呼び出し引数が曲線の評価結果から導かれること、同じ `fxHit` では再走査が起きず参照が変わったときだけ作り直すこと、`fxHit` が無いときと設定が無効のときは本体経路へ戻ること、曲線の評価の例外ではこの修正だけを無効化して戻すことを確認した。あわせて指紋検査（`ValidateShape`）が本体 r1.4.1.2 の IL の形を受け入れ、走査の型の替え間違い・`includeInactive` 明示の3引数・`localScale` へ別の曲線の結果・`fxHit` 以外の対象の走査・曲線の割当て替え・`FxPlayNew` の引数替えを弾くことも確認した。

効果の見込みは推定である。被弾演出 RPC を受けるたびに、子孫の全走査2回（`fxHit` の階層の深さに比例）とプールのリストの出し入れ2回が、プレハブごとに最初の1回だけのコストに置き換わる。残るのは曲線の評価3回、配列の走査と値の書き込み、`localScale` への書き込み、`FxPlayNew` の呼び出しで、いずれも本体も行う処理である。獲得はホストと各参加者の受信ごとの CPU 負荷の削減であり、通信量は変わらない。この宝石は詠唱が多発する戦闘で被弾者の数だけ RPC を送るため、参加者の負荷が高い場面（多数の敵を巻き込む詠唱）ほど差が開く。初回ラウンドの検証は `tools/balance/gen_cs.py --check`、`src/SodRpg.Mod` の Release ビルド、`tests/Issue73.Native.Tests`（当時803件全件合格）、`tests/SodRpg.Mod.Startup.Tests`（238件合格・1件は既存のスキップ）で行った。修正ラウンド（レビュー指摘 F1）で指紋の強化と境界テスト12件を足した後は、`src/SodRpg.Mod` の Release ビルドと `tests/Issue73.Native.Tests` 全件（815件）を再実行した。この環境（net8 の実行環境が無く .NET 10 へのロールフォワード）では805件合格で、失敗した10件（CursorIdlePerfTests・DashSweepStepPerfTests・PositionSyncIdlePerfTests の IL 形状の検証）は修正前の同じコミットでも同じ環境で同じ10件が失敗しており、この修正の前後で失敗の集合は変わらない。追加した12件はすべて合格である。実機（ゲーム内）での確認は未実行である（この環境ではゲームを動かせないため）。なお指紋は既知の命令の並びと回数を見るため、本体が数えていない種類の文を将来追加した場合は検出できない。ゲーム更新のときはこの指紋の見直しが必要である（検出強化の改善案は台帳 #623 に記録した）。

レビューの修正ラウンド2では、指摘 F1（見本 IL が手組みで実物の本体 IL と突き合わせていない）と F2（`FxPlayNew` 内の例外で本体へ戻すと演出が二重に入る）に対応した。F2 は前述のとおり `FxPlayNew` の呼び出しを try の外へ出した。F1 は実 DLL（`Dew.Contents.dll` r1.4.1.2）から `ilspycmd -il` で取り出した受け口の命令列（下に記録）を確認の基準にした。実物では、曲線3つの評価は `ldarg.0 / ldfld <曲線> / ldarg.2 / callvirt Evaluate / stloc 0〜2` の並びで、評価の前に `dup` や `conv` は挟まらない。子走査2回は `ldarg.0 / ldfld fxHit / ldloca.s / call GetComponentsInChildrenNonAlloc<T>`（bool を取らない2引数）で、ループは列挙子（`GetEnumerator` / `MoveNext` / `get_Current`）で組み立てられ、音源のループでは列挙子の現在要素を `dup` で複製して `pitchMultiplier` と `volumeMultiplier` の2つの書き込みに使う（各 `stfld` の直前は `ldloc` のまま）。`localScale` は `ldarg.0 / ldfld fxHit / callvirt get_transform / call get_one / ldloc.1 / call op_Multiply / callvirt set_localScale` で、`FxPlayNew` は `ldarg.0 / ldarg.0 / ldfld fxHit / ldarg.1 / call` で呼ぶ。この確認をテストで保証するため、`GemResponsibilityHitPerfTests` に2件を足した。1つは実 DLL を Mono.Cecil で読み、命令列のオペランドを境界のスタブへ読き替えて（ローカルは番号を保った LocalBuilder へ）`ValidateShape` に通し、ループの組み立てや `dup` を含む実物の全体を受け入れることを確かめる。もう1つは見本 IL（`ShapeIl`）のうち指紋検査が解釈できる命令だけを取り出した並び（窓）が実物と同じであることを確かめる。見本 IL には実物と同じ `dup` と `FxPlayNew` の手前の `ldarg.0` を足してあり、拒否の見本6種はこの形のままで弾ける。ゲームの DLL が無い環境（CI など）ではこの2件は確認なしに終える。DLL の場所は `tests/repro` の抽出スクリプトと同じ `SOD_MANAGED` 環境変数で受け取る。
