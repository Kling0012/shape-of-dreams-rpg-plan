# perf-loop/20261019-2159

対象: mod src/SodRpg.Mod/ClientSession.KillSync.cs。このファイルから毎フレーム呼ばれる経路を、呼び出し側（ClientSession.cs の `_tickSteps`、ClientSession.RunChoices.cs の `TickRunChoices`）の両方から見た。ゲストが通信を受けるたびに走る処理（`OnMonsterKill`・`ReceiveMonsterOwnership`・`ReceiveDynamicDifficulty`）と、撃破ごとの `CaptureNativeKill`・`ResolveClassifiedDeaths`、受領送信の2経路（`TickKillSync` の旧ホスト向け経路と `TickKillReceiptDelta`）も読んだ。この2経路は前回までのループ（20261018-1829・20261019-1250）で間引き済みで、今回は触らない。

直した内容: `TickKillClassification`（分類の済んだ撃破を保留報酬の列へ移し、期限の巡った分類待ちを整理する処理）が、1フレームに2回走っていた。1回は `_tickSteps` の独自の段（ClientSession.cs:270、`ContinueReady` で止まらない）、もう1回は `TickRunChoices` の中（ClientSession.RunChoices.cs、`ContinueReady` を通り抜けた後）だった。2つの呼び出しは別々のコミット（#70 で内側、翌日の #73 で外側）で足されたもので、内側の1回は直前の外側の1回の直後に同じ処理を繰り返すだけだった。`TickRunChoices` から呼び出しを外し、外す理由を1行のコメントで残した。

結果が変わらない理由: 残す呼び出しは、外した呼び出しより前に毎フレーム必ず走る（外した側は `!ContinueReady` の間は走らないので、残す側のほうが網羅する）。2つの呼び出しの間に走るのは `ContinueReady` の評価と `TickInfinity` だけで、この間に `_killClassifications` や保留報酬の列に触れる処理は存在しない（`_killClassifications` へのアクセスは grep で ClientSession.KillSync.cs だけと確かめた）。通信の受信とネイティブの撃破イベントはフレームの間に届くので、同じ目の2つの文の間で分類の状態が変わることはない。内側の呼び出しは必ず外側と同じ状態を見るため、外しても1フレームの中の結果は同じで、`TickRunChoices` の後続の処理（`TryFinishSecureArrival` の `HasPendingKillClassification` 判定、`FlushPendingRunRewards`、`TryConcludeRun`）が見る状態も変わらない。

効果の見込み（推定）: 撃破が分類を待っている間（戦闘から精算までの窓。ゲストは撃破ごとにホストの事実を待つので、この状態のフレーム数は多い）に、毎フレーム2回走っていた `KillClassificationLedger` の先頭確認と解決済み被害者の解放、必要時の未識別死亡の掃除が1回になる。1回の走査自体は小さいので、削れるのはフレームのごく一部。ホストとゲストのどちらでも効き、ゲストでは撃破の疎通が悪いほど窓が長くなるため効き目が伸びる。
