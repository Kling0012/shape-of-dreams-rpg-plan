# perf-loop/20261024-0705

## 対象

`src/SodRpg.Mod/FeverFxThrottle.cs` のうち、`FxCameraShake.Play` に付けている `FeverCameraShakePatch`（Fever の爆発が自分のカメラシェイクの振幅を上限内に収めるためのパッチ）。

## 直した内容

この Prefix は、ゲーム内の**すべての**カメラシェイクの再生ごとに `GetComponentInParent<Ai_Gem_E_Fever_Explosion>()` を呼び、自分の親をたどって Fever の爆発かどうかを調べていました。ほとんどのシェイク（敵の死亡・ボスの攻撃など）は Fever と無関係で、走査は毎回空振りします。

そこで、Fever の爆発が `OnCreate` に入った時点で、自分の持っている `FxCameraShake` を `ConditionalWeakTable` に事前登録するようにしました（`FeverExplosionFxPatch.Prefix` から `FeverCameraShakePatch.RegisterShake` を呼ぶ）。`Play` 側の Prefix は、辞書を1回引くだけでよくなり、親方向の走査をやめました。

## 結果が変わらない理由

本体は `OnCreate` の中で `GetComponentInChildren<FxCameraShake>()` で自分のシェイクを1つ記録し（`_cameraShake`）、再生はその記録したシェイクでのみ行われます。登録は同じ `OnCreate` の直前で同じ方法で行うため、登録される「爆発↔シェイク」の組は本体が記録するものと同じです。

旧コードが上限（Cap）を付けていたのは「親をたどると Fever 爆発に到達し、かつその爆発の記録したシェイクそのもの」の場合だけです。新しい辞書は同じ組だけを登録し、`Play` 側でも同じ同一性確認（`Fields.Shake(explosion) == __instance`）をそのまま残しています。プール再利用で `OnCreate` をやり直すときは登録もやり直し、`OnCreate` の外で再生が起きても辞書は残っているので、旧コードと同じくその場で上限を付け直します。爆発の `explosionRadius` と `_origShakeAmplitude` はこれまでどおり再生時に実物から読むため、値も同じです。

失敗時の扱いも同じです。登録は `OnCreate` の Prefix の先頭で行うので、爆発側の最適化が fail-soft で無効になっていても登録は続きます。辞書の登録や参照で例外が出たら、これまでどおり警告を1回出してこの上限だけを外し、本体の再生に戻します。

## 効果の見込み（推定）

カメラシェイクの再生は、敵の死亡や爆発など戦闘中に頻繁に起こり、ホスト・参加者のどちらの PC でもローカルに走ります。1回の再生ごとにあったコンポーネント走査（親を1つずつたどる `GetComponent` 連続呼び出し）が、小さな辞書1回の参照に置き換わるのが今回の削減です（1回あたり数マイクロ秒、戦闘中で毎秒数十マイクロ秒程度の推定）。削減量は大きくありませんが、参加者を含む全クライアントのシェイク再生の共通経路から、確実に無駄を1つ取り除けます。
