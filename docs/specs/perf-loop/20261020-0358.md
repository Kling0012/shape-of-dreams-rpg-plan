# perf-loop/20261020-0358

対象は MOD の `src/SodRpg.Mod/ClientSession.PressureDividend.cs` である。ゲスト（参加者）側の経路は二つある。ひとつは受信処理 `OnPressureDividend`（ホストから届く討伐証拠ごとに走り、中身は文字列比較と受信ごとの小さな確保だけですでに薄い）。もうひとつは毎フレームの `FlushPendingPressureDividends` で、`ClientSession.RunChoices.cs` の `TickRunChoices` → `FlushPendingRunRewards` から毎フレーム呼ばれる。こちらが今回の改善先である。

直した内容は、`FlushPendingPressureDividends` の先頭に「精算待ちが空なら抜ける」判定を足すことである。従来は保留が 0 件のフレームでも、呼ばれるたびに `RunActive` の再計算（`Profile.Run.RunId == ActiveRunId` の文字列比較と `Profile.LobbyReturnedRunIds.Contains` の文字列ハッシュを含む）、Infinity の停止判定、`Drain` の引数チェックと runId の文字列比較まで進んでから 0 を返していた。変更後は `Count == 0` の 1 回の整数参照で抜ける。

結果が変わらない理由は次のとおりである。`PendingPressureDividends.Drain` はキューが空のとき、先頭の null チェックと runId の文字列比較だけを行い、ループに入る前に何も変更せず 0 を返す（副作用がないことは `src/SodRpg.Core/Game/Mechanisms/PendingPressureDividends.cs` の実装で確認した）。付与は `Drain` のループ内でしか起こらず、`DeferKillSave()` も `awarded > 0` のときしか呼ばれないので、空のキューでは従来の経路も外から見える変化を何も起こさない。通知用デリゲートの遅延生成も、空のキューでは通知が発生しないため省いてよく、保留が入った最初の精算で従来どおり作られる。キューに保留があるフレームは判定を 1 つ余計に通るだけで、以後の流れ（`RunActive`・停止中の保持・精算・二度精算されないこと）は従来どおりである。この停止中の保持と回復後の精算は `tests/Issue73.Native.Tests/NativeAcceptanceTests.cs` の `HaltedInfinityHoldsDividendReceiptsUntilSaveAgreementRecovers` と `HaltedInfinityZeroBudgetDividendStillSettlesOnRecovery` が同じ `FlushPendingPressureDividends` を通して検証していて、両方とも通った。

効果の見込み（推定）は、保留が空の毎フレームで走っていた文字列比較 2 回と `HashSet<string>` の文字列ハッシュ 1 回と数個のプロパティ参照が、整数 1 回の参照に置き換わることである。ホスト・参加者の両方で毎フレーム走る経路なので、1 フレームあたり 0.1〜0.3 マイクロ秒程度の削減と見るが、数値は推定で実機での計測は行っていない。

検証は `python3 tools/balance/gen_cs.py --check`（変化なし）、`dotnet build src/SodRpg.Mod -c Release -p:GameDir=... -p:ModDeployDir=/tmp/perfloop-x`（0 エラー、警告 6 件は既存のもの）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/Issue73.Native.Tests -c Release`（551 件全通）、`DOTNET_ROLL_FORWARD=LatestMajor dotnet test tests/SodRpg.Mod.Startup.Tests -c Release`（225 件通過・1 件スキップは既存のもの）を実行してすべて通した。実機（ゲーム内）での確認は未実行であり、コードとテストで理論上正しいことを確かめた段階である。
