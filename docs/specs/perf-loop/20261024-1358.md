# perf-loop/20261024-1358

対象: `Dew.Core/MusicManager.cs`（BGM の再生とフェード。本体コードなので MOD から Harmony パッチで軽くする）

## 直した内容

`MusicManager.LogicUpdate` はロジックtickごと（最大30Hz、`LogicUpdateManager.MinLogicUpdateInterval = 1/30`）に、ホスト・参加者の全クライアントで走ります。フェードが終わって曲の切り替えもない定常状態では、メソッド末尾が毎tick同じ値の float を計算し直し、`_activeSource.volume` と `_activeSource.pitch` に同じ値を書き続けます。Unity の `AudioSource` の setter は、値が同じでも音声スレッド側の更新対象に印を付けるネイティブ呼び出しです。つまり定常状態の末尾では、この2回の書き込みが毎tick無意味に走っています。BGM でフェードが動くのは曲の切り替え（ゾーン移動など）の前後だけで、それ以外のtickは定常状態です。

そこで `NativeMusicSourceIdlePerf`（`src/SodRpg.Mod/NativePerfPatches.cs`）を追加しました。Transpiler で `MusicManager.LogicUpdate` と `MusicManager.DoCrossFade` の6つの書き込み箇所（LogicUpdate に volume×3・pitch×1、DoCrossFade に volume×1・pitch×1。実 DLL の IL で確認）を、前回書き込んだ値と比較して同じなら書き込みを省くガード関数に付け替えます。ガードは設定オフのときもキャッシュを更新するので、設定の切り替えでキャッシュと実値がずれることがありません。書き込みを省くのは、2つのメソッドの書き込みが両方ガードへ付け替わったことを Transpiler が確認した後だけです（どちらかが本体の形と違って付け替わらないときは、ガードは毎回書きます。キャッシュは付け替わっていない側の直接書き込みを見られないため）。キャッシュの更新は音源への書き込みが戻ってから行うので、書き込みが例外で失敗したときも、次の同値書き込みは省かれずに再試行されます。

MOD 設定に `nativeMusicSourceIdle`（既定は有効）を追加しました。

## 結果が変わらない理由

ガードは「前回書き込んだ値と同じなら書かない」だけです。書き込みは値が同じなら冪等なので、省いても音源のプロパティの状態は1つも変わりません。フェード中は毎tick値が変わるので、従来どおり毎tick書きます。

「前回書き込んだ値」が実値と一致する根拠は、この2つの AudioSource の volume・pitch を書いている場所が MusicManager のこの6箇所だけであることです。確かめた範囲は次のとおりです。

- `Play`/`Stop` は次の曲を登録するだけで音源に触れない。`Pause`/`UnPause` は volume・pitch を書かない。
- 外部で `_source` を使うのはデバッグ用の `DewConsoleCommands`（`.time` を書くだけ）。`AudioManager.SetupAudioSource` は `Start` で1回だけ走り、最初のガード書き込みより前（ガードの初期値は NaN なので最初の1回は必ず書く）。
- 逆コンパイルした Dew.Core 全体の検索で、`set_volume`/`set_pitch` はこの2メソッドにしかない。

計算式は本体のまま変えていません。比較は同じ式の結果に対する完全な float 同士の一致なので、書くか省くかだけが違いで、書かれる値は同じです。

Transpiler は本体の形（メソッドごとの書き込み箇所の数）を確認し、違う形ならそのメソッドを何も変えずに警告を1回出します（fail-soft）。この確認はメソッドごとなので片方だけ付け替わらない状態があり得ますが、その間はガードが毎回書くので、付け替わっていない側の直接書き込みが原因のずれは起きません。ガード内の例外は本体の書き込みと同じ条件で同じ例外になる想定で、追加の握りつぶしはしていません。

## 効果の見込み（推定）

推定です。定常状態の1ロジックtickあたりネイティブ setter 2回（volume・pitch）を省きます。Unity の AudioSource への managed→native 遷移1回を 0.1〜0.3µs とすると、30Hz で毎秒 6〜18µs 程度の削減で、フレーム時間に対しては0.02%未満の軽微な改善です。ミラージュのポストプロセス（`nativeMirageVolumeIdle`）や詠唱テレグラフ（`nativeCastTelegraphIdle`）と同じ「同じ値の再書き込みを省く」種類の変更で、ホスト・参加者とも同じだけ軽くなります。
