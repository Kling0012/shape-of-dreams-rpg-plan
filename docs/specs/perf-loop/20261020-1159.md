# perf-loop/20261020-1159

対象は mod `src/SodRpg.Mod/HostAuthority.BossGlacialCore.cs`（458行）である。本体のジェム `Gem_U_GlacialCore`（氷結の核、通称 Skoll）に、MOD の報酬「ボス魂」が絡むときの治癒の横取り・連射の間隔短縮・視覚の配信を担うファイルである。

見えた構造は次のとおりである。ホスト側の毎フレーム経路は `BeginSkollCoreUpdate`（`ActiveLogicUpdate` の Prefix、本体はゲストでは `!isServer` で即returnするので transpile 点はゲストで走らない）と `TickSkollCores`（ホストティック）、被弾ごとの経路は `OnDealDamage` の Prefix とコルーチンの `MoveNext` のフックである。ゲスト側で走る MOD コードはどれも `NetworkServer.active` の1分岐で抜ける保護だけで、確保も全走査もなかった。視覚は `SkollPublishBurst` が `PublishBossVisual`（kind 9、残数カウンタ）へ出す。`PublishBossVisual` 側には同一値の早期returnと kind 9 の0.1秒間引き（coalesce）が既にある。

直した内容は、`SkollPublishBurst` が視覚の `due` に毎回の現在時刻を渡すのをやめ、バースト開始時刻（新設の `SkollCoreState.BurstDue`、`CompleteSkollCoreHeal` がバースト開始時に記録、解放時に0に戻す）を渡すようにしたことである。`due` が毎ティック変わるせいで `PublishBossVisual` の同一値判定（15項目の一致比較）が必ず失敗し、残数も位置も変わっていない間も、0.1秒ごとの間引き送信が全人間プレイヤーへ続いていた。固定後は、持ち主がその場に止まっていて残数が変わらないフレームは送信も保留も発生しない。残数が変わったとき（発射ごと）・持ち主が動いたとき（coalesce で最大10Hz）・残数が0になるとき（最後の発射かバースト中の解放での削除の即時送信）は、いずれも現在と同じ経路で送られる。BurstUntil の自然な満了では、効果は開始時に届いた `expires` の期限で host・client の両側から取り除かれ（game-time-deadlines）、追加の電文は出ない。host 側は `PruneBossVisualState` が効果を先に外すため、期限の切れた効果への削除電文は発行されない。

結果が変わらない理由は次のとおりである。クライアント側（`ClientSession.BossVisuals.cs`）で kind 9 の `due` が効く場所は、受信検証の有限値チェック、`pending = effect.due > now` による色と線幅、`progress`（`finalRadius >= 0` のときだけ半径に使う）の3つである。Skoll のバーストは `finalRadius` を渡さない（-1）ので `progress` は未使用であり、`pending` は受信時の `clockOffset` 補正後に `due` がほぼ確実に過去になる（送信から到着までの遅延ぶん `now` が進む）ため、現在コードの10Hz更新でも常に false に保たれる。開始時刻に固定しても同じく false であり、描画される色・線幅・半径は変わらない。削除メッセージではクライアントは `due` を読まず、キャプション（残数表示）は `count` から更新されるので、残数が変わるときだけ届く現在の性格も変わらない。

これに加えて、Issue73.Native.Tests に Skoll バースト表示のテスト（`SkollBurstTests`、7件）を追加した。`HostAuthority.BossGlacialCore.cs` から `CompleteSkollCoreHeal`・`CountSkollCoreShot`・`TickSkollCores`・`SkollPublishBurst`・`SkollReleaseCore` を、`HostAuthority.BossVisuals.cs` から `PublishBossVisual` と視覚状態を、既存の抽出タスク（NativePersistence.targets）でそのまま抜いて実行し、次を確かめる。(1) 残数も位置も変わらないティックが間引き窓をまたいで続いても差分も保留も出ないこと（改定も起きない）。対照として、持ち主が動いただけのティックは直前の送信から0.1秒の間引き窓の中では即送ではなく保留に入ることも、別のシナリオで確かめる。(2) 発射で残数が減ると即座に差分が出て、`due` はバースト開始時刻のまま届くこと。(3) 発射で残数が尽きるときとバースト中の解放では残数0の削除差分が即座に出ること、BurstUntil の満了では残数が0になり効果が `expires` の期限で取り除かれること（追加の電文なし）。(4) 同じ `BurstVisual` の id で次のバーストが始まると `BurstDue` が新しい開始時刻に更新されて新たに送られること。抽出に必要な本体 API と未リンク部位の境界は `SkollBurstBoundary.cs` に置いた。テスト内の時刻は本体の時計と同じく単調に進む並びにしてあり（発射の時刻はバースト期限から逆算）、時計を巻き戻すことでしか作れない場面は検証しない。

効果の見込み（推定）は、バーストが生きている間の無変化の差分送信（持ち主が静止している間は最大毎秒10通・受信者ごと）と、それに伴うホスト側の JSON 直列化が0になることである。バーストは発動ごとに数秒続くので、戦闘中のホストの送信量と各ゲストの受信・検証処理をわずかに減らす見込みである（推定）。持ち主が動いている間の位置追従の更新（最大10Hz）は見た目を保つために残す。
