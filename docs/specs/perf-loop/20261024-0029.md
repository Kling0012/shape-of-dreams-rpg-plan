# perf-loop/20261024-0029

## 対象

mod src/SodRpg.Mod/HostAuthority.BossPolaris.cs（Polaris ボス装備＝boss_polaris のホスト側処理）。このファイルはホストだけで走り、参加者への通信はボス演出メッセージの送信だけだが、ティックごとの `TickPolarisBoss` と、被弾・攻撃・メモリ使用・移動完了の各アクティベーションごとに呼ばれる `DispatchPolarisBoss` が主な処理なので、3（毎フレーム・被弾ごとの経路の無駄）の観点で見た。

## 直した内容

`DispatchPolarisBoss` は、受理されたイベント1件ごとに `PolarisState` が9種一括の `BossFind`（`Build.BossMoves` の全走査）をやり直していた。その後も攻撃を並べるループで装備区分ごとに最大6回、位相処理で stage2 を、反撃で head を、三連の締めで stage6 を、それぞれ個別に `BossFind` していた。メイン攻撃1ヒットごとに最大で16回の全走査が走る計算になる。また毎ティックの `TickPolarisBoss` も、状態が存在する間ずっと同じ9種一括の全走査を繰り返していた（1つ目は装備が減ったら状態を捨てるため、2つ目は `state.Mask` の更新のため）。

そこで、9種の在確認と `(entry, profile)` の判定を `PolarisCombat` に覚えるようにした。走査を行うのは状態の作成時と、装備エポック（`rt.ShieldEquipmentEpoch`）が変わった最初の1回（`PolarisState` と `TickPolarisBoss` の両方）だけで、以後のイベント処理とティック処理は覚えた判定を流用する。位相の stage2・締めの stage6・反撃の head は、`BossFind` が失敗した場合と同じく判定が null のときの早期 return に置き換えた。

レビュー指摘（C-II）への修正で、状態を持たない経路の処理順を元に戻した。`PolarisState` の状態作成は、従来どおり書き込みをしない在確認（`PolarisMask`）を先に行い、区分が1つでもあれば `Rent` → `Reset` → `PolarisScan` で判定を覚える。Polaris の報酬だけを装備している英雄のように区分が1つも無いまま毎イベント呼ばれる経路で、`Rent` → `Reset`（`Seen[256]` などのクリア）→ `Return` の固定費が毎イベントかかるのを避ける（作成時に走査が2回になるが、作成は1回きりである）。あわせて `BossEnsure` の `Build` 差し替え処理に、`PolarisCombat` のキャッシュがここの状態破棄を前提としている旨のコメントを生産者側にも追加した。

## 結果が変わらない理由

`BossFind` の結果は `rt.Powers.Build.BossMoves` の内容と静的な `BossProfiles` だけで決まり、`BossMoves` は `Build` の生成後にどこからも変更されない。装備の付け替えは必ず別インスタンスの `Build` になり、`BossEnsure` は `Build` の差し替え・装備エポック・部屋・走・所有者の寿命のいずれかが変わるたびに `ClearBossEffects` → `ClearPolarisBoss` で状態を一度捨てるので、`PolarisCombat` が生きている間は覚えた判定が古くなる窓がない。生きている間にエポックだけが変わる経路でも、`PolarisState` と `TickPolarisBoss` の変更パスが9種を走査し直して `Mask` と判定を付け直し、消えた区分があれば従来どおり状態を捨てる。攻撃ループは以前と同じく `state.Mask` のビットでしか入らないので、走査をやめたことで新しい区分が動き出すこともない。クールダウン・ダメージ・演出・通信の内容は何も変わらない。この処理はホストだけで走り、送信の量と回数は変わらない。

## 効果の見込み（推定）

`Build.BossMoves` は最大64件で、走査1回ごとに最大64回の文字列比較と `BossProfiles.TryGetMove` の辞書引きを行う。以前は Polaris 装備の状態がある間、ティックごとに9回、受理されたイベントごとに9回＋区分ごとに最大7回の全走査が続いた。60fps 換算で Polaris 装備1人分の状態があるだけで毎秒540回、メイン攻撃のヒット1回ごとに最大16回の全走査がなくなる（推定。1回は数百ナノ秒だが、戦闘中ずっと走る経路の固定費である）。参加者の PC には届かない処理だが、ホストのフレーム時間の裾を下げる。
