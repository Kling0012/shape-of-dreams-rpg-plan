# perf-loop/20261019-2338

## 対象

mod src/SodRpg.Mod/ClientSession.Diagnostics.cs（遠征の診断ログ。参加者（ゲスト）側の `ClientSession.Tick` から毎フレーム呼ばれる `TrackRun` の最初の1ステップと、ラン開始・終了・確定・転送・ビルド適用・圧力受信の各イベントから呼ばれる経路）。

呼び出し側の実行頻度も確認した。`ObserveNativeRunForDiagnostics` は毎フレームだが、中身は `NetworkedManagerBase<T>.softInstance` の静的フィールド読みと `GameManager.runId`（自動実装プロパティ。reflection-dump で `Network<runId>k__BackingField` を確認）の参照比較だけですでに最小。`DiagnosePressureReceipt` はホスト側が送信を5〜30秒間隔で重複排除している（HostAuthority.cs の `SendPressure`）ため受信は数秒に1回以下。`DiagnoseBuildSubmission` はビルド送信 tick のうち、前回の送信から5〜30秒以上経ったときにだけ通る経路。つまりこのファイルに高頻度の経路はなく、無理な作り替えはしない。

## 直した内容

`DiagnoseExpedition` が1回の呼び出しで `HeroKeyOf(hero)` を2回計算していたのを1回にまとめた。1回目は装備状態の検索キー（`Profile.Heroes.TryGetValue`）、2回目は出力文字列の `hero=` 項で、同じ値を2度計算していた。`HeroKeyOf` は `h.GetType().Name` であり、ClientSession.cs の既存コメント（SendBuildIfNeeded 内）が明記するとおり、Unity の null チェック（ネイティブ呼び出し）と `Type.Name` の文字列確保（Mono では呼び出しごとに新しい文字列）を伴う。最初に1度だけ計算してローカル変数に入れ、検索と出力の両方で使い回す。

## 結果が変わらない理由

`HeroKeyOf` は入力が同じなら同じ文字列を返すだけの純粋な計算で、副作用はない。出力文字列は1文字も変わらず（`hero` が null のときは従来どおり `none`）、`Profile.Heroes.TryGetValue` に渡すキーも同じ。計算を前に移しただけなので、例外が出たときの try/catch での握りつぶしも含めて挙動は同じ。診断ログの内容・出力条件・行数上限（ExpeditionDiagnostics の48行制限と重複排除）はすべて変わらない。

## 効果の見込み（推定）

`DiagnoseExpedition` はランあたり十数回（開始前後・終了・確定・転送・適用受信）しか走らないため、効果は小さい。それでも呼び出しごとに `Type.Name` の文字列確保1回と Unity ネイティブの null チェック1回が減る（推定。1遠征あたり十数回の確保が減る程度）。毎フレーム経路は元々数命令しかないため触っておらず、このファイルでこれ以上の guest 側の削減余地は見つからなかった。
