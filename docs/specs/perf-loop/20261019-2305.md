# perf-loop/20261019-2305

## 対象

`src/SodRpg.Mod/ClientSession.OverflowBonus.cs`（鞄あふれの追加ドリームダストのクライアント側）。`ClientSession` の tick 配列から毎フレーム呼ばれる `TickSatchelOverflow` → `TickOverflowBonus` の経路を見た。

## 直した内容

`TickOverflowBonus` は、送信そのものが 2 秒・5 秒・30 秒の間隔に間引かれている一方で、間引きの判定に必要な計算（`UpdateOverflowBonusPreference` の全ガード、`ReleaseStaleOverflowBonus`、メッセージ項目の変化検出）を毎フレーム行っていた。ゲスト側ではこれに `GameManager.softInstance.runId`・`ZoneManager.softInstance.currentZoneIndex` の読み出しと、遠征 ID の文字列比較が毎フレーム含まれる。

そこで定期入口 `TickOverflowBonusPeriodic` を新しく作り、0.25 秒間隔で本体の `TickOverflowBonus` を呼ぶようにした（`ClientSession.cs` の tick 配列側の呼び出しを差し替え）。毎フレームの全評価は 60fps で約 4%、144fps で約 1% になる。

## 結果が変わらない理由

この評価の入力が動くのは、設定変更・ホストの応答受信・あふれの発生・ゾーン移動のときだけだ。このうち設定変更（`ConfigureOverflowBonus`）と応答受信（`OnOverflowBonusResult`）は独自に再評価と再送解禁をするため、間引きの影響を受けない。あふれの発生とゾーン移動は、メッセージ項目の変化検出（`changed`）で送信間隔を無視してすぐ送る仕組みに載っていて、検出が最大 0.25 秒遅れるだけだ。未払いの再送は元々 2 秒間隔なので、ホスト側の支払いタイミングへの影響はその誤差より十分に小さい。

間引いてはいけない経路は直接呼び出しを残した。遠征終了時の確定前の最終送信（`ClientSession.RunChoices.cs` の `TryConcludeRun`）である。ここが間引かれると、遠征の消去後に未払い分が「諦め」扱いになってしまうため、必ず即時に送る。接続のし直し（`ResetOverflowBonusConnection`）では間引きの期限を 0 に戻すので、再接続直後の最初の評価も今どおり即時に行う。

送信メッセージの内容・間隔（2 秒・5 秒・30 秒）と、受け取れるダストの額は変わらない。

## 効果の見込み（推定は推定と書く）

参加者（ゲスト）側で、この tick の評価が毎フレームから 0.25 秒間隔になる。1 回の評価はフィールド読み出しと短い文字列比較が中心の小さなものなので、絶対量の見込みはフレームあたり 1〜2 桁少ない命令数の削減（推定）。GC の確保は元々この経路にないため、削減対象は CPU の比較と読み出しのみ。
