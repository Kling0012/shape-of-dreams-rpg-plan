# perf-loop/20261019-1754

対象は本体 `Dew.Core/Hero.cs` と、そこから毎フレーム・被弾ごと・通信ごとに呼ばれる処理である。実 DLL からの逆コンパイルと空白正規化 diff で一致を確認済み。

通信の観点では、Hero.cs の SyncVar（loadout・exp・isKnockedOut・isInCombat・skin）と撃破・アシスト通知の RPC がすべてイベント駆動で、Mirror が同値を送らずダーティビットもまとめて送るため、減らせる送信はなかった。被弾ごとの KillTracker 掃除走査の間引きは、既存の `NativeKillTrackerCullPerf` がすでに同じ箇所を扱っていた。

直した内容は `Hero.FrameUpdate` の武器スケール更新である。このメソッドは毎フレーム・各英雄ごとに、武器と納刀武器の `Transform.localScale` を `Vector3.SmoothDamp` で更新していて、スケールが目標に収束したあとも同じ値の計算と Transform への同じ値の書き込みが描画フレームごとに続く。これを外す Harmony の Transpiler（`NativeHeroWeaponIdlePerf`）を追加した。MOD 設定 `nativeHeroWeaponIdle`（既定は有効）で切れ、書き方が変わっていたときは警告を1回出して何もしない。

結果が変わらない理由は次のとおりである。すでにスケールが目標と一致し速度が正確に 0 のとき、Unity の `Vector3.SmoothDamp` は式のうえで入力と同じ値を返し、速度も 0 のままである。その直後の Transform への書き込みは同じ値を書くだけで、読む側が得る値も、引き続く `SetActive` の比較結果も変わらない。静止していない間、速度が残っている間、NaN、設定オフのときは、すべて元の本体の経路を通る。対象の 2 箇所（4 引数の `SmoothDamp` 呼び出しと、その直後の `set_localScale`）は実 DLL の IL で数と並びを確認した。既存の `NativeWeaponFxPerf`（同じメソッドの確保と走査を置き換える）とは置き換える命令が重ならないため、適用の順序に左右されない。

効果の見込み（推定）は、各英雄の静止中に描画フレームごとの Transform への同じ値のネイティブ書き込み 2 回（子への TransformChanged 伝搬を含む）と SmoothDamp の計算が省れることである。4 人協力のクライアントで 1 秒あたり 0.1〜0.3ms 程度の削減を見込むが、これは推定で、実機での計測は行っていない。
