# perf-loop/20261023-2325

対象は `src/SodRpg.Mod/HostAuthority.BossSkoll.cs` である。直した内容は、Skoll の印表示の配送で、`SkollPublishMarks` が `PublishBossVisual` に渡す `due` を毎回の現在時刻から印の蓄積開始時刻（`SkollState` に追加した `MarkDue`）に固定した点である。印が付くときに開始時刻を記録し、状態の消去時に戻す。同じ規約は氷核のバースト表示（`SkollPublishBurst`、`HostAuthority.BossGlacialCore.cs`）で既に採用済みで、そちらには説明コメントと検証テスト（`SkollBurstTests`）もある。

送信が減るしくみは次のとおりである。`PublishBossVisual`（`HostAuthority.BossVisuals.cs`）には、前回と全フィールドが同じなら何も送らずに返る同一性判定がある。印は持ち主（ヒーロー）の移動に合わせて位置を追従させるため毎ティック再発行していて、従来は `due` に毎回の現在時刻を渡していた。そのため、位置も数も変わっていないティックでもこの判定が必ず失敗し、差分は kind 9 の間引き（10Hz 抑制）の保留に入ったうえで、約100ミリ秒ごとに revision を1つ進めて全員へ1通ずつ送られていた。クライアント側（`ClientSession.BossVisuals.cs`）でその差分が変えるものは何もない。`due` を固定すると、静止中で数が変わらないティックは同一性判定で止まり、送信も保留も revision の更新もなくなる。移動時は kind 9 の間引きが従来どおり働き、数の増減と削除は即時のままである。

結果が変わらない理由は次のとおりである。クライアントで `due` を読むのは `pending = effect.due > now`（表示色の濃さとリングの太さ）だけで、リングの半径は `finalRadius` が負のとき受信値のままなので `due` からの進行度は使われていない。従来の送信でも `due` は送信フレームの `Time.time` 以下で、クライアントは受信時刻との差し引きのあと `pending` を false と判定する。開始時刻は必ずそれより過去なので、固定後も `pending` は false のままである。印の数・位置の追従・削除のタイミングは、変更前と同じ経路で届く。

効果の見込みは推定だが、印が付いていて持ち主が静止している間のティックで、全員宛ての差分送信（1つの印につき従来は最大10通/秒）と、各参加者の `OnBossEffects`（全効果の検証付きの受信処理）がその分だけなくなる。印は付与のたびに寿命が延びるため実戦では付き続ける時間が長く、戦闘中に継続して掛かっていた無駄である。削減量は印が付いている対象の数と静止している割合に依存し、1試合あたりの規模は小さい。ホスト側も、毎ティックの保留処理が同一性判定の早期 return になる。
