# perf-loop/20261019-1523

対象: mod src/SodRpg.Mod/NativeActorLifetime.cs。

直した内容: この MOD は、死んだ被害者を参照する孤立したステータス効果を検出して片付けるために、毎フレームの更新の入口で `CanUpdate` を呼ぶガードを3つ置いている（`Actor.LogicUpdate`・`StatusEffect.FrameUpdate`・そして以前は `Actor.FrameUpdate` にも）。このうち `Actor.FrameUpdate` へのガード（`NativeStatusActorFrameGuard`）を削除した。このガードは、シーンにいる全アクター（英雄・魔物・弾・効果）の毎フレームの `Actor.FrameUpdate` に1回ずつ Harmony のフックを足しておき、中身は「StatusEffect かどうか」を確かめて効果以外はそのまま通すだけだった。効果については、`StatusEffect.FrameUpdate` のガードが同フレームに同じ `CanUpdate(effect, false)` を必ず先に実行していて、2回目の呼び出しの間に走るコードは何も無い（`StatusEffect.FrameUpdate` の最初の文が `base.FrameUpdate()` であり、その間は Harmony の受け渡しだけ）ため、2回目は必ず同じ結果になる。つまり `Actor.FrameUpdate` 側のガードは、効果では必ず同じ確認の重複であり、効果以外では何もしない無駄な呼び出しだった。

結果が変わらない理由: 実 DLL の逆コンパイル（Dew.Core）で、`StatusEffect.FrameUpdate` が `base.FrameUpdate()`（`Actor.FrameUpdate`）を最初に呼ぶこと、`AbilityInstance` は `FrameUpdate` を上書きしないこと、`LogicUpdateManager` がインターフェイス経由の仮想呼び出しで最も派生した `FrameUpdate` を呼ぶことを確かめた。したがって効果インスタンスが `Actor.FrameUpdate` に届く経路は `StatusEffect.FrameUpdate` の base 呼び出しだけで、その手前のガードが false を返せばそもそも `Actor.FrameUpdate` は走らない。片方だけ通って片方だけ通らない分岐は存在しない。残る2つのガード（`Actor.LogicUpdate` の被害者確認と `StatusEffect.FrameUpdate` の毎フレーム確認）は何も変えておらず、孤立効果の検出と後始末の動作はすべて同じ経路で続く。

効果の見込み（推定）: `Entity` は `FrameUpdate` を上書きしないため、英雄・魔物はもとより弾（`Projectile.FrameUpdate` の base 呼び出し）も毎フレーム `Actor.FrameUpdate` を通る。削除により、シーンの全アクターで毎フレーム1回の Harmony prefix 呼び出しと、効果ごとに毎フレーム1回の `CanUpdate` の重複実行がなくなる。1呼び出しは数十ナノ秒程度なので、戦闘中の数百アクター×60fps でもフレームあたり数マイクロ秒から十数マイクロ秒の見込みで、小さい（推定）。実測はできていない。
