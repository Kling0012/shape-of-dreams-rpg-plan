# perf-loop/20261019-1924

対象は本体 `Dew.Core/DewPlayer.cs` と、そこから毎フレーム・被弾ごと・通信ごとに呼ばれる処理である。実 DLL（`Shape of Dreams_Data/Managed/Dew.Core.dll`）から ilspycmd で再取り出しし、メソッド名・引数名・呼び出し箇所を照合済み（2026-10-19）。

毎フレーム経路は `LogicUpdate` 配下の4つに分けられる。ゲーム内の状態通知（`LogicUpdate_InGame`。すでに値が変わったときか 0.05 秒ごとに間引かれている）、ネットワーク化された画面内タイマー（`LogicUpdate_InGame_NetworkedOnScreenTimer`）、途中参加（`LogicUpdate_MidJoin`。条件がそろうまで即 return）、ロビー（`LogicUpdate_Lobby`。設定確認のみ）。タイマー以外は送信の間引きやガードをすでに持っており、減らせる送信はタイマーに集中した。ほかに毎フレームの確保や全走査の候補はなく、ゲストの受信処理に乗るのはタイマーの TargetRpc だった。

直した内容は、画面内タイマーの値の同値再送を省く Harmony の Prefix（`NativePlayerTimerIdlePerf`）である。本体の `DewPlayer.LogicUpdate_InGame_NetworkedOnScreenTimer` はホストの各ロジックフレームで、そのプレイヤーに表示中のネットワーク化タイマーごとに `TpcSetNetworkedOnScreenTimerValue(id, valueGetter())` を無条件に送る。このタイマーを作る本体の処理は `ChargingChannel`（チャージ技能の画面内バー）だけで、その値はチャージが満ちたあとはホールドしている間ずっと 1f のままなので、狙いをつけている間、本体は変化のない同じ float を毎ロジックフレーム送り続ける。パッチはプレイヤーごと・タイマー id ごとに「受信側がすでに持っている値」を覚え、それとビット等しい送信だけを止める。覚えた値は作成時の `TpcCreateNetworkedOnScreenTimer` の受信側へ初期値を運ぶ Postfix（`NativePlayerTimerCreateSeedPerf`）で播種し、送るたびに更新する。接続が切れている・まだ準備のできていない相手（`connectionToClient` が null か `isReady` が false）には Mirror が TargetRpc を届けられないため、その窓では覚えず播種もせず常に送る。消去の通知（`TpcRemoveNetworkedOnScreenTimer`）に Postfix（`NativePlayerTimerRemoveForgetPerf`）を足し、通知された id の記憶を捨てて、プレイヤーごとの表がチャージ技能の使用回数ぶん増え続けるのを防ぐ。MOD 設定 `nativePlayerTimerIdle`（既定は有効）で切れ、対象のメソッドが見つからない・書き方が変わっているときは警告を1回出して何もしない。

結果が変わらない理由は次のとおりである。受信側（`UserCode_TpcSetNetworkedOnScreenTimerValue`）は `RefValue<float>` への代入だけで、イベントもタイムアウトもなく、同じ値をもう一度受け取っても表示も判定も変わらない。等値の比較は float の `==` なので NaN は常に送られ、-0f と 0f がまとまるだけではチャージ率（0 以上）に影響しない。タイマーの id はプレイヤーごとの単調増加カウンター（`_nextOnScreenTimerId`。`Init` では消されない）で再利用されないため、消したタイマーの古い記憶が新しいタイマーを誤って止めることはない。消去の通知そのものは改変せず、バーの消え方は本体どおりである。接続のない・未準備の相手に記憶を進めないのは、届かない送信を覚えて、準備が整えたあとの最初の同値 set を誤って止めるのを防ぐためである（最悪でも重複1通が余分に送られるだけ）。送信形式は変えていないので、MOD なしの相手との併用でも相手側の動作は変わらない。

効果の見込み（推定）は、チャージを満ちたまま構えている各プレイヤーについて、ホストの送信処理と Mirror の writer 確保、その受け手である参加者側の受信・解析・代入がロジックフレームごと（60fps 換算で毎秒 60 通）から 0 通になることである。チャージを満ちたまま狙う技能の多い英雄では、参加者の受信処理として毎秒数十通の RPC が常時消える。数値は推定で、実機での計測は行っていない。

検証は `python3 tools/balance/gen_cs.py --check`、`dotnet build src/SodRpg.Mod -c Release`、`dotnet test tests/Issue73.Native.Tests -c Release`（511 件。このうち `PlayerTimerIdlePerfTests` の 8 件が今回の修正ラウンドで追加した、Prefix・Postfix の送否の境界（播種直後の同値・異値・2 回目の省き・NaN・設定無効・未準備の接続・受信側の値の系列・消去の忘れ・0f と -0f）の直接検証である）、`dotnet test tests/SodRpg.Mod.Startup.Tests -c Release`（225 件通過・1 件スキップ）をすべて実行して通した。実機（ゲーム内）での確認は未実行である。
