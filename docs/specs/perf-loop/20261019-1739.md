# perf-loop/20261019-1739

対象: mod src/SodRpg.Mod/EnemyOwnershipNative.cs の `EnemyOwnershipRetarget`（本体 `EntityAI.UpdateAIContext` への Harmony Prefix/Postfix）。

直した内容: ホスト上の全 AI エンティティ（魔物・召喚・ボス）が、本体の AI の刻みごとに通る `UpdateAIContext` の接後処理で、所有権の候補でないエンティティまで毎回 `RetargetOwnership` を呼んでいた。`RetargetOwnership` は最初の1行の `TryOwnership` が失敗すると何もせずに戻るが、その呼び出し1回と、中の `_enemyOwnership` 辞書引き（候補でなければ必ずミスする）が刻みごとに残る。そこで Prefix の判定結果を `__state`（bool から byte に変更。0=候補でない、1=候補で再照準なし、2=候補で再照準あり）に込め、0 のときは Postfix を丸ごと省くようにした。候補でないのは、すべての召喚とヒーロー（辞書に入らない）、ボスと除外・共有目標の魔物、そして所有権が動いていない場面の全エンティティ（`PrepareEnemyOwnership` は `OwnershipAvailable` が偽の間は状態を作らないため）。

結果が変わらない理由: `IsOwnershipRetargetCandidate`（HostAuthority.EnemyOwnership.cs:695）が偽になるすべての条件（`ai`／`ai.entity` の null、辞書ミス、`state.Excluded`、`state.SharedObjective`、`state.Owner == null`、`_enemyOwnershipEnabled == false`、Targeting の失敗フラグ）は、`TryOwnership(Targeting)`（同455行目）が見る条件の部分集合である。`_enemyOwnershipEnabled` と失敗フラグは `OwnershipAvailable` → `OwnershipRunning` の中で再検査される。候補でなければ `RetargetOwnership`（同700行目）は冒頭の早期リターンで何も観測できることをしないため、この呼び出しを省いても振る舞いは変わらない。この包含関係と「早期リターンが観測できる副作用を持たないこと」は、Issue73.Native.Tests の `Every_non_candidate_skip_condition_leaves_RetargetOwnership_an_observable_no_op`（上記の全条件を1つずつ再現し、retargetDue の両値で Aggro・標的・交戦記録・挑発・ログが動かないことを確かめる）と `Candidates_keep_retargeting_by_retargetDue_as_before`（候補の刻みは retargetDue の真偽に応じて従来どおり動くこと）で検証する。候補だったエンティティでは従来どおり `RetargetOwnership(ai, retargetDue)` を呼ぶ（bool から byte への置き換えは呼び出しと引数の値を変えない）。Prefix の try の中で例外が出た場合、旧コードは `__state = false` のまま Postfix を通していたので、catch 側で `__state = 1`（再照準なし）を入れて同じ呼び出しにそろえた。参加者側（サーバでない側）は Prefix が必ず 0 を残すので、旧い `if (NetworkServer.active)` のガードと同じになる。通信は変更していない。Aggro・スポーン・破棄の各パッチには触れていない。

Prefix と Postfix の間で候補判定が変わる経路: 旧コードは Postfix 時点で `TryOwnership` を評価し、新コードは Prefix 時点の候補判定で省くため、1回の `UpdateAIContext` の実行中に非候補から候補へ反転すると挙動が変わる。判定材料（`_enemyOwnership` の項目、`Owner`、`Excluded`、`SharedObjective`、`_enemyOwnershipEnabled`、Targeting の失敗フラグ）への書き込みをすべて追うと、書き手は (1) そのエンティティ自身のスポーン確定（`PrepareEnemyOwnership`／`FinalizeEnemyOwnership`。EnemyOwnershipNative.cs のスポーン系パッチから。最初の AI 刻みより前に完了する）、(2) ホスト側の定期走査（`StageAreaScan` → `ScanArea` → `ScanEnemyOwnership`、HostAuthority.cs:382 の段階リストから HostAuthority 自身の更新で駆動。CoopOmens の結界による `RefreshSharedObjectiveOwnership` と掃除・付け替えもこの走査から）、(3) 設定の読み込み（`ConfigureEnemyOwnership`、DreamforgeMod.EnemyOwnership.cs:11）の3つだけで、いずれも `EntityAI.UpdateAIContext` の同期呼び出し連鎖の中には現れない。Unity の単一メインスレッドでは Prefix と Postfix の間（1回の同期呼び出しの内側）に走査や設定読み込みは割り込めない。失敗フラグ `_ownershipFailed` は `FailOwnership` の `|=`（HostAuthority.EnemyOwnership.cs:116-117）で立つ一方通行で、候補から非候補の方向にしか動かない（その場合も旧コードは Postfix の `TryOwnership` で同じ早期リターンになる）。したがって非候補から候補へ反転する経路はなく、Postfix での判定やり直しは不要である。

効果の見込み（推定）: 候補でない AI エンティティの刻みごとに、インスタンス呼び出し1回（try/catch の入り口と辞書ミス1回を含む）を省く。本体の刻み間隔は `GetAIInterval`（逆コンパイルで確認）により、ヒーロー召喚とボスが 0.25 秒、目標を持つ魔物が 0.5 秒、持たない魔物が 1 秒。召喚を多用する構成では召喚が十数〜数十体になり、1体あたり秒4回動くため、省ける呼び出しは1秒あたり数十回になりうる。ソロや所有権が無効な場面では全エンティティが候補外になるため効果が最も大きい。呼び出し1回は数百ナノ秒程度の見込みで、削減量としては小さい（推定）。実測はできていない。
