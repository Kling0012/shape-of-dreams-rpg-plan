# perf-loop/20261018-1503

対象は本体 `Dew.Core/Accessory_AttachPoint.cs`。装飾品（帽子・腰の装飾など）を英雄のモデルへ毎フレーム追従させるコンポーネントで、`LateUpdate` が `UpdatePosition` を呼び、その中で `FindOffset` が走る。

## 直した内容

`FindOffset(entityOrSkinName)` は `customOffsets` のリストを名前の一致で線形探索する。`LateUpdate` はモデルが変わらない限り同じ文字列（`_cachedOriginalName`）を毎フレーム渡すため、リストが変わらなければ結果は毎フレーム同じになる。この照会を `NativePerfPatches.cs` に足した `NativeAccessoryOffsetPerf`（Harmony の Prefix/Postfix）でキャッシュし、名前・リストの参照・件数が前回と同じなら本体の走査を省いて前回の結果を返す。設定は `nativeAccessoryOffsetCache`（既定は有効）。

## 結果が変わらない理由

`FindOffset` は引数の文字列と `customOffsets` の中身だけから決まる検索で、確認した本体のコードには実行時に `customOffsets` を書き換える処理がない。キャッシュはこの前提に依存する。鍵の判定は Unity に依存しない値型 `AccessoryOffsetCacheKey` に切り出した。文字列の参照・リストの参照・件数を比較し、どれかが変われば本体で検索し直す。内容が同じでも別の文字列インスタンスなら本体で検索する。モデルが変わり、`_cachedOriginalName` が別の参照になった場合も同じ条件で外れる。

件数を変えずに要素を差し替えたり、要素の `entityName` を書き換えたりする操作は検出できない。検索結果が変わる編集でも古い結果を返し得るため、本体の更新や他の MOD がその操作を行う場合は `nativeAccessoryOffsetCache` を無効にする必要がある。リストの参照と件数だけで任意の編集を検出できるとは扱わない。

キャッシュするのは見つかった `AttachOffset` の参照で、位置・回転・拡大率は毎フレーム `UpdatePosition` の本体の計算が読み直す。追従、HatHalo の浮遊と向き、拡縮の補正は本体のまま。パッチ先が見つからない・実行時に例外が出たときは警告1回で本体の動作に戻る（fail-soft）。設定で切れる。

## 効果の見込み（推定）

毎フレームの文字列比較の繰り返しがなくなる。装飾品1つにつき毎フレーム数十〜数百ナノ秒、実行中の装飾品は十数個程度なので、全体では毎フレーム数マイクロ秒程度の削減と推定する（微小）。`customOffsets` が空の装飾品はもともと比較が早く終わるため、削減はほぼなく、英雄ごとの調整を多く持つ装飾品ほど効く。

実機での確認はしていない。2026-10-18 の前の修正ラウンドでは実 DLL を参照した Release ビルドが成功し、既存の `NativeStartupTests` 16件も合格した。ただし、これらは装飾品キャッシュの一致・不一致や検索結果の同値性を直接検証していない。直接テストは既存スイートになく、今回のテスト作成禁止の指示に従い追加していない。原則 II の同値性テスト要件は未完了。

前の修正依頼に記載されたレビューでは、F1 の鍵の切り出しと成立前提の明記を対応済みとし、残る直接テストを CRITICAL から MEDIUM に下げ、「このラウンドではマージを止めない」としている。この扱いを原則 II の改定や例外承認とはみなさない。
