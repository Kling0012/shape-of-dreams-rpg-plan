# perf-loop/20261018-1503

対象は本体 `Dew.Core/Accessory_AttachPoint.cs`。装飾品（帽子・腰の装飾など）を英雄のモデルへ毎フレーム追従させるコンポーネントで、`LateUpdate` が `UpdatePosition` を呼び、その中で `FindOffset` が走る。

## キャッシュの成立条件

`FindOffset(entityOrSkinName)` は `customOffsets` のリストを名前の一致で線形探索する。`LateUpdate` はモデルが変わらない限り同じ文字列（`_cachedOriginalName`）を毎フレーム渡すため、リストが変わらなければ結果は毎フレーム同じになる。`NativePerfPatches.cs` の `NativeAccessoryOffsetPerf` は、名前・リストの参照・件数・各要素の参照が前回と同じなら本体の走査を省いて前回の結果を返す。設定は `nativeAccessoryOffsetCache`（既定は有効）。

Postfix は、設定が有効で、機能が停止しておらず、Harmony が注入する `__runOriginal` が真のときだけ結果を格納する。他 MOD の Prefix が本体の実行を省略した場合、その結果はキャッシュしない。無効時は Prefix も Postfix もキャッシュを使わず、本体の検索だけが走るため、鍵の要素の参照配列の確保や `ConditionalWeakTable` への登録は発生しない。格納条件は Unity に依存しない `AccessoryOffsetStoreGate` で判定する。

## 結果が変わらない理由

`FindOffset` は引数の文字列と `customOffsets` の中身だけから決まる検索で、確認した本体のコードには実行時に `customOffsets` を書き換える処理がない。キャッシュはこの前提に依存する。鍵の判定は Unity に依存しない `AccessoryOffsetCacheKey<T>` が担う。文字列の参照・リストの参照・件数に加えて各要素の参照を比較し、どれかが変われば本体で検索し直す。内容が同じでも別の文字列インスタンスなら本体で検索する。モデルが変わり、`_cachedOriginalName` が別の参照になった場合も同じ条件で外れる。件数を変えない要素の差し替えは、要素の参照が変わるため検出する。

要素を差し替えずにその要素の `entityName` を書き換える操作は検出できない。検索結果が変わる編集でも古い結果を返し得るため、本体の更新や他の MOD がその操作を行う場合は `nativeAccessoryOffsetCache` を無効にする必要がある。

キャッシュするのは見つかった `AttachOffset` の参照で、位置・回転・拡大率は毎フレーム `UpdatePosition` の本体の計算が読み直す。追従、HatHalo の浮遊と向き、拡縮の補正は本体のまま。パッチ先が見つからない・実行時に例外が出たときは警告1回で本体の動作に戻る（fail-soft）。設定で切れる。

## 同値性の検証

鍵と結果の格納（`AccessoryOffsetCacheKey<T>` と `AccessoryOffsetCache<T>`）は Unity に依存しないため、`tests/SodRpg.Mod.Startup.Tests/AccessoryOffsetCacheTests.cs` が直接検証する。

鍵の一致は同じ文字列参照・リスト参照・件数・要素の参照で成立する。文字列のインスタンスが違う（内容が同じでも）、リストのインスタンスが違う、件数が変わる、同件数で要素を差し替える場合は一致しない。

要素を差し替えずに `entityName` の値を書き換えた編集は検出できず、書き換え後も前回の結果を返して再検索しない。テストはこの制限と書き換え後の素の検索結果との食い違いも検証する。Postfix の格納条件（設定・`_disabled`・`__runOriginal` の組合せ）は `AccessoryOffsetStoreGate` の真偽表テストで検証する。

キャッシュ経由の結果は `FindOffset` と同じ線形探索（名前の完全一致と `Skin_` のとき `Hero_` へのフォールバック）を模した関数の結果と、`null` を含めて参照として一致する。要素の差し替え・追加・削除・リストの入れ替えの前後でも一致する。一度 `null` を格納した後は、鍵が同じ間は再検索せず `null` を返す。

## 効果の見込み

毎フレームの文字列比較の繰り返しがなくなる。かわりに鍵の判定で件数分の参照比較（`ReferenceEquals`）が毎フレーム走る。参照比較は文字列比較より安く、探索の削減は残ると推定する。削減量は実測していない。実機での確認もしていない。

## 未実装の改善案

効果の見込みが小さいため、次の案は実装していない。計測できる環境が得られたときに判断する。

- リストが短い装飾品ではキャッシュしない（件数のしきい値）。
- `Prepare` の段階で対象を絞る。
- 要素を差し替えずに `entityName` の値を書き換える編集を検出する必要が出た場合は、キャッシュへ書き込むときに各要素の `entityName` の参照も記録して、鍵の判定で比較する。比較する参照が件数分増え、検出できる編集の範囲が広がる見込み。
- 既定を無効にする案。現在は有効である。毎フレームの削減は残り、fail-soft で設定で切れ、他の native 系の設定とも既定が揃っているためである。
