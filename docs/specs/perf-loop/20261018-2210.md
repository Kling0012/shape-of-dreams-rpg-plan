# perf-loop/20261018-2210

## 対象

mod src/SodRpg.Mod/ClientSession.cs（毎フレームの `Tick` → `SendBuildIfNeeded`）。

## 直した内容

`SendBuildIfNeeded` の中の `RefreshForbiddenGearNotice`（禁忌装備 #415 の警告の出力確認）の呼び出しを、送信スロットルの早期 return の前から後ろへ移した。この確認は装備15欄それぞれについて `Profile.FindStash`（倉庫の全走査）を呼ぶ。ホストが #415 の対応を宣言していない間（MOD なし・旧版のホスト）は早期 return に入らないため、これまでビルドを送らない tick でも毎フレーム走査が回っていた。移動後はビルドを実際に評価する tick（変更・強制再送・ハートビート。確認応答のあるホストで30秒、無いホストで5秒間隔）でのみ走る。

## 結果が変わらない理由

警告の内容・条件は同じで、確認する時期だけが送信の評価点に揃う。警告の条件（装備15欄の遺物が禁忌化済みか再調律上限超過か）を変える本番の経路は、装備の装着・外し、再調律、禁忌化のすべてが MarkDirty(true)（UI の `Act(..., true)`・`MarkDirty`）を通り、ホストの能力応答は `OnBuildInputCapability` が `_buildDirty = true` を立てる。MarkDirty(true) は `_allocationBuildDue` も0に戻すため、どちらも早期 return に入らず、変更の次の評価tickで警告が出る。ロビーで星の編集を束ねている間（0.15秒）だけ、能力応答の反映がその束ねの解消まで待たれ得る。

遠征中の鞄（`Run.Satchel`）の遺物を変える経路（夢の事件の ShadowExchange など）は MarkDirty を通らないが、装備できるのは `Profile.Stash` の遺物だけ（`Rules.Equip` は `FindStash` を要求する）で、鞄の遺物は装備できない。このため倉庫だけの変化で警告の条件が変わることはなく、MarkDirty を足す必要もない。警告の解除は、ホストから #415 対応の宣言が届いた時点で `OnBuildInputCapability` の中で同時に済み、tick を待たない。

残る遅れは、ホストが能力に一切応答しない場合の20秒の期限を過ぎた時点から次のビルド評価tick（ハートビート1回）までの間で、警告文の表示が遅れるだけ。間隔は確認応答のあるホストで30秒、無いホストで5秒。ビルド本体の送信・抑制の条件は変えていない。現行版のホスト（`_hostForbiddenInput` が立つ）とソロプレイ（`NetworkServer.active`）は従来から最初の1行で return しており、挙動は完全に同じ。

## 効果の見込み（推定）

MOD なし・旧版のホストに参加している間、毎フレームの「装備15欄 × 倉庫の遺物数」の文字列比較がなくなる。倉庫500個・60fpsなら約4万5千回/秒の比較に当たる（推定。実際の削減量は倉庫の大きさとフレームレートに依存）。
