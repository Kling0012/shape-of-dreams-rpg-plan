# perf-loop/20261020-0952

対象は MOD `src/SodRpg.Mod/InfinityBosses.cs`（345行）である。まず参加者（ゲスト）側の経路の有無から確認した。このファイルがフックする本体の処理は `RoomMonsters.SpawnMonsterImp` の1つだけである。逆コンパイル（`Dew.Core/RoomMonsters.cs`）で呼び出し元を調べると、`SpawnMonsterImp` の呼び出し箇所はサーバー側のスポーン・コルーチン（`OnRoomStartServerRoutine` から始まる波の生成ループ）の1箇所だけで、1秒ごとの環境スポーン（`DoEnvSpawnLogicUpdate`）も `isServer` で守られていた。つまりこのパッチはホストでしか走らず、**このファイルにゲスト側で走る経路はない**。`CurrentBossPlan` の取得・`SaveBossPlan` の書き込み・`ApplyBossRoom`（ゾーン生成時）・`InfinityBossSoulDeath`（ボス撃破時）も、呼び出し元をたどるとすべてホスト側の遷移ごとの処理で、毎フレームの経路もない。そのため指示どおり観点 3（スポーンごとの経路の無駄）で見た。

見えた構造は次のとおりである。`InfinityBossSpawn` の Prefix と Postfix は部屋のモンスター1体1体の出現ごとに走る（波の生成中は0.1〜0.5秒間隔で連続する）。Prefix は `InfinityMode.ReplacementBoss` を呼び、Postfix は `InfinityMode.ObserveSpawnedBoss` を呼ぶが、この2つの入口のガードでは、`NetworkServer.active` の次に `InfinityMode.Enabled` を評価してから、安価な `is BossMonster` の型判定と `settings?.rule?.isBossSpawn` の確認をしていた。`Enabled` は `State` getter（`ClientSession.HostRun` の取得、`GameManager.softInstance?.runId` との文字列比較、`run.Infinity ?? _initial`）と `NativeEnvelopePresent`（`customData.ContainsKey(RuntimeKey)`）をたどる複合プロパティで、ボスを出す設定ではない通常モンスターの出現では、その評価結果は使われずに捨てられる。スポーンの大多数は通常モンスターなので、出現ごとに最大2回（Prefix と Postfix で1回ずつ）、答えに関係しない評価を払っていたことになる。

直した内容は、この2つの入口のガードの並べ替えである。`ReplacementBoss` では `!(original is BossMonster)` と `settings?.rule?.isBossSpawn != true` を先にし、`Enabled` を最後に移した。`ObserveSpawnedBoss` では `!(entity is BossMonster)` を先にし、`Enabled` を最後に移した。これで通常モンスターの出現は型判定だけで MOD 側を抜ける。

結果が変わらない理由は次のとおりである。並べ替えたのは短絡評価の OR 条件の順序だけで、並べ替えた条件はどれも副作用のない読み取りである。`Enabled` の構成要素を確認したところ、`Available` は自動プロパティ、`State` getter は `ClientSession.HostRun`（`NetworkServer.active`・`_hostSession`・`RunActive`・`Profile.Run` の読み取りのみ）と `softInstance?.runId` の比較とフィールド参照、`NativeEnvelopePresent` は `customData.ContainsKey` であり、書き込みや遅延初期化がない。順序を変えても真偽は1つも変わらず、呼び出し側は `InfinityBossSpawn` の Prefix・Postfix の2箇所だけである。null が渡った場合も `is` は false を返すので、元のガードと同じ結果になる。

効果の見込み（推定）は、通常モンスターの出現ごとに、`Enabled` の評価（プロパティ参照の連鎖と辞書の `ContainsKey` 数回ぶん、1回あたり数百ナノ秒程度）が Prefix と Postfix の2回丸ごとなくなることである。波の生成中は毎秒数回の出現があるので、合計では毎秒数マイクロ秒程度の推定で、効果は小さい。ただし本体のスポーン経路に乗る純粋な無駄であり、MOD パッチのオーバーヘッドを非ボスの出現でほぼゼロにする。数値は推定で、実機での計測は行っていない。

見送った候補は次のとおりである。(1) `Enabled` のフレーム単位のキャッシュ。効果はこの並べ替えより大きいが、`Enabled` はロビー設定や実行状態の変化に即座に従う必要があり、同値性を証明できない。(2) `PrepareBossTarget` が delve ごとに `SaveBossPlan` を2回呼ぶ重複。ただし2回目は `ZoneId` の確定を含むので、書き込みが同じになるとは限らず、外せない。(3) ゲスト側の軽量化。このファイルにはゲストで走る経路が存在しないため、対象がない。
