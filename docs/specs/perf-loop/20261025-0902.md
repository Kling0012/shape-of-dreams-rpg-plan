# perf-loop/20261025-0902

対象は MOD `src/SodRpg.Mod/InfinityBosses.cs`（348行）である。まず全体の見取りとして、このファイルに毎フレームで走る経路はない。`InfinityBossSpawn` の Harmony パッチ先 `RoomMonsters.SpawnMonsterImp` は、本体の逆コンパイル（`Dew.Core/RoomMonsters.cs:2274`）が `Dew.SpawnEntity(..., serverActor, ...)` でスポーンするホスト専用の生成経路であり、ゲストは走らない。`CurrentBossPlan`、`PrepareBossTarget`、`ApplyBossRoom`、`ReplacementBoss`、`ObserveSpawnedBoss` はいずれもゾーン生成ごと・スポーンごと・フォールバック時のみで、頻度は低い。そのためゲスト（参加者）に関係するのはホストが `GameSettingsManager.customData`（本体の SyncDictionary）に書く計画文の同期だけで、その送信側を見た。

見えた構造は次のとおりである。`SaveBossPlan` は `settings.customData[BossKey]` に無条件に書いており、Mirror の `SyncIDictionary` のインデクサ（`Mirror/SyncIDictionary.cs:74`）は新旧の値を比較しないので、同じ内容の書き込みでも OP_SET 差分を記録して次の同期で全クライアントに再送する。再保存が重なる経路は3つある。`ObserveSpawnedBoss` は BossMonster の出現ごとに `plan.ActualBossTypeName` を書いて保存するので、同じボス種が同じ区間でもう一度出たとき（多段階の遭遇や Postfix の再試行）に同じ内容を再送する。`FallBackBoss` は `Warned` フラグが警告文だけを1回に抑え、保存自体は失敗のたびに走るので、フックが壊れたままの区間では delve ごとに同じ内容を再送する。`PrepareBossTarget` の1つ目の保存（`InfinityBosses.cs:115`）は計画が未変更のときの再書き込みである。各再送1件につき、各ゲストは `OnDeserializeDelta` を走らせ、本体の customData.Callback（`GameSettingsManager.cs:1162`）が `Dew.Debounce` のクロージャと `"GameSettingsManager::customData::" + key` の文字列連結を確保する。

直した内容は、`SaveBossPlan` での変更検知である。直列化した JSON が customData に既にある値と同じなら書き込まずに帰る。MOD 内の他の customData 書き込み（`ClientSession.InfinitySettings.cs:161`、`AutoCastCoopSettings.cs:47`、`LevelEssenceRuntime.cs:91`、`InfinityMode.PersonalChoices.cs:154`）がすでに同じ形のガードを持っているので、それに揃えた。

結果が変わらない理由は次のとおりである。省くのは「存在する値と完全に一致する文字列の書き込み」だけで、ホスト・ゲストの辞書の最終内容は1つも変わらない。ホストの `CurrentBossPlan` は customData から読むテキスト比較キャッシュであり、スキップしたときも customData の値と `_bossPlanText` は一致し続ける（customData 側が先に変わっていれば `CurrentBossPlan` が既に `_bossPlanText` を同期済みで、鍵が消えていれば TryGetValue が失敗して書き込む）。ゲストが受け取るべき状態の変化（計画の新設・変更・消去）はすべて値が変わる書き込みなので、従来どおり1回は届く。届け必須の送信（状態の確定・撃破・報酬）を間引いた箇所はない。

効果の見込み（推定）は、同一内容の再保存1件ごとに、ホストの OP_SET 差分1件（鍵と計画文の JSON 約200バイト）と各ゲストでの逆列化・コールバック処理1件がなくなることである。ボス戦が数分ごとに終わる無限モードで、同一ボスの再出現やフォールバックの繰り返しのたびに乗っていた無駄であり、頻度は低いが確実に減る分だけゲストの受信負荷が下がる。数値は推定で、実機での計測は行っていない。
