# v1.31 multiplayer fixes: host build validation

Scope: `mp-sync.md` #1, `mp-host.md` #1, `mp-ui-save.md` #1 and #11 only. Core remains pure C# 9 / netstandard2.0; Mod remains netstandard2.1. No game launch, GUI, game-directory writes or commit.

## Findings

### mp-sync.md #1 — fabricated effects with zero allocated stars

**Verdict: confirmed.** The existing multipart receiver and decoder bounded packet sizes and generic values, but did not establish an allocation entitlement. The exact `fake1` review payload was accepted by `Build.Decode` before this fix. The pre-fix regression expecting rejection failed with an actual non-null Build.

**Root cause:** independent derived effect and spent-point fields crossed the authority boundary. Identifier syntax was mistaken for registered star identity. Generic gimmick clamping did not validate the sender's hero, rank, memory, effect, trigger or modifiers.

**Fix:** `HostBuildValidation.TryAccept` reconstructs the production Build from canonical allocation/loadout inputs and the authenticated native hero type supplied by Mod. `TryValidateAllocation` checks registered hero-qualified IDs, ranks, explicit choices, graph/authored prerequisites and keystone prerequisites, and sums every rank's actual cost plus keystone cost against `StarProgression.MaxSpendablePoints` (304). The declared spent-point value must match that sum; the accepted Build receives the independently calculated sum. `Build.Decode` now preserves the four legal codex bonus points instead of truncating them to the XP-only 300-point cap. DreamPressure's existing balance cap is unchanged; its source is now the validated Build rather than an independent client assertion.

Combat sections `g/l/c/f/n/j/v` must match the canonical production output. Comparison uses the original wire sections, not just the generically clamped decoder result: unsupported parameters must not disappear during decoding and thereby evade rejection. This binds gimmicks, links, pairs, cluster boosts/parameters/choices, exact values, channels, contributors and native modifiers to the same validated allocation and equipped sources. Scalars and conditional base powers are reconstructed, not accepted as independent claims.

**Tests:** `HostBuildValidationTests.Fabricated_zero_cost_effects_are_rejected`, `Three_hundred_independently_firing_fake_effects_are_rejected`, `Understated_spent_points_do_not_suppress_pressure`, `Connected_route_cluster_choice_and_pair_derive_the_same_combat_and_pressure`, `Sender_hero_tree_and_allocation_identity_are_authoritative`, and generated-tree budget/boundary cases. Generated definitions are necessary for the 304/305-point boundary: today's Cetus tree cannot spend all 304 points. No invalid per-star rank is substituted for the aggregate-budget scenario.

### mp-host.md #1 — independently firing fabricated combat effects

**Verdict: confirmed.** The exact two-entry `audit0/audit1` review payload also produced a non-null Build in the pre-fix regression. Correct framing and known native memory names did not make its invented stars legal.

**Root cause:** the same missing source entitlement permitted many independent per-star firing states without any legal allocation.

**Fix:** the canonical host boundary above rejects fabricated effects, including packets with otherwise valid input envelopes. Actual existing star IDs are insufficient: all emitted fields and rank-derived values must agree with the production tree computation. Pair IDs/ranks alone are also insufficient without the bridge and endpoint allocations. The host applies only the reconstructed Build. Generic-valid channels/contributors and native cap profiles are not ownership entitlements.

**Tests:** both exact review payloads; 300 fake Burst entries; mutations of existing star ID, memory, trigger, effect, value, argument, cooldown, duration, radius, target count and chance; link, pair and cluster value/rank tampering; empty allocations claiming registered links/pairs; valid-but-unallocated native modifiers and fabricated channel contributors.

### mp-ui-save.md #1 — fabricated stats/powers and effect-driven overload

**Verdict: confirmed.** Per-entry global caps and count limits existed, but were not limits on what the declared equipment and stars could actually produce.

**Root cause:** aggregate combat values were accepted without reconstructing their sources. Equipped relic count, raw roll ranges, slot/rarity eligibility, unique identity and historical enhancement milestones were not part of host acceptance.

**Fix:** `HostGearValidation.TryValidate` validates each equipped relic's base, unique/base correspondence, rarity, level, enhancement/limit-break bounds, awakening metadata, source-specific affix/power counts and duplicate/illegal effects. Host input parsing additionally enforces equipped slot agreement, one source per slot and distinct equipped UIDs. Raw numeric values are clamped to production per-source maxima before enhancement/awakening and Build aggregation. Affix caps use the actual slot pool and rarity/item-level scaling; ordinary first powers allow legitimate full-range retuning, Epic minor powers retain their lower-half range, authored unique powers retain their own values/order, and the +20 bonus affects only the first power. Recovery may reset current enhancement while retaining historical milestones and boosted raw powers; such legitimate history is preserved. The host replaces independently claimed scalar/conditional totals with the actual capped equipped + star computation, including registered pact/daily modifiers.

Every allocated rank contributes to the shared point budget regardless of whether it grants a stat, power, link or gimmick. A syntactically valid huge effect list cannot create additional independent firing states on the host.

**Tests:** `Scalar_and_conditional_totals_are_reconstructed_from_gear_and_stars`, equipped duplicate/slot mismatch cases, mixed-source point-budget cases, and `HostGearValidationTests`: aggregate-cap raw gear, flat/percent scaling, duplicate/unbounded lists, invalid identity/metadata/effect kinds, unique/base mismatch, first-only milestone boosts, Rare retuned full-range versus Epic minor range, every authored unique at maximum enhancement/awakening and after recovery, real crafting/retuning/MemoryWell paths, negative extremes and slot-pool bypasses.

### mp-ui-save.md #11 — unrestricted OnBuild application and broadcasts

**Verdict: confirmed.** The previous identical-packet shortcut preserved combat state, but still forced a pressure broadcast and full acknowledgment for every completed transfer. Changed builds decoded and reapplied immediately without a per-player deadline.

**Root cause:** application, recomputation and broadcasts were coupled to packet arrival rather than a bounded per-player update schedule.

**Fix:** `BuildUpdateCoalescer` retains one latest complete payload per player. First consumption is immediate; subsequent consumptions are separated by at least 0.5 seconds (**N = 2 per second**). Submissions never postpone that deadline, so continuous changes cannot debounce a legitimate update indefinitely. `HostAuthority.BuildValidation.cs` drains the coalescers in Tick; reconstruction, native application and acknowledgments therefore run at the bounded cadence. Identical payloads, or different payloads reconstructing to the same canonical Build, only receive a throttled acknowledgment: no combat-state reset and no forced pressure refresh. Changed accepted builds mark pressure dirty; normal pressure publication handles actual pressure changes. Pending uploads wait for the authenticated native hero to be available.

Bad transfer/protocol/input packets reject only that player's submission. Existing accepted data remains unchanged. Receive, validation/drain and deferred native application boundaries catch exceptions per player rather than throwing into the host loop. A generic warning is logged once per player for the current authority/roster lifetime, without a player name. Disconnect, authority replacement and detach clear the queue/log state. Cached validated Builds cannot be attached to a different hero tree on respawn.

**Tests:** `BuildUpdateCoalescerTests` covers a continuous 64 Hz flood, final latest delivery, bursts, independent players, throttled identical acknowledgments, non-starvation, return-to-last-build deduplication, late polling and invalid/backwards/large clocks. `Rejected_player_does_not_affect_another_players_latest_legal_update` exercises rejection and acceptance across independent player streams. Runtime smoke also delivered `update127` at the next eligible deadline after the 64 Hz flood.

## Protocol decision

**Bump once: 12 → 13**, in `NetMessages.cs`. Protocol 12 transmits derived effects but no complete allocation/loadout representation. Missing source identities/ranks cannot be recovered safely from its totals; accepting old uploads would preserve the exploit. There is no legacy inference or fallback.

The protocol-13 upload payload is `Build.Encode() | canonicalInputs` (without spaces). Applied summaries retain the existing Build grammar. Multipart message fields and native JSON-envelope sizing are unchanged. Transfer admission adds a bounded 65,536-character input allowance to the existing derived-Build bound; all payloads remain ASCII and every fragment retains the native string byte limit.

Required input sections:

- `D`: dream level; `H`: heat; `M`: hero mastery kill count; `K`: optional selected keystone ID.
- `T`: comma-separated `starId=rank=choiceIndex`, with `-1` only for non-choice stars.
- `R`: comma-separated `slot:uid:baseId:uniqueId:rarity:itemLevel:enhance:limitBreaks:awakenLevel:awakenPoints:enhanceMilestones:affixes:powers`; affixes/powers use `enumId=value` joined by `+`.
- `P`: distinct registered pact IDs; `Y`: registered daily ID or zero.

The native caller supplies the hero identity; no client-supplied hero field selects the tree. Saved progression and relic ownership remain client-owned. This proves structural legality and per-source caps, not that a client honestly earned its declared progression, gear or personal run modifiers. All multiplayer participants must use protocol 13.
