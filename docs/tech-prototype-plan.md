# 技術プロトタイプ計画（案）

対象: `README.md`（設計提案 v0.1）第16章「技術方針と実現性の前提」と第17章「開発段階と依存関係」
作成日: 2026年10月1日
位置づけ: 実装計画の提案であり、承認済みの仕様ではありません。リポジトリへの反映は行っていません。実機・本体アセンブリでの確認も行っていません。

## 0. この計画の目的と範囲

第16章の「開発開始時に確かめる接続点」のうち、次の3つを**最小の縦断スライス**として実機で確かめます。

| 記号 | 最小構成 | 確かめたいこと |
| --- | --- | --- |
| A | 能力値変更 1つ | 補正を追加し、着脱・ロード・切断・MOD停止のどれでも残留なく除去できるか |
| B | 保存アイテム 1つ | MOD独自の保存が、再起動・プロフィール切替・旧版データ・書込み中断に耐えるか |
| C | 重複しない協力報酬 1つ | ホスト確定の報酬が、再送・再接続・ホスト終了でも二重付与も取りこぼしもしないか |

README第16章の4つ目の接続点（発動連鎖と性能計測）は、この最小構成には含めません。連鎖を作るには装備と発動ルールが先に必要で、第17章の依存関係（共通の発動ルールは大量の装備より先）に従い、次の試作へ回します。

**この試作で作らないもの**: 本物の装備定義、製作、地域進行、取引、ホスト移行、見栄えのあるUI、バランス調整。

**成功の定義**: 次の問いに、実機の結果で「はい／いいえ／代替案が必要」と答えられること。

1. この方法で能力補正を安全に出し入れできるか。
2. 独立保存で、保存事故（消失・重複・補正の残留）を防げるか。
3. 協力報酬を一意に確定できるか。

第20章の「作業を止めて判断すべき条件」（独立保存の安全性を確保できない、協力報酬を一意に確定できない）は、この3問に対応します。**いいえ**になった場合はコンテンツ拡張へ進まず、方式を見直します。

## 2. 全体構成

```
┌─ 純C#コア（Unity非依存・単体テスト可能）──────────────┐
│  ModifierSpec     能力補正の定義とID                    │
│  Ledger           アイテム台帳（保存・移行・検証）       │
│  GrantProtocol    報酬の確定・再送・重複排除（状態機械） │
│  AtomicFile       一時保存→置換、バックアップ、検証      │
└──────────────────▲───────────────────────────────────┘
                   │ 薄いインターフェース
┌─ ゲーム接続層（Harmonyパッチ／ModBehaviour）───────────┐
│  StatAdapter      EntityStatus へ補正を追加／削除        │
│  SaveAdapter      プロフィールIDの取得、保存先の決定     │
│  NetAdapter       MOD独自メッセージの送受信              │
│  DebugOverlay     台帳・補正・報酬ログの一時表示         │
└────────────────────────────────────────────────────────┘
```

**分け方の理由**: 保存と報酬の重複排除はゲームを起動しなくても検証できる論理です。ここを純C#にしておくと、実機で2人協力を組みにくい場合でも、クライアントの切断や再送を模擬する自動テストで主要な危険を先に確認できます。第16章の「ゲームへの接続部分は薄く保つ」方針とも一致します。

純C#コアは、本体の対象ランタイム（.NET Framework 4.x系の見込み。**要確認**）で動く書き方に限定します。

## 4. 要素A: 能力値変更 1つ

### 目的

README第16章の「能力補正を一つ追加し、着脱・ロード・切断後に正しく除去できるか確認する」を実機で通す。

### 仕様（仮置き）

- 補正ID: `sodrpg:test_charm:stat`（接頭辞でMOD名を示し、他MODの補正と衝突しない）。
- 効果: 能力値を1種類だけ変更する。**どの能力値にするかはSP-1で決める**（補正の追加・削除が確認でき、結果をログと画面で見分けやすいもの。候補は最大HPまたは攻撃力）。第6章の「回復や防御の過剰な乗算」を避けるため、防御・回復系は選ばない。
- 値は定数ではなくデータ定義（JSONまたは純C#の定義クラス）から読み、後で調整しやすくする。
- 付与の契機: 「保存アイテムBを所持している／装備している」を条件にする。着脱は試験用ホットキーまたはデバッグオーバーレイのボタンで行う。

### 設計上の要点

1. **付与と除去を1か所に集める**。`StatAdapter.Apply(hero, spec)` と `StatAdapter.Remove(hero, spec)` だけが補正に触れる。
2. **冪等にする**。すでに付いている補正を二重に付けない。付いていない補正の除去は何もしない。
3. **除去の契機を網羅する**: 装備解除、アイテム消失、シーン遷移、ロード、切断、`OnDestroy`（MOD停止）、ヒーローの破棄。
4. **MOD停止時に残留しない**。`OnDestroy` で自分の補正をすべて除去し、Harmonyを自分のIDで解除する。
5. 補正の計算順はSP-1で確認し、加算・乗算の区別を記録する。

### 合格テスト

| ID | 手順 | 期待する結果 |
| --- | --- | --- |
| A-1 | 付与して能力値を確認し、解除して再確認 | 変化と復元が値で一致する |
| A-2 | 同じ付与操作を2回行う | 効果が二重にならない |
| A-3 | 付与中にセーブして終了、再起動してロード | 条件が満たされていれば1回だけ付与され、未装備なら付かない |
| A-4 | 付与中にMODを無効化して拠点またはメニューへ戻る | 補正が残らない |
| A-5 | 協力中、クライアントが切断・再接続する | 補正が残留せず、再接続後に正しく1回だけ付与される |
| A-6 | 他のMODを入れていない状態と、1つ入れた状態を比較 | 他MODの補正を壊さない（`UnpatchAll` で他のパッチを巻き込まない） |

## 5. 要素B: 保存アイテム 1つ

### 目的

README第14章の「版番号付きの独立保存」を最小の形で作り、保存事故の主要な型（書込み中断、旧版、プロフィール取り違え、重複）を一通り試す。

### 保存するもの

試験用アイテム `test_charm`（装備としての性質は要素Aの補正のみ）と、要素Cが付与する素材 `dream_shard` の所持数。第4章の推奨（使用権・成果と装着中の個体は別データ）にならい、**台帳には「所持」だけを書き、「今回装着中」は保存しない**。

### 保存形式（仮案）

```jsonc
{
  "schemaVersion": 1,
  "profileKey": "<プロフィール識別子>",
  "revision": 17,                      // 保存のたびに+1。巻戻り検出に使う
  "items": [
    { "itemId": "test_charm", "instanceId": "uuid", "acquiredBy": "grantId" }
  ],
  "materials": { "dream_shard": 3 },
  "appliedGrants": [ "grantId", ... ],   // 付与済みの報酬ID（重複排除用）
  "checksum": "…"
}
```

- 安定したIDを使い、表示名や配列順に依存しない（第16章）。
- 保存先はプロフィールごとの独立ファイル。本体のセーブデータは変更しない。
- `appliedGrants` は要素Cの重複排除の根拠。**アイテムの付与と `appliedGrants` への追記は同一の保存で行う**（片方だけ書かれる状態を作らない）。

### 書込み手順

1. 内容を検証する（重複ID、存在しない参照、上限外の値を拒否。第14章の運用上の安全性）。
2. 一時ファイルへ書き、書込み完了後にフラッシュ。
3. 既存ファイルを直前バックアップへ退避してから一時ファイルと置換する（アトミックな置換が使えない環境ではその手順を明文化する。**ファイルシステムの挙動は要確認**）。
4. 起動時は、本体とバックアップを検証し、有効なもののうち revision が最大のものを読む。**一時ファイルは読まない**（確定点は置換の完了であり、確定前の内容を読むと、ackを返していない付与を「あった」ことにして、後の書込み失敗で失う恐れがあるため。純C#コアの模擬試験で実際に見つかった欠陥）。どちらも無効なら**黙って空の台帳を作らず**、ロードを止めて復旧手順を表示する。

### 旧版移行の確認用の最小枠

`schemaVersion: 1` に加えて、わざと `schemaVersion: 0`（欄が1つ少ない形）を用意して移行処理を一度通します。移行は元ファイルを残し、失敗時は読み込みを止めます。この枠は実際の旧データがない段階でも移行処理の型を検証するためのものです。

### 合格テスト

| ID | 手順 | 期待する結果 |
| --- | --- | --- |
| B-1 | 付与して終了、再起動して読み込む | アイテムと素材が同じ内容で残る |
| B-2 | 保存の書込み中にプロセスを強制終了する（一時ファイル作成後・置換前・置換後それぞれ） | どの時点でも、直前または直後の整合した状態で復旧する |
| B-3 | 台帳ファイルを手で壊す（途中で切る、値を改変、チェックサム不一致） | 隔離または復旧が表示され、黙って別物に置換されない |
| B-4 | プロフィールを切り替える | 他のプロフィールの台帳が見えず、混ざらない |
| B-5 | `schemaVersion: 0` のファイルを読む | 元を残して移行され、失敗時は読み込みを止める |
| B-6 | MODを外して本体だけを起動し、その後MODを戻す | 本体のセーブが壊れず、台帳も維持される |
| B-7 | 存在しないアイテムID、上限外の値を含む台帳を読む | 隔離され、残りは読める。結果が表示される |

## 6. 要素C: 重複しない協力報酬 1つ

### 目的

README第13章の「敵、報酬、取引、成長の確定はホスト側」「再接続時に報酬を再配布せず、確定済みの結果を再表示する」を最小の形で通す。

### 報酬の定義（仮）

「指定した1つの条件（例: 試験用の部屋をクリア、または試験用の敵を1体撃破）で、**参加者全員がそれぞれ `dream_shard` を1つ受け取る**」。内容を素材の個数にするのは、重複したときに数字で一目で分かるためです。経験値や撃破の最後の一撃に依存させません（第13章の公平性）。

### 報酬ID（冪等キー）

```
grantId = H( runId | triggerId | rewardDefId | recipientProfileKey )
```

- `runId`: 遠征（部屋）ごとに、ホストが開始時に発行する識別子。
- `triggerId`: 報酬を発生させた出来事（部屋ID等）。
- 同じ出来事・同じ受取人からは、何回呼んでも同じ `grantId` が出る。**ここが重複排除の核**です。

### 状態機械

```
Rolled(ホスト)  ──確定──▶  Committed(ホスト・送信待ち)  ──送信──▶  Delivered(クライアント受信)
                                                                      │ 台帳へ書込み(要素B)
                                                                      ▼
                                              Persisted(クライアント)  ──ack──▶  Closed(ホスト)
```

- **ホスト**: 報酬を `Committed` として自分の未配布リスト（outbox）へ記録し、`Closed`（ack受信）になるまで再送する。
- **クライアント**: 受信した `grantId` が `appliedGrants` にあれば**再付与せず**、ackだけ返す（確定済みの結果として再表示）。なければ台帳へ付与と `appliedGrants` 追記を同時に保存し、保存後にackを返す。
- **ホスト自身の取り分**も同じ経路（自分宛てのクライアント扱い）で処理し、特別扱いしない。
- **付与の確定点はクライアントの保存完了**とする。ホストは「送った」ではなく「ackを受けた」で閉じる。

### 失敗の型と方針

| 状況 | 方針 |
| --- | --- |
| メッセージの重複・遅延・順序入替 | `grantId` で吸収。何度届いても付与は1回 |
| クライアントの切断→再接続 | ホストの未配布リストを再送。クライアントは重複を弾く。結果画面は確定済みを再表示 |
| ack喪失 | ホストが再送、クライアントは付与済みとして再ackのみ |
| 保存失敗（クライアント） | ackを返さず、エラーを表示。ホストの再送で再試行 |
| ホスト終了（クライアントが `Persisted` 済み） | 受け取り済みの分は残る。二重にはならない |
| ホスト終了（`Committed` で未送信） | **取りこぼしが起こり得る**。初期の方針は「記録して通知し、再開しない」。必要ならホスト側にも未配布リストの保存を追加（P5で判断） |
| 途中参加 | 初期案は拠点・安全地点のみ。遠征中は許可しない（第13章の初期案） |
| 同一出来事の二重発火（ホスト側の二重呼び出し） | `grantId` が同じなので、ホストの台帳が先に弾く |

**「取りこぼし」と「重複」は別の指標として数えます。** 重複は即時に不合格、取りこぼしは方針として許容範囲を決めた上で件数を記録します。

### 同期の責任

- 報酬の抽選・確定・付与の判断はホストのみ。クライアントは「受け取った」の通知を返すだけで、自分から付与を要求しない（要求させるとしても、ホストが `grantId` で再判定する）。
- クライアントの保存内容をホストが信用しすぎない。ホストは「このクライアントがこの `grantId` を保存した」というackの内容だけを根拠にする。
- 参加者全員のMOD版と設定の照合は、**この試作では版番号の比較のみ**実装し、不一致時の参加可否の方針（第13章）は次段階で詳細化する。

### 合格テスト

| ID | 手順 | 期待する結果 |
| --- | --- | --- |
| C-1 | 2人で報酬条件を達成 | 両者が `dream_shard` をちょうど1つ受け取る（合計2つ、重複なし） |
| C-2 | 同じ報酬メッセージを意図的に2〜3回送る（模擬または実機） | 付与は1回 |
| C-3 | クライアントを受信直後・保存前に切断し、再接続 | 取りこぼしも重複もない。結果画面は確定済みを再表示 |
| C-4 | クライアントを保存後・ack前に切断し、再接続 | 付与は1回のまま、ホストが再ackで閉じる |
| C-5 | ホストが報酬確定後に終了 | クライアントの `Persisted` 分は維持される。未送信分の扱いが記録どおりになる |
| C-6 | ホスト側で同じ出来事を二重発火させる | 二重付与されない |
| C-7 | 100回繰り返す連続試験（模擬）。切断・遅延・並べ替えをランダムに混ぜる | 重複が0件。取りこぼしの件数と原因が記録される |
| C-8 | 報酬付与直後にクライアントが保存を強制終了（要素B-2と組合せ） | `appliedGrants` と所持数が常に整合 |

## 7. 純C#コアの自動テスト（P2）

実機で組みにくい状況を、ゲームなしで再現します。

- **報酬プロトコルの模擬ネットワーク**: メッセージの欠落・重複・遅延・並べ替え、クライアントの停止・再開、ホスト停止を乱数（固定シード）で発生させ、不変条件を検査する。
  - 不変条件1: 同じ `grantId` の付与は台帳に高々1回。
  - 不変条件2: `Closed` になった報酬は、必ず受取人の台帳に存在する。
  - 不変条件3: 台帳の `materials` の合計は、`appliedGrants` から再計算した値と一致する。
- **保存の障害注入**: 書込みの各段階で例外を投げ、再読み込み後に有効な状態が得られることを確認する。
- **移行**: `schemaVersion` 0→1の変換、未知の版の拒否。
- **検証**: 重複ID、存在しない参照、上限外の値の拒否。

自動テストが全部通っても、実機の合格テスト（4〜6章）の代わりにはなりません。

**実装状況**: この章の純C#コアと自動テストは、リポジトリの `src/SodRpg.Core` と `tests/SodRpg.Core.Tests` に実装済みです（`dotnet test` で全件通過）。模擬ネットワークの試験では、保存の確定点に関する欠陥（上記5章の手順4）を実際に検出し、修正しました。残る既知の限界は次のとおりです。
- ディスク上の本体が後から壊れてバックアップへ戻る場合、ack済みでバックアップより新しい付与は失われる（ホストはClosedにしているため再送されない）。重要な付与はホスト側にも履歴を持つ案をP5で判断する。
- 実ファイルシステム（`File.Replace`）の中断時の挙動は、Linuxでの単純な読み書きテストのみ。Windowsでの確認は実機で行う。実機でしか分からない点（フック、同期、ファイルシステム）は実機で確認します。

## 8. 作業の順序と依存

```
P0 環境確認
  └─ P1 スパイク SP-1〜SP-7（並行可。ただしSP-1,3,4,5は結論が必要）
        ├─ P2 コア実装（AtomicFile → Ledger → GrantProtocol の順）
        │     └─ P3 接続（StatAdapter → SaveAdapter → NetAdapter）
        │           └─ P4 協力検証（SP-6の結果で実機か模擬かが決まる）
        └─ P5 判定
```

- 保存（B）を協力報酬（C）より先に作る。付与の確定点が保存完了であるため。
- 能力値（A）は保存（B）に依存せず先行できるが、「所持→補正」の条件付けはBの後。
- UIは検証用の簡易表示（`OnGUI`ベースのオーバーレイ）に限定する。README第17章の「必要情報は小規模試作から使える状態に」を、**台帳・補正・付与ログの表示**に絞って満たす。見た目は磨かない。

## 9. 判断ゲート（P5）

### Go（第17章の段階1「共通基盤」へ進む）

次をすべて満たす場合。

- A・Bの合格テストがソロで全件通る。
- Cの合格テストで、重複0件、取りこぼしの原因が説明され方針が決まっている。
- 純C#コアの不変条件テストが通る。
- 他MODを1つ併用した状態でも、補正・保存が壊れない（A-6）。

### 方式見直し（コンテンツ拡張を止める）

次のいずれかの場合。第20章の停止条件に対応します。

- 独立保存の安全性（B-2、B-3、B-6）を確保できない。
- 協力報酬の重複を防げない（C-2〜C-4、C-6）。
- 能力補正を安全に除去できない（A-3〜A-5）。

### 代替案の候補（不合格時の出発点）

| 不合格の内容 | 代替案 |
| --- | --- |
| 補正の追加・除去APIが使えない | Harmonyで能力値計算に差し込み、補正の一覧をMOD側で管理する |
| 公式の保存領域が使えない | 独自ファイルのみで運用（既に基本案） |
| MOD独自メッセージが送れない | 本体の既存同期（JSON上書き、既存のコマンド）へ報酬をエンコードして相乗りする。難しければ、ホスト確定の結果を各人の次回起動時に突合する方式に後退 |
| 同一環境で2人協力を組めない | 模擬ネットワークの自動テストを主、実機は最小限の確認に限定（SP-6） |
| 本体更新で署名が変わる | 対象版を固定し、更新時に差分確認を行う（第19章） |

## 10. リスクと注意

| リスク | 早期の兆候 | 対処 |
| --- | --- | --- |
| 本体更新によるAPI変更 | 更新後にHarmonyパッチが当たらない | 対象ビルドを記録し、更新ごとにスパイクを再実行 |
| パッチの範囲が広すぎる | 他MODやゲーム本体の動作が変わる | パッチは最小の箇所に限定し、IDで自分のものだけ解除する |
| 既存MODのコード再利用 | 許諾が不明なまま流用 | **コードは流用しない**。事例として方式を読むだけにとどめ、実装は独自に行う（第19章の方針） |
| テスト用の保存が実プロフィールを壊す | 実プレイのデータで検証 | 検証用プロフィールを使い、実データに触れない。検証前にバックアップを取る |
| 協力試験の環境不足 | 2人分の環境が用意できない | SP-6で早めに確認し、模擬テストへ切り替える |
| 個人情報の混入 | 識別子やログに本名・IDが残る | ログには版と状態のみ、識別子はハッシュ化して記録（第14章） |
